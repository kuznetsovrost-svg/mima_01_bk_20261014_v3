# Данные для задач агента — куда класть промпт, исходники, результаты, примеры, журнал
## Полный гайд по организации задач в Hermes Agent

────────────────────────────────────────────────────────────────────────────
0. ЗАЧЕМ ЭТОТ ГАЙД
────────────────────────────────────────────────────────────────────────────

Когда задача сложная и хочется сформулировать её в виде отдельного
файла (Markdown), а не одной команды в чате, возникают вопросы:

  1. Где разместить сам промпт?
  2. Где хранить исходные данные (вложения, документы, .csv, .pdf)?
  3. Куда положить результаты (отчёты, гайды, CSV-выгрузки)?
  4. Где хранить примеры и справочные материалы для агента?
  5. Как вести журнал состояний выполнения?

Эти 5 вопросов — не косметика, а архитектурное решение. Если
положить всё «куда попало», через месяц вы потратите час на то,
чтобы вспомнить, что где лежит.

Гайд написан после практической работы на этом хосте. Все пути
реальные (берутся из исходного кода Hermes Agent). Рекомендации
учитывают:
  - Встроенные каталоги профиля: workspace/, plans/, home/, sandboxes/.
  - Сегментацию промптов, исходников, результатов, примеров, журнала.
  - Конкуренцию между профилями (изоляцию).
  - Long-running задачи (состояние «в работе»).

────────────────────────────────────────────────────────────────────────────
1. АНАТОМИЯ ПРОФИЛЯ — ЧТО ГДЕ
────────────────────────────────────────────────────────────────────────────

Каждый профиль `~/.hermes/profiles/<name>/` имеет:

   workspace/   ← файлы агента (промпты, исходники, результаты, черновики)
   plans/       ← планы и журнал
   home/        ← HOME для sandbox-окружения
   sandboxes/   ← изолированные окружения (Singularity/контейнеры)
   sessions/    ← журнал чат-сессий (НЕ для задач, для диалогов)
   logs/        ← runtime-логи gateway и операций
   memories/    ← SOUL/MEMORY/USER и связанные
   skills/      ← per-profile навыки
   cron/        ← cron-задачи
   hooks/       ← pre/post-tool события
   image_cache/
   audio_cache/
   state.db     ← SQLite, история сессий (НЕ для задач)
   .env         ← секреты
   SOUL.md      ← личность
   config.yaml  ← конфиг

Для default корень — сразу `~/.hermes/` (не в `profiles/`).

────────────────────────────────────────────────────────────────────────────
2. 5 КАТЕГОРИЙ ДАННЫХ — СВОДНАЯ ТАБЛИЦА
────────────────────────────────────────────────────────────────────────────

  ┌─────────────────────┬────────────────────────────────────────────────────┐
  │ Категория           │ Куда положить                                      │
  ├─────────────────────┼────────────────────────────────────────────────────┤
  │ Промпт задачи       │ workspace/inbox/ (если разовый) или задача          │
  │                     │ целиком через `hermes project new` / `kanban add`  │
  │                     │ для долгосрочных                                   │
  │                     │                                                    │
  │ Исходные данные     │ workspace/inbox/<задача>/inputs/                   │
  │ (attachments)       │                                                    │
  │                     │                                                    │
  │ Результаты          │ workspace/outbox/<задача>/outputs/ или             │
  │                     │ workspace/results/ (для всех сразу)                │
  │                     │                                                    │
  │ Примеры и справка   │ workspace/references/ (общая для профиля)          │
  │                     │ или inputs/<задача>/refs/                          │
  │                     │                                                    │
  │ Журнал состояний    │ plans/<задача>.md (с датами, статусом) или        │
  │                     │ отдельный файл state.json                         │
  └─────────────────────┴────────────────────────────────────────────────────┘

Всё это **внутри `~/.hermes/profiles/<name>/workspace/`** —
ваша основная «песочница». Не размазывайте по дому, по /tmp,
по другим профилям — это источник путаницы.

────────────────────────────────────────────────────────────────────────────
3. ПРОМПТ ЗАДАЧИ (TASK.MD)
────────────────────────────────────────────────────────────────────────────

3.1. Когда сохранять в файл, а не в чат.
   Промпт в файл стоит сохранять, если:
   - задача длиннее 5-7 строк;
   - задача сложная (требует вложений / контекста);
   - задача будет повторяться или её состояние нужно сохранять;
   - задача обрабатывается несколькими профилями;
   - задача требует журнала состояний.

3.2. Имя файла.
   Краткое, kebab-case, с датой и/или номером:

   inbox/TASK-2026-07-04-audit-mima.md
   inbox/TASK-2026-07-04-rag-chunking.md
   inbox/TASK_42_migration.md
   inbox/refactor-auth-module.md

3.3. Структура task-файла (шаблон).

   # Task: <name>
   # state: draft | in_progress | blocked | review | done
   # profile: <имя_профиля>
   # created: 2026-07-04
   # updated: 2026-07-04

   ## Goal
   <Что нужно сделать — 1-2 строки, конкретно>

   ## Context
   <Где это в системе, зачем>

   ## Requirements
   - <требование 1>
   - <требование 2>

   ## Inputs
   Список файлов, которые будут переданы агенту.
   - /workspace/inbox/TASK-.../inputs/data.csv
   - /workspace/references/style-guide.md

   ## Outputs
   Что должно получиться.
   - CSV-файл с N строками
   - MD-гайд в /workspace/results/TASK-...

   ## Acceptance
   - [ ] критерий 1
   - [ ] критерий 2
   - [ ] критерий 3

   ## Status (обновлять по мере работы)
   - 2026-07-04 10:00 — created
   - 2026-07-04 10:15 — agent started, logging...
   - 2026-07-04 10:42 — first output, 80% готово

3.4. Где физически.
   `~/.hermes/profiles/<name>/workspace/inbox/TASK-2026-07-04-...md`

   Причина именно `inbox/`: это «входящие», агент забирает оттуда.

3.5. Как передать агенту.
   - Через Hermes project (`hermes project new`) — наиболее родной путь.
   - Через skill `kanban` (`hermes kanban add`) с вложением.
   - Вручную: `hermes chat "что написано в TASK-2026-07-04-...md и лежит в workspace/inbox"`.
   - Через cron: с указанием пути к task-файлу.

3.6. Слать ли в git?
   Да. workspace/ можно держать в git. .env и runtime-артефакты
   (state.db, gateway.*) — нет. workspace — это по сути
   «исходники задач + результаты», git-friendly.

────────────────────────────────────────────────────────────────────────────
4. ИСХОДНЫЕ ДАННЫЕ (ATTACHMENTS)
────────────────────────────────────────────────────────────────────────────

4.1. Где размещать.
   `~/.hermes/profiles/<name>/workspace/inbox/<task-id>/inputs/`

   Подкаталог `inputs/` потому что:
   - чёткая граница: «это входные данные»;
   - можно сразу заархивировать / перенести / удалить
     после завершения задачи;
   - структура не мешает структуре outputs/.

   Примеры inputs:
   - manual.pdf
   - data.csv
   - spec.md
   - logs/jan.log.tar.gz
   - screenshots/fig1.png

4.2. Можно один файл?
   Да, для простых задач: положите `inputs/data.csv` без подкаталога.
   Но `inputs/` лучше — единообразие.

4.3. Если данных МНОГО (>100 MB).
   - Не кладите в `workspace/inbox/<task>/inputs/`. Используйте
     отдельный каталог `workspace/datasets/` или внешнее
     хранилище (S3, NFS).
   - В task-файле укажите абсолютный путь: `/mnt/datasets/<name>/`.

4.4. Если данные чувствительные.
   Подумайте: должны ли они быть в workspace?
   - Если секреты — никогда, в workspace.
     Секреты в .env, доступ через env-vars.
   - Если PII (персональные данные) — лучше НЕ в git,
     использовать шифрование, или вынести за пределы
     `~/.hermes`.

4.5. Именование inputs.
   Имя файла должно отражать роль, не обязательно уникальное.
   Схема:
     inputs/<descriptive-name>.<ext>
   Примеры:
     manual-v2.pdf
     users-export-2026-q2.csv
     photos-2026-06-30.tar

   Если в задаче 10 PDF — не нумеруйте. Используйте `_v1`, `_v2`,
   если версионно.

4.6. Кто кладёт inputs?
   - Вы (через `cp`, `mv`, `wget`, S3 CLI).
   - Сам агент (через tool): `cp`, `wget`, `git clone`.
   - Крон (`hermes cron add` job может класть что-то в inputs/).
   Важно: inputs/ не должны менять во время работы агента.
   Если меняются — класть в `inputs/<task-id>/version-2/`.

4.7. Что делать с input'ами после задачи?
   - Если были временные — удалить (`rm -rf workspace/inbox/<task-id>/inputs/`).
   - Если долгосрочные (датасеты) — оставить в `workspace/datasets/`.
   - Если результаты + inputs нужны для аудита — положить в
     `~/.hermes/profiles/<name>/archive/<YYYY>/<task-id>/`.

────────────────────────────────────────────────────────────────────────────
5. РЕЗУЛЬТАТЫ (OUTPUTS)
────────────────────────────────────────────────────────────────────────────

5.1. Где размещать.
   `~/.hermes/profiles/<name>/workspace/results/<task-id>/`

   Подкаталог `results/<task-id>/` — для каждой задачи свой.
   Так видно, что к чему относится.

5.2. Альтернативный путь.
   `~/.hermes/profiles/<name>/workspace/outbox/<task-id>/`
   Подходит, когда результаты передаются downstream (другому
   профилю, человеку), и важно отделить «готово к отправке».

   Я предпочитаю `results/` для постоянных, `outbox/` для
   «ещё отправлю».

5.3. Что класть в outputs.
   - Финальные отчёты, гайды, инструкции.
   - Промежуточные версии (если хотите историю).
   - Логи выполнения (короткие).
   - Финальный артефакт (CSV / PDF / MD).

5.4. Именование outputs.
   `<topic>_<version>.<ext>`
   - rag-chunking-rules_v1.md
   - rag-chunking-rules_v2.md
   - rag-chunking-rules_final.md

   Если задача с одиночным результатом — можно без версии:
   report.md, data.csv.

5.5. Если результаты — большие файлы.
   - CSV > 10 МБ — в `workspace/results/` с предупреждением.
   - Бинарные файлы (PDF, изображения) — ок.
   - Архивы > 100 МБ — лучше выносить в `~/.hermes/profiles/<name>/archive/`
     и сжимать в `.tar.gz`.

5.6. Как выводить из Hermes.
   Когда агент заканчивает задачу, он часто «отдаёт» результат
   в чат. Настройте skill, чтобы при финальном ответе:
   - если файл > 1000 символов — сохранить в results/
   - в чат отправить MEDIA: ссылку
   - в плане отметить «done»

5.7. Долгосрочное хранение.
   `~/.hermes/profiles/<name>/archive/<YYYY>/<task-id>/` —
   для вещей, которые нужно хранить месяцы и годы.
   Удобно для аудита и бэкапов.

5.8. Что НЕ класть в outputs.
   - Временные файлы (`*.tmp`, `*.swp`).
   - Логи размером > 10 МБ (это в `logs/`).
   - Кэши.
   - Бинарные дебажные файлы.

────────────────────────────────────────────────────────────────────────────
6. ПРИМЕРЫ И СПРАВОЧНЫЕ МАТЕРИАЛЫ
─────────────────────────────────────────────────────────────────────────────────────────────────────
6.1. Где размещать.
   `~/.hermes/profiles/<name>/workspace/references/`

   Общая для профиля коллекция материалов, на которые опирается
   агент. Это «библиотека».

6.2. Отличие от inputs/.
   - `inputs/<task>/` — входные данные конкретной задачи, временные.
   - `references/` — постоянные справочные материалы для профиля.

   Примеры references:
   - coding-style.md
   - api-reference.md
   - security-policy.md
   - domain-glossary.md
   - templates/

6.3. Отличие от skills/.
   Скиллы — это «как делать» (процедурное). References — это
   «что есть» (фактическое). Например:
   - SKILL `python-code-review` описывает формат ревью.
   - REFERENCE `coding-standards.md` описывает правила PEP8 проекта.

6.4. Если references для конкретной задачи.
   `~/.hermes/profiles/<name>/workspace/inbox/<task-id>/refs/`

   Когда СПРАВКА нужна только для этой задачи — не загрязняйте
   общий `references/`. Положите в `inputs/<task-id>/refs/` или
   в `inputs/<task-id>/refs.md` (если один файл).

6.5. Шаблоны (templates/).
   `workspace/references/templates/`:
   - task-template.md
   - report-template.md
   - result-template.md

   Удобно: новый task создавать через `cp templates/task-template.md
   inbox/TASK-...md`, и заполнять.

6.6. Гигантские references.
   Если reference большой (>100 МБ) — вынести в
   `workspace/references/big/` или вообще в `~/Documents/...`
   и подключать через path-link в task-файле.

6.7. Версионирование references.
   Если вам важно «как было в июне», не правьте существующий
   справочник, а создавайте версию:
   - references/coding-standards-v2026-q2.md
   - references/coding-standards-v2026-q3.md

   Если нужна «текущая» — это либо ссылка `references/coding-standards.md → v2026-q3`,
   либо заглавный файл со ссылками на активную версию.

────────────────────────────────────────────────────────────────────────────
7. ЖУРНАЛ СОСТОЯНИЙ ВЫПОЛНЕНИЯ
────────────────────────────────────────────────────────────────────────────

7.1. Что журналировать.
   - Старт задачи (timestamp, кто запустил).
   - Какие шаги сделаны.
   - Какие артефакты созданы / удалены.
   - Какие ошибки встретились и как решены.
   - Когда завершено.

7.2. Где размещать.
   `~/.hermes/profiles/<name>/plans/<task-id>.md`

   `plans/` уже есть в каждом профиле (видел в коде). Используем.

7.3. Формат журнала (шаблон).

   # Plan: TASK-2026-07-04-rag-chunking

   ## State
   **active** | draft | blocked | done

   ## Profile
   mi_mg_01

   ## Created
   2026-07-04 10:00

   ## Updated
   2026-07-04 10:42

   ## Goal
   Сделать гайд по чанкингу руководства пользователя (300 стр) для RAG.

   ## Steps
   - [x] 2026-07-04 10:00 — создать task-файл
   - [x] 2026-07-04 10:15 — агент начал
   - [x] 2026-07-04 10:30 — собран раздел 1
   - [ ] 2026-07-04 11:00 — собрать раздел 2
   - [ ] 2026-07-04 11:30 — финализировать гайд

   ## Errors
   - 2026-07-04 10:30 — TypeError в Python-скрипте; исправлено в ревизия 2.

   ## Outputs
   - results/TASK-2026-07-04/ЧАНКИ01.txt
   - inbox/TASK-2026-07-04/progress.json

   ## Decisions
   - 384 токена / 17% overlap (см. обсуждение в MEMORY.md)

7.4. Альтернатива — JSON state.
   `~/.hermes/profiles/<name>/plans/<task-id>.json`:

   ```json
   {
     "id": "TASK-2026-07-04-rag-chunking",
     "state": "active",
     "profile": "mi_mg_01",
     "created": "2026-07-04T10:00:00+03:00",
     "updated": "2026-07-04T10:42:00+03:00",
     "steps": [
       {"ts": "10:00:00", "status": "done", "title": "создать task-файл"},
       {"ts": "10:15:00", "status": "done", "title": "агент начал"},
       {"ts": "10:30:00", "status": "done", "title": "раздел 1"},
       {"ts": "11:00:00", "status": "pending", "title": "раздел 2"}
     ],
     "errors": [
       {"ts": "10:30:00", "msg": "TypeError", "fix": "ред. 2"}
     ],
     "outputs": [
       "results/TASK-2026-07-04/ЧАНКИ01.txt"
     ]
   }
   ```

   MD — для человека, JSON — для агента и автоматизации.
   MD читается без инструмента, JSON — структурировано.

7.5. Kanban для долгосрочных.
   Если задач много и хочется board'а — `hermes kanban add` или
   `hermes project new`. Это уже 2026-формат.

   Kanban board хранит:
   - статус (todo/in_progress/review/done)
   - ответственного (профиль)
   - чек-лист
   - ссылки на inputs/results

   Не нужно держать параллельный MD.

7.6. Когда какой формат.
   - 1-2 задачи → MD-план в `plans/<id>.md`.
   - 5-20 задач → Kanban board.
   - Long-running pipeline с ветками → JSON state + MD-сводка.

7.7. Что не журналировать.
   - Промежуточные «компиляция рутинга» — не нужно.
   - Частые микро-шаги в чате (это в `logs/` или `state.db`).
   - Содержимое вывода (оно в `results/`, не в журнале).

────────────────────────────────────────────────────────────────────────────
8. ШАБЛОН РАЗМЕЩЕНИЯ — ПОЛНАЯ КАРТИНА
────────────────────────────────────────────────────────────────────────────

Когда появляется новая задача, создавайте такую структуру:

  ~/.hermes/profiles/<profile>/
  ├── workspace/
  │   ├── inbox/
  │   │   └── TASK-2026-07-04-rag-chunking/
  │   │       ├── task.md                  ← промпт
  │   │       ├── inputs/                  ← исходные данные
  │   │       │   ├── source-doc.pdf
  │   │       │   └── glossary.md
  │   │       └── progress.json            ← состояние
  │   ├── results/
  │   │   └── TASK-2026-07-04-rag-chunking/
  │   │       ├── ЧАНКИ01.txt             ← результат 1
  │   │       └── notes.md                 ← заметки
  │   ├── references/                      ← общие справки
  │   │   ├── coding-standards.md
  │   │   ├── api-reference.md
  │   │   └── templates/
  │   │       └── task-template.md
  │   ├── datasets/                        ← большие статичные данные
  │   │   └── wikitext-2024.tar
  │   └── archive/                         ← старые задачи
  │       └── 2026-Q2/
  │           └── TASK-2026-05-12-old-thing/
  ├── plans/
  │   ├── TASK-2026-07-04-rag-chunking.md  ← журнал
  │   ├── TASK-2026-06-19-...md
  │   └── TASK-2026-05-12-...md
  ├── sessions/                            ← чат-сессии
  ├── logs/                                ← runtime-логи
  ├── sandboxes/                           ← Singularity/etc
  ├── memories/
  ├── skills/
  ├── cron/
  ├── hooks/
  └── state.db

────────────────────────────────────────────────────────────────────────────
9. ПРАКТИКИ
───────────────────────────────────────────────────────────────────────
9.1. Создавайте структуру ДО начала задачи, а не «по ходу».
   Если кладёте входные данные постепенно в разные места, потом
   не найдёте. Шаблон inbox/<task-id>/inputs/ — до первого
   обращения к агенту.

9.2. После завершения задачи — архивируйте.
   ```bash
   tar czf archive/<YYYY>/<task-id>.tar.gz \
       inbox/<task-id> results/<task-id> plans/<task-id>.md
   ```
   ИЛИ, если хотите видеть на диске: `mv inbox/<task-id>
   archive/<YYYY>/`.

9.3. Не смешивайте задачи в одном inbox/.
   Если две задачи используют один и тот же `inputs/`, разнесите
   в разные подкаталоги. Иначе потом перепутаете.

9.4. Если задача превращается в серию — выносите в projects/.
   Kanban / project-board для долгосрочных задач. Подробнее —
   `hermes project --help`.

9.5. Не храните большие бинарники в workspace/.

12. ЧАСТЫЕ ОШИБКИ
────────────────────────────────────────────────────────────────────────────

12.1. Все файлы в корне workspace/.
   → `workspace/data.csv` вместо `workspace/inbox/TASK-.../inputs/`.
   Через месяц — каша.

12.2. Inputs и outputs не разделены.
   → `workspace/manual.pdf` рядом с `workspace/result.md` — путаетесь.

12.3. Промпт задачи НЕ записан (только в чате).
   → Через день в чате не найдёте, что делали.

12.4. Журнал задачи в Telegram-сообщениях.
   → Telegram не для долгосрочного хранения. В `plans/<id>.md`.

12.5. Большие inputs (>100 МБ) в workspace/.
   → `workspace/datasets/` или внешнее хранилище.

12.6. Секреты в workspace/inbox/<task>/inputs/.
   → Секреты в .env, workspace можно случайно закоммитить.

12.7. results в inbox/.
   → results/ и inputs/ визуально неотличимы, если они в
     одной директории.

12.8. archive/ путают с workspace/.
   → archive/ для старых задач; workspace/inbox/ для активных.

12.9. Журнал в одном MD, а JSON в другом.
   → Либо MD, либо JSON, либо оба с ясной связью.

12.10. Каждый профиль «видит» workspace через свой HERMES_HOME.
    → У каждого свой workspace. Если хотите делить inputs между
      профилями — вынесите в общий путь (но это уже НЕ workspace).

12.11. Cron добавляет файлы в workspace/, но не чистит их.
    → Используйте `hermes cron run` для уборки с фильтром
      по дате / имени.

12.12. Промпт в task.md, но в нём ссылки на inputs/ без
    относительной структуры.
    → Промпт должен быть self-contained: «открой inputs/data.csv»,
      а не «пользователь упомянул вчера файл, найди сам».

13. ЧЕКЛИСТ «ХОРОШАЯ ОРГАНИЗАЦИЯ ЗАДАЧ»
──────────────────────────────────────────────────────────────────────
Каждый раз при старте новой задачи:

  □ Создан `inbox/TASK-YYYY-MM-DD-name/`?
  □ Внутри — `task.md` с шаблоном?
  □ Создан `inputs/` (даже если пустой)?
  □ Создан `results/<task-id>/` (даже если пустой)?
  □ Создан `plans/<task-id>.md` (журнал)?
  □ Если используется kanban — задача добавлена через `hermes kanban add`?
  □ Если есть справка — положена в `inputs/<task-id>/refs/` или общий `references/`?
  □ Шаблон скопирован из `references/templates/task-template.md`?

Каждый раз при закрытии задачи:

  □ `task.md` обновлён (`state: done`, чек-боксы отмечены)?
  □ Журнал в `plans/<task-id>.md` синхронизирован?
  □ Финальный результат в `results/<task-id>/`?
  □ Если данные чувствительные — удалены из `inputs/`?
  □ Если задача долгосрочная — добавлена в `archive/<YYYY>/`?
  □ Если делали backup'ы — `.tar.gz` в нужном месте?

────────────────────────────────────────────────────────────────────────────────────
14. ПРОДВИНУТЫЕ ТЕМЫ
──────────────────────────────────────────────────────────────────────
14.1. Multi-profile задача.
   Один профиль пишет в `workspace/results/X.md`, второй —
   читает. Промежуточное «доставка» — через git push/pull в
   shared-repo, или симлинк, или скрипт в cron.

14.2. Locking.
   Если два профиля пишут в один файл — нужна блокировка. По
   умолчанию профили изолированы, так что это редкая проблема.

14.3. Encryption.
   Если workspace содержит чувствительное — рассмотрите
   `gocryptfs` или `age`. Шифруется на уровне ОС, не Hermes.

14.4. Прямой чат vs файл.
   Простой вопрос «что делает X» — в чат.
   Сложная задача с вложениями — файл + workspace.

14.5. Версионирование tasks.
   `inbox/TASK-2026-07-04-rag-chunking/` это v1.
   Если переоткрыли — `inbox/TASK-2026-07-04-rag-chunking-v2/`
   или просто переписали task.md с датой.

14.6. Workspace в git.
   workspace/ можно держать в git, если он < 1 ГБ.
   .gitignore должно покрывать `inputs/<task>/__pycache__/` и т.п.

14.7. Мониторинг.
   Cron + watcher может следить за workspace/inbox/ и автоматом
   запускать новые задачи. Это «agent-loop».

────────────────────────────────────────────────────────────────────────────────────
15. ЗАКЛЮЧЕНИЕ
──────────────────────────────────────────────────────────────────────
Главное правило: **один task-id = одна папка с полным набором
(prompt + inputs + outputs + journal)**.

Структура:

  workspace/inbox/TASK-<id>/task.md         ← промпт
  workspace/inbox/TASK-<id>/inputs/         ← данные
  workspace/results/TASK-<id>/              ← результаты
  plans/TASK-<id>.md                        ← журнал
  references/                               ← общие справочники

Если вы следуете этой структуре:
- через месяц вы найдёте ЛЮБУЮ задачу по `grep -r TASK-` или
  через `find workspace/ -name 'TASK-*'`;
- легко делиться с другим профилем — копируете `inbox/TASK-.../`;
- легко архивировать — `tar czf archive/<id>.tar.gz inbox/TASK-...`;
- легко автоматизировать — `find workspace/inbox -name task.md` →
  обработать.

Если нарушать — за полгода workspace превращается в свалку,
и новая задача требует сначала «прибраться».

Файлы и каталоги в Hermes 2026 — это подсказка авторам проекта,
что «здесь будет ваша работа». Используйте их по назначению, и
агент будет работать как коллега, а не как магия.
