1. КОРОТКИЙ ОТВЕТ
═══════════════════════════════════════════════════════════════════

Да, .bpmn подойдёт отлично — это семантически богатый формат,
специально предназначенный для описания процессов. Но есть нюансы,
которые важно знать до передачи файла.

═══════════════════════════════════════════════════════════════════
2. ЧТО ТЫ МОЖЕШЬ ПРИСЛАТЬ (ОТ ЛУЧШЕГО К ХУДШЕМУ)
═══════════════════════════════════════════════════════════════════

  Формат                          Извлечение   Что я могу
  ──────────────────────────────  ───────────  ──────────────────────
  .bpmn (XML)                     ⭐⭐⭐⭐⭐    Всё: задачи, шлюзы,
                                              потоки, роли, таймеры,
                                              события, артефакты
  .drawio / .dio                  ⭐⭐⭐⭐      Схема + лейблы; роли и
                                              таймеры часто теряются
  Текст (markdown, structured)    ⭐⭐⭐        Хорошо, если структурировано
  Скриншот диаграммы + текст      ⭐⭐          OCR неидеален
  Видео / устное описание         ⭐            Плохо для точного workflow

BPMN — один из лучших форматов для передачи workflow агенту.

═══════════════════════════════════════════════════════════════════
3. ЧТО Я ИЗВЛЕКУ ИЗ .bpmn
═══════════════════════════════════════════════════════════════════

Извлекается автоматически:
  ✓ Задачи (user task, service task, script task)
  ✓ Шлюзы (XOR, AND, OR) с условиями
  ✓ Последовательность (sequence flows с условиями)
  ✓ События (start, end, intermediate, timer, error)
  ✓ Роли / участники (lanes, pools)
  ✓ Артефакты (data objects, data stores)
  ✓ Таймеры (timer events, due dates)
  ✓ Multi-instance (для параллельных задач)
  ✓ Subprocesses (call activity, embedded subprocess)
  ✓ Compensation / error handling
  ✓ Message flows (между пулами)

Не будет в skill (если не прописано в BPMN):
  ✗ Семантика бизнес-правил (только то, что в BPMN явно)
  ✗ Частоты событий (если не указаны в таймерах)
  ✗ SLA / deadlines (если не прописаны явно)
  ✗ Конкретные тексты писем / сообщений
  ✗ Доменная логика извне

═══════════════════════════════════════════════════════════════════
4. ВАРИАНТЫ ПЕРЕДАЧИ WORKFLOW
═══════════════════════════════════════════════════════════════════

Вариант A: только .bpmn (минимум)
────────────────────────────────
  @Hermes вот файл workflow.bpmn, сделай из него skill

  Я сделаю всё сам. Будет базовая структура — задачи, шлюзы,
  потоки. Тонкости (формулировки, edge cases, обработка ошибок)
  могут быть утеряны.

Вариант B: .bpmn + контекст (рекомендуемый)
────────────────────────────────────────────
  @Hermes @/path/to/workflow.bpmn

  Контекст:
    - Это процесс согласования договоров в B-PP1-8
    - Основной пользователь — юрист, согласующий — руководитель
    - SLA: 5 рабочих дней на согласование
    - При отклонении — возврат инициатору с комментарием
    - При эскалации — уведомление в Telegram канал "contracts"
    - Особый случай: если сумма > 10М — обязательное доп.
      согласование CFO

  → Skill получится богаче и точнее, особенно в edge cases.

Вариант C: .bpmn + 2 файла контекста (максимум)
────────────────────────────────────────────────
  @Hermes @workflow.bpmn
  @business-context.md
  @examples.md  (3-5 реальных кейсов с разными ветками)

  → Лучшее качество. Примеры дают discover patterns — что часто
    идёт не так.

═══════════════════════════════════════════════════════════════════
5. ЧТО Я СОЗДАМ ИЗ .bpmn
═══════════════════════════════════════════════════════════════════

Структура skill:

  ~/.hermes/skills/<workflow-name>/
  ├── SKILL.md                  # step-by-step инструкция
  ├── references/
  │   ├── workflow-diagram.md   # описание в markdown
  │   └── decision-tree.md      # дерево решений (из шлюзов)
  ├── templates/
  │   ├── step-N-template.md    # шаблоны для каждой задачи
  │   └── notification.md       # шаблоны уведомлений
  ├── scripts/
  │   ├── validate.py           # проверка что все шаги пройдены
  │   └── progress.py           # отслеживание прогресса
  └── assets/
      └── workflow.bpmn         # исходник (для reference)

6. КОНКРЕТНЫЕ ШАГИ, КОТОРЫЕ Я СДЕЛАЮ
═══════════════════════════════════════════════════════════════════

  1. Парсинг .bpmn → список задач, шлюзов, потоков, ролей
  2. Извлечение decision points → дерево решений
  3. Генерация SKILL.md → пошаговый алгоритм
  4. Создание templates → шаблоны для каждой задачи
  5. Создание validation script → проверка правильности прохождения
  6. VERIFICATION checklist → что должно быть в каждом экземпляре

═══════════════════════════════════════════════════════════════════
7. ЧТО СТОИТ ПРИСЛАТЬ ВМЕСТЕ С .bpmn
═══════════════════════════════════════════════════════════════════

  Файл / информация              Зачем
  ──────────────────────────────  ─────────────────────────────
  .bpmn                           Основной процесс
  Краткое описание бизнес-домена  Контекст
  3-5 реальных кейсов             Покрытие edge cases
  Список ролей (если не в lanes)  Кто что делает
  SLA / deadlines                 Временные ограничения
  Точки интеграции                Куда отправлять уведомления
  Failure modes                   Что ломается (для fail-safe)
  Связанные skills                Что переиспользовать
                                  (failsafe-rules, memory-hygiene)

═══════════════════════════════════════════════════════════════════
8. ОГРАНИЧЕНИЯ .bpmn
═══════════════════════════════════════════════════════════════════

Что может быть НЕ в .bpmn:
  • Бизнес-правила вида «если сумма > 100К, то...» — нужно
    в текстовом описании
  • Конкретные тексты писем / сообщений — отдельным файлом
  • Unstated assumptions — то, что подразумевается, но не записано
  • Частотность событий (только таймеры, не «в среднем раз в неделю»)
  • Приоритеты (если не указаны явно через приоритет задач)

═══════════════════════════════════════════════════════════════════
9. ЕСЛИ НЕТ .bpmn, НО ЕСТЬ ОПИСАНИЕ ПРОЦЕССА
═══════════════════════════════════════════════════════════════════

Присылай текстом в любом формате:
  • Markdown с шагами
  • Нумерованный список
  • Просто текст «сначала X, потом Y, если Z, то...»

Я могу:
  1. Нормализовать описание в BPMN (если попросишь)
  2. Сразу сделать skill из текста (быстрее)

Пример текстового описания, которое годится:

  «Процесс согласования договоров:
   1. Инициатор создаёт заявку в BPM (поле: сумма, контрагент, тип)
   2. Если сумма < 100К — автосогласование руководителем (1 день)
   3. Если сумма 100К-1М — доп. согласование юр.отделом (2 дня)
   4. Если сумма > 1М — доп. CFO (3 дня)
   5. При отклонении на любом шаге — возврат инициатору
   6. При эскалации — уведомление в Telegram
   7. После всех согласований — подписание ЭЦП
   8. Архивирование в 1С + оповещение инициатора»

Это уже можно превратить в skill.

11. КОНКРЕТНЫЕ РЕКОМЕНДАЦИИ
═══════════════════════════════════════════════════════════════════

Для качественного skill пришли:
  1. .bpmn файл (или путь к нему)
  2. 2-3 абзаца контекста о бизнес-смысле
  3. Список ролей (если не в lanes)
  4. (опционально) 3-5 реальных кейсов

Для максимального качества добавь:
  5. SLA / deadlines
  6. Точки интеграции (email/Telegram/API)
  7. Failure modes и recovery
  8. Связанные skills для переиспользования

После получения я:
  1. Спарсю .bpmn
  2. Создам skill с references/templates/scripts
  3. Сделаю validation script
  4. Дам VERIFICATION checklist
  5. Покажу результат, попрошу одобрить

═══════════════════════════════════════════════════════════════════
12. ШПАРГАЛКА
═══════════════════════════════════════════════════════════════════

  Есть .bpmn?                   → отлично, присылай + контекст
  Есть .drawio?                 → могу, но роли/таймеры потеряются
  Только описание текстом?      → могу, нормализую в skill
  Только скриншот?              → OCR, качество ниже
  Не знаешь формат?             → пришли что есть, разберёмся

  После создания skill:
    1. Агрегирую в .hermes/skills/<workflow>/
    2. Зарегистрирую в Hermes
    3. Покажу SKILL.md на review
    4. После одобрения — зафиксирую
