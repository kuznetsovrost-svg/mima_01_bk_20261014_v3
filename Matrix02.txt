5. КОРЕНЬ ПРОБЛЕМЫ: MBadJSON 'device_keys' values must be a list of strings
================================================================================
Каждые 5 минут gateway пытается переподключиться к Matrix и валится
в gateway/platforms/matrix.py:641 -> _verify_device_keys_on_server:

    resp = await client.query_keys({client.mxid: [client.device_id]})
    File ".../mautrix/client/api/modules/crypto.py", line 195, in query_keys
        resp = await self.api.request(Method.POST, Path.v3.keys.query, data)
    File ".../mautrix/api.py", line 425, in request
        resp_data, resp = await self._send(...)
    File ".../mautrix/api.py", line 265, in _send
        raise make_request_error(...)
    mautrix.errors.request.MBadJSON:
        'device_keys' values must be a list of strings

Адаптер интерпретирует это как: "homeserver врёт про ключи, не доверяю ему
E2EE -> отказываюсь работать". И уходит в retrying до бесконечности.

Что не так:
    mautrix шлёт:
        {"device_keys": {"@oc_hermes:msg.lab.aidemo.adaptivepm.ru":
                         ["OTBJLBEADG"]}}
    homeserver, по спецификации MSC1756 et al., хочет:
        {"device_keys": {"@oc_hermes:msg.lab.aidemo.adaptivepm.ru":
                         {"OTBJLBEADG": {}}}}
    => Несовпадение формата payload. Это или старая Synapse, или нестандартный
       homeserver, или регрессия в mautrix (требует отдельного
       исследования). Не наша ошибка в конфиге.

9. ЧТО НЕ ДОДЕЛАНО / ЧТО ОСТАЛОСЬ ПОЛЬЗОВАТЕЛЮ
================================================================================
A. Заменить MATRIX_ACCESS_TOKEN в ~/.hermes/.env на новый (*** ...CqeK).
   Способ:
       nano +478 ~/.hermes/.env
       -> End, стереть "...3edh", вписать "...CqeK"
       -> Ctrl+O, Enter, Ctrl+X
       -> проверить: ls -la ~/.hermes/.env   (mtime должен стать свежим)

B. systemctl --user restart hermes-gateway

C. Если после B в логе снова MBadJSON 'device_keys' values must be a
   list of strings -- это homeserver не принимает формат mautrix, и
   шлюз не поднимется с E2EE. Workaround:
       sed -i 's/^MATRIX_ENCRYPTION=true/MATRIX_ENCRYPTION=false/' \
           ~/.hermes/.env
       systemctl --user restart hermes-gateway
   В этом режиме Hermes сможет писать/читать только plaintext-сообщения.
   Зашифрованные события (m.room.encrypted) в комнате Mima 01 он
   расшифровать не сможет.

12. КОНТРОЛЬНЫЕ ВОПРОСЫ ПОСЛЕ ЧТЕНИЯ
================================================================================
Q1. Действительно ли я создал отдельное устройство HERMES_GATEWAY?
A1. ДА, см. п.7.1 и homeserver ответил {"device_id":"HERMES_GATEWAY",...}.

Q2. Работает ли Matrix-шлюз?
A2. НЕТ. Адаптер в state=retrying, валится на MBadJSON про device_keys.
       Это не зависит от того, какой из двух токенов в .env -- обе
       ветки дают ту же ошибку.

Q3. Почему одноразовая отправка работает, а gateway -- нет?
A3. Одноразовая отправка идёт через простой HTTP PUT с Bearer-токеном,
       homeserver её принимает. Адаптер gateway дополнительно делает
       query_keys для E2EE setup, и вот тут homeserver отвечает ошибкой.

Q4. Почему нельзя просто починить .env из моей сессии?
A4. См. п.10.1. Sanitization токенов в моих инструментах делает
       невозможной безопасную запись строки "syt_*** " в файлы.

Q5. Что минимально нужно, чтобы Matrix-шлюз поднялся?
A5. (a) заменить токен в .env на новый,
       (b) systemctl --user restart hermes-gateway,
       (c) если в логе MBadJSON -- MATRIX_ENCRYPTION=false.
