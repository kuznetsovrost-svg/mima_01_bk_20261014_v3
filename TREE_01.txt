TREE_01.txt — Как предоставить HERMES сведения о иерархии объектов ИС
====================================================================
Версия: 1.0
Дата:    2026-06-16
Назначение: рекомендации по подготовке описания иерархического
            дерева (графа объектов) информационной системы для
            последующих запросов к агенту HERMES.


0. ГЛАВНАЯ ИДЕЯ
---------------
HERMES видит текст. Чтобы он мог отвечать на запросы про дерево
("где X?", "что входит в Y?", "родитель Z?", "всё, где owner=ivanov"),
ему нужны четыре вещи — и все обязательны:

  (а) КОМПАКТНОЕ представление структуры, укладывающееся в контекст.
  (б) СТАБИЛЬНЫЕ ИДЕНТИФИКАТОРЫ узлов, на которые можно ссылаться.
  (в) КРАТКИЕ МЕТАДАННЫЕ: тип, описание, свойства.
  (г) УДОБНЫЙ ДОСТУП — файл, который агент способен перечитать
      целиком, либо набор чанков под индексацию.

Дерево без ID или без метаданных бесполезно для запросов, отличных
от "назови всё подряд". Голый JSON на тысячи узлов — антипаттерн:
он раздувает контекст и ломает grep-стратегию.


1. КАНОНИЧЕСКАЯ СХЕМА УЗЛА
--------------------------
Каждый узел описывается одной строкой (для индексов) или одним
блоком (для подробных чанков). Минимум полей:

  ID          стабильный уникальный идентификатор (UUID, slug,
              код из ИС). Никогда не переименовывать задним числом.
  PATH        путь от корня через '/'. Пример: /org/div/analytics.
              Каноническая форма: единый регистр, разделитель,
              кодировка — что выберете, но единообразно.
  PARENT_ID   ID родителя. Можно опустить, если есть PATH.
  TYPE        класс узла (OrgUnit, Server, Service, Document...).
              Позволяет фильтровать: "все Service в поддереве X".
  NAME        человекочитаемое имя ("Команда аналитики").
  DESC        1 строка (5–15 слов) о сути узла. Без переносов.
  PROPS       пары k=v, разделитель ';'. owner=ivanov; env=prod.
  LEAF        true / false. Проставлять ЯВНО, чтобы не парсить
              по "отсутствию детей".
  REF         внешние ссылки (URL, ID в смежных системах).

Пример индексной строки:
  org.div.analytics  /org/div/analytics  OrgUnit
    "Команда аналитики"  "BI-отчёты, дашборды, витрины"
    leaf=false  owner=petrov


2. ВЫБОР ФОРМАТА ПО РАЗМЕРУ ДЕРЕВА
----------------------------------
A) Маленькое дерево  (≤ 200 узлов, ≤ 30k токенов)
   Формат: единый indented outline в одном файле.
   Плюс: агент видит всю структуру сразу, может "гулять глазами".
   Минус: при росте перестаёт влезать в контекст.

B) Среднее дерево  (200–2000 узлов)
   Формат: INDEX.txt (плоский список ID + PATH + TYPE + DESC)
           + CHUNKS/<root_id>.txt — подробный outline по ветвям.
   Агент сначала читает INDEX, затем подтягивает нужный CHUNK.

C) Большое дерево  (> 2000 узлов)
   Формат: SUMMARY.md (≤ 30 строк, верхнеуровневое описание)
           + INDEX.txt (плоский список)
           + CHUNKS/<id>.txt по 50–300 узлов в каждом.
   Агент: SUMMARY → INDEX → конкретный CHUNK.
   Для семантического поиска — embeddings (LanceDB / Chroma) по DESC.


3. ФОРМАТ ИНДЕКСА
----------------
Плоский CSV/TSV с фиксированным порядком колонок. Колонка PATH
обязательна — это самая частая точка входа для запросов.

  id<TAB>path<TAB>type<TAB>name<TAB>desc<TAB>leaf<TAB>props

Пример (TAB-разделитель):

  org.root            /org                          OrgUnit   Организация                 Корневой узел                                false
  org.div.analytics   /org/div/analytics            OrgUnit   Команда аналитики           BI-отчёты, дашборды, витрины                 false   owner=petrov
  doc.001             /org/div/analytics/doc.001    Document  Q1-отчёт                    Квартальный отчёт 2026Q1                     true    url=https://...

Альтернатива: JSON Lines (jsonl) — по одному JSON-объекту на строку.
Парсить удобнее программно, читать глазами — чуть хуже.


4. ФОРМАТ OUTLINE (для CHUNK'ов)
--------------------------------
2-space отступ. Узел — одна строка формата:

  <indent><name>  [id=<ID>, type=<TYPE>]

Пример:

  Организация  [id=org.root, type=OrgUnit]
    Команда аналитики  [id=org.div.analytics, type=OrgUnit]
      Q1-отчёт  [id=doc.001, type=Document]
      Q2-отчёт  [id=doc.002, type=Document]
    Команда разработки  [id=org.div.dev, type=OrgUnit]
      Сервис A  [id=svc.a, type=Service]
        База B  [id=db.b, type=DB]

Правила:
  - Имя первым — взгляд сразу цепляется за смысл.
  - ID и TYPE в одних скобках — машино- и человекочитаемо.
  - Свойства (PROPS) выносятся в отдельную строку с префиксом "@":
        Сервис A  [id=svc.a, type=Service]
          @owner=team-x; env=prod; sla=99.9; tags=api,critical


5. МЕТАДАННЫЕ ФАЙЛА (ШАПКА)
---------------------------
В начале каждого файла — блок комментариев с:

  - # INDEX — <имя дерева>
  - # version: <semver>
  - # date:    YYYY-MM-DD
  - # nodes:   N
  - # format:  TSV / JSONL / Outline
  - # root:    <root_id>
  - # rules:   paths lower-case, '/' separator, no spaces
  - # encoding: UTF-8 (без BOM)
  - # lineage: <откуда выгружено, какой скрипт, какой источник>

Версия и дата критичны — снимки устаревают, агент должен уметь
сказать "этот снимок от 2026-06-16, на сегодня может быть неактуален".


6. СВОЙСТВА (PROPS) — СОГЛАШЕНИЕ
-------------------------------
  - Ключи в нижнем регистре, без пробелов: env, owner, sla, pii.
  - Значения строковые, без '=' и ';'.
  - Список — через запятую: tags=bi,finance,quarterly.
  - Даты — ISO 8601: created=2026-01-15.
  - Если значение содержит спецсимволы — JSON-quote:
        label="Q1'26 — отчёт; финал"
  - Ключи из небольшого фиксированного словаря (env, owner, sla,
    pii, tier, status, region, created, updated, tags) — их
    агенту легче фильтровать. Свободный текст — в DESC.


7. КАК АГЕНТ ИСПОЛЬЗУЕТ ЭТИ ДАННЫЕ
----------------------------------
Загрузив INDEX (и при необходимости CHUNK'и), агент отвечает на:

  "дай путь к X"              — поиск по ID или name в INDEX.
  "родитель Y"                — split PATH, последний сегмент.
  "дети Z"                    — выбрать из INDEX все с префиксом path.
  "поддерево Z"               — загрузить CHUNK, где Z — корень.
  "все узлы с owner=ivanov"   — grep/filter по PROPS в INDEX.
  "всё типа Service в /org"   — filter INDEX по type + path-prefix.
  "путь от A до B"            — подняться по PARENT_ID до LCA.
  "что изменилось с прошлой версии" — diff двух INDEX-файлов.

Чтобы это работало, INDEX должен быть либо:
  - загружаемым ЦЕЛИКОМ в контекст, либо
  - доступным агенту через grep-инструмент (terminal, search_files).
Второй путь масштабируется лучше — файл не грузится в контекст,
агент ищет по запросу.


8. ДОСТАВКА В HERMES
--------------------
8.1. Один раз для сессии
     Положить INDEX (и при необходимости CHUNK'и) в рабочую
     директорию сессии или в ~/.hermes/knowledge/<тема>/.
     Сказать агенту: "Это дерево ИС, INDEX в INDEX.txt, CHUNK'и
     в ./chunks/. Используй search_files для навигации."

8.2. На лету, в Matrix-чате
     - Маленькое дерево: вставить indented outline прямо в сообщение.
     - Среднее: прикрепить файл MEDIA:INDEX.txt, в теле сообщения
       одна строка-инструкция: "это дерево X, формат Y, всего N узлов,
       корневой ID = Z".
     - Большое: прикрепить несколько файлов (SUMMARY + INDEX + CHUNKS)
       одним пакетом, либо прислать только SUMMARY + INDEX, а CHUNK'и
       досылать по запросу.

8.3. Долгосрочно, через RAG
     Положить в embeddings-стор (LanceDB / Chroma) и дать агенту
     инструмент поиска. Агент делает query → получает top-K узлов
     с PATH и DESC. Самый масштабируемый путь для деревьев на
     десятки тысяч узлов.


9. ЧЕК-ЛИСТ ПЕРЕД ОТПРАВКОЙ
---------------------------
[ ] У всех узлов есть уникальный ID.
[ ] PATH канонизированы (один регистр, один разделитель, без пробелов).
[ ] Явно проставлен LEAF=true у листьев.
[ ] TYPE указан у всех узлов (хотя бы один общий тип-родитель).
[ ] DESC — 1 строка, без переносов, без кавычек-ловушек.
[ ] Файл UTF-8 без BOM, переводы строк LF (или CRLF единообразно).
[ ] В начале файла — шапка с версией, датой, числом узлов, форматом.
[ ] Индекс и outline согласованы: каждый ID из outline есть в INDEX.
[ ] Кросс-ссылки (REF) — по ID, а не по именам.
[ ] Снапшот имеет версию и дату — можно откатиться или сравнить.


10. ЧАСТЫЕ ОШИБКИ (АНТИПАТТЕРНЫ)
--------------------------------
  X Большой JSON всего дерева в одном файле — раздувает контекст,
    ломает grep-стратегию, нечитаемо.
  X Дублирование информации — одно и то же имя в 5 местах без ID.
    Переименование превращается в ад.
  X Пути с пробелами / кириллицей в URL-части — ломает парсинг.
  X Смешение path-нотаций: где-то /a/b, где-то a/b, где-то [a][b].
  X Листы не помечены — агент парсит "есть ли в INDEX потомки",
    что медленно и ненадёжно.
  X Описания на 3 строки с переносами — рвут CSV/TSV-строку.
  X Нет SUMMARY — агент не понимает, о чём это дерево вообще.
  X Снапшот без даты — через месяц непонятно, актуален ли он.


11. ШАБЛОН ФАЙЛА INDEX.txt
--------------------------
  # INDEX — <имя дерева>
  # version: <semver>
  # date:    YYYY-MM-DD
  # nodes:   N
  # format:  TSV (id, path, type, name, desc, leaf, props)
  # root:    <root_id>
  # rules:   paths lower-case, '/' separator, no spaces
  # encoding: UTF-8 no BOM
  # lineage: <скрипт выгрузки / источник>
  #
  id<TAB>path<TAB>type<TAB>name<TAB>desc<TAB>leaf<TAB>props
  ...


12. ШАБЛОН ФАЙЛА CHUNK.txt
--------------------------
  # CHUNK <id> — <name>
  # parent:   <parent_id>
  # nodes:    N
  # subtree:  <path>
  #
  <name>  [id=<ID>, type=<TYPE>]
    <child-name>  [id=<ID>, type=<TYPE>]
      @key=value; key=value
    ...


13. МИНИМАЛЬНЫЙ ПРИМЕР (чтобы было от чего отталкиваться)
---------------------------------------------------------

        @env=prod; sla=99.9
