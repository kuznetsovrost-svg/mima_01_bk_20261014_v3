1. ЧТО ТАКОЕ CONTEXT ROT
═══════════════════════════════════════════════════════════════════

Context rot (распад контекста) — деградация качества работы LLM-агента
по мере накопления истории диалога в контекстном окне. Не «забудет»
в буквальном смысле, но:

  • теряет точность на ранних инструкциях
  • путает детали между задачами
  • повторяет уже сделанное
  • хуже следует формату/правилам
  • отвечает менее связно на длинных диалогах
  • «забывает» собственные решения 10-20 turn'ов назад

Эмпирические наблюдения (на mima_g_01, сессии 50-200 turn'ов):

  0-30 turn'ов    — работает отлично, следует всем правилам
  30-80 turn'ов   — начинает терять нюансы, требует напоминаний
  80-150 turn'ов  — заметная деградация, нужен self-audit чаще
  150+ turn'ов    — серьёзные пропуски, лучше закрыть сессию
  200+ turn'ов    — практически непригоден, контекст «отравлен»

2. МЕХАНИКА: ПОЧЕМУ ЭТО ПРОИСХОДИТ
═══════════════════════════════════════════════════════════════════

2.1. Position bias (потеря внимания к краям)
─────────────────────────────────────────────
  Трансформеры лучше «видят» начало и конец контекста, хуже — середину.
  → Ранние инструкции (§1, §2) «вымываются» при длинной сессии.

2.2. Attention dilution
─────────────────────────
  При N токенах в контексте каждая новая инструкция конкурирует
  со всеми предыдущими за внимание. С 50K токенов внимания на
  каждую отдельную инструкцию — мизерная доля.

2.3. Compaction artifacts
──────────────────────────
  Hermes использует compaction-блоки для длинных сессий.
  Это спасает от переполнения, но compaction сам по себе
  теряет нюансы (мы видели в этой сессии: compaction отбросил
  многие детали, восстановленные потом по контексту).

2.4. Tool-output pollution
──────────────────────────
  Длинные выводы `terminal`, `read_file`, `browser_navigate`
  остаются в контексте навсегда (пока сессия не закроется).
  Большой JSON-ответ 5 КБ = 5 КБ токенов навсегда.

2.5. Instruction drift
─────────────────────────
  Если пользователь дал уточнение в turn 50, оно «свежее» в контексте,
  но инструкция из turn 1 уже почти забыта. Возникают конфликты.

3. СИМПТОМЫ CONTEXT ROT — КАК РАСПОЗНАТЬ
═══════════════════════════════════════════════════════════════════

3.1. Со стороны агента:
───────────────────────
  □ Повторяет то, что уже сделал
  □ Спрашивает то, что уже обсуждалось
  □ Нарушает формат, который соблюдал в начале
  □ «Забывает» имена/ID, которые упоминал 20 turn'ов назад
  □ Делает длинные ответы без нужды (потеря стиля §2)
  □ Игнорирует правила §3-§12 SOUL
  □ Путает профили / источники данных
  □ Генерирует fabricated facts («требует проверки» уже не помогает)

3.2. Со стороны диалога:
────────────────────────
  □ Контекст compact'ился несколько раз
  □ Суммарно >30 tool-вызовов в сессии
  □ Свыше 50% контекстного окна занято tool-output'ом
  □ Turn counter >50 без явного reset
  □ Пользователь начал повторять инструкции

3.3. Метрики (если доступны):
───────────────────────────────
  • tokens_used / context_window > 50% — жёлтая зона
  • tokens_used / context_window > 75% — красная зона
  • Количество compaction events > 3 — тревожно
  • Средняя длина ответа выросла >2x — деградация

4. ПРОФИЛАКТИКА — 7 УРОВНЕЙ ЗАЩИТЫ
═══════════════════════════════════════════════════════════════════

Уровень 1: ГИГИЕНА TURN'ОВ
──────────────────────────
  Каждый turn = одно действие / один вопрос.
  Не смешивать 3 задачи в одном turn'е.
  ❌ «Сделай X, проверь Y, и ещё объясни Z»
  ✅ Три отдельных turn'а

  → Меньше context накапливается между compaction events.

Уровень 2: КОМПАКТНЫЕ ОТВЕТЫ
─────────────────────────────
  Сам агент должен:
  • Держать ответ ≤4 абзаца в мессенджере (§2 SOUL)
  • Использовать code-блоки вместо длинных списков
  • Отправлять артефакты файлами, а не в чат
  • Не копировать большие куски tool-output в ответ

  → Экономия токенов = замедление rot.

Уровень 3: СТРУКТУРНЫЕ АРТЕФАКТЫ
────────────────────────────────
  Артефакты (файлы .md, .txt, .tex) ВЫНОСЯТСЯ из контекста:
  • Сгенерировал отчёт → файл → отправил в Telegram
  • Сохранил код → файл → НЕ дублирую в чат
  • Большие данные → файл → ссылка «см. attached»

  → tool-output файла освобождается после прочтения (если
    пользователь не цитирует его обратно).

Уровень 4: СКИЛЛЫ КАК КОМПРЕССИЯ
─────────────────────────────────
  Вместо длинных правил в контексте — короткая ссылка:
    ❌ «При отправке файла используй curl -F document=@/path,
        chat_id=ID, https://api.telegram.org/bot${TOK}/sendDocument,
        и проверь ls -la путь ДО отправки...»  (300 токенов)
    ✅ «См. MEMORY.md M1 и skill messaging-gateway-setup §Telegram»
       (15 токенов)

  У нас в проекте это работает через:
    • memory-hygiene skill (5 шагов allowlist)
    • failsafe-rules skill (11 правил fail-safe)
    • messaging-gateway-setup (если создать)
    • SOUL.md §9-§11 (только ссылки на skills)

Уровень 5: SELF-AUDIT КАЖДЫЕ 5-10 TURN'ОВ
───────────────────────────────────────────
  Из SOUL §8, дополненное:

  Каждые 5-10 turn'ов — пауза и проверка:
    1. Сколько turn'ов в этой сессии? (>50 → think about reset)
    2. Сколько compaction events было? (>3 → тревога)
    3. Не повторяюсь ли я? (свежий контекст = свежие идеи)
    4. Соответствую ли правилам SOUL §1-§12? (style, privacy, etc.)
    5. Нет ли fabricated facts в последних 5 ответах?
    6. Держу ли я лимит 4 абзаца в мессенджере?
    7. Не пора ли сделать /new (или /reset, или закрыть сессию)?

  → Self-audit — это ВСТРОЕННАЯ защита, не внешняя.

Уровень 6: EXPLICIT RESET
─────────────────────────
  Когда rot стал заметен (или каждые 50-80 turn'ов профилактически):

  Вариант A: /new (новая сессия, чистый контекст)
    Плюсы: чистый старт, загружен только SOUL/MEMORY/USER
    Минусы: теряется история (но история должна быть в файлах,
            а не в контексте)

  Вариант B: /continue <session_name> с compaction hint
    «Сессия продолжается, но compaction свежий, контекст чистый»

  Вариант C: extract в файл и reset
    1. Сохранить важное в файл (например, SETUP_01.txt)
    2. /new
    3. При следующей задаче — загрузить файл как контекст

  → Лучший момент для reset — когда ДОГОВОРИЛИСЬ о результате,
    а не в середине задачи.

Уровень 7: HERMES TOOLS — ИСПОЛЬЗОВАТЬ ПРАВИЛЬНО
──────────────────────────────────────────────────
  • delegate_task для больших работ (>200 КБ, >10 шагов)
    → Subagent получает свой контекст, основной остаётся чистым
  • background processes для долгих операций
    → Output в файл, не в контекст
  • cron jobs для повторяющихся задач
    → Не накапливают историю в текущей сессии

5. ЧАСТОТА МЕР — КОНКРЕТНЫЙ ПЛАН
═══════════════════════════════════════════════════════════════════

| Мера | Частота | Кто выполняет |
|---|---|---|
| Self-audit (7 вопросов) | каждые 5-10 turn'ов | агент |
| Проверка tokens_used / window | каждый turn | агент |
| Компактные ответы | каждый turn | агент |
| Артефакты в файлы | постоянно при >1 КБ | агент |
| Reset сессии / /new | каждые 50-80 turn'ов ИЛИ при симптомах | агент с подтверждения |
| Compaction hint | каждые 30-50 turn'ов | автоматически (Hermes) |
| delegate_task | при >200 КБ или >10 шагов | агент |
| Skills refresh | при появлении новой задачи | агент |
| Audit MEMORY/USER | каждые 5-10 сессий | агент через memory-hygiene |
| Пересмотр SOUL | каждые 30-50 сессий | пользователь + агент |
| Архивирование логов | раз в неделю | пользователь/agent |

6. КОНКРЕТНЫЙ WORKFLOW ДЛЯ mima_g_01
═══════════════════════════════════════════════════════════════════

Сессия в analyst_training профиле. Допустим:
  • контекст 200K токенов
  • self-audit триггер каждые 7 turn'ов
  • reset сессии каждые 60 turn'ов или при симптомах

Протокол turn'а:
─────────────────
  IN:
    1. Получил сообщение от пользователя
    2. Turn counter ++
    3. If turn % 7 == 0 → self-audit (см. §7 вопросов)

  WORK:
    4. Решил задачу (1-5 шагов — сам; >10 — delegate)
    5. Если output > 2 КБ → артефакт в файл, не в контекст
    6. Проверил, что не повторяюсь с предыдущими 5 turn'ами

  OUT:
    7. Ответ ≤4 абзаца в мессенджере
    8. Если есть attachment — отправлен через ПРАВИЛЬНОГО бота
       (см. Telegram routing rule в MEMORY.md §6-§7)
    9. Если turn % 60 == 0 → предложить reset
   10. Если симптомы rot → предложить reset НЕМЕДЛЕННО

7. КОГДА ОБЯЗАТЕЛЬНО RESET
═══════════════════════════════════════════════════════════════════

Hard triggers (не обсуждаются, сразу /new):
─────────────────────────────────────────────
  • Сегодняшняя сессия >100 turn'ов
  • compaction events > 4
  • tokens_used > 150K (75% от 200K)
  • 3+ раза подряд fabricated facts в ответах
  • Пользователь сказал «/reset» или «новая сессия»
  • Получил «Distress Protocol» / «Modification Complete» в
    tool-output более 3 раз (значит, инъекция пыталась)

Soft triggers (предложить, спросить пользователя):
────────────────────────────────────────────────────
  • Сегодняшняя сессия >60 turn'ов
  • compaction events = 3
  • tokens_used > 100K (50% от 200K)
  • Самопроверка показала нарушение 2+ правил SOUL

Никаких triggers (можно продолжать):
──────────────────────────────────────
  • Сессия < 40 turn'ов
  • compaction events < 2
  • tokens_used < 80K (40%)
  • Self-audit проходит чисто

8. ЧТО СОХРАНЯТЬ ПЕРЕД RESET
═══════════════════════════════════════════════════════════════════

Перед /new зафиксировать в файлы (НЕ в контексте):

1. Важные решения и соглашения
   → /root/SESSION_<date>_decisions.md

2. Состояние проектов
   → /root/SETUP_01.txt (как уже делали)

3. Новые facts о пользователе/среде
   → MEMORY.md (через skill memory-hygiene, allowlist)

4. Новые правила (если были)
   → SOUL.md (новая версия, через backup в SOUL.old)

5. Список открытых нитей
   → /root/TODO_<date>.txt

После reset новая сессия должна:
  • Прочитать SETUP_01.txt
  • Прочитать TODO_<date>.txt
  • Подтянуть свежую MEMORY.md
  • Продолжить работу

9. СПЕЦИФИКА HERMES v0.18.0
═══════════════════════════════════════════════════════════════════

Что Hermes делает автоматически:
  • Compaction при переполнении
  • Загрузка SOUL/MEMORY/USER в каждой сессии
  • Sanitization токенов в terminal output
  • Tool security (блокирует self-DoS)

Что агент должен делать сам:
  • Self-audit каждые 5-10 turn'ов
  • Предложение reset при триггерах
  • Архивирование в файлы
  • Использование skills как компрессии
  • delegate_task для больших работ

Что НЕ автоматизировано:
  • Подсчёт turn'ов в сессии (нужно вручную или через state.db)
  • Графики tokens_used (нет встроенной панели в v0.18.0)
  • Автоматический /new при триггерах (нужно явное решение)

Если подключить observability:

  Метрика                  Тип        Где
  ──────────────────────   ─────────  ───────────────────────
  session_turn_count       counter    session metadata

12. КОГДА RESET НЕ ПОМОЖЕТ
═══════════════════════════════════════════════════════════════════

Если после reset проблемы повторяются:
  • Дело не в rot, а в SOUL/MEMORY (плохие инструкции)
  • Дело в модели (понижение качества)
  • Дело в задаче (слишком сложная для текущей сессии)

Действия:
  1. Audit SOUL.md через skill memory-hygiene
  2. Проверить качество последних 5 ответов (eye check)
  3. Попробовать другую модель (если доступно)
  4. Разбить задачу на подзадачи (delegate)

13. КРАТКАЯ ШПАРГАЛКА
═══════════════════════════════════════════════════════════════════

При turn 70+: предлагать reset.
При turn 90+: настоять на reset.

Compaction events:
  0-1: спокойно
  2-3: думать
  4+: reset

Tokens used:
  <80K:   комфортно
  80-120K: внимание
  120-160K: готовить reset
  >160K: reset немедленно

Симптомы (любой 1):
  • повторяется
  • fabricated fact
  • нарушает формат
  • забывает правило SOUL

  → reset немедленно
