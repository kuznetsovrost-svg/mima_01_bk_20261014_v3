НЕ РАБОТАЕТ БЕЗ ТОКЕНА:

  • Создание репозиториев через POST /user/repos
  • Push в репо, где у kuznetsovrost-svg НЕТ прав (например,
    публичный форк чужого проекта — нужен PAT с правом write)
  • Загрузка/скачивание артефактов Actions, пакетов, релизов —
    почти везде нужен authed REST
  • Любые действия от имени организации kuznetsovrost-svg-org
    (если такая есть) — нужна отдельная авторизация

ЧТО НУЖНО ДОБАВИТЬ (если потребуется REST-write):
  1) PAT fine-grained (рекомендую) или classic с минимальными
     скоупами под задачу. Создаётся вручную на github.com →
     Settings → Developer settings → Personal access tokens.
  2) На хосте задать через `gh` (когда установят) или env:
       export GITHUB_TOKEN=...
       export GH_TOKEN=...
     Hermes НЕ санитайзит env-переменные (санитайзит только
     3+ подряд `*` в bash-аргументах — это про реальные токены
     с `*` в середине, env более безопасен).
  3) Альтернатива: netrc `machine api.github.com login x password TOKEN`
     в режиме 600, тогда curl -n подхватит.

================================================================================
5. РЕКОМЕНДОВАННЫЕ ПАТТЕРНЫ ДЛЯ HERMES
================================================================================
  • Любую работу с GitHub делать либо `git …@github.com` (SSH),
    либо `curl -H "Authorization: Bearer $GITHUB_TOKEN"` (REST).
  • Если токен содержит `*` (некоторые GitHub-PAT начинаются с
    ghp_/ghs_/github_pat_ — там `*` нет, НО если длинные
    секреты в f-строках попадают в bash — Hermes их обнулит до
    `***`). Безопасный путь: записать токен в файл и
    `curl -H @file` или `curl -H "$(cat /tmp/tok)"`.
  • Команды git pipeline-ов (clone → commit → push) можно
    гонять через `delegate_task` с `toolsets=['terminal']`
    или прямо в `terminal()` — оба пути эквивалентны, и
    оба уважают `url.*.insteadof`.
  • Для больших операций (массовое клонирование, CI-pipeline
    на чужом репо) поднимать `cronjob` с `no_agent=true` —
    `script` пишет, scheduler шлёт stdout пользователю.
