## 2. Финальный description (этот вариант, отдельной секцией)

```yaml
description: "Use when the user wants a health-check report on a specific PMForesight project (ИСУП «Форсайт», PMForesight) via its MCP server. Loads on 'здоровье проекта', 'оцени проект', 'health check', 'project status report', 'анализ проекта', or by Code/ProjectId. Produces a dual-format report (Markdown inline + HTML file via MEDIA:) covering: (1) КТ schedule compliance (red/yellow by PlanDate–ForecastDate deviation); (2) project data completeness (Куратор, Руководитель, Паспорт, стадия ЖЦ, трудозатраты, платежи); (3) look-ahead КТ relevance (overdue КТ where ForecastDate < today); (4) financial status (forecast, прогноз фин.результата по окончании и его отклонение от планового, отклонение текущей стоимости от плана); (5) technical metadata (date, time, MCP version, user). Verdict: БОЛЕН / ТРЕБУЕТ ВНИМАНИЯ / ЗДОРОВ by critical-remark count. Visible data is filtered by the user's permissions in the host Форсайт system."
```

## 5. Недостатки / проблемы

| # | Проблема | Серьёзность | Комментарий / Решение |
|---|----------|-------------|------------------------|
| 1 | **`forecast` без перевода** | низкая | Технический термин; в скобках идёт русская расшифровка — норм |
| 2 | **Нет упоминания `red/yellow/blue` (синий/Информационное)** | низкая | Намеренное упрощение: синий не меняет вердикт — о нём можно не упоминать в `description`. Подробности — в SKILL.md |
| 3 | **Нет триггера «оценка здоровья»** | низкая | Триггеры должны быть короткими; «оценка здоровья» — лучше через `tags` (`health-check`, `оценка-здоровья`) |
| 4 | **Нет привязки к MCP-вызовам** | нет проблемы | Правильно — implementation detail не должны протекать в user-facing promise |
| 5 | **«Visible data» без объяснения «видимое что?»** | очень низкая | По конвенции Hermes — нормальная формулировка; секция «Ограничения» в SKILL.md раскроет детали |
| 6 | **Использование тире «–» вместо «-»** | косметика | Unicode-тире для диапазонов; в YAML допустимо, в MD рендерится корректно |
| 7 | **«на host Форсайт system»** — `Форсайт system` звучит как «система Форсайт» с инвертированным порядком | очень низкая | Грамматически приемлемо, но можно было «host Форсайт» (без `system`). Мелочь |
| 8 | **В `(3)` не указаны пороги (2 / 10 дней)** | нет проблемы | Пороги — implementation detail, не обещание |
| 9 | **Скилл в `/root/SKILL-FST-HOWPROJET.md` ещё не оформлен как skills** | **критично** | Перед коммитом нужно создать структуру `~/.hermes/profiles/fst-control/skills/productivity/fst-howproject/SKILL.md` |
| 10 | **Имя скилла `fst-howproject` — моё предложение, не согласовано** | **критично** | Нужно согласовать финальное имя с пользователем (альтернативы: `project-health-report`, `fst-project-health`) |
| 11 | **`metadata.hermes` блок отсутствует в этом description** | нет проблемы | `metadata` — отдельное поле frontmatter, не часть `description`. Будет в SKILL.md |

## 7. Что нужно сделать перед коммитом

1. **Согласовать имя скилла:** `fst-howproject` / `project-health-report` / `fst-project-health`.
2. **Создать каталог:**
   ```
   ~/.hermes/profiles/fst-control/skills/productivity/fst-howproject/
   └── SKILL.md
   ```
3. **Перенести** содержимое `/root/SKILL-FST-HOWPROJET.md` → `SKILL.md` с этим frontmatter.
4. **Дополнить** `metadata.hermes`:
   ```yaml
   metadata:
     hermes:
       tags: [mcp, pmpractice, foresight, project-health, health-check, kpi, report, html, markdown, ru]
       related_skills:
         - fst-pmpractice
         - project-search
         - project-timing-control
         - project-completeness-check
         - project-effort-plan
         - project-effort-write
         - project-payment-schedule
   ```
5. **Обновить** `related_skills` у зависимых скиллов (добавить `fst-howproject` в их списки — двусторонняя навигация).
6. **Перенести** «Историю изменений» из workflow в секцию `## История` SKILL.md (от v0.1 до v1.3 + переход в skill).
