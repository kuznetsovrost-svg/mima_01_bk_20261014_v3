Файл-ответ, который ты сейчас просишь записать, должен быть **осмысленным ответом**, а не просто шаблоном. Я сделал и то, и другое: ниже — **готовый универсальный шаблон задачи** (task.md) + **короткая памятка по работе с ним** для профиля Hermes Agent.

────────────────────────────────────────────────────────────────────────────
0. ГДЕ ЭТОТ ФАЙЛ ИСПОЛЬЗУЕТСЯ
────────────────────────────────────────────────────────────────────────────

Этот `Шаблон_задачи_01.txt` — **документ-инструкция**, не сам шаблон.
Сам шаблон лежит в:

   ~/.hermes/profiles/<имя_профиля>/workspace/references/templates/task-template.md

Для каждого профиля — свой экземпляр шаблона. Скопировали —
заполнили — отдали агенту:

```bash
cp ~/.hermes/profiles/<profile>/workspace/references/templates/task-template.md \
   ~/.hermes/profiles/<profile>/workspace/inbox/TASK-YYYY-MM-DD-<name>/task.md
```

Если у профиля ещё нет шаблона — взять содержание секции 1 ниже и
положить в `task-template.md`.

────────────────────────────────────────────────────────────────────────────
1. ГОТОВЫЙ УНИВЕРСАЛЬНЫЙ ШАБЛОН TASK.MD
────────────────────────────────────────────────────────────────────────────

Скопируйте текст ниже в `task-template.md`. Заполняйте только
нужные секции; лишние удаляйте под конкретную задачу.

```
# Task: <краткое имя задачи>
state: draft                       # draft | in_progress | blocked | review | done
profile: <имя_профиля>
created: YYYY-MM-DD
updated: YYYY-MM-DD
author: <кто поставил задачу>
priority: normal                  # low | normal | high | urgent

## Goal
Что нужно сделать. 1-2 строки. Конкретно и измеримо.

## Context (опционально)
Зачем задача. Где будет использоваться результат. Какие ограничения.

## Requirements
- <требование 1 — измеримое>
- <требование 2>
- <требование 3>

## Inputs
- inputs/<file1.ext> — описание
- inputs/<file2.ext> — описание
(всё, что агент должен прочитать)

## Outputs
- results/<task-id>/<file1.ext> — описание
- results/<task-id>/<file2.md> — описание
(что должно появиться в результате)

## Acceptance Criteria
- [ ] критерий 1
- [ ] критерий 2
- [ ] критерий 3

## Constraints / Limits
- Бюджет токенов: <например, <5000>
- Время выполнения: <например, <30 мин>
- Sensitive data: <нет / есть — какая>

## Style Guide (опционально)
- references/style-guide.md (общий)
- inputs/<task-id>/refs/<конкретное>

## Status Log (обновлять по ходу)
- YYYY-MM-DD HH:MM — created
- <обновления>

## Decisions (опционально)
Почему выбран такой подход. Полезно для аудита.

## Out of scope (опционально)
Что НЕ нужно делать.
```

────────────────────────────────────────────────────────────────────────────
2. НАЗНАЧЕНИЕ КАЖДОЙ СЕКЦИИ
────────────────────────────────────────────────────────────────────────────

2.1. `state` (обязательно).
   Одно из: `draft`, `in_progress`, `blocked`, `review`, `done`.
   Агент смотрит на эту строку первой и сразу понимает фазу.
   Менять по ходу работы. После завершения = `done`.

2.2. `profile` (обязательно).
   Имя профиля Hermes, через который задача будет решаться.
   Пример: `mi_mg_01`, `code_reviewer`, `default`.

2.3. `created` / `updated` (обязательно).
   Дата создания и последнего изменения. Менять `updated` при правках.

2.4. `author` (опц.).
   Кто поставил задачу. Часто — Rost, но может быть другой.

2.5. `priority` (опц.).
   `low` / `normal` / `high` / `urgent`. Используйте, если у вас
   много задач и нужна сортировка.

2.6. `Goal` (обязательно).
   1-2 строки: что нужно сделать. Конкретно и измеримо.
   ПЛОХО: «посмотреть данные и сделать отчёт».
   ХОРОШО: «посчитать топ-10 пользователей по событиям в inputs/events.csv
           и записать результат в results/<id>/top_users.txt».

2.7. `Context` (опц.).
   Зачем задача. Где будет использоваться. Какие ограничения
   (бизнес, временные, технические).

2.8. `Requirements` (опц., но полезно).
   Список измеримых требований. Каждое — отдельный пункт.
   ПЛОХО: «хорошее качество».
   ХОРОШО: «покрытие тестами > 80%», «соответствие PEP8», «файл
           не больше 500 строк».

2.9. `Inputs` (обязательно, если есть входные данные).
   Список файлов, которые агент должен прочитать. Все файлы уже
   должны быть в `inputs/<task-id>/` (см. гайд «Данные для задач агентов»).

2.10. `Outputs` (обязательно).
   Что должно получиться. Конкретные пути и имена файлов.

2.11. `Acceptance Criteria` (обязательно).
   Чек-лист критериев приёмки. Без них вы не поймёте, готова ли задача.
   Каждый критерий — отдельный `- [ ]`. По мере выполнения — `- [x]`.

2.12. `Constraints / Limits` (опц.).
   Бюджет токенов, время выполнения, чувствительные данные.
   Помогает агенту не выходить за рамки.

2.13. `Style Guide` (опц.).
   Ссылки на справочные документы по стилю (если есть).
   Не дублируйте style-guide в каждой задаче — ссылайтесь.

2.14. `Status Log` (обязательно, обновлять).
   Хронология событий: created → started → first output → ...
   Время пишется в формате `YYYY-MM-DD HH:MM`.

2.15. `Decisions` (опц.).
   Какие приняты решения в ходе работы. Полезно для аудита:
   «Почему был выбран X, а не Y».

2.16. `Out of scope` (опц.).
   Что НЕ делать. Защищает от разрастания задачи.

────────────────────────────────────────────────────────────────────────────
3. КАК СОЗДАТЬ ЗАДАЧУ ИЗ ШАБЛОНА
────────────────────────────────────────────────────────────────────────────

Шаг 1. Создать каталог задачи:

```bash
TASK_ID="TASK-$(date +%Y-%m-%d)-<короткое-имя-латиницей>"
TASK_DIR="$HOME/.hermes/profiles/<profile>/workspace/inbox/${TASK_ID}"
mkdir -p "${TASK_DIR}/inputs"
```

(Имя — kebab-case, латиница. Пример: `TASK-2026-07-04-rag-chunking`.)

Шаг 2. Скопировать шаблон и заполнить:

```bash
cp $HOME/.hermes/profiles/<profile>/workspace/references/templates/task-template.md \
   "${TASK_DIR}/task.md"
$EDITOR "${TASK_DIR}/task.md"
```

Шаг 3. Положить входные данные в `inputs/`:

```bash
cp /path/to/some.csv "${TASK_DIR}/inputs/"
```

Шаг 4. Создать `progress.json`:

```bash
cp $HOME/.hermes/profiles/<profile>/workspace/references/templates/progress.json.template \
   "${TASK_DIR}/progress.json"
$EDITOR "${TASK_DIR}/progress.json"
```

Шаг 5. Создать план в `plans/`:

```bash
PLAN="$HOME/.hermes/profiles/<profile>/plans/${TASK_ID}.md"
touch "$PLAN"
$EDITOR "$PLAN"
```

Шаг 6. Создать каталог для будущих результатов:

```bash
mkdir -p "$HOME/.hermes/profiles/<profile>/workspace/results/${TASK_ID}"
```

Шаг 7. Передать агенту. Варианты:

```bash
# Через Hermes chat с явным указанием файла:
hermes --profile=<profile> chat \
  "Открой task.md в inbox/${TASK_ID}/ и выполни."

# Через Kanban:
hermes kanban add "$TASK_ID" --profile=<profile> --file="${TASK_DIR}/task.md"

# Через cron (периодически):
hermes cron add "*/5 * * * *" \
  "hermes --profile=<profile> chat 'проверь inbox/*/task.md (state=draft или in_progress)'"
```

────────────────────────────────────────────────────────────────────────────
4. ЖИЗНЕННЫЙ ЦИКЛ state
────────────────────────────────────────────────────────────────────────────

```
draft  ──►  in_progress  ──►  review  ──►  done
                  │  ▲            │  ▲
                  ▼  │            ▼  │
                blocked          (rev. цикл)
```

4.1. `draft` (задача поставлена).
   Кто-то (Rost/вы) создал task-файл, но агент ещё не запускался.

4.2. `in_progress` (агент работает).
   Агент начал. Статус логируется в `progress.json` и `plans/<id>.md`.

4.3. `blocked` (застряли).
   Агент ждёт решения от пользователя. Зафиксировать в Status Log,
   что именно блокирует.

4.4. `review` (готово, проверка).
   Агенты отдали outputs. Пользователь проверяет.
   Если в `Acceptance Criteria` что-то не выполнено — назад в `in_progress`.

4.5. `done` (завершено).
   Все критерии приёмки отмечены `- [x]`. Агент закрыл сессию.
   Можно архивировать: `tar czf archive/<YYYY>/<task-id>.tar.gz inbox/<task-id>/`.

────────────────────────────────────────────────────────────────────────────
5. ПРАВИЛА ИМЕНОВАНИЯ
────────────────────────────────────────────────────────────────────────────

5.1. `TASK-ID`: `TASK-YYYY-MM-DD-<короткое-имя>`.
   Примеры хороших имён:
     TASK-2026-07-04-rag-chunking
     TASK-2026-07-04-fail2ban-setup
     TASK-2026-07-04-csv-stats

   Плохих имён избегать:
     TASK-1          (нет даты)
     TASK-2026-07-04 (нет темы)
     TASK-2026-07-04-Process All Things (заглавные, пробел)

5.2. Имя каталога совпадает с TASK-ID.
5.3. Имена файлов в outputs — без пробелов.

6. ГДЕ ЧТО ЛЕЖИТ (СВОДКА)
────────────────────────────────────────────────────────────────────────────

  workspace/inbox/TASK-<id>/
    ├── task.md        ← промпт (этот шаблон)

Подробнее — в гайде «Данные для задач агентов» (`Данные_для_задач_агентов_01.txt`).

────────────────────────────────────────────────────────────────────────────
8. ЧАСТЫЕ ОШИБКИ ПРИ ИСПОЛЬЗОВАНИИ ШАБЛОНА
────────────────────────────────────────────────────────────────────────────

8.1. Goal расплывчатый.
   ПЛОХО: «сделать отчёт».
   ХОРОШО: «посчитать топ-10 пользователей по событиям и записать в
           results/<id>/top_users.txt, формат — markdown table».

8.2. Acceptance без измеримости.
   ПЛОХО: «качественно».
   ХОРОШО: «все три файла созданы», «всего 1000 строк прочитано»,
           «coverage > 80%».

8.3. Outputs без точных путей.
   ПЛОХО: «сделать файл».
   ХОРОШО: «results/TASK-<id>/summary.md, формат — markdown».

8.4. Забыли progress.json / plans/.
   Через неделю не вспомните, на чём остановились. Всегда создавайте.

8.5. Status Log остаётся пустым.
   Первая запись: «created». Затем — каждый раз, когда меняется
   фаза или появляется вывод.

8.6. Decisions не пишутся.
   Через полгода забудете, почему выбор был сделан. Запишите в момент
   принятия.

8.7. Constraints не указаны.
   Агент может уйти в бесконечный цикл. Ограничьте budget токенов
   и время.

8.8. Длинные Requirements — лишний noise.
   Если требований > 10 — разбейте на подзадачи или используйте
   чек-лист.

8.9. Без Out of scope — задача разрастается.
   Всегда пишите, что НЕ нужно делать. Это защита.

────────────────────────────────────────────────────────────────────────────
9. КОГДА ИСПОЛЬЗОВАТЬ ШАБЛОН, А КОГДА — НЕТ
────────────────────────────────────────────────────────────────────────────

9.1. Использовать шаблон, если:
   - задача сложнее 5-7 строк в чате;
   - задача требует входных данных;
   - задача требует журнала состояний;
   - задача повторяется (шаблон — единый формат);
   - задачу нужно показать коллеге.

9.2. НЕ использовать шаблон, если:
   - простой вопрос в чате;
   - разовый скрипт, не требующий структуры;
   - одноразовая диагностика;
   - «Rost спросил, что такое X» — это в чат, не в файл.

13. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

Этот шаблон — рабочий инструмент, а не формальный артефакт. Когда
вы его копируете и заполняете:

  1. Замените `<placeholders>`.
  2. Удалите лишние секции.
  3. Заполните Goal + Acceptance + Outputs (обязательно).
  4. Создайте progress.json и plans/<id>.md рядом.
  5. Передайте агенту.

Когда задача завершена — переведите state в `done`, отметьте все
Acceptance-чекбоксы, обновите progress.json. Через месяц tar
архив — `archive/<YYYY>/<task-id>.tar.gz`.

Главное правило: **«один task-id = одна папка = один журнал»**.
Это то, что делает workspace пригодным для долгосрочного
использования. Без этого — через полгода вы потратите день на
разбор «что где лежит».
