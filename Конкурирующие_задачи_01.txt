# Конкурирующие задачи в Hermes Agent — что реально происходит
## (default-профиль + другой профиль + два разных Telegram-бота, две задачи одновременно)

────────────────────────────────────────────────────────────────────────────
0. СУТЬ ВОПРОСА
────────────────────────────────────────────────────────────────────────────

Ситуация, которую ты описал:

  • У тебя в Telegram два бота (например, @MMRV_Hermes_bot — профиль default,
    и @MimaG01Bot — профиль mi_mg_01).
  • Бот default-профиля получил задачу A и начал её выполнять.
  • Бот mi_mg_01-профиля тут же получил задачу B.
  • Происходят ли они параллельно, или задача A прервётся?

Короткий ответ (для impatient): **обе задачи идут параллельно**. Никаких
прерываний между профилями нет, потому что это **разные процессы** Python,
с разными asyncio-event-loop'ами, разными state.db и разными сессиями.

Но есть нюансы в ПРЕДЕЛАХ одного профиля — там лимит есть (см. §5).
И есть тонкости с shared resources (Bot API rate limit, LLM API rate
limit, файловая система и т.п.) — их надо учитывать, иначе «параллельно»
превращается в «конфликт».

────────────────────────────────────────────────────────────────────────────
1. АРХИТЕКТУРА HERMES AGENT — ЧТО ПОД КАПОТОМ
────────────────────────────────────────────────────────────────────────────

Чтобы понять параллелизм, надо знать три уровня изоляции профилей:

1.1. Профиль = отдельный каталог с состоянием.
   ~/.hermes/profiles/<имя>/
     ├── state.db                  ← SQLite, журнал сессий
     ├── gateway.pid
     ├── gateway_state.json
     ├── config.yaml
     ├── .env                      ← секреты (mode 600)
     ├── SOUL.md                   ← system prompt
     ├── sessions/<id>/            ← чат-сессии
     ├── memory/                   ← long-term memory
     ├── skills/, plugins/, cron/  ← кастомизация
     ├── cache/, logs/             ← runtime-артефакты
     └── ...

   Эти каталоги НЕ пересекаются: state.db default не видит state.db
   mi_mg_01, и наоборот. Если default запускает песочницу — она лежит в
   default/sandbox/, второй профиль про неё не знает.

1.2. Профиль = отдельный gateway-процесс.
   Каждый профиль со своим gateway запускается отдельной командой:

     hermes --profile=default gateway run
     hermes --profile=mi_mg_01 gateway run

   Это два разных python-процесса, два разных PID, две разные systemd
   unit'а (если включить через `hermes gateway install` в каждом профиле).

   На практике на одном сервере это выглядит так:
     PID 1847  python -m hermes_cli.main gateway run    (default)
     PID 2301  python -m hermes_cli.main gateway run    (mi_mg_01)

   Каждый из них — самостоятельный long-polling-клиент к своему Telegram
   bot token, со своим event-loop, со своей памятью, со своим logging.

1.3. Профиль = отдельные сессии.
   Gateway, получив входящее сообщение, открывает/продолжает чат-сессию
   в каталоге профиля: sessions/<id>/. Сессия — это «контекстная нить»:
   история сообщений, scratchpad, attachments, активный model state.

   Ключевое: сессии НЕ пересекаются между профилями. Сообщение,
   пришедшее в Telegram-бот default, обрабатывается в сессии default'а
   и **никак не трогает** сессию mi_mg_01.

────────────────────────────────────────────────────────────────────────────
2. ЧТО ПРОИСХОДИТ В ТВОЁМ СЦЕНАРИИ (ХРОНОЛОГИЯ)
────────────────────────────────────────────────────────────────────────────

Время  T=0:
  • В Telegram ты пишешь боту @MMRV_Hermes_bot: «Проверь диск».
  • Telegram Bot API держит long-poll на этот бот — это процесс default
    gateway (PID 1847).
  • getUpdates возвращает этот update. default-gateway принимает
    решение: открыть (или продолжить) сессию agent:main:telegram:dm:<chat_id>.

Время  T=0.05:
  • default-gateway стартует внутреннюю обработку:
      - грузит session из sessions/<chat>/,
      - вызывает LLM (model API),
      - пишет ответ обратно в Telegram через sendMessage.
  • На это время default-gateway НЕ блокируется на сообщения — он
    продолжает держать long-poll, и если придёт ещё один update,
    создаст ещё одну сессию.

Время  T=0.5 (через полсекунды):
  • В Telegram ты пишешь боту @MimaG01Bot: «статус сервера».
  • Telegram Bot API держит long-poll на этот бот — это процесс mi_mg_01
    gateway (PID 2301). **Другой процесс**.
  • getUpdates возвращает update. mi_mg_01-gateway **независимо**
    стартует свою сессию, свой вызов LLM, свой sendMessage.

Дальше параллельно:

  default-gateway → agent:default:task-A   (PID наследуется от 1847)
  mi_mg_01-gateway → agent:mi_mg_01:task-B (PID наследуется от 2301)

  Обе задачи реально идут ОДНОВРЕМЕННО:
  • могут занять один и тот же CPU, и тогда одна чуть медленнее;
  • могут стучаться в LLM API — там rate limit на аккаунт (и это
    может быть проблемой, см. §6);
  • файлы у них разные, БД разные — НЕ конфликтуют.

────────────────────────────────────────────────────────────────────────────
3. ГДЕ ГАРАНТИРОВАННО НЕТ КОНКУРЕНЦИИ
────────────────────────────────────────────────────────────────────────────

3.1. SQLite state.db — РАЗНЫЕ БД.
   У каждого профиля свой файл state.db. Конкурентных операций нет.
   Шевелится только VACUUM / WAL, и то по очереди внутри каждого
   gateway-event-loop'а.

3.2. Telegram API — РАЗНЫЕ ТОКЕНЫ.
   Каждый бот работает со своим токеном → с разных аккаунтов.
   Telegram Bot API не считает их конкурентами друг друга.

3.3. Memory / vector store (если есть).
   Если каждый профиль использует локальный ChromaDB / FAISS —
   файлы разные, никаких блокировок.

3.4. systemd unit — РАЗНЫЕ UNIT'Ы.
   default и mi_mg_01 — два hermes-gateway.service (у каждого своя
   директива User=, WorkingDirectory=/root/.hermes/profiles/<name>).
   Restart=always одной инстанции не влияет на другую.

────────────────────────────────────────────────────────────────────────────
4. В ПРЕДЕЛАХ ОДНОГО ПРОФИЛЯ — КАК УСТРОЕНА ПАРАЛЛЕЛЬНОСТЬ
────────────────────────────────────────────────────────────────────────────

Внутри одного gateway-процесса ситуация интереснее. Здесь
asyncio-цикл управляет несколькими задачами.

Главная константа: `max_concurrent_sessions` в config.yaml.
По умолчанию = 5 (на 2026). Можно увеличить.

4.1. Что считается «сессией».
   Одна user-сессия (например, agent:main:telegram:dm:505586502) = одна
   нитка агента, которая сейчас активна (отправила ответ, но не
   получила фидбек в течение некоторого окна) или простаивает (ждёт
   следующего user input).

   Важно: gateway **не считает «сколько задач всего обработано с
   утра»** — он считает только **сколько сейчас одновременно висит**.

4.2. Что происходит при превышении лимита.
   Допустим, лимит = 5, у тебя уже 5 сессий «зависло» (пользователь
   написал, бот ему ответил, но юзер не подтвердил окончание).
   Шестая сессия → user получает:

     «Hermes is at the active session limit (5/5).
      Try again when another session finishes.»

   Это значит: вторая задача в том же профиле может **ОТКЛОНЯТЬСЯ**,
   а не «прерывать первую».

   Чтобы избежать этого:
   • увеличить max_concurrent_sessions;
   • или закрывать старые сессии явно (--resume old-session завершить).

4.3. Прерывание ВНУТРИ одной сессии.
   Если user в той же сессии отправит новое сообщение ИЛИ если сработает
   cron-задача → текущая работа может быть cancel'нута через interrupt.
   Это поведение «своих» interrupt'ов, не «конкурентных задач».

4.4. Где реально возможна проблема — LLM.
   Две сессии одного профиля = два concurrent request к LLM API.
   Если у тебя 100 rpm budget, а обе сессии в один момент стучатся —
   они съедят 2 rpm, остальные 98 в минуту ещё есть.
   Если активны все 5 — это уже 5 одновременных, а LLM-API считает
   их независимо. Лимит LLM-API — это не «профильный», это глобальный
   per-API-key.

   На практике для серьёзных нагрузок ставят Anthropic batch API или
   свой прокси с rate-limit'ом.

────────────────────────────────────────────────────────────────────────────
5. CONCRETE EXAMPLE: ЧТО ГДЕ «ПРЕРВЁТСЯ» В ТВОЁМ КЕЙСЕ
────────────────────────────────────────────────────────────────────────────

Опять же: **прерывания между профилями нет**. Только внутри одного
профиля возможны следующие сценарии:

5.1. Profile=default.
   • bot @MMRV_Hermes_bot получил задачу A.
   • Внутри default-gateway запущена coroutine обработки.
   • Если есть свободные слоты (active_sessions < max_concurrent_sessions) —
     coroutine идёт до конца: LLM думает, tool calls, sendMessage,
     финал.
   • Если лимит исчерпан ДО старта — задача A получит reject ещё до
     того, как agent начнёт думать.
   • Если лимит исчерпан ВО ВРЕМЯ работы A — задача A **не прервётся**
     (она уже считает слот занятым, другая не может вытеснить).
     Другая задача получит reject.

5.2. Profile=mi_mg_01.
   • bot @MimaG01Bot получил задачу B.
   • Полностью независимая обработка.
   • Не «прерывает» задачу A в default.

5.3. Внутри default: что если cron сработает во время задачи A?
   • cron-задача стартует как отдельный session-id.
   • Если active_sessions < max → стартует параллельно (две сессии в
     одном gateway, общая quota).
   • Если active_sessions == max → cron-таска получит ошибку «at limit».
   • Cron-задача **не убивает** user-сессию (это by design — user
     важнее).

5.4. Что если один user отправит два сообщения подряд?
   • Это одна и та же session-id.
   • Второе сообщение → interrupt первой, потом продолжение.
   • Это «своё» прерывание (внутри одной сессии), а не конкуренция.

────────────────────────────────────────────────────────────────────────────
6. РЕАЛЬНЫЕ ОГРАНИЧЕНИЯ И УЗКИЕ МЕСТА
────────────────────────────────────────────────────────────────────────────

Даже когда «прерывания нет», есть вещи, которые могут затормозить
параллельную работу:

6.1. Telegram rate limit.
   • 30 msg/sec глобально per bot.
   • 1 msg/sec per chat.
   • Если обе сессии (default + mi_mg_01) одновременно пишут в один
     и тот же чат → вторая попадёт в retry-очередь Telegram.
   • Решение: настроить очереди отправки per-chat (Hermes умеет с
     batching).

6.2. LLM API rate limit.
   • OpenAI / Anthropic считают на аккаунт (или на ключ).
   • Если обе gateway используют ОДИН ключ → обе сессии делят budget.
   • Решение: разные ключи (default и mi_mg_01) или fallback.

6.3. CPU.
   • 2 python-процесса × asyncio = 2 event-loop'а. CPU делится
     шедулером. На 4-core машине обычно хватает.
   • Hermеs не блокирует event-loop на длительных операциях (есть
     run_in_executor для терминала, ssh, итд).

6.4. Файловая система.
   • Разные профили — разные state.db, разные sandbox, разные логи.
   • Если запустить ТЕСТ в одном профиле, он может писать гигабайты
     в /tmp, съедая место для второго. Лимитируйте sandbox size.

6.5. systemd-управление.
   • Если на хосте один root, и оба gateway — root-services, Restart=always
     у одного при падении не выключает другой.

6.6. Network.
   • Если upstream-канал узкий (например, 1 Gbit/s в обе стороны),
     то 5 активных сессий с большими tool-output могут упираться в
     сеть.
   • На этом сервере (mima-g-01) канал обычно 100 Mbit/s — для 5
     сессий обычно хватает.

────────────────────────────────────────────────────────────────────────────
7. КАК СДЕЛАТЬ ПАРАЛЛЕЛЬНУЮ РАБОТУ НАДЁЖНОЙ (ПРАКТИКА)
────────────────────────────────────────────────────────────────────────────

7.1. Каждому профилю — свой LLM-API key.
   default использует ANTHROPIC_API_KEY_A, mi_mg_01 — _B.
   Это решает 95% rate-limit issues.

7.2. Каждому профилю — свой Telegram bot.
   • @MMRV_Hermes_bot  ↔  default
   • @MimaG01Bot       ↔  mi_mg_01
   Запрещено использовать один bot двумя gateway — это даст polling
   conflict (см. §8).

7.3. Лимитировать active_sessions.
   config.yaml:
     agent:
       max_concurrent_sessions: 5

   Подбирай под LLM budget:
   • 5 сессий × 60 sec LLM response = 5 запросов в минуту.
   • Если LLM API даёт 60 rpm → ты впритык.
   • Если 12 rpm → уменьши до 2 сессий на профиль.

7.4. Уведомления о перегрузке.
   Если `at limit` срабатывает часто — сделай cron-нотификацию:
     hermes cron add "monitor" "*/5 * * * *" \
       "hermes status && notify если active_sessions/max > 0.9"

7.5. Имена сессий — разные префиксы.
   default → agent:main:*
   mi_mg_01 → agent:mi_mg_01:*

   Помогает при отладке: видно, какая сессия какому профилю принадлежит.

7.6. Логи — отдельно.
   Каждый профиль логирует в свой logs/gateway.log. По умолчанию
   ротация 5×50MB. Если хочешь дольше — увеличь или настрой
   logrotate.

7.7. Sandbox — отдельно.
   Если у тебя в config.yaml sandbox=on, то каждая сессия получает
   /tmp/<session_id>/. Под одним профилем их много, под другим — нет.
   Учитывай quota /tmp.

7.8. Backup-скрипты.
   `hermes backup` per profile. Не запускай «глобально», чтобы не
   схватить lock.

────────────────────────────────────────────────────────────────────────────
8. ИСКЛЮЧЕНИЯ, КОГДА ЗАДАЧИ КОНФЛИКТУЮТ (ХОТЯ И НЕ ДОЛЖНЫ)
────────────────────────────────────────────────────────────────────────────

Эти случаи редки, но возможны:

8.1. Один Telegram-bot token на два gateway.
   • Антипаттерн. → polling conflict → 409 → оба в цикле retry.
   • Решение: разные боты.

8.2. Один LLM API key, и оба профиля запрашивают параллельно.
   • Rate limit → 429 → retry-with-backoff → замедление, не «прерывание».
   • Решение: разные ключи.

8.3. Один файл-блокировка (если ты делаешь свой скрипт с fcntl.flock).
   • Если скрипт — single-writer, multi-reader, второй ждёт.
   • Не баг Hermes, by design.

8.4. Квоты ОС: max user processes, open files.
   • На этом сервере лимиты ulimit -u / -n не менялись (дефолт).
   • Если запустить 50 gateway-инстансов — упрёшься в nproc.
   • Каждый gateway — один основной процесс + 1 ssh subprocess при
     terminal-tool. На 5 сессий ≈ 5+1 = 6 процессов.

8.5. Жёсткий scheduler overhead.
   • Если ты запустил cron-задачу, которая сама стартует 100
     под-задач, и они все стучатся в Telegram одновременно → да,
     сеть упрётся в rate-limit.
   • Решение: батчинг.

8.6. Memory leak в долгоживущей сессии.
   • Hermes имеет memory-инструменты, и без явной команды «забудь»
     контекст накапливается.
   • К долгоживущим сессиям — регулярно /compact.

9. КАК ПОСМОТРЕТЬ, ЧТО ИДЁТ ПАРАЛЛЕЛЬНО (ИНСТРУМЕНТЫ)
────────────────────────────────────────────────────────────────────────────

9.1. hermes status
   $ hermes status
   Profile: default
   Active sessions: 2/5
   Bot: @MMRV_Hermes_bot (connected)

   $ hermes --profile=mi_mg_01 status
   Profile: mi_mg_01
   Active sessions: 1/5
   Bot: @MimaG01Bot (connected)

9.2. ps -ef | grep hermes
   # Два процесса, оба gateway run.

9.3. ss -tnp
   # Два держателя long-poll к api.telegram.org (если разные IP/порты — но

9.4. session_listing (CLI)
   $ hermes --profile=default sessions list
   $ hermes --profile=mi_mg_01 sessions list

9.5. journalctl
   $ journalctl --user -u hermes-gateway.service -f
   # Показывает логи ОБОих gateway (если они под одним юзером).
     Чтобы разделить — загляни в HERMES_PROFILE=/ HERMES_HOME= в env.

────────────────────────────────────────────────────────────────────────────
10. FAQ — короткие ответы
────────────────────────────────────────────────────────────────────────────

Q: «Прервётся ли задача A, когда придёт задача B?»
A: Нет, если A и B в разных профилях. Да, частично — если в одном
   профиле и лимит active_sessions исчерпан.

Q: «Можно ли поставить задачу, чтобы она принудительно прервала A?»
A: Только через interrupt в той же сессии (новый user input в чате).
   Через отдельную сессию — нет.

Q: «Сколько параллельных задач можно держать?»
A: active_sessions_per_profile × num_profiles × min(LLM API rpm).
   На практике — 5 × 2 × 12 = ~120 задач/час на 2 профилях.

Q: «Один cron-job может запустить две одинаковые задачи?»
A: Да, если активных сессий хватит. Используй flock или pid-based lock
   в самом скрипте, если хочешь «строго одну инстанцию».

Q: «Две задачи одновременно пишут в один Telegram-chat — что будет?»
A: Hermes queues сообщения per chat, шлёт последовательно. Получатель
   получит оба, но вразбивку (не факт, что в порядке старта).

Q: «Как убить зависшую задачу в default?»
A: hermes --profile=default cancel <session_id>
   или отправь в чат «/cancel».

Q: «Стоит ли держать mi_mg_01 как отдельный профиль или хватит default?»
A: Профиль оправдан, если:
   • разный LLM провайдер/ключ;
   • разная личность (SOUL.md);
   • разный набор skills / plugins / cron;
   • изоляция состояния (логи, память, сессии).
   Если всё одинаковое — проще держать одну инстанцию и различать
   сессии по chat_id.

────────────────────────────────────────────────────────────────────────────
11. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

В описанной тобой ситуации:

  • default-профиль получил задачу A.
  • mi_mg_01-профиль получил задачу B.
  • Обе выполняются ПАРАЛЛЕЛЬНО, в разных процессах, в разных
    сессиях, в разных БД.
  • Никаких прерываний «между профилями» в Hermes не существует —
    это by-design архитектура изоляции.

Внутри ОДНОГО профиля — лимит `max_concurrent_sessions` (по умолчанию 5).
Если он исчерпан, новая задача ОТКЛОНЯЕТСЯ (не прерывает старую).
Если лимит не исчерпан — задачи идут параллельно, делят rate-limit
LLM-API и CPU.

Главное, что нужно помнить:
  1. Разные профили = разные процессы = изоляция.
  2. Один токен = один gateway (не нарушай; polling conflict).
  3. LLM rate-limit — общий на аккаунт, не на профиль.
  4. Зависшие сессии — закрывай явно (cancel).

Если будешь ставить mi_mg_01 — имей в виду, что всё его состояние
