## 3. Polling conflict — разбор единственного наблюдения

В логе gateway за период **19:58:39 — 20:08:49** (≈10 минут, до текущего
restart) виден циклический WARNING:

```
WARNING gateway.platforms.telegram: Telegram polling conflict (1/5)
  — previous session still held open on Telegram's servers. Waiting 20s for it to expire.
  Error: Conflict: terminated by other getUpdates request; make sure that only one bot instance is running
INFO    gateway.platforms.telegram: Telegram polling resumed after conflict retry 1/5
```

Это сообщение означает «на стороне Telegram есть ещё одна активная getUpdates-сессия
с этим токеном, кроме моей». После restart в 20:17:49 (это первая запись в свежем
логе systemd-юнита) polling стартовал чисто:

```
20:17:52 INFO  set_my_commands OK
20:17:52 INFO  Connected to Telegram (polling mode)
20:17:52 INFO  ✓ telegram connected
```

Затем в **20:18:32** появился **один** conflict — причина была моим собственным
`curl …/getUpdates` в этой диагностической сессии: каждый `getUpdates` занимает
long-poll-слот на стороне Telegram, и когда 2 инстанса (curl + gateway) дерутся за
один токен, Telegram отдаёт 409 второму. Через 20 секунд Telegram отпустил мой
curl-коннект, и в **20:18:56** логе:

```
INFO gateway.platforms.telegram: Telegram polling resumed after conflict retry 1/5
```

**Вывод:** polling-конфликт self-healing'ится за один 20-секундный backoff. Это не
баг — это документированное поведение при случайном дублировании polling-клиентов.
За последние 5 минут (с момента завершения моего curl-теста) — **0 конфликтов**.

## 5. Замечания (некритичные, для сведения)

- **Пары /api-call'ы в этой диагностике сами вызывали polling conflict**, потому что
  curl и gateway не должны одновременно дёргать `getUpdates` с одного токена.
  Workaround для будущих диагностик: пользоваться `webhookInfo` и `sendMessage`
  (исходящие) — они не занимают long-poll-слот.

- **Pairing flow выключен** (`pairing: true` не задан явно → default behavior).
  Для single-user бота это нормально; если в будущем потребуется принимать
  сообщения от других пользователей, добавить:
  ```yaml
  # ~/.hermes/config.yaml
  gateway:
    platforms:
      telegram:
        allowed_users: [505586502, <other_id>]
  ```
  и перезапустить gateway (`systemctl --user restart hermes-gateway`).

- **`allowed_chats: ''`** — пустой, это не баг. CSV-строка матчится как
  substring, пустая = «без ограничений на группы». Так как `can_join_groups=true`,
  бот технически может быть инвайтнут в группу — но `allowed_users` всё равно
  должен включать chat_id группы, чтобы бот отвечал в ней.

- **systemd linger уже включён** (`loginctl enable-linger $USER` было выполнено
  ранее). Gateway переживёт logout SSH.
