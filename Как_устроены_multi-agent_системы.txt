# Как устроены multi-agent системы (полная детализация)

## 0. Зачем архитектору понимать multi-agent системы

Multi-agent системы — это парадигма, где несколько специализированных LLM-агентов координируются для решения задачи, непосильной одному агенту. Это не "несколько LLM подряд", а **оркестрация ролей, состояния, инструментов и памяти**.

Архитектор агентов проектирует именно такие системы — для бизнеса, где один LLM:
- Не умещает весь контекст.
- Не справляется с одной задачей за разумное число шагов.
- Требует разных промптов/инструментов для подзадач.
- Нуждается в разделении ответственности (кто за что отвечает).

---

## 1. Определение и базовая модель

### Что такое multi-agent система

Multi-agent система (MAS) — это набор автономных LLM-агентов, которые:
- Имеют **специализированные роли** (планировщик, исполнитель, ревьюер, и т.д.).
- **Коммуницируют** друг с другом через сообщения или общую память.
- **Координируются** через оркестратор (централизованный) или emergent протокол (децентрализованный).
- **Делят состояние** через общий store (graph, vector DB, file system).
- **Используют общие или раздельные инструменты** в зависимости от архитектуры.

### Single-agent vs multi-agent

| Аспект | Single-agent | Multi-agent |
|---|---|---|
| Контекст | Один большой context window | Разделён между агентами |
| Роли | Одна инструкция в system prompt | Каждый агент имеет свою роль |
| Инструменты | Все доступны | Распределены по ролям |
| Стоимость | Дешевле (меньше LLM calls) | Дороже (больше calls) |
| Надёжность | Точка отказа — один агент | Устойчивость через специализацию |
| Отладка | Проще (один лог) | Сложнее (граф вызовов) |
| Качество | Ограничено одной моделью | Каждый шаг — своя оптимизация |
| Масштабируемость | Упирается в context | Масштабируется добавлением агентов |

### Когда использовать multi-agent

✅ **Использовать:**
- Задача разбивается на независимые подзадачи.
- Нужны разные персоны/тоны зрения.
- Длинные pipeline (>10 шагов), где один агент теряет фокус.
- Разные модели для разных этапов (быстрая для парсинга, умная для рассуждения).
- Критична верификация (агент-ревьюер проверяет агента-исполнителя).

❌ **НЕ использовать:**
- Задача умещается в один контекст.
- Простой Q&A или чат-бот.
- Нет бюджета на координацию (каждый вызов = latency + cost).
- Команда не готова к overhead отладки.

## 2. Паттерны оркестрации

### 2.1. Supervisor (централизованный)

**Схема:**
```
                  Supervisor
                 /     |     \
            Agent A  Agent B  Agent C
              ↓        ↓        ↓
            Tools     Tools     Tools
```

**Как работает:**
- Supervisor получает задачу.
- Разбивает на подзадачи.
- Делегирует конкретным агентам.
- Собирает результаты, принимает решение о завершении.

**Плюсы:**
- Простая отладка (всё через supervisor).
- Контроль над потоком.
- Легко добавить guardrails на уровне supervisor.

**Минусы:**
- Bottleneck: supervisor становится узким местом.
- Supervisor может "сломаться" при большом графе.

**Фреймворки:** LangGraph (Supervisor pattern), CrewAI (иерархия), AutoGen (GroupChat manager).

**Когда использовать:** 90% production multi-agent систем. Стандарт индустрии.

---

### 2.2. Peer-to-peer (децентрализованный)

**Схема:**
```
        Agent A ←→ Agent B
           ↕         ↕
        Agent C ←→ Agent D
```

**Как работает:**
- Все агенты равноправны.
- Коммуницируют через общую шину сообщений.
- Каждый решает, кому передать задачу.

**Плюсы:**
- Нет единой точки отказа.
- Emergent поведение (агенты находят неожиданные решения).

**Минусы:**
- Сложная отладка (граф сообщений).
- Возможны циклы и тупики.
- Нет гарантий завершения.

**Когда использовать:** Исследовательские задачи, симуляции (Society of Mind, debate).

**Примеры:** AutoGen GroupChat (без менеджера), Emergence, OpenAI Swarm.

---

### 2.3. Hierarchical (иерархия)

**Схема:**
```
              Top-level Planner
              /        |        \
        Mid-1       Mid-2       Mid-3
       / | \       / | \       / | \
    L1 L2 L3    L4 L5 L6    L7 L8 L9
```

**Как работает:**
- Top-level планирует всю задачу.
- Mid-level агенты планируют свои подзадачи.
- Low-level агенты исполняют конкретные действия.

**Плюсы:**
- Масштабируется на большие задачи.
- Разделение ответственности по уровням абстракции.

**Минусы:**
- Высокая latency (много уровней).
- Ошибки на нижнем уровне каскадируют вверх.

**Когда использовать:** Длинные планы (deep research, автогенерация кода, сложные RAG с рассуждением).

---

### 2.4. Pipeline (конвейер)

**Схема:**
```
Input → Agent A → Agent B → Agent C → Output
```

**Как работает:**
- Данные проходят через последовательность агентов.
- Каждый обрабатывает свою часть и передаёт дальше.

**Плюсы:**
- Простота.
- Детерминированность.

**Минусы:**
- Нет обратной связи.
- Ошибки ранних агентов каскадируют.

**Когда использовать:** ETL-подобные задачи (парсинг → enrich → summary).

**Примеры:** LangChain LCEL chain, Haystack pipeline.

---

### 2.5. Debate / Voting

**Схема:**
```
       Task
        ↓
   Agent A    Agent B    Agent C
   (proposal) (proposal) (proposal)
        ↓        ↓         ↓
       Aggregator / Judge
              ↓
        Final Answer
```

**Как работает:**
- Несколько агентов генерируют разные решения.
- Judge (отдельный агент или тот же) выбирает лучшее.
- Может быть несколько раундов debate.

**Плюсы:**
- Повышает качество через diversity.
- Самокоррекция через peer review.

**Минусы:**
- Дорого (3-5x LLM calls).
- Зависит от качества judge.

**Когда использовать:** Задачи, где ошибка дорога стоит (медицина, финансы, код-ревью).

**Примеры:** Multi-agent debate (Du et al. 2023), Self-Consistency, ReAct debate.

---

### 2.6. Map-Reduce

**Схема:**
```
        Input
         ↓
   ┌─────┼─────┐
   ↓     ↓     ↓
  Map1  Map2  Map3  (параллельная обработка)
   ↓     ↓     ↓
   └─────┼─────┘
         ↓
       Reduce
         ↓
       Output
```

**Как работает:**
- Map-агенты параллельно обрабатывают куски данных.
- Reduce-агент агрегирует результаты.

**Плюсы:**
- Параллелизм (быстрее).
- Масштабируется на большие объёмы.

**Минусы:**
- Reduce может быть узким местом.

**Когда использовать:** Summarization длинных документов, batch-анализ, parallel research.

## 3. Фреймворки для multi-agent систем

### 3.1. LangGraph (LangChain)

**Что это:** Stateful граф-фреймворк для LLM-приложений.

**Архитектура:**
- Граф = nodes (агенты/функции) + edges (переходы) + state (общее состояние).
- Циклы поддерживаются нативно.
- Persistence через checkpointers (SQLite, Postgres).

**Пример:**
```python
from langgraph.graph import StateGraph

class AgentState(TypedDict):
    messages: list
    next: str

def planner(state): ...
def executor(state): ...
def reviewer(state): ...

workflow = StateGraph(AgentState)
workflow.add_node("planner", planner)
workflow.add_node("executor", executor)
workflow.add_node("reviewer", reviewer)
workflow.add_edge("planner", "executor")
workflow.add_edge("executor", "reviewer")
workflow.add_conditional_edges("reviewer", should_continue)

app = workflow.compile()
```

**Плюсы:**
- Гибкость (любая топология).
- Persistence и human-in-the-loop.
- Production-ready.

**Минусы:**
- Крутая кривая обучения.
- Boilerplate.

---

### 3.2. CrewAI

**Что это:** Role-based multi-agent фреймворк.

**Архитектура:**
- Crew = набор Agents с ролями.
- Tasks = подзадачи с expected output.
- Process = sequential или hierarchical.

**Пример:**
```python
from crewai import Agent, Task, Crew

researcher = Agent(
    role="Researcher",
    goal="Find latest research",
    tools=[search_tool]
)

writer = Agent(
    role="Writer",
    goal="Write blog post"
)

task1 = Task(description="Research AI agents", agent=researcher)
task2 = Task(description="Write summary", agent=writer)

crew = Crew(agents=[researcher, writer], tasks=[task1, task2])
result = crew.kickoff()
```

**Плюсы:**
- Простой API.
- Интуитивная модель ролей.

**Минусы:**
- Меньше гибкости чем LangGraph.
- Сложнее кастомная логика.

---

### 3.3. AutoGen (Microsoft)

**Что это:** Conversational multi-agent фреймворк.

**Архитектура:**
- AssistantAgent — LLM-агент.
- UserProxyAgent — человек или код.
- GroupChat — несколько агентов в чате.

**Пример:**
```python
from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent("assistant", llm_config={...})
user_proxy = UserProxyAgent("user", code_execution_config={"work_dir": "coding"})

user_proxy.initiate_chat(
    assistant,
    message="Plot a chart of NVDA stock price"
)
```

**Плюсы:**
- Сильная code execution история.
- Хорош для исследований.

**Минусы:**
- Менее production-ready.
- Сложнее контролировать поток.

---

### 3.4. Haystack (deepset)

**Что это:** Pipeline-фреймворк для NLP/AI-приложений.

**Архитектура:**
- Pipeline = nodes + connections.
- Каждый node — компонент (retriever, reader, prompt, generator).

**Когда использовать:** RAG-тяжёлые задачи, поисковые системы.

---

### 3.5. Swarm (OpenAI)

**Что это:** Экспериментальный фреймворк для децентрализованных агентов.

**Ключевая идея:** Агенты передают задачи друг другу через handoff.

**Когда использовать:** Простые peer-to-peer сценарии, прототипы.

---

### 3.6. Сравнительная таблица

| Фреймворк | Архитектура | Сложность | Production | Гибкость | Кривая обучения |
|---|---|---|---|---|---|
| LangGraph | Граф | Высокая | Отличная | Максимальная | Высокая |
| CrewAI | Role-based | Средняя | Хорошая | Средняя | Низкая |

| Hermes | Event-driven | Средняя | Хорошая | Средняя | Средняя |

## 4. Коммуникация между агентами

### 4.1. Через сообщения

```python
# Сообщение с метаданными
{
    "from": "planner",
    "to": "executor",
    "type": "task",
    "content": {...},
    "metadata": {"priority": "high", "context_id": "abc123"}
}
```

**Транспорты:**
- In-memory queue (asyncio.Queue).
- Redis pub/sub.
- Kafka / RabbitMQ для распределённых систем.
- WebSocket для real-time UI.

### 4.2. Через общую память

**Shared State:**
- Граф знаний (Neo4j, Memgraph).
- Vector store для эмбеддингов.
- File system / S3 для больших данных.

**Memory patterns:**
- Working memory — текущая задача.
- Episodic memory — история действий.
- Semantic memory — факты о мире.

### 4.3. Через инструменты

Агенты могут вызывать общие инструменты (БД, API, файлы), что делает их коммуникацию implicit.

## 5. Состояние и persistence

### State management

**Локальное состояние** (в рамках одного запуска):
```python
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    current_step: str
    artifacts: dict
    errors: list
```

**Persistent state** (между запусками):
- Checkpointers в LangGraph (MemorySaver, SqliteSaver, PostgresSaver).
- Thread ID для идентификации сессии.

### Когда persistence критична

- Human-in-the-loop (прерывание и возобновление).
- Длинные задачи (>10 минут).
- Multi-user приложения.
- Audit и debugging.

## 6. Memory в multi-agent системах

### Типы памяти

**1. Short-term (контекстное окно):**
- История диалога.
- Последние N сообщений.
- Ограничено размером контекста модели.

**2. Long-term:**
- Vector store (Qdrant, Milvus).
- Knowledge graph (Neo4j).
- Structured DB (PostgreSQL с JSONB).

**3. Episodic:**
- История действий каждого агента.
- Sequence of tool calls.
- Used для обучения и отладки.

**4. Semantic:**
- Факты о пользователе, домене, мире.
- Извлекаются из истории и обновляются.

**5. Procedural:**
- Какие workflows работают.
- Успешные паттерны решений.

### Memory sharing между агентами

**Shared memory:** все агенты читают и пишут в одну память.
- Плюсы: согласованность.
- Минусы: contention, security (один агент видит всё).

**Private memory:** каждый агент имеет свою память.
- Плюсы: изоляция.
- Минусы: дублирование, сложнее sharing.

**Hybrid:** общая для метаданных, приватная для контекста.
- Стандарт для production.

## 7. Tool use в multi-agent

### Tool registry

Централизованный реестр инструментов:
```python
{
    "search_web": {"agent": "researcher", "rate_limit": "10/min"},
    "write_file": {"agent": "coder", "rate_limit": "100/min"},
    "send_email": {"agent": "communicator", "rate_limit": "5/min"},
    "query_db": {"agent": "analyst", "rate_limit": "50/min"}
}
```

### Распределение инструментов

**По ролям:**
- Planner — search, read.
- Executor — write, compute.
- Reviewer — read, validate.
- Communicator — send, notify.

**Sandbox для каждого агента:**
- Чтобы один агент не мог выполнить `send_email` или `delete_file`.

### Dynamic tool loading

Агенты загружают инструменты по необходимости (для экономии контекста):
```python
def planner_with_tools(state):
    if state["task_type"] == "research":
        tools = [search_tool, read_tool]
    elif state["task_type"] == "code":
        tools = [code_exec_tool, file_tool]
    return planner_agent.bind_tools(tools).invoke(state)
```

## 8. Планирование и разбиение задач

### Task decomposition

**Стратегии:**
1. **Sequential:** A → B → C (простая цепочка).
2. **Parallel:** A, B, C одновременно → merge.
3. **Hierarchical:** Plan → sub-plans → actions.
4. **Conditional:** if/else по результатам.
5. **Iterative:** refine пока не достигнут критерий.

### Planning algorithms

**ReAct (Reason + Act):**
```
Thought: нужно найти информацию о X
Action: search_web("X")
Observation: нашёл Y
Thought: Y подтверждает Z
Final Answer: Z
```

**Plan-and-Execute:**
```
Plan:
  1. Search for X
  2. Verify Y
  3. Generate summary
Execute step 1 → Execute step 2 → Execute step 3
```

**Reflexion:**
```
Execute → Reflect → Improve → Re-execute
```

**Tree of Thoughts:**
```
Generate multiple paths → Evaluate each → Choose best
```

### Когда какой planning

- ReAct — для простых tasks с 1-3 шагами.
- Plan-and-Execute — для средних с 5-10 шагами.
- Reflexion — для критичных к качеству.
- Tree of Thoughts — для задач с несколькими решениями.

## 9. Guardrails и валидация

### 9.1. На уровне supervisor

- Проверка завершённости (task done?).
- Валидация выходов перед передачей.
- Budget control (max steps, max cost).

### 9.2. На уровне отдельного агента

- Output validation (JSON schema, Pydantic).
- Content filtering (toxicity, PII).
- Hallucination detection (когда возможно).

### 9.3. На уровне системы

- End-to-end evals (golden sets).
- Monitoring (LangSmith, Langfuse, Helicone).
- Alerting на аномалии.

## 10. Observability и debugging

### Что логировать

- Каждый вызов агента: вход, выход, latency, cost.
- Каждое сообщение между агентами: from, to, content (sanitized).
- Каждый tool call: tool, args, result, error.
- Финальное решение: кто решил, на основании чего.

### Инструменты

- **LangSmith** — для LangChain/LangGraph.
- **Langfuse** — open-source альтернатива.
- **Helicone** — LLM-specific observability.
- **OpenTelemetry** — стандарт для распределённых трейсов.
- **Weights & Biases** — для экспериментов.

### Визуализация графа

- Mermaid diagrams для статического графа.
- LangGraph Studio для интерактивной визуализации.
- Custom dashboards с помощью Grafana.

## 11. Production considerations

### Performance

- **Latency:** supervisor + N агентов = O(N * t_agent). Mitigate через parallelism.
- **Throughput:** async execution, batching.
- **Cost:** оптимизация через модель selection (быстрая для простых задач, умная для сложных).

### Reliability

- **Retries** с exponential backoff.
- **Circuit breaker** для сломанных tools/agents.
- **Fallback** на более простую стратегию.
- **Timeouts** на каждом уровне.

### Security

- **Sandbox** для каждого агента (нельзя всем всё).
- **Audit log** всех действий.
- **Approval workflow** для критичных операций (send_email, delete_file, payment).
- **Prompt injection defense** на каждом входе.

### Cost optimization

- **Model cascade:** простая задача → дешёвая модель; сложная → дорогая.
- **Semantic caching:** кэш по эмбеддингу запроса.
- **Batch processing:** группировка нескольких запросов.
- **Token optimization:** компактные промпты, structured outputs.

## 12. Архитектурные anti-patterns

### ❌ Что НЕ делать

**1. Supervisor как bottleneck:**
- Supervisor обрабатывает каждое сообщение → медленно.
- Fix: делегировать часть решений агентам.

**2. Бесконечные циклы:**
- Agent A → Agent B → Agent A → ... без выхода.
- Fix: max iterations, exit conditions.

**3. Гигантский context:**
- Все агенты видят всё → дорого и медленно.
- Fix: scoped contexts, summary chains.

**4. Нет observability:**
- "Что-то сломалось, но непонятно что".
- Fix: трейсинг с первого дня.

**5. Agent-per-everything:**
- Создавать новый агент на каждый чих.
- Fix: agents = роли, не задачи. Использовать tools для разнообразия.

**6. Shared mutable state без locks:**
- Два агента пишут в одну переменную → race condition.
- Fix: immutable state или explicit locking.

**7. Только static prompts:**
- System prompt фиксирован → нет адаптации.
- Fix: dynamic prompts на основе контекста.

**8. Игнорирование ошибок:**
- Tool fails → агент продолжает как ни в чём не бывало.
- Fix: explicit error handling, retries, fallback.

## 13. Практические примеры

### 13.1. Research pipeline

```
Planner: декомпозирует запрос на 3 research questions
   ↓
Researcher 1: ищет по вопросу 1 (parallel)
Researcher 2: ищет по вопросу 2 (parallel)
Researcher 3: ищет по вопросу 3 (parallel)
   ↓
Synthesizer: объединяет результаты
   ↓
Reviewer: проверяет качество и полноту
   ↓
Output
```

### 13.2. Code generation

```
Planner: разбивает задачу на подзадачи (architecture, modules, tests)
   ↓
Architect: проектирует структуру
   ↓
Coder 1, 2, 3: пишут разные модули (parallel)
   ↓
Tester: запускает тесты, валидирует
   ↓
Reviewer: проверяет код, стиль, безопасность
   ↓
Final code (с commit message)
```

### 13.3. Customer support

```
Triage Agent: классифицирует запрос
   ↓
(branch by category)
   ├→ Billing Agent (RAG по платежам)
   ├→ Technical Agent (RAG по продукту + tools)
   └→ General Agent (FAQ)
   ↓
Response Generator: формулирует финальный ответ
   ↓
Quality Check: проверяет tone, accuracy
   ↓
Send to customer
```

### 13.4. Data analysis

   ↓
Planner: выбирает аналитические методы
   ↓
Analyzer: выполняет анализ (может быть несколько параллельно)
   ↓
Visualizer: генерирует графики
   ↓

   ↓

## 14. Оценка качества multi-agent систем

### Метрики

**Task-level:**
- Success rate (% задач, решённых корректно).
- Cost per task.
- Latency per task.

**Agent-level:**
- Tool call accuracy.
- Hallucination rate.
- Error rate.

**System-level:**
- Coordination overhead (время на коммуникацию).
- Convergence rate (как быстро агенты достигают решения).
- Robustness (как система справляется с ошибками отдельных агентов).

### Evals

- **Golden sets:** заранее размеченные задачи с правильными ответа
- **LLM-as-judge:** отдельный LLM оценивает качество.
- **Human eval:** экспертная оценка на подвыборке.
- **A/B тесты:** сравнение двух версий системы.

## 16. Ключевые принципы (резюме)

1. **Multi-agent ≠ серебряная пуля.** Single-agent проще и дешевле. Переходить только при необходимости.

2. **Supervisor pattern — стандарт индустрии.** Используйте его как стартовую точку.

3. **State management — критичен.** Persistent state, checkpointers, thread IDs — must-have.

4. **Memory design — ключ к качеству.** Правильное разделение short-term/long-term/episodic.

5. **Observability с первого дня.** Без трейсинга невозможно отлаживать multi-agent.

6. **Defense in depth.** Guardrails на supervisor, agent, system уровнях.

7. **Cost & latency — first-class citizens.** Оптимизируйте модели по задачам, кэшируйте, батчьте.

8. **Evals перед deploy.** Golden sets, LLM-as-judge, human eval.

9. **Iterate, не perfect.** Начните с простого supervisor pattern, добавляйте сложность по мере необходимости.

10. **Production-ready сразу.** Sandboxing, retries, fallbacks, monitoring — не afterthought.
