# Новый профиль Hermes Agent — какие файлы заполнять, где они лежат, когда создавать
## Полный гайд по настройке профиля с нуля

────────────────────────────────────────────────────────────────────────────
0. ЗАЧЕМ ЭТОТ ГАЙД
────────────────────────────────────────────────────────────────────────────

В Hermes Agent профиль — это **изолированная рабочая директория со
своим состоянием**: свои сессии, память, навыки, секреты, личность,
cron-задачи и gateway-процесс. Каждый профиль = отдельный каталог.

Этот гайд — сводный, он перекрывает 4 предыдущих (SOUL.md, MEMORY.md,
USER.md, SKILL.md). Здесь я отвечаю на три вопроса сразу:

  1. Что заполнять для нового профиля.
  2. Как назвать и где расположить каждый файл.
  3. Когда вообще создавать новый профиль, а когда дописать в существующий.

Документ написан после практической работы на этом сервере: реальные
пути, реальные файлы, реальная команда `hermes profile create`.

────────────────────────────────────────────────────────────────────────────
1. ГДЕ ЛЕЖИТ ПРОФИЛЬ — АНАТОМИЯ
────────────────────────────────────────────────────────────────────────────

Корень профиля:
   ~/.hermes/profiles/<имя_профиля>/

Полный каталог внутри (что мы видим на этом сервере для
`analyst_training`):

   analyst_training/
   ├── SOUL.md                  ← личность и стиль
   ├── config.yaml              ← главный конфиг
   ├── .env                     ← секреты (mode 600)
   ├── profile.yaml             ← метаданные профиля (внутреннее)
   ├── distribution.yaml        ← если из дистрибутива
   ├── .clean_shutdown          ← маркер нормального закрытия
   ├── state.db                 ← SQLite, история сессий
   ├── gateway.pid              ← runtime: PID активного gateway
   ├── gateway_state.json       ← runtime: состояние gateway
   ├── gateway.lock
   ├── channel_directory.json
   ├── memories/
   │   ├── MEMORY.md            ← факты о мире (динамика)
   │   └── USER.md              ← факты о пользователе
   ├── skills/                  ← per-profile навыки
   │   └── <name>/SKILL.md
   ├── cron/                    ← per-profile cron-задачи
   ├── hooks/                   ← pre/post tool события
   ├── sessions/                ← история чат-сессий
   ├── logs/                    ← логи шлюза и операций
   ├── sandboxes/               ← изолированные окружения для terminal
   ├── image_cache/             ← кэш картинок
   ├── audio_cache/             ← кэш голоса
   ├── bin/                     ← локальные CLI-обёртки
   ├── plans/                   ← blackboard планов
   ├── skins/                   ← UI-темы (web dashboard)
   ├── home/                    ← «дом» профиля для sandbox-окружений
   ├── workspace/               ← файлы агента
   └── pairing/                 ← device pairing для Matrix/и т.п.

Профиль `default` живёт сразу в `~/.hermes/` (не в `profiles/`):
   ~/.hermes/SOUL.md
   ~/.hermes/.env
   ~/.hermes/memories/MEMORY.md
   ~/.hermes/memories/USER.md
   ~/.hermes/skills/
   ...

Именованные профили — каждый в своей поддиректории. У default и
named профилей структура каталогов одинаковая, отличается только
корневой путь.

────────────────────────────────────────────────────────────────────────────
2. МИНИМАЛЬНЫЙ НАБОР ФАЙЛОВ ДЛЯ НОВОГО ПРОФИЛЯ
────────────────────────────────────────────────────────────────────────────

Минимум, чтобы профиль заработал:

  ┌────────────────────────────┬──────────────────────────────────────────┐
  │ Файл                       │ Что в нём                                │
  ├────────────────────────────┼──────────────────────────────────────────┤
  │ SOUL.md                    │ Роль агента + стиль + запреты            │
  │ .env                       │ Секреты (mode 600)                       │
  │ config.yaml                │ Модель, провайдеры, инструменты, шлюз    │
  │ memories/MEMORY.md         │ Факты об окружении                       │
  │ memories/USER.md           │ Факты о пользователе                     │
  │ (skills/<name>/SKILL.md)*  │ Per-profile навыки, если нужны           │
  └────────────────────────────┴──────────────────────────────────────────┘

Из них обязательно при создании: только SOUL.md и .env.
Остальное создаётся при первом использовании.

────────────────────────────────────────────────────────────────────────────
3. ЧТО ЗАПОЛНЯТЬ И ГДЕ — ПОДРОБНО ПО КАЖДОМУ ФАЙЛУ
═══════════════════════════════════════════════════════════════════════════
3.1. SOUL.md  →  `~/.hermes/profiles/<name>/SOUL.md`
────────────────────────────────────────────────────────────────────────────

Что это: личность агента, его роль, стиль общения, запреты.

Когда писать: один раз при создании профиля. Дополнять — редко,
при смене роли.

Что внутри (5 разделов, ~2-4 КБ):
  1. Имя и роль.
  2. Круг задач (что делает, что НЕ делает).
  3. Стиль общения (язык, длина, эмодзи, обращение).
  4. Инструменты и conventions.
  5. Контекст окружения (хосты, провайдеры).

Что НЕ писать:
  - «You are Hermes Agent…» (это уже в базовом system prompt).
  - Токены.
  - Длинные манифесты без конкретики.

────────────────────────────────────────────────────────────────────────────
3.2. .env  →  `~/.hermes/profiles/<name>/.env`  (mode 600)
────────────────────────────────────────────────────────────────────────────

Что это: секреты для аутентификации и runtime-настройки.
ТОЛЬКО сюда, НИКУДА больше.

Что внутри (типичные переменные):
  ANTHROPIC_API_KEY=<...>          # или OPENAI_API_KEY
  ANTHROPIC_BASE_URL=<...>         # если кастомный endpoint
  HERMES_MODEL=MiniMax-M3
  TELEGRAM_BOT_TOKEN=<...>         # опционально — другой бот на профиль
  TELEGRAM_ALLOWED_USERS=<chat_id>
  MATRIX_HOMESERVER=<...>          # опционально
  MATRIX_ACCESS_TOKEN=<...>
  ...

Что НЕ писать:
  - В MEMORY.md или SKILL.md (см. §5 — это нарушает санитизацию).
  - В SOUL.md (статика, забудется через месяц).
  - В USER.md (PII в плане безопасности).

Права: обязательно `chmod 600`.

────────────────────────────────────────────────────────────────────────────
3.3. config.yaml  →  `~/.hermes/profiles/<name>/config.yaml`
────────────────────────────────────────────────────────────────────────────

Что это: главный конфиг профиля. Модель, провайдеры, тулсеты,
messaging, поведение.

Когда писать: сразу после создания. Можно запустить `hermes model`
для визарда, или редактировать напрямую.

Ключевые секции:
  model:           — default model + provider + base_url
  providers:       — список провайдеров с ключами
  fallback_providers:    — fallback
  toolsets:        — какие тулсеты активны
  agent:           — max_turns, max_concurrent_sessions, timeouts
  messaging:       — telegram/matrix/...
  memory:          — provider (built-in / mem0 / etc.)
  cron:            — расписание для профиля
  hooks:           — pre/post tool events

Что НЕ дублировать:
  - Не пишите сюда секреты — они в .env.
  - Не пишите сюда личность агента — это в SOUL.md.

────────────────────────────────────────────────────────────────────────────
3.4. memories/MEMORY.md  →  `~/.hermes/profiles/<name>/memories/MEMORY.md`
────────────────────────────────────────────────────────────────────────────

Что это: долгосрочные факты об окружении, инфраструктуре, проектах.

Когда писать:
  - При создании профиля — засеять «базовый набор фактов».
  - По ходу работы — модель сама дописывает через `memory write`.

Что внутри (с датами, ~2-10 КБ):
  ## Хосты (таблица)
  ## Networking (особенности)
  ## Доступы (ссылки на .env, без секретов)
  ## Квоты / лимиты
  ## Установленные сервисы
  ## Конвенции (стиль кода, формат файлов)
  ## Выученные правила окружения (с датами)
  ## История решений (с обоснованиями)

Что НЕ писать: токены, эфемерные состояния, размытые предпочтения.

────────────────────────────────────────────────────────────────────────────
3.5. memories/USER.md  →  `~/.hermes/profiles/<name>/memories/USER.md`
────────────────────────────────────────────────────────────────────────────

Что это: факты о пользователе, который разговаривает с агентом.

Когда писать:
  - При создании — заполнить базовые (имя, язык, часовой пояс).
  - По ходу работы — модель дописывает через `memory write --target=user`.

Что внутри (5 разделов, ~0.5-2 КБ):
  ## Identity (имя, контакт, роль)
  ## Communication (стиль, длина, обращение)
  ## Work style (стэк, привычки)
  ## Sensitivities (что нельзя)
  ## Boundaries (границы роли)

Что НЕ писать: секреты, чужие PII, медицинскую/юридическую инфу.

────────────────────────────────────────────────────────────────────────────
3.6. skills/<name>/SKILL.md  →  `~/.hermes/profiles/<name>/skills/...`
────────────────────────────────────────────────────────────────────────────

Что это: per-profile навыки для конкретных операций.

Когда создавать: когда 2+ раза повторился паттерн и нужны точные команды.

Что внутри (обязательно):
  - YAML frontmatter (name, description как триггер, version, tags).
  - When to Use.
  - Step-by-step (с код-блоками).
  - Pitfalls.

Файлы `skills/` в профиле — **только** для текущего профиля.
Глобальные скиллы лежат в `~/.hermes/skills/` (вне `profiles/`).

Полный гайд — `Запонение_skill_MD.txt`.

────────────────────────────────────────────────────────────────────────────
4. ИМЕНОВАНИЕ ПРОФИЛЯ
────────────────────────────────────────────────────────────────────────────

4.1. Формат имени.
   - Только латиница, цифры, дефис, подчёркивание.
   - Длина 3-32 символа (валидатор).
   - Без пробелов, без спец-символов.

4.2. Хорошие имена.
   - `mi_mg_01`      — привязка к инфраструктуре.
   - `code_reviewer` — привязка к функции.
   - `default`       — зарезервированное имя для основного профиля.
   - `analyst_training` — если есть смысл.
   - `briefing_daily` — привязка к задаче.

4.3. Плохие имена.
   - `My Profile` — пробелы, заглавные.
   - `prof1` — не описательное.
   - `admin` — конфликтует с системными именами.
   - `123` — начинается с цифры (часто проблема).

4.4. Конвенция именования.
   - snake_case (для технических, например `mi_mg_01`).
   - role-based (для функциональных, например `code_reviewer`).
   - kebab-case НЕ допускается (Hermes требует lowercase + underscore).

────────────────────────────────────────────────────────────────────────────
5. ГДЕ ФАЙЛЫ — СВОДНАЯ ТАБЛИЦА
────────────────────────────────────────────────────────────────────────────

  ┌────────────────────────────┬─────────────────────────────────────┐
  │ Файл                       │ Путь                                │
  ├────────────────────────────┼─────────────────────────────────────┤
  │ SOUL.md                    │ profiles/<name>/SOUL.md             │
  │ .env                       │ profiles/<name>/.env  (600)         │
  │ config.yaml                │ profiles/<name>/config.yaml         │
  │ profile.yaml               │ profiles/<name>/profile.yaml        │
  │ distribution.yaml          │ profiles/<name>/distribution.yaml   │
  │ MEMORY.md                  │ profiles/<name>/memories/MEMORY.md  │
  │ USER.md                    │ profiles/<name>/memories/USER.md    │
  │ SKILL.md                   │ profiles/<name>/skills/<name>/SKILL │
  │ gates (custom)             │ profiles/<name>/skills/<name>/...   │
  │ cron jobs                  │ profiles/<name>/cron/...            │
  │ hooks                      │ profiles/<name>/hooks/...           │
  │ state.db                   │ profiles/<name>/state.db            │
  │ gateway.pid                │ profiles/<name>/gateway.pid         │
  │ gateway_state.json         │ profiles/<name>/gateway_state.json  │
  │ session dirs               │ profiles/<name>/sessions/<id>/      │
  │ logs                       │ profiles/<name>/logs/...            │
  │ secrets / token cache      │ profiles/<name>/auth.json           │
  └────────────────────────────┴─────────────────────────────────────┘

Для `default` корень не в `profiles/`, а напрямую в `~/.hermes/`.

────────────────────────────────────────────────────────────────────────────
6. ЧТО НЕ ДОЛЖНО БЫТЬ В ПРОФИЛЕ, НО ЧАСТО ПЫТАЮТСЯ
────────────────────────────────────────────────────────────────────────────

6.1. Токены и API-ключи в MEMORY.md / SOUL.md / SKILL.md.
   → Hermes-санитизация превратит их в `***`. Положите в `.env`.

6.2. Личные данные (PII) в открытом виде.
   → Если не нужны — не пишите.

6.3. Чужие конфиги и SSH-ключи.
   → Только ключи текущего пользователя.

6.4. Логи с чувствительными данными.
   → В `logs/` могут попасть токены из curl. Чистите регулярно.

6.5. Старые бэкапы и .bak файлы.
   → Сделайте отдельный backup-каталог (`hermes backup` создаёт
     tar.gz), не держите .env.bak рядом.

6.6. Runtime-артефакты в git.
   → `state.db`, `gateway.pid`, `gateway_state.json` — runtime,
     не коммитить.

────────────────────────────────────────────────────────────────────────────
7. КОГДА СОЗДАВАТЬ НОВЫЙ ПРОФИЛЬ (А НЕ ДОПОЛНЯТЬ СУЩЕСТВУЮЩИЙ)
────────────────────────────────────────────────────────────────────────────

7.1. СИЛЬНЫЕ СИГНАЛЫ — нужен новый профиль.

  а) ДРУГОЙ БОТ / ДРУГОЙ CHANNEL.
     У вас уже есть default с Telegram @MMRV_Hermes_bot. Хотите
     второй бот @MimaG01Bot — это новый профиль.
     Причина: один бот = один активный gateway. polling conflict.

  б) ДРУГОЙ LLM-ПРОВАЙДЕР ИЛИ API KEY.
     Default ходит в Anthropic-совместимое API. Хотите
     OpenAI/Anthropic напрямую — нужны разные .env, разные ключи.
     Альтернатива — credentials pool, но для rate-limit
     изоляции новый профиль лучше.

  в) ДРУГАЯ ЛИЧНОСТЬ (SOUL.md).
     Default: оперативный ассистент. Хотите senior reviewer —
     другая роль, другой стиль, другой SOUL.md.

  г) ИЗОЛЯЦИЯ СОСТОЯНИЯ.
     Default работает над prod-инфрой, вам нужен профиль
     для тестов на dev — отдельные каталоги, память, логи.

  д) ДРУГОЙ ПОЛЬЗОВАТЕЛЬ (USER.md).
     С default работает Rost, с профилем `code_reviewer` —
     будет работать другой человек. USER.md будет другой.

  е) ПЛАТНОЕ vs БЕСПЛАТНОЕ ИСПОЛЬЗОВАНИЕ.
     Разные профили — разные счётчики расходов, разные
     квоты.

7.2. СЛАБЫЕ СИГНАЛЫ — обычно НЕ нужен новый профиль.

  а) Просто другая задача (спросить рецепт, проверить код).
     → Один профиль с разными skills.

  б) Чуть другой стиль ответов.
     → Поменять SOUL.md одного профиля дешевле.

  в) Тот же пользователь и бот.
     → Один профиль.

  г) Просто хочется добавить rules.
     → Дописать в SOUL.md / MEMORY.md текущего профиля.

  д) Хочется «поэкспериментировать».
     → Можно создать отдельный sandbox-профиль (см. §10),
       но не засорять основной.

7.3. УНИВЕРСАЛЬНЫЙ ТЕСТ.
   Задайте себе 5 вопросов:
   1. Этот профиль будет работать с **другим пользователем** или **другим ботом**?
   2. У него **другие секреты** / API keys?
   3. У него **другая личность** (роль)?
   4. **Изоляция состояния** (память, логи) оправдана?
   5. Этот профиль будет **висеть долго и параллельно** с основным?

   Если хотя бы на 3 из 5 — «да», создавайте новый профиль.
   Если меньше — дополняйте существующий.

7.4. АНТИПАТТЕРНЫ.
   - Создавать новый профиль «на каждый чих» → много шума,
     много терпимостей, сложная поддержка.
   - Использовать один профиль на всех — разные пользователи
     видят память друг друга. UX страдает.
   - Создавать профиль только ради имени → не имеет смысла.

────────────────────────────────────────────────────────────────────────────
8. КОГДА ДОПОЛНЯТЬ ТЕКУЩИЙ ПРОФИЛЬ, А НЕ СОЗДАВАТЬ НОВЫЙ
────────────────────────────────────────────────────────────────────────────

8.1. Дополнить SOUL.md:
   - Новая роль (стали ревьюером из devops'а).
   - Новые запреты (научились на ошибке).
   - Новый тон общения.

8.2. Дополнить MEMORY.md:
   - Новый хост.
   - Новая конвенция.
   - История решений.
   Это **всегда** дополнение существующего, новый профиль не нужен.

8.3. Дополнить USER.md:
   - Сменился TZ.
   - Сменилась роль.
   - Появились новые предпочтения.

8.4. Добавить новый SKILL.md:
   - Новый паттерн операций.
   - Это **всегда** дополнение, не новый профиль.

8.5. Добавить cron-задачу:
   - В этом же профиле, разные триггеры.
   - Cron — это mode профиля, не отдельная личность.

8.6. Добавить hook:
   - pre_tool_call / post_tool_call.
   - Hook — mode профиля.

────────────────────────────────────────────────────────────────────────────
9. ПРИМЕРЫ (4 ПРОФИЛЯ)
═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 1. Уже есть `default` — делаем операционный профиль `mi_mg_01`
═══════════════════════════════════════════════════════════════════════════

Когда: хотите изолировать работу с инфраструктурой mima_g_01 от общих
разговоров.

Создание:
```bash
hermes profile create mi_mg_01
hermes profile use mi_mg_01
```

Что появилось в `~/.hermes/profiles/mi_mg_01/`:
   ├── SOUL.md           (513 байт, шаблон)
   ├── config.yaml       (пустой)
   ├── .env              (пустой)
   ├── memories/         (пустая)
   ├── skills/
   ├── cron/
   ├── logs/
   ├── sessions/
   └── state.db          (SQLite, пустая)

Шаг 1 — заполнить SOUL.md:

См. `Запонение_SOUL_MD.txt` → пример 1. Положить туда:
  - имя: `mi_mg_01 — Operations Assistant`
  - роли: операционные задачи для mima_g_01.
  - стиль: краткие ответы, без эмодзи-кроме severity, на «ты».
  - НЕ делать: не запускать `apt upgrade`, не дампать `/etc/shadow`.
  - окружение: mima-g-01, root, IPv4, ssh ключ.

Шаг 2 — заполнить .env:

  HERMES_MODEL=MiniMax-M3
  ANTHROPIC_API_KEY=<existing-key>
  ANTHROPIC_BASE_URL=https://api.minimax.io/anthropic
  # Telegram не нужен, если общаетесь через default.
  # Если нужен свой — создайте нового бота в @BotFather.

`chmod 600 .env`.

Шаг 3 — заполнить config.yaml:

  model:
    provider: minimax
    default: MiniMax-M3

  agent:
    max_concurrent_sessions: 5

  toolsets:
    - hermes-cli

  messaging: {}              # отключить gateway по умолчанию

Или, если хотите свой Telegram-бот:

  messaging:
    telegram:
      enabled: true
      home_chat: 505586502

Шаг 4 — заполнить MEMORY.md:

См. `Запонение_memory_MD.txt` → пример 1. Положить таблицу хостов,
Networking, доступы, конвенции именования файлов, learned rules
окружения.

Шаг 5 — заполнить USER.md:

Короткий раздел про Rost (имя, telegram, MSK, стиль).

Шаг 6 — НЕ создавать нового Telegram-бота без необходимости.

Если хотите свой — `hermes gateway setup` запустит визард.
Но пока этот профиль работает «без бота», через CLI/chat.

Шаг 7 — начать использовать:

  hermes profile use mi_mg_01
  hermes chat
  # или
  hermes --profile=mi_mg_01 gateway run

Пояснения:
  • Создание через `hermes profile create` порождает пустые
    шаблоны. Не копируется автоматически из default — нужно
    клонировать явно (см. §11).
  • SOUL.md имеет 513-байтный шаблон. Используйте как baseline
    (см. гайд SOUL.md).
  • Каждый профиль = отдельный gateway (если запущен). Не
    запускайте два gateway с одним ботом.
  • Память и логи — отдельные. Старый gateway не видит новый.

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 2. Уже есть `default` — делаем ролевой профиль `code_reviewer`
═══════════════════════════════════════════════════════════════════════════

Когда: хотите, чтобы при ревью кода соблюдались специфические правила,
не загрязняя default.

Создание:
```bash
hermes profile create code_reviewer
hermes profile use code_reviewer
```

Шаг 1 — SOUL.md.

См. `Запонение_SOUL_MD.txt` → пример 2. Положить:
  - роль: «code_reviewer — ревьюер кода, никогда не пишет код сам».
  - стиль: «формат: проблема / почему / фикс»;
  - НЕ делать: «не писать код», «не подхалимничать»;
  - окружение: Python 3.11+, ruff, mypy strict.

Шаг 2 — .env.

Можно использовать тот же ANTHROPIC_API_KEY, или отдельный, если
хотите разделить счётчики расходов. Для простого ревью можно без
своего Telegram-бота.

Шаг 3 — config.yaml.

```yaml
model:
  provider: minimax
  default: MiniMax-M3
toolsets:
  - hermes-cli
agent:
  max_concurrent_sessions: 3
messaging:
  telegram:
    enabled: false
```

Шаг 4 — MEMORY.md.

Список репозиториев, conventions, свободные PR.

Шаг 5 — USER.md.

Это **другой профиль**, но USER.md может быть похожим (тот же
Rost). Или другой — если ревью делает другой человек.

Шаг 6 — Skills.

Можно добавить `code-review-format` skill (см. `Запонение_skill_MD.txt`
→ пример 3).

```bash
mkdir -p ~/.hermes/profiles/code_reviewer/skills/code-review-format
# положить SKILL.md туда
```

Пояснения:
  • Здесь самый ценный артефакт — SOUL.md. Без него модель будет
    делать всё подряд, не только ревью.
  • Skills — дополнительная опция; в этом профиле один skill
    покрывает большинство случаев.
  • Telegram не нужен → messaging отключен → профиль работает
    только через CLI или API.

ПРИМЕР 3. Уже есть `default` и `mi_mg_01` — добавляем копию для тестов
═══════════════════════════════════════════════════════════════════════════

Когда: хотите поэкспериментировать, проверить миграцию — но не
испортить `mi_mg_01`.

Создание через клонирование:
```bash
hermes profile create mi_mg_01_test --clone mi_mg_01
hermes profile use mi_mg_01_test
```

Что произошло:
  • Скопировано: SOUL.md, memories/MEMORY.md, memories/USER.md.
  • НЕ скопировано: state.db (SQLite), gateway.* (runtime), sandboxes/.
  • Создано заново: пустые skills/, cron/, hooks/, sessions/.

Шаг 1 — проверить, что всё на месте:

```bash
ls -la ~/.hermes/profiles/mi_mg_01_test/
cat ~/.hermes/profiles/mi_mg_01_test/SOUL.md
```

Шаг 2 — изменить .env для тестового:

Здесь **важно**: в клонированном профиле `.env` пустой (не копируется
автоматически из соображений безопасности). Положите свой API key.

Шаг 3 — поменять messaging, чтобы не конфликтовать с ботами оригинала.

Шаг 4 — запустить.

```bash
hermes --profile=mi_mg_01_test gateway run
```

Пояснения:
  • `--clone` не копирует секреты, runtime, state.db, sandboxes —
    это by design.
  • Если хотите полную копию включая state.db (например, тест
    continuity) — нужно копировать вручную.
  • Когда тест пройден — `hermes profile delete mi_mg_01_test`.

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 4. Совсем новый пользователь (другой человек) — профиль с нуля
═══════════════════════════════════════════════════════════════════════════

Когда: коллега хочет свой профиль, делить USER.md не хочется.

Создание:
```bash
hermes profile create colleague
```

Шаг 1 — SOUL.md.

Личность коллеги — ДРУГАЯ. Может быть ревностным ко всему default,
или захотеть «помощник-аналитик». Написать заново.

Шаг 2 — .env.

Если используется тот же LLM key — копировать. Если свой — попросить
коллегу сделать `hermes auth login <provider>`.

Шаг 3 — config.yaml.

Те же базовые параметры, но другие messaging (Telegram). Коллега
создаёт своего бота в @BotFather → кладёт его токен в .env.

Шаг 4 — USER.md.

Про коллегу: имя, роль, стиль. **Не копировать** Rost'овский.

Шаг 5 — MEMORY.md.

У коллеги СВОЯ инфраструктура, свои хосты, свои conventions.

Шаг 6 — Skills.

Если у коллеги другие интересы, добавить соответствующие SKILL.md.

Пояснения:
  • НЕ упрощайте через `--clone default` с заменой USER.md —
    могут остаться скрытые зависимости.
  • Лучше создать с нуля и явно перенести то, что нужно.
  • Когда у двух профилей пересекаются пользователи — это сигнал,
    что они могут стать одним. Если пересечения нет — это
    правильное разделение.

10. SANDBOX-ПРОФИЛИ И ЭКСПЕРИМЕНТАЛЬНЫЕ ВЕТКИ
────────────────────────────────────────────────────────────────────────────

10.1. Что это.
   Профиль для тестов: новый скил, обновление, A/B-тест.

10.2. Когда создавать.
   - Перед обновлением Hermes — иметь fallback-профиль.
   - Перед большим изменением в SOUL/MEMORY — проверить на копии.
   - Перед добавлением скила с чужим кодом — изолировать.

10.3. Создание.
   ```bash
   hermes profile create sandbox_skill_test --clone default
   ```
   → копия, не оригинал.

10.4. Откат.
   ```bash
   hermes profile delete sandbox_skill_test
   ```
   Удаление полное, необратимое. Перед удалением:
   ```bash
   hermes profile export sandbox_skill_test -o /tmp/sandbox.tar.gz
   ```

────────────────────────────────────────────────────────────────────────────
11. КОМАНДЫ HERMES ДЛЯ СОЗДАНИЯ И УПРАВЛЕНИЯ ПРОФИЛЯМИ
────────────────────────────────────────────────────────────────────────────

11.1. Создание.
   $ hermes profile create <name>
   $ hermes profile create <name> --clone <src>
   $ hermes profile create <name> --description "..."

11.2. Просмотр.
   $ hermes profile list
   $ hermes profile show <name>
   $ hermes profile info <name>
   $ hermes profile describe <name>          # описание

11.3. Переключение.
   $ hermes profile use <name>               # sticky default
   $ hermes --profile=<name> chat            # одноразовая команда

11.4. Удаление.
   $ hermes profile delete <name>
   $ hermes profile export <name> -o /tmp/<name>.tar.gz

11.5. Импорт и обновление.
   $ hermes profile import /tmp/<name>.tar.gz
   $ hermes profile install <git-url>     # установить дистрибутив
   $ hermes profile update                # обновить дистрибутив

11.6. Метаданные.
   $ hermes profile rename <old> <new>
   $ hermes profile alias <name>           # создать wrapper

12. ЖИЗНЕННЫЙ ЦИКЛ ПРОФИЛЯ (ОТ СОЗДАНИЯ ДО УДАЛЕНИЯ)

День 7: Развитие.

────────────────────────────────────────────────────────────────────────────
13. ЧАСТЫЕ ОШИБКИ
────────────────────────────────────────────────────────────────────────────

13.1. Создание профиля «на каждый чих».
   → Шум в `hermes profile list`, путаница в активных
     сессиях, сложно держать USER.md актуальным.

13.2. Клонирование без проверки .env.
   → `.env` пустой после clone, gateway не запустится.

13.3. Использование default для всего.
   → Не изолирован, USER.md перегружен, LLM-API budget общий.

13.4. Два gateway на один бот.
   → polling conflict → бесконечный цикл рестартов.

13.5. Не класть файлы в нужные пути.
   → SOUL.md положили в `~/.hermes/SOUL.md` — не подхватится.
     Должен быть `~/.hermes/profiles/<name>/SOUL.md`.

13.6. Удаление профиля без экспорта.
   → Потеря SOUL/MEMORY/USER/skills. Hermes backup →
     «hermes profile export» → `.tar.gz`. Потом удаление.

13.7. Забыть `chmod 600 .env`.
   → Hermes security lock откажет работать.

13.8. Положить токен в MEMORY.md / SOUL.md.
   → Санитизация заменит на `***` при показе, но при
     экспорте может всплыть. Используйте `.env`.

13.9. Сделать profile clone без редактирования SOUL.md.
   → Будет копия. Не забудете, для чего профиль.

13.10. Сделать профиль под sandbox, а потом забыть о нём.
   → DEFAULT_PROFILE = sandbox_skill_test, а не default.
     Тестовый «уехал» в основную работу, оригинал default
     простаивает.

────────────────────────────────────────────────────────────────────────────
14. ЧЕКЛИСТ «ХОРОШИЙ НОВЫЙ ПРОФИЛЬ»
────────────────────────────────────────────────────────────────────────────

  □ Имя в snake_case / kebab-case (lowercase + underscore)?
  □ Команды `hermes profile create` или `--clone` отработали?
  □ SOUL.md заполнен (5 разделов, ~2 КБ)?
  □ .env mode 600, без секретов в SOUL/MEMORY/USER/SKILL?
  □ config.yaml с моделью + toolsets + messaging?
  □ memories/MEMORY.md засеян базовыми фактами?
  □ memories/USER.md не пустой?
  □ Если нужен gateway — свой бот в @BotFather создан?
  □ webhook сброшен (`deleteWebhook`)?
  □ `hermes --profile=<name> doctor` показывает OK?
  □ Тестовый запуск gateway прошёл?
  □ `hermes profile use` сохраняет sticky default корректно?
  □ Если эксперимент — экспорт перед удалением?

15. СВЯЗЬ С 4 ПРЕДЫДУЩИМИ ГАЙДАМИ
────────────────────────────────────────────────────────────────────────────

  SOUL.md    →  `Запонение_SOUL_MD.txt`     (этот набор файлов)
  MEMORY.md  →  `Запонение_memory_MD.txt`   (что в MEMORY.md)

────────────────────────────────────────────────────────────────────────────
16. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

Новый профиль — это серьёзный шаг. Не делайте это ради имени.
Делайте это, когда:
  1. Другой бот или другой канал (обязательно).
  2. Другой API key (для rate-limit изоляции).
  3. Другая личность (роль, стиль).
  4. Другая инфраструктура, не изолируемая через MEMORY.

В остальных случаях — расширяйте существующий:
  - SOUL.md для новых правил.
  - MEMORY.md для новых фактов.
  - USER.md для новых предпочтений.
  - SKILL.md для новых навыков.

Главное правило: **Профиль — это изоляция**. Если что-то не надо
изолировать — это не профиль.

Если в будущем будете путаться — откройте
`~/.hermes/profiles/`, посмотрите на каталоги. Их количество должно
быть ≤ 5. Если больше, вы, скорее всего, создаёте профили слишком
легко. Если 1, и `default` уже стал комбайном — пора разделить.
