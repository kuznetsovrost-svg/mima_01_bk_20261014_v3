# Подготовка задачи для AI-агента в Hermes — полный гайд
## Как поставить задачу, где разместить, что включить

────────────────────────────────────────────────────────────────────────────
0. КОРОТКО
────────────────────────────────────────────────────────────────────────────

**Задача для AI-агента — это не «вопрос в чате».** Это документ
с контекстом, требованиями и критериями приёмки. Чем лучше
подготовлена задача, тем лучше результат.

Главные правила (по моему опыту на этом хосте):

  1. **Задача сложнее 5-7 строк → в файл**, не в чат.
  2. **Один task-id = одна папка** с полным набором
     (task.md + inputs + progress.json + plans/<id>.md).
  3. **Всегда пишите Acceptance Criteria** — без них задача
     «висит в воздухе».
  4. **Inputs кладите ДО передачи агенту**, не «по ходу».
  5. **Owner и приоритет** обязательны.
  6. **Цель в одной строке** — без неё задача разрастается.
  7. **Границы (Out of scope)** обязательны.
  8. **Состояние отслеживайте** через `state` + `progress.json`.

────────────────────────────────────────────────────────────────────────────
1. ГДЕ РАЗМЕЩАТЬ ЗАДАЧУ
────────────────────────────────────────────────────────────────────────────

1.1. **В каталоге профиля** (рекомендуется).
   Главная конвенция — `inbox/<TASK-ID>/` внутри профиля.

   Полный путь:
     ~/.hermes/profiles/<profile>/workspace/inbox/TASK-YYYY-MM-DD-<name>/

   Внутри:
     - task.md        ← сам промпт
     - progress.json  ← машинное состояние
     - inputs/        ← входные данные

   Журнал:
     ~/.hermes/profiles/<profile>/plans/TASK-YYYY-MM-DD-<name>.md

   Это **изолированное** место для каждой задачи. Удобно
   находить, удобно архивировать.

1.2. **В Kanban** (для долгосрочных).
   `hermes kanban add "<task>" --profile=<profile>` — добавляет
   задачу в kanban-board. Доска хранит статус (todo/in_progress/
   review/done), worktree, branch.

   Для задач с **автоматической декомпозицией** и **ветками** —
   Kanban лучше, чем inbox/.

1.3. **В Hermes Project** (для workspace-уровня).
   Если у вас есть `hermes project create myproject`, kanban-board
   привязывается к проекту. Задачи получают ветки
   `<project-slug>/<task-id>`.

1.4. **В чате / команде**.
   Для простых запросов (1 строка, 1 ответ) — пишите в чат:

     @hermes прочитай /tmp/data.csv и посчитай сумму по колонке amount

   Это НЕ задача в смысле «файл с требованиями». Это чат-сообщение.

1.5. **Через cron** (для периодических).
   `hermes cron add "*/5 * * * *" "..."` — для регулярных задач.
   Промпт фиксируется в cron-job, результат пишется в workspace.

1.6. **Через hooks** (для событийных).
   `~/.hermes/profiles/<profile>/hooks/` — pre/post-tool события.
   Это автоматические задачи на каждое действие.

────────────────────────────────────────────────────────────────────────────
2. СТРУКТУРА КАТАЛОГА ЗАДАЧИ
────────────────────────────────────────────────────────────────────────────

Стандартная структура `inbox/TASK-YYYY-MM-DD-<name>/`:

  inbox/TASK-2026-07-04-fix-bug/
  ├── task.md           ← ОБЯЗАТЕЛЬНО: промпт с требованиями
  ├── progress.json     ← state машины (state, steps, errors)
  ├── inputs/           ← входные данные (опц., но обычно есть)
  │   ├── source.csv
  │   └── reference.md
  ├── refs/             ← локальная справка (если только для задачи)
  ├── scratch/          ← черновики (опц.)
  └── outputs/          ← промежуточные результаты (опц.)

Журнал:
  plans/TASK-2026-07-04-fix-bug.md   ← ОБЯЗАТЕЛЬНО для долгих задач

────────────────────────────────────────────────────────────────────────────
3. СОДЕРЖАНИЕ TASK.MD — РЕКОМЕНДУЕМАЯ ПРАКТИКА
────────────────────────────────────────────────────────────────────────────

3.1. **Frontmatter / metadata** (8 полей).

```
# Task: <краткое имя>
state: <draft|todo|in_progress|blocked|review|done>
profile: <имя_профиля>
created: YYYY-MM-DD
updated: YYYY-MM-DD
author: <кто поставил>
priority: <low|normal|high|urgent>
estimate: <S|M|L|XL>
```

3.2. **Goal** (обязательно).
   Что нужно сделать. 1-2 строки. Конкретно и измеримо.

   ХОРОШО:
     Посчитать топ-10 пользователей по событиям в inputs/events.csv
     и записать в results/TASK-2026-07-04-stats/top_users.txt.

   ПЛОХО:
     Сделать отчёт.
     Посмотреть данные.

3.3. **Context** (опц.).
   Зачем задача. Где будет использоваться результат. Какие
   ограничения (бизнес, временные, технические).

   Пример:
     Метрика нужна для еженедельного дашборда. Дедлайн —
     пятница 18:00. Если задержка — лучше показать частичный
     результат.

3.4. **Requirements** (обязательно).
   Список измеримых требований. Каждое — отдельный пункт.

   Пример:
     - Всего прочитано ≥ 1000 строк из events.csv.
     - Top-10 отсортирован по убыванию числа событий.
     - Формат top_users.txt — markdown list с username и счётчиком.

3.5. **Inputs** (обязательно, если есть данные).
   Список файлов, которые агент должен прочитать. Все файлы
   уже должны быть в `inputs/`.

   Пример:
     - inputs/events.csv (1000+ строк, формат: user_id, username,
       event_at, action).
     - inputs/glossary.md (терминология проекта).

3.6. **Outputs** (обязательно).
   Что должно получиться. Конкретные пути и имена файлов.

   Пример:
     - results/TASK-2026-07-04-stats/top_users.txt
     - results/TASK-2026-07-04-stats/actions_summary.md

3.7. **Acceptance Criteria** (обязательно).
   Чек-лист критериев приёмки. Без них задача не имеет
   «завершения».

   Пример:
     - [ ] top_users.txt создан и содержит 10 строк.
     - [ ] Цифры в файле соответствуют пересчёту по events.csv.
     - [ ] actions_summary.md содержит 5 разделов: всего,
           top-10, активные действия, по часам, по дням.
     - [ ] Стиль соответствует references/style-guide.md.
     - [ ] progress.json обновлён с шагами.

3.8. **Constraints / Limits** (опц.).
   - Бюджет токенов: <5000.
   - Время выполнения: <30 минут.
   - Sensitive data: нет / есть — какая.

3.9. **Style Guide** (опц.).
   Ссылки на справочные документы:
     - references/style-guide.md (общий).
     - inputs/<task>/refs/<конкретное>.

3.10. **Status Log** (обязательно, обновлять).
    Хронология событий:
      - 2026-07-04 10:00 — created.
      - 2026-07-04 10:15 — agent started.
      - 2026-07-04 10:42 — first output (50% done).
      - 2026-07-04 11:05 — task complete.

3.11. **Decisions** (опц.).
    Какие приняты решения в ходе работы. Полезно для аудита.
    Пример:
      - Использовал Python stdlib вместо pandas — проще, на этом
        хосте нет pip.
      - Сортировал по (events_count desc, username asc) для
        стабильного порядка.

3.12. **Out of scope** (опц., но полезно).
    Что НЕ делать. Защищает от разрастания.

    Пример:
      - Не строить графики (matplotlib нет).
      - Не анализировать данные за пределами events.csv.

────────────────────────────────────────────────────────────────────────────
4. PROGRESS.JSON — МАШИННОЕ СОСТОЯНИЕ
────────────────────────────────────────────────────────────────────────────

4.1. Минимальный шаблон.

```json
{
  "task_id": "TASK-2026-07-04-fix-bug",
  "state": "in_progress",
  "profile": "mi_mg_01",
  "created": "2026-07-04T10:00:00+03:00",
  "updated": "2026-07-04T10:42:00+03:00",
  "author": "Rost",
  "priority": "high",
  "steps": [
    {
      "ts": "2026-07-04T10:00:00+03:00",
      "status": "done",
      "title": "task создан"
    },
    {
      "ts": "2026-07-04T10:15:00+03:00",
      "status": "in_progress",
      "title": "agent начал"
    }
  ],
  "errors": [],
  "outputs": [],
  "decisions": []
}
```

4.2. Обновление.
   Агент (или человек) дописывает шаги по мере выполнения:
   - `done` — выполнено.
   - `in_progress` — сейчас делается.
   - `pending` — запланировано.
   - `failed` — провалено (с описанием в `errors`).

4.3. Зачем нужен.
   - JSON машиночитаем → автоматизация.
   - Удобен для дашборда / мониторинга.
   - Атомарное состояние — не зависит от того, что написано в MD.

────────────────────────────────────────────────────────────────────────────
5. PLANS/<ID>.MD — ЖУРНАЛ ЗАДАЧИ
────────────────────────────────────────────────────────────────────────────

5.1. Структура.

```markdown
# Plan: TASK-2026-07-04-fix-bug

## State
**in_progress**

## Profile
mi_mg_01

## Goal
<1 строка — копия из task.md>

## Steps
- [x] 2026-07-04 10:00 — task создан
- [x] 2026-07-04 10:15 — agent started
- [ ] 2026-07-04 11:00 — прочитать inputs/events.csv
- [ ] 2026-07-04 11:30 — посчитать статистику
- [ ] 2026-07-04 12:00 — записать outputs

## Errors
(пусто)

## Outputs
- results/TASK-2026-07-04-fix-bug/top_users.txt
- results/TASK-2026-07-04-fix-bug/actions_summary.md

## Decisions
- 2026-07-04 10:30 — Использовал Python stdlib вместо pandas.
```

5.2. Зачем нужен.
   - Читается человеком без инструментов.
   - История решений и изменений.
   - Дублирует progress.json, но в MD-формате.

5.3. Обновлять одновременно с progress.json.
   Или только один из них — на ваше усмотрение.

────────────────────────────────────────────────────────────────────────────
6. ВХОДНЫЕ ДАННЫЕ (INPUTS)
────────────────────────────────────────────────────────────────────────────

6.1. Где размещать.
   `inbox/<TASK-ID>/inputs/`

   Не корень inbox/, не workspace, не /tmp. Только в inputs/.

6.2. Именование.
   `inputs/<descriptive-name>.<ext>`

   Примеры:
     inputs/manual-v2.pdf
     inputs/users-export-2026-q2.csv
     inputs/logs/jan.log

6.3. Большие данные (>100 МБ).
   - НЕ класть в inputs/.
   - Вынести в `workspace/datasets/` или внешнее хранилище.
   - В task.md указать абсолютный путь.

6.4. Секреты и PII.
   - НЕ класть в inputs/ (можно случайно закоммитить).
   - Секреты — в .env (mode 600).
   - PII — шифрование или вынос за пределы `~/.hermes/`.

6.5. Формат.
   - CSV: UTF-8 with BOM для Excel-совместимости.
   - JSON: pretty-print для читаемости.
   - PDF: OCR-ready, не отсканированный.
   - Markdown: если данные текстовые.

────────────────────────────────────────────────────────────────────────────
7. РЕЗУЛЬТАТЫ (OUTPUTS)
────────────────────────────────────────────────────────────────────────────

7.1. Где размещать.
   `~/.hermes/profiles/<profile>/workspace/results/<TASK-ID>/`

   Не в `inbox/`, не в `workspace/`. Только в results/.

7.2. Именование.
   - `<topic>_v<N>.<ext>` для версионных.
   - `<topic>.<ext>` для одиночных.

   Примеры:
     results/TASK-.../report_v1.md
     results/TASK-.../report_v2.md
     results/TASK-.../report_final.md

7.3. Когда артефакт готов.
   Агент создаёт файл в results/<TASK-ID>/ и:
   1. Обновляет progress.json (новый шаг done, добавляет в outputs[]).
   2. Обновляет plans/<TASK-ID>.md (новый output в Outputs, +1 шаг done).
   3. (опц.) Отправляет в чат: «готово, файл в results/<TASK-ID>/...».

7.4. Долгосрочное хранение.
   После завершения задачи:
   - Актуальные файлы остаются в results/<TASK-ID>/.
   - Старые (за прошлые месяцы) — переносятся в
     `workspace/archive/<YYYY>/<TASK-ID>/`.

────────────────────────────────────────────────────────────────────────────
8. СПРАВОЧНЫЕ МАТЕРИАЛЫ (REFERENCES)
────────────────────────────────────────────────────────────────────────────

8.1. Где размещать.
   - **Общие для профиля:** `workspace/references/<file>.md`
   - **Только для задачи:** `inbox/<TASK-ID>/refs/`

8.2. Что в references.
   - Style guides (style-guide.md).
   - Coding standards.
   - API references.
   - Domain glossary.
   - Project conventions.
   - Host quick-ref (как в mi_mg_01 — IP, SSH, secrets).

8.3. Иерархия приоритетов для агента.
   - В task.md указано Style Guide → это самая высокая
     специфичность.
   - В references/ — общие правила профиля.
   - В AGENTS.md — архитектура проекта.
   - В SOUL.md — стиль общения.

────────────────────────────────────────────────────────────────────────────
9. ЖИЗНЕННЫЙ ЦИКЛ ЗАДАЧИ
────────────────────────────────────────────────────────────────────────────

   ┌─────────┐
   │  draft  │ — задача поставлена, агент ещё не запущен
   └────┬────┘
        │
        ▼
   ┌─────────┐
   │  todo   │ — задача в очереди, готова к запуску
   └────┬────┘
        │
        ▼
   ┌──────────────┐
   │ in_progress  │ — агент работает
   └────┬─────────┘
        │
        ├────► blocked  — нужен ввод от пользователя
        │
        ▼
   ┌─────────┐
   │ review  │ — агенты отдали outputs, идёт проверка
   └────┬────┘
        │
        ▼
   ┌─────────┐
   │  done   │ — критерии приёмки выполнены
   └─────────┘

9.1. Переходы.
   - draft → todo: после проверки задачи человеком.
   - todo → in_progress: агент начал.
   - in_progress → blocked: ждём ввода от пользователя.
   - blocked → in_progress: пользователь дал ввод.
   - in_progress → review: агенты отдали outputs.
   - review → in_progress: что-то не сошлось, нужна доработка.
   - review → done: всё проверили, архивируем.

9.2. Длительность каждой фазы.
   - draft → todo: минуты.
   - todo → in_progress: часы / дни (планирование).
   - in_progress: минуты / часы (выполнение).
   - review: часы / дни (проверка человеком).
   - done: постоянно (сохраняем).

────────────────────────────────────────────────────────────────────────────
10. ПЕРЕДАЧА ЗАДАЧИ АГЕНТУ
────────────────────────────────────────────────────────────────────────────

10.1. Варианты.
   - **Через чат:** «@hermes открой task.md в inbox/<id>/ и выполни».
   - **Через Kanban:** `hermes kanban add "<id>" --file=task.md`.
   - **Через cron:** `hermes cron add "..."`.
   - **Через subagent:** `delegate_task --goal="..." --context="..."`.
   - **Через project-bound board:** `hermes project use <slug>` +
     работа в его контексте.

10.2. Что агент ДОЛЖЕН прочитать.
   1. task.md — главное.
   2. Все файлы из inputs/.
   3. Style Guide (если указан).
   4. AGENTS.md (из cwd или workspace).
   5. SOUL.md (для стиля).

10.3. Что агент НЕ должен читать.
   - /etc/shadow, секреты.
   - Случайные большие бинарники.
   - Всё подряд в workspace/ (только явно указанные inputs/).

10.4. Что агент должен сделать после.
   1. Создать outputs в results/<TASK-ID>/.
   2. Обновить progress.json.
   3. Обновить plans/<TASK-ID>.md.
   4. (опц.) Сообщить в чат: «готово».

11. ПРИМЕР ЗАДАЧИ (ПОЛНЫЙ, С ВСЕМИ СЕКЦИЯМИ)
────────────────────────────────────────────────────────────────────────────

```markdown
# Task: sample-stats — анализ events.csv
state: draft
profile: mi_mg_01
created: 2026-07-04
updated: 2026-07-04
author: Rost
priority: normal
estimate: S

## Goal
Подсчитать статистику использования по CSV `events.csv`:
- общее число уникальных пользователей и событий;
- top-10 пользователей по числу событий;
- top-5 по активным действиям (upload/download);
- распределение событий по часам суток;
- уникальные пользователи по дням.

## Context
Демонстрационная задача для проверки шаблонов профиля mi_mg_01.
Результат используется для smoke-test нового навыка.

## Requirements
- Подсчёт по реальному содержимому `inputs/events.csv`.
- Использовать Python stdlib (csv, collections) — pip недоступен.
- Без интерактивных подтверждений.
- Стиль — `references/style-guide.md` (русский язык, без markdown-
  таблиц для Telegram).

## Inputs
- `inputs/events.csv` (синтетический лог, ~30 строк, формат:
  user_id, username, event_at, action).

## Outputs
- `results/TASK-2026-07-04-sample-stats/top_users.txt`.
- `results/TASK-2026-07-04-sample-stats/actions_summary.md`.

## Acceptance Criteria
- [ ] `top_users.txt` содержит 10 строк, отсортированных по убыванию
      числа событий.
- [ ] Цифры в файле совпадают с ручным подсчётом по `events.csv`.
- [ ] `actions_summary.md` содержит 5 разделов:
      Общая статистика / Top-10 / Активные действия / По часам /
      По дням.
- [ ] Формат даты-времени: ISO 8601.
- [ ] Стиль соответствует `references/style-guide.md`.
- [ ] `progress.json` обновлён.
- [ ] `plans/TASK-2026-07-04-sample-stats.md` синхронизирован.

## Constraints
- Бюджет токенов: <3000.
- Время выполнения: <2 минуты wall-clock.
- Sensitive data: нет.

## Style Guide
- `references/style-guide.md` (общий).
- `references/host-quick-ref.md` (специфика хоста).

## Status Log
- 2026-07-04 13:36 — created (Rost).
- 2026-07-04 HH:MM — agent started.
- 2026-07-04 HH:MM — outputs ready.

## Decisions
- Использовать Python stdlib (csv, collections) — на этом
  сервере pip-окружение можно не трогать.
- Время суток группировать по hour-бакетам 00-23.

## Out of scope
- Графики (matplotlib не установлен).
- A/B-тесты.
- Перенос в другую СУБД.
```

12. ЧЕКЛИСТ «ХОРОШАЯ ЗАДАЧА»
────────────────────────────────────────────────────────────────────────────

Перед передачей агенту проверьте:

  □ ID задачи: `TASK-YYYY-MM-DD-<name>`?
  □ Каталог создан: `inbox/<TASK-ID>/`?
  □ task.md заполнен ВСЕМИ секциями?
  □ Goal — 1-2 строки, конкретно?
  □ Acceptance Criteria — чек-лист, измеримый?
  □ Inputs лежат в `inputs/`?
  □ Outputs описаны конкретными путями?
  □ Constraints указаны (если есть)?
  □ Style Guide указан (если есть)?
  □ Priority и Estimate заданы?
  □ Owner указан?
  □ Out of scope указан (если есть)?
  □ progress.json создан?
  □ plans/<TASK-ID>.md создан?

Если хотя бы 2 пункта не выполнены — задача сырая. Допишите.

13. ЧАСТЫЕ ОШИБКИ ПРИ ПОСТАНОВКЕ ЗАДАЧ
────────────────────────────────────────────────────────────────────────────

13.1. **Goal без измеримости**.
   ПЛОХО: «посмотреть данные».
   ХОРОШО: «посчитать топ-10 пользователей по событиям».

13.2. **Acceptance без критериев**.
   ПЛОХО: «качественно».
   ХОРОШО: «coverage > 80%», «файл создан», «цифры совпадают».

13.3. **Inputs без указания пути**.
   ПЛОХО: «возьми файл».
   ХОРОШО: «inputs/events.csv, 1000 строк».

13.4. **Outputs без конкретных путей**.
   ПЛОХО: «запиши куда-нибудь».
   ХОРОШО: «results/<TASK-ID>/summary.md».

13.5. **Забытый progress.json**.
   Через неделю не вспомните, на чём остановились.

13.6. **Status Log пустой**.
   Первая запись: «created». Без неё задача без истории.

13.7. **Decisions не пишутся**.
   Через месяц забудете, почему выбор был сделан.

13.8. **Без Out of scope**.
   Задача разрастается. Всегда ограничивайте.

13.9. **Inputs в workspace/inbox/<id>/, а не inputs/**.
   Один файл в корне task-каталога теряется. Всегда в inputs/.

13.10. **Outputs в inbox/<id>/**.
    Это перемешивает входные и выходные данные. Всегда в results/.

13.11. **Без приоритета**.
    Непонятно, что делать первым. Всегда приоритет.

13.12. **Без оценки (estimate)**.
    Непонятно, сколько это займёт. Всегда S/M/L/XL.

13.13. **Один task-id на 10 разных задач**.
    Каждая задача — отдельный файл и каталог.

13.14. **Задача в чате, а не в файле**.
    Если задача сложнее 5-7 строк — в файл, иначе через месяц
    не найдёте.

13.15. **Длинная Requirements (>10 пунктов)**.
    Разбейте на подзадачи или используйте чек-лист.

────────────────────────────────────────────────────────────────────────────
14. СПЕЦИАЛЬНЫЕ СЛУЧАИ
────────────────────────────────────────────────────────────────────────────

14.1. **Задача требует секретов**.
   Не кладите секреты в task.md или inputs/. Используйте:
     - .env (mode 600) с переменной.
     - В task.md укажите: «использовать env TELEGRAM_BOT_TOKEN».

14.2. **Задача требует больших данных (>100 МБ)**.
   Не кладите в inputs/. Положите в workspace/datasets/
   или внешнее хранилище. В task.md укажите абсолютный путь.

14.3. **Задача долгая (multi-session)**.
   Используйте progress.json для отслеживания состояния
   между сессиями. В каждой сессии читайте progress.json,
   чтобы восстановить контекст.

14.4. **Задача требует доступа к БД**.
   Секреты БД — в .env. В task.md — только endpoint и формат.

14.5. **Задача — это рефакторинг**.
   Acceptance = «все тесты проходят», «coverage не ниже X».
   Out of scope = «не менять API».

14.6. **Задача — это новый навык**.
   Цель: «создать SKILL.md в skills/<name>/». Inputs:
   документация по домену. Outputs: готовый SKILL.md +
   references/<file>.md.

14.7. **Задача требует subagent**.
   В task.md укажите «использовать subagent для X», дайте
   goal и context. Это экономит ваш контекст.

15. ИНСТРУМЕНТЫ HERMES ДЛЯ ЗАДАЧ
────────────────────────────────────────────────────────────────────────────

15.1. **Создание задачи**.
   ```bash
   # Создать каталог:
   mkdir -p ~/.hermes/profiles/<profile>/workspace/inbox/<id>/inputs

   # Скопировать шаблон:
   cp workspace/references/templates/task-template.md \
      inbox/<id>/task.md

   # Заполнить и передать агенту.
   ```

15.2. **Через Kanban** (для долгосрочных).
   ```bash
   hermes kanban add "<title>" \
     --profile=<profile> \
     --description="<описание>" \
     --priority=<high|normal|low>
   ```

15.3. **Через Project** (для workspace-уровня).
   ```bash
   hermes project create myproject \
     --slug=myproject \
     --folders=~/code/myproject \
     --board=myproject-board \
     --use
   ```

15.4. **Через cron** (для регулярных).
   ```bash
   hermes cron add "0 9 * * 1" \
     "hermes --profile=<profile> chat 'выполни inbox/<id>/task.md'"
   ```

15.5. **Через subagent**.
   ```bash
   # Использовать delegate_task из текущей сессии:
   delegate_task \
     --goal="выполни задачу" \
     --context="task.md в inbox/<id>/"
   ```

────────────────────────────────────────────────────────────────────────────
16. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

**Задача — это документ, а не сообщение в чате.** Хорошая задача
имеет:

  1. ID в формате `TASK-YYYY-MM-DD-<name>`.
  2. Каталог в `inbox/<TASK-ID>/`.
  3. task.md с 8-12 секциями.
  4. progress.json для машинного состояния.
  5. plans/<ID>.md для журнала.
  6. inputs/ для входных данных.
  7. Конкретные Outputs в results/<ID>/.
  8. Acceptance Criteria как чек-лист.
  9. Out of scope как защита от разрастания.
  10. Priority и Estimate.

Главное:
  • Чем лучше задача, тем лучше результат.
  • Без Acceptance Criteria — задача «висит в воздухе».
  • Без Constraints — агент может уйти в бесконечный цикл.
  • Без Out of scope — задача разрастается.

Поставьте 5 задач по этим правилам — и через неделю вы
заметите, что агент стал работать **предсказуемо** и
**завершаемо**. Без этого — каждый раз начинаете с нуля.
