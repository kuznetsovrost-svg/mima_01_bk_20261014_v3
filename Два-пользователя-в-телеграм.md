1. ПОСТАНОВКА ЗАДАЧИ
═══════════════════════════════════════════════════════════════════

Есть Hermes-агент (отдельный профиль). С ним общаешься ты
через своего Telegram бота.

ЗАДАЧА:
  • Другой пользователь Telegram (со своим аккаунтом)
    должен иметь возможность обращаться к ТОМУ ЖЕ агенту
    на равне с тобой.
  • Желательно, чтобы ты видел переписку другого
    пользователя с этим ботом.

═══════════════════════════════════════════════════════════════════
2. КОРОТКИЙ ОТВЕТ
═══════════════════════════════════════════════════════════════════

Hermes это уже умеет через механизм allowed users + shared chat
scope. Базовая идея:

  1. Твой бот работает на одном профиле (analyst_training)
  2. Через channel_directory.json задаёшь список chat_id,
     которые могут писать этому боту
  3. Другой пользователь пишет тому же боту — сообщения
     маршрутизируются в тот же профиль
  4. Ты видишь всю переписку, потому что все сессии хранятся
     в одном state.db профиля

3. АРХИТЕКТУРА
═══════════════════════════════════════════════════════════════════

Система выглядит так:

  ┌─────────────────────────────────────────────────────────┐
  │ Один Telegram бот (например, @MMRV_Hermes_bot)         │
  │ Один Hermes профиль (например, analyst_training)        │
  │ Один gateway процесс                                    │
  │                                                         │
  │   Telegram        Маршрутизация            Hermes       │
  │   ─────────       ──────────────            ──────       │
  │   Rost (1)     ─┐                         ┌─ session A  │
  │   OtherUser(2) ─┤── channel_directory ────┼─ session B  │
  │   ...          ─┘     .json                └─ state.db   │
  │                                                         │
  │ Оба видят переписку через state.db                      │
  └─────────────────────────────────────────────────────────┘

Telegram-бот один — видит сообщения от всех, кто пишет ему.
Каждое сообщение содержит chat_id отправителя. Hermes
маршрутизирует по channel_directory.json.

4. МЕХАНИЗМ TELEGRAM ROUTING В HERMES
═══════════════════════════════════════════════════════════════════

4.1. Allowlist (TELEGRAM_ALLOWED_USERS)
──────────────────────────────────────
В .env активного профиля задаётся allowlist chat_id, которые
могут общаться с ботом:

  # В .env активного профиля
  TELEGRAM_ALLOWED_USERS=505586502,123456789,987654321

Если TELEGRAM_ALLOWED_USERS пуст или * — бот принимает всех
(небезопасно).

Где найти:
  /root/.hermes/<profile>/.env          ← для основного профиля
  /root/.hermes/profiles/<name>/.env    ← для именованного

4.2. Channel Directory (channel_directory.json)
───────────────────────────────────────────────
Управляет тем, какой чат → какой профиль/тред:

  {
    "updated_at": "2026-07-23T12:00:00",
    "platforms": {
      "telegram": [
        {
          "id": "505586502",
          "name": "Rost",
          "type": "dm",
          "thread_id": null
        },
        {
          "id": "123456789",
          "name": "Alice",
          "type": "dm",
          "thread_id": null
        }
      ]
    }
  }

Где найти:
  /root/.hermes/<profile>/channel_directory.json

6. ВАРИАНТ 1: ВСЕ В ОДНУ СЕССИЮ (РЕКОМЕНДУЮ)
═══════════════════════════════════════════════════════════════════

Описание:
  И ты, и другой пользователь пишут тому же боту — все
  сообщения идут в одну общую conversation history.

Плюсы:
  ✓ Минимальная настройка
  ✓ Все видят переписку друг друга (через state.db)
  ✓ Агент помнит контекст разговора со всеми

Минусы:
  ✗ Контекст смешивается — agent может запутаться «кому отвечать»
  ✗ Нет изоляции между пользователями

Когда подходит:
  • Два пользователя работают над общим проектом
  • Один процесс (например, общий kanban)
  • Не страшно что agent отвечает «обоим сразу»

Что нужно сделать:

  # 1. Узнать HERMES_HOME и активный профиль
  echo "Profile: $(cat ~/.hermes/active_profile)"

  # 2. Посмотреть текущий .env
  cat /root/.hermes/profiles/analyst_training/.env | grep TELEGRAM

  # 3. Добавить chat_id второго пользователя в allowlist
  # Замени 123456789 на реальный chat_id
  sed -i 's/^TELEGRAM_ALLOWED_USERS=.*/TELEGRAM_ALLOWED_USERS=505586502,123456789/' \
      /root/.hermes/profiles/analyst_training/.env

  # 4. Проверить
  grep TELEGRAM_ALLOWED_USERS /root/.hermes/profiles/analyst_training/.env

  # 5. Перезапустить gateway (из внешнего ssh, не из gateway)
  hermes gateway restart

Что должен сделать второй пользователь:

  1. Открыть чат с ботом @MMRV_Hermes_bot
  2. Нажать /start
  3. Написать любое сообщение — оно попадёт в общую сессию

Что ты увидишь:

  1. Логи: journalctl --user -u hermes-gateway -f | grep "123456789"
  2. Историю: hermes sessions show <session_id>
  3. Уведомления (если настроишь push)

═══════════════════════════════════════════════════════════════════
7. ВАРИАНТ 2: TELEGRAM TOPICS
═══════════════════════════════════════════════════════════════════

Описание:
  В Telegram-группе используются topics (топики) для разделения
  диалогов внутри одного чата.

Плюсы:
  ✓ Каждый пользователь в своём thread
  ✓ Изолированный контекст внутри одного профиля
  ✓ Можно делать «отдельные sub-контексты» для разных тем

Минусы:
  ✗ Telegram topics доступны только для Premium-групп
  ✗ Бот должен уметь работать с topics

Когда подходит:
  • Уже есть Telegram Premium
  • Хочется визуального разделения переписок

Структура channel_directory.json:

  {
    "platforms": {
      "telegram": [
        {
          "id": "GROUP_ID",
          "name": "Project Chat",
          "type": "supergroup",
          "thread_id": "100"     // topic для тебя
        },
        {
          "id": "GROUP_ID",
          "name": "Project Chat",
          "type": "supergroup",
          "thread_id": "200"     // topic для второго
        }
      ]
    }
  }

8. ВАРИАНТ 3: ОТДЕЛЬНЫЕ ПРОФИЛИ С ОБЩИМ STATE
═══════════════════════════════════════════════════════════════════

Описание:
  Создать 2 профиля (analyst_training_rost, analyst_training_alice),
  но они разделяют общий state.db (read-only или shared).

Плюсы:
  ✓ Полная изоляция контекстов
  ✓ Каждый пользователь со своим набором skills/settings
  ✓ Можно давать разные права

Минусы:
  ✗ Сложнее настроить
  ✗ Агент не видит «общую картину»
  ✗ Удваивается storage

Когда подходит:
  • Пользователи не должны видеть приватные данные друг друга
  • Compliance/безопасность

Команды для создания:

  hermes profile create analyst_training_rost
  hermes profile create analyst_training_alice

  # Настроить каждому свой .env
  # Rost:
  #   TELEGRAM_ALLOWED_USERS=505586502
  #   TELEGRAM_BOT_TOKEN=<token_for_rost_bot>
  # Alice:
  #   TELEGRAM_ALLOWED_USERS=123456789
  #   TELEGRAM_BOT_TOKEN=<token_for_alice_bot>

  # Запустить оба gateway (разные процессы)
  hermes -p analyst_training_rost gateway start
  hermes -p analyst_training_alice gateway start

9. ВАРИАНТ 4: MULTI-AGENT (ПРОДВИНУТЫЙ)
═══════════════════════════════════════════════════════════════════

Описание:
  Один бот + один профиль + каждый пользователь маршрутизируется
  в свой «agent instance» через delegate_task.

Плюсы:
  ✓ Очень гибко
  ✓ Можно давать разные skills разным пользователям
  ✓ Изоляция контекстов + общий agent kernel

Минусы:
  ✗ Требует программирования
  ✗ Делегирование overhead

Когда подходит:
  • Разные уровни доступа (admin/user/guest)
  • Разные skills per user

10. КАК УВИДЕТЬ ПЕРЕПИСКУ ДРУГОГО ПОЛЬЗОВАТЕЛЯ
═══════════════════════════════════════════════════════════════════

10.1. В варианте 1 (общая сессия)
────────────────────────────────
Переписка обоих уже в state.db. Видна:

  • В kanban.db (если активен kanban)
  • В логах ~/.hermes/profiles/<name>/logs/gateway.log
  • В ~/.hermes/profiles/<name>/sessions/<session_id>.json

Команды:
  hermes sessions list              # список сессий
  hermes sessions show <id>         # содержимое сессии
  tail -f /root/.hermes/profiles/<name>/logs/gateway.log

10.2. В варианте 2 (topics)
───────────────────────────
Каждый topic — отдельная «sub-session». Сообщения разделяются
по message_thread_id.

10.3. В варианте 3 (отдельные профили)
──────────────────────────────────────
Переписка каждого пользователя в своём каталоге:

  /root/.hermes/profiles/<name>_rost/sessions/
  /root/.hermes/profiles/<name>_alice/sessions/

11. КОНКРЕТНЫЕ ШАГИ ДЛЯ ВАРИАНТА 1 (РЕКОМЕНДУЕМЫЙ)
═══════════════════════════════════════════════════════════════════

Что понадобится от тебя:

  1. chat_id второго пользователя — он должен:
     • Написать боту /start
     • Посмотреть в Telegram логах gateway
     • Или через @userinfobot (отправит JSON с id)

  2. Согласие второго пользователя — он должен явно подтвердить,
     что хочет работать с этим ботом.

  3. Соглашение о контексте — что переписка общая, нет приватности
     между пользователями.

Команды для настройки:

  # 1. Проверить активный профиль
  cat ~/.hermes/active_profile

  # 2. Найти нужный .env (для активного профиля)
  PROFILE=$(cat ~/.hermes/active_profile)
  ENV_FILE="/root/.hermes/profiles/${PROFILE}/.env"

  # 3. Посмотреть текущий allowlist
  grep TELEGRAM_ALLOWED_USERS "$ENV_FILE"

  # 4. Добавить chat_id второго пользователя
  # Замени 123456789 на реальный chat_id
  sed -i 's/^TELEGRAM_ALLOWED_USERS=.*/TELEGRAM_ALLOWED_USERS=505586502,123456789/' \
      "$ENV_FILE"

  # 5. Проверить
  grep TELEGRAM_ALLOWED_USERS "$ENV_FILE"

  # 6. Перезапустить gateway (из внешнего ssh, не из gateway)
  hermes gateway restart

  # 7. Проверить что оба chat_id теперь работают
  journalctl --user -u hermes-gateway -f

Что должен сделать второй пользователь:

  1. Открыть чат с ботом @MMRV_Hermes_bot
  2. Нажать /start
  3. Написать любое сообщение — оно попадёт в общую сессию

13. МОНИТОРИНГ — УВИДЕТЬ КТО ЧТО ПИШЕТ
═══════════════════════════════════════════════════════════════════

В логах gateway:

  journalctl --user -u hermes-gateway -f | grep -E "chat_id|message"

В state.db:

  sqlite3 /root/.hermes/profiles/analyst_training/state.db \
    "SELECT chat_id, message, timestamp FROM messages ORDER BY timestamp DESC LIMIT 20;"

Через Hermes CLI:

  hermes sessions list
  hermes sessions show <session_id>

Уведомления (опционально):

  # При каждом сообщении от любого пользователя шлём тебе в личку
  cat >> /root/.hermes/hooks/post-message.sh << 'EOF'
  #!/bin/bash
  CHAT_ID="$1"
  MESSAGE="$2"
  if [ "$CHAT_ID" != "505586502" ]; then
    curl -sS -X POST "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/sendMessage" \
      -d chat_id=505586502 \
      -d text="⚠️ Новый чат активен: ${CHAT_ID}: ${MESSAGE}"
  fi
  EOF
  chmod +x /root/.hermes/hooks/post-message.sh

14. БЕЗОПАСНОСТЬ
═══════════════════════════════════════════════════════════════════

14.1. Проверка allowlist
────────────────────────
  Всегда задавайте allowlist (TELEGRAM_ALLOWED_USERS).
  Никогда не оставляйте * или пустым — иначе любой пользователь
  сможет писать боту.

14.2. Логирование
─────────────────
  Включите audit log для всех сообщений:
  hermes config set telegram.audit_log true

14.3. Лимиты
────────────
  Задавайте rate limits:
  hermes config set telegram.rate_limit_per_user 60  # 60 msg/min

14.4. Шифрование данных
──────────────────────
  state.db содержит ВСЕ сообщения. Защитите файл:
  chmod 600 /root/.hermes/profiles/*/state.db
  Не отправляйте state.db в общий backup.

14.5. Backup и retention
────────────────────────
  Задайте retention:
  hermes config set sessions.retention_days 30
  (через 30 дней переписка автоматически удаляется)

15. TROUBLESHOOTING
═══════════════════════════════════════════════════════════════════

Проблема: Второй пользователь пишет, но бот не отвечает.

  # Проверить allowlist
  grep TELEGRAM_ALLOWED_USERS /root/.hermes/profiles/analyst_training/.env

  # Проверить что chat_id точно правильный
  # Через @userinfobot или в логах:
  journalctl --user -u hermes-gateway -f | grep -i "rejected"

  # Проверить что gateway запущен
  hermes gateway list

Проблема: Бот отвечает, но не видит сообщений другого пользователя.

  # Проверить что channel_directory.json содержит обоих
  cat /root/.hermes/profiles/analyst_training/channel_directory.json

  # Проверить логи
  tail -f /root/.hermes/profiles/analyst_training/logs/gateway.log

Проблема: Пользователь получает ответы, но ты не видишь переписку.

  # В варианте 1 переписка общая, должна быть в state.db
  hermes sessions list

  # Для мониторинга — добавить hook (см. §13)

Проблема: Каждый пользователь хочет свои skills.

  → Перейти на вариант 3 (отдельные профили)
