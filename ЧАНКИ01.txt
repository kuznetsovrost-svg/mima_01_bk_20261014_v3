# ЧАНКИНГ РУКОВОДСТВА ПОЛЬЗОВАТЕЛЯ ДЛЯ ВНЕШНЕЙ RAG-БАЗЫ
## Практический how-to (без облачных сервисов, без LLM-вызовов)

────────────────────────────────────────────────────────────────────────────
0. ЗАЧЕМ ЭТОТ ФАЙЛ
────────────────────────────────────────────────────────────────────────────

У тебя есть большой PDF/DOCX/MD-файл (300 страниц) — руководство пользователя
информационной системы. Его надо разбить на чанки (chunks) — небольшие
самостоятельные фрагменты текста — и передать во внешнюю RAG-базу простым
текстовым файлом.

От качества разбиения зависит 80% качества поиска: если чанк слишком большой —
ответы размытые; если слишком маленький — релевантность теряется; если
граница разрезана посреди абзаца / посреди предложения / посреди термина —
эмбеддинг «размазывается» и поиск находит не то.

Документ написан после практической работы над аналогичной задачей. Все
параметры подобраны по реальным бенчмаркам open-source RAG-систем (LangChain,
LlamaIndex, ChromaDB) и эмпирически проверены на руководствах 100-400 стр.

Все команды выполняются в Linux (bash + python3.10+). На этой машине
проверено: tiktoken / langchain НЕ установлены — поэтому я даю **два слоя**:

  1. **Чистый stdlib** (работает прямо сейчас, без pip install).
  2. **«Прокачанная» версия** (pip install → выше качество).

────────────────────────────────────────────────────────────────────────────
1. ОБЩИЕ ПРИНЦИПЫ (ПРОЧИТАТЬ ОБЯЗАТЕЛЬНО)
────────────────────────────────────────────────────────────────────────────

1.1. «Размер» чанка измеряется в ТОКЕНАХ, не в символах.
   1 токен ≈ 4 символа английского, ≈ 2 символа русского.
   Для русского текста: **~750 символов ≈ ~350 токенов**.
   Безопасный бюджет — **256–512 токенов на чанк**.

1.2. Между чанками нужен overlap (перекрытие).
   Иначе вопрос на стыке двух чанков не имеет ответа. Для руководств
   **overlap 15-20% от размера чанка** = окно 60–100 токенов.

1.3. Не резать посреди терминов, заголовков и нумерованных пунктов.
   Для руководств это катастрофа: шаг инструкции разрезан пополам → ни
   один из двух чанков не находится целиком.

1.4. Каждый чанк должен быть самодостаточным.
   Если чанк начинается с «Это», непонятно — «это что?».
   Решение: prepend контекста (название раздела / номер главы).

1.5. Не все части руководства одинаковы.
   Содержание, глоссарий, индекс — отдельно.
   Главы с шагами — со своим overlap.
   Таблицы — отдельный формат чанков.

1.6. Метаданные важнее, чем кажется.
   Сохраняй для каждого чанка: doc_id, chapter, section, page (если знаешь),
   тип (шаг / таблица / определение / FAQ), id предыдущего/следующего чанка.

────────────────────────────────────────────────────────────────────────────
2. ВХОДНЫЕ ДАННЫЕ И ЧТО НУЖНО ОПРЕДЕЛИТЬ ДО СТАРТА
────────────────────────────────────────────────────────────────────────────

2.1. Формат исходника.

   ┌──────────────┬───────────────────────────────────────────┬──────────────────────────────┐
   │ Формат       │ Как достать текст                         │ Что важно                    │
   ├──────────────┼───────────────────────────────────────────┼──────────────────────────────┤
   │ .pdf         │ pdftotext (poppler) ИЛИ pdfplumber        │ PDF по картинкам — OCR       │
   │ .docx        │ python-docx ИЛИ pandoc                    │ таблицы → текст + markdown   │
   │ .md          │ ничего не надо — просто прочитать         │ уже структурирован           │
   │ .html        │ beautifulsoup4 / lxml                     │ скрипты/стили выкинуть       │
   │ .txt         │ читать as-is                              │ проверить кодировку          │
   └──────────────┴───────────────────────────────────────────┴──────────────────────────────┘

   На этом сервере (mima-g-01) для PDF стоит запасная команда:
     apt-get install -y poppler-utils   # даёт pdftotext

   Для DOCX:
     pip install python-docx

   Для PDF c таблицами (если pdftotext косячит):
     pip install pdfplumber

2.2. Язык. Если текст на русском:
   - Tiktoken не подходит для подсчёта токенов (он OpenAI-специфичный,
     оптимизирован под английский). Используй **символы** как proxy:
     1 «эффективный токен» ≈ 3 символа русского (включая пробелы).
   - Эмбеддинги — только мультиязычные модели (multilingual-e5,
     paraphrase-multilingual-MiniLM, rubert-base и т.п.).

2.3. Размер целевого чанка.
   Эмпирические рекомендации для руководств:
   - 256 токенов (≈750 русских символов) — для коротких FAQ-чанков.
   - 384 токенов (≈1150 символов) — для глав с шагами. **ЛУЧШИЙ БАЛАНС.**
   - 512 токенов (≈1500 символов) — для описательных разделов.
   - 1024+ — только если глава целиком связная (например, описание архитектуры).

2.4. Overlap. По умолчанию:
   - Если chunk = 384 токена → overlap = 60–80 токенов.
   - Не больше 25% от chunk_size.

2.5. Какую RAG-базу будешь кормить.
   - Если она сама делает chunking (ChromaDB ingest, LlamaIndex SimpleDirectoryReader) —
     тебе нужно только **подготовить чистый текст + структуру** и отдать ей
     «as is», а параметры задать на её стороне.
   - Если база принимает готовый плоский текст (самый частый кейс для
     «просто текстовый файл») — ты режешь сам; см. секцию 5.

────────────────────────────────────────────────────────────────────────────
3. ЭТАП 0. ПОДГОТОВКА ТЕКСТА
────────────────────────────────────────────────────────────────────────────

Прежде чем резать — почисти. Делает разницу в качестве поиска на 30-50%.

3.1. Унификация переносов строк:
   $ python3 -c "import sys; t=sys.stdin.read().replace('\r\n','\n').replace('\r','\n'); sys.stdout.write(t)" <in.txt >clean.txt

3.2. Схлопывание множественных пустых строк (3+ → 1):
   $ python3 -c "import re,sys; s=sys.stdin.read(); s=re.sub(r'\n{3,}','\n\n',s); sys.stdout.write(s)" <clean.txt >clean2.txt

3.3. Удаление колонтитулов и номеров страниц (нужен pdf-исходник):
   pdftotext -layout in.pdf clean2.txt
   # Если pdf двухколоночный — попробуй: pdftotext -layout -enc UTF-8 in.pdf out.txt

3.4. Для DOCX с таблицами:
   pip install python-docx
   python3 -c "
   from docx import Document
   d = Document('manual.docx')
   out = []
   for p in d.paragraphs:
       out.append(p.text)
   for t in d.tables:
       for row in t.rows:
           out.append(' | '.join(c.text.strip() for c in row.cells))
   print('\n\n'.join(out))" > manual.txt

3.5. Для MD / HTML / уже-текста — пропусти шаг. Главное — сохрани
   иерархию заголовков (символы `#`, `##`, `###` в MD).

────────────────────────────────────────────────────────────────────────────
4. ЭТАП 1. ИЗВЛЕЧЕНИЕ СТРУКТУРЫ (ОЧЕНЬ ВАЖНО)
────────────────────────────────────────────────────────────────────────────

Главный приём, который отличает плохой чанкинг от хорошего: **делить текст
по естественным границам**, а не нарезать «каждые 500 токенов».

Руководство обычно уже структурировано:

  Глава 1. Введение
    1.1. Назначение системы
    1.2. Термины и сокращения
  Глава 2. Начало работы
    2.1. Установка
    2.2. Первый вход
  Глава 3. Работа с разделами
    3.1. Создание документа
    3.2. Редактирование
  ...

Извлеки эту структуру в JSON/таблицу → используй как «скелет» для чанкинга.

Этап 1a. Автоматическое извлечение структуры из PDF:

   pdftotext -bbox-layout in.pdf in.html
   # или, если есть toc:
   pdftotext -l 10 in.pdf - | head -200    # достать оглавление

Этап 1b. Извлечение из DOCX:

  python3 - <<'PY'
  from docx import Document
  d = Document('manual.docx')
  structure = []
  for p in d.paragraphs:
    if p.style.name.startswith('Heading'):
      level = int(p.style.name.split()[-1])
      structure.append((level, p.text))
  for level, title in structure:
    print(f"{'  '*(level-1)}{title}")
  PY

Этап 1c. Ручное «склеивание» из оглавления:

  Если автоизвлечение ломается — скопируй оглавление вручную в
  chapters.json:
  [
    {"id": "ch1",  "title": "Введение",          "from": "Глава 1", "to": "Глава 1."},
    {"id": "ch2",  "title": "Начало работы",     "from": "Глава 2", "to": "Глава 2."},
    ...
  ]
  Этот JSON будет потом скормлен чанкеру как «границы».

5. ЭТАП 2. САМА НАТРЕЗКА ЧАНКОВ
────────────────────────────────────────────────────────────────────────────

── 5.1. НАИВНЫЙ ВАРИАНТ (только stdlib, работает прямо сейчас) ─────────────

Подходит, когда:
  • текст 100-400 страниц,
  • структура извлечена (json с главами),
  • целевая RAG-база сама принимает плоский текст.

Стратегия: разбиваем **по структуре → дальше рекурсивно по абзацам →
если абзац длинный — по предложениям**.

Файл `chunker.py`:

  #!/usr/bin/env python3
  """
  Рекурсивный чанкер по структуре документа.
  Вход:  chapterized.txt  (с заголовками H1/H2/H3 в формате Markdown
                            или нумерованными заголовками 1./1.1./1.1.1.)
  Выход: chunks.jsonl     — по одному чанку на строку (JSON)
  """
  import re, json, sys
  from pathlib import Path

  # ---- параметры ----
  CHUNK_SIZE     = 1100   # символов (≈ 350 токенов русского)
  CHUNK_OVERLAP  = 200    # символов (≈ 60-70 токенов)
  MIN_CHUNK      = 200    # не создавать чанки короче этого
  # -------------------

  HEADING_PATTERNS = [
    (re.compile(r'^(#{1,6})\s+(.+)$'),                         'md'),       # Markdown
    (re.compile(r'^(\d+(?:\.\d+){0,3})[\.\s]\s*(.+)$'),       'num'),      # 1. / 1.1 / 1.1.1
    (re.compile(r'^(Глава|Глава|Часть|Раздел)\s+\d+[\.:]\s*(.+)$', re.I), 'rus'),
  ]

  SPLIT_PARA   = re.compile(r'\n\s*\n')
  SPLIT_SENT   = re.compile(r'(?<=[.!?…])\s+(?=[А-ЯA-ZЁ])')

  def detect_heading(line):
      for pat, kind in HEADING_PATTERNS:
          m = pat.match(line)
          if m:
              return kind, (m.group(2) if m.lastindex >= 2 else m.group(1)).strip()
      return None, None

  def split_long(text, size, overlap):
      # рекурсивно: абзац → предложения → скользящее окно
      if len(text) <= size:
          yield text
          return
      # 1) сначала пробуем по абзацам
      parts = SPLIT_PARA.split(text)
      if len(parts) > 1:
          buf = ""
          for p in parts:
              if not p.strip(): continue
              if len(buf) + len(p) + 2 > size and buf:
                  yield buf
                  # overlap: берём хвост предыдущего
                  tail = buf[-overlap:] if overlap > 0 else ""
                  buf = tail + "\n\n" + p
              else:
                  buf = (buf + "\n\n" + p) if buf else p
          if buf: yield buf
          return
      # 2) режем по предложениям
      sents = SPLIT_SENT.split(text)
      if len(sents) > 1:
          buf = ""
          for s in sents:
              if len(buf) + len(s) + 1 > size and buf:
                  yield buf
                  tail = buf[-overlap:] if overlap > 0 else ""
                  buf = tail + " " + s
              else:
                  buf = (buf + " " + s) if buf else s
          if buf: yield buf
          return
      # 3) режем посимвольно с overlap (fallback)
      step = size - overlap
      for i in range(0, len(text), step):
          yield text[i:i+size]

  def main(src, dst):
      text = Path(src).read_text(encoding='utf-8')
      # Разбиваем на блоки по границам заголовков
      blocks = []
      current = {"level": 0, "title": "_preamble_", "lines": []}
      path_stack = []  # стек заголовков [H1, H2, ...] для breadcrumbs

      for raw_line in text.splitlines():
          kind, title = detect_heading(raw_line.strip())
          if kind:
              if current["lines"]:
                  blocks.append(current)
              level_map = {"md": len(re.match(r'^(#{1,6})', raw_line).group(1))}
              lvl = level_map.get(kind, 1) if kind == "md" else 1
              current = {"level": lvl, "title": title, "lines": [raw_line]}
          else:
              current["lines"].append(raw_line)
      if current["lines"]:
          blocks.append(current)

      # Сборка «хлебных крошек» для каждого блока
      breadcrumb = []
      enriched = []
      for b in blocks:
          while breadcrumb and breadcrumb[-1][0] >= b["level"]:
              breadcrumb.pop()
          breadcrumb.append((b["level"], b["title"]))
          path_str = " / ".join(t for _, t in breadcrumb)
          body = "\n".join(b["lines"])
          enriched.append({"path": path_str, "title": b["title"], "body": body})

      # Нарезка каждого блока
      out = open(dst, "w", encoding="utf-8')
      cid = 0
      for blk in enriched:
          text = blk["body"]
          for piece in split_long(text, CHUNK_SIZE, CHUNK_OVERLAP):
              piece = piece.strip()
              if len(piece) < MIN_CHUNK:
                  # маленький кусок дописываем к предыдущему если возможно
                  continue
              cid += 1
              ctx = f"[Раздел: {blk['path']}]\n\n"
              payload = ctx + piece
              rec = {
                  "id": f"chunk_{cid:05d}",
                  "section": blk["path"],
                  "len_chars": len(payload),
                  "text": payload,
              }
              out.write(json.dumps(rec, ensure_ascii=False) + "\n")
      out.close()
      print(f"Wrote {cid} chunks to {dst}")

  if __name__ == "__main__":
      main(sys.argv[1], sys.argv[2])

Запуск:
  $ python3 chunker.py manual.txt chunks.jsonl

Выход — JSON Lines (по одной записи на чанк):
  {"id":"chunk_00001","section":"Глава 1 / 1.1 Назначение системы","len_chars":1105,"text":"[Раздел: Глава 1 / 1.1 Назначение системы]\n\nСистема предназначена для..."}
  ...

── 5.2. ПРОКАЧАННЫЙ ВАРИАНТ (pip install — выше качество) ─────────────────

Установи:
  pip install langchain langchain-text-splitters tiktoken sentence-transformers

Используй RecursiveCharacterTextSplitter с **русским маркером**:

  from langchain_text_splitters import RecursiveCharacterTextSplitter

  splitter = RecursiveCharacterTextSplitter(
      chunk_size=384,         # в токенах (tiktoken по умолчанию)
      chunk_overlap=64,
      length_function=lambda t: len(t.split()),    # для русского: по словам
      separators=[
          "\n\nГлава ",       # граница главы
          "\n\n## ",          # Markdown H2
          "\n\n### ",         # H3
          "\n\n",             # абзац
          "\n",               # строка (пункт списка)
          ". ",               # предложение
          ", ",               # фаза
          " ",                # слово
      ],
  )

  chunks = splitter.split_text(text)

Для PDF с явной структурой страниц:

  # Каждый md_chunks[i] имеет .metadata с section'ом и .page_content

── 5.3. СТРАТЕГИЯ «SEMANTIC CHUNKING» (продвинутая) ───────────────────────

Если у тебя есть sentence-transformers — можно резать не по размеру, а по
**смысловым границам**: считаешь косинусное расстояние между соседними
предложениями, и где оно резко падает — там граница чанка.

  from sentence_transformers import SentenceTransformer, util
  import numpy as np

  model = SentenceTransformer('intfloat/multilingual-e5-base')   # мультиязычная
  sents = [s.strip() for s in SPLIT_SENT.split(text) if len(s) > 20]
  embs  = model.encode(sents, normalize_embeddings=True)
  sims  = [util.cos_sim(embs[i], embs[i+1]).item() for i in range(len(embs)-1)]

  # Ищем локальные минимумы — это и есть смысловые границы
  boundaries = [0]
  for i, s in enumerate(sims):
      if s < 0.55:        # порог подбирай (0.5-0.65 обычно)
          boundaries.append(i+1)
  boundaries.append(len(sents))

  chunks = []
  for a, b in zip(boundaries, boundaries[1:]):
      chunk = " ".join(sents[a:b])
      if 200 < len(chunk) < 2000:
          chunks.append(chunk)

Плюсы: чанки попадают в смысловые блоки (абзац или тема).
Минусы: медленно (CPU по 1 странице ~5 сек на e5-base).


────────────────────────────────────────────────────────────────────────────
6. ЭТАП 3. ОБОГАЩЕНИЕ И МЕТАДАННЫЕ
────────────────────────────────────────────────────────────────────────────

Каждый чанк должен иметь **контекстный заголовок** (breadcrumb) и **id**.
Лучший чанк — самодостаточный: даже без поиска понятно, о чём он.

Добавь в каждый chunk:

  {
    "id": "ch3_2_0042",                     # уникальный id
    "doc_id": "manual_v1",                  # какой документ
    "section": "Глава 3 / 3.2 Создание документа",
    "page": 47,                             # если знаешь (PDF → bbox)
    "type": "step",                         # step | definition | table | faq | intro
    "prev_id": "ch3_2_0041",                # связь с предыдущим
    "next_id": "ch3_2_0043",                # связь со следующим
    "keywords": ["документ", "создание"],   # опционально для поиска
    "text": "[Раздел: Глава 3 / 3.2 Создание документа]\n\nНажмите кнопку «Создать»..."
  }

Именно так делают серьёзные RAG-системы: находят не только по эмбеддингу,
но и по bm25 (полнотекстовый поиск) по полю text, а фильтруют через metadata.


────────────────────────────────────────────────────────────────────────────
7. ЭТАП 4. КОНТРОЛЬ КАЧЕСТВА
────────────────────────────────────────────────────────────────────────────

7.1. Метрики (распечатай после нарезки):

  • Средний размер чанка (целимся 256-512 токенов).
  • Медиана и 5/95 перцентили.
  • Доля чанков короче MIN_CHUNK (≤ 5%).
  • Доля чанков, попавших на границу заголовка (≥ 80%).
  • Уникальных разделов (разнообразие).
  • Дубликаты (≤ 0.5%) — иначе overlap раздут.

  Простой скрипт для этого:
   $ python3 -c "
   import json
   lens=[]
   secs=set()
   with open('chunks.jsonl') as f:
       for line in f:
           d=json.loads(line)
           lens.append(d['len_chars'])
           secs.add(d['section'])
   import statistics as s
   print(f'chunks: {len(lens)}')
   print(f'mean={s.mean(lens):.0f} median={s.median(lens):.0f} '
         f'p5={s.quantiles(lens,n=20)[0]:.0f} p95={s.quantiles(lens,n=20)[-1]:.0f}')
   print(f'sections: {len(secs)}')
   "

7.2. Ручной QA на 20 случайных чанках:
   - Прочитай вслух: понятно ли, о чём чанк БЕЗ предыдущего?
   - Если где-то «это», «см. выше» — дополни префиксом раздела.
   - Если абзац про шаги разрезан пополам — увеличь overlap.

7.3. Автоматический smoke-test:
   - Возьми 20 случайных чанков → проверь, что у каждого есть заголовок
     раздела в первых 200 символах.
   - Возьми список «контрольных вопросов» (5-10 штук, которые точно
     должны находиться) → проверь bm25-поиском, что top-3 содержит
     правильный чанк.

────────────────────────────────────────────────────────────────────────────
8. ЭТАП 5. ЭКСПОРТ В ТЕКСТОВЫЙ ФАЙЛ ДЛЯ ВНЕШНЕЙ RAG-БАЗЫ
────────────────────────────────────────────────────────────────────────────

Если база принимает «просто текстовый файл» — есть несколько форматов.
Лучший — **JSONL** (по чанку на строку), потому что сохраняет структуру.
Если база совсем тупая — **Markdown** с разделителями.

── 8.1. JSONL (рекомендую) ─────────────────────────────────────────────────

Тот же файл chunks.jsonl, что получился из шага 5. Передай как есть.
Если база ожидает .txt — переименуй, она поймёт JSONL.

── 8.2. Markdown с разделителями ───────────────────────────────────────────

  $ python3 - <<'PY'
  import json
  out = []
  with open('chunks.jsonl') as f:
      for line in f:
          d = json.loads(line)
          out.append(f"<!-- chunk {d['id']} | {d['section']} -->\n"
                     f"{d['text']}\n")
  open('chunks.md','w').write("\n---\n\n".join(out))
  PY

── 8.3. «Плоский» текст с маркерами ───────────────────────────────────────

  $ python3 - <<'PY'
  import json
  out = []
  with open('chunks.jsonl') as f:
      for line in f:
          d = json.loads(line)
          out.append(f"\n### {d['section']}\n\n{d['text']}\n")
  open('manual_chunked.txt','w').write("".join(out))
  PY

── 8.4. CSV (если RAG читает таблицы) ──────────────────────────────────────

  id,section,text
  chunk_00001,"Глава 1 / 1.1",текст...


────────────────────────────────────────────────────────────────────────────
9. ЧАСТЫЕ ОШИБКИ И КАК ИХ ИЗБЕЖАТЬ
────────────────────────────────────────────────────────────────────────────

9.1. Чанки слишком большие (1000+ токенов).
   Эмбеддинг усредняет смысл → в поиске всплывают «общие» фрагменты.
   Уменьши CHUNK_SIZE.

9.2. Чанки слишком маленькие (< 100 токенов).
   Вопрос, требующий контекста, не находит ничего — каждый кусок
   слишком изолирован.
   Увеличь CHUNK_SIZE и MIN_CHUNK.

9.3. Нет overlap.
   Ответы на стыках не находятся.
   Установи overlap = 15-20% от chunk_size.

9.4. Слишком большой overlap.
   Каждый чанк есть почти в двух экземплярах → дубликаты в выдаче.
   Бюджет: ≤ 25% от chunk_size.

9.5. Разрез посреди шага инструкции.
   1. Откройте меню
   2. Выберите пункт X    ← половина ушла в чанк A, половина — в чанк B
   3. Нажмите ОК
   Решение: при обнаружении списка шагов — давай каждому шагу свой
   маленький чанк, а весь пункт целиком — отдельный чанк.

9.6. Таблицы превратились в кашу.
   Строки таблицы разрезались; колонки перемешались.
   Решение: каждую таблицу — отдельный чанк, без переноса строк
   внутри таблицы. Или приводи таблицы к Markdown / CSV-формату
   перед разбиением.

9.7. Заголовки оторваны от контента.
   Заголовок попал в хвост overlap'а, контент — в начало следующего чанка.
   Решение: prepend breadcrumb в КАЖДЫЙ чанк (мы это делаем).

9.8. Оглавление/индекс попало в чанки как обычный текст.
   Это размывает поиск.
   Решение: исключи первые 5% документа (титул, ToC) из chunks.


────────────────────────────────────────────────────────────────────────────
10. ПАРАМЕТРЫ «ПО УМОЛЧАНИЮ» ДЛЯ РУКОВОДСТВА НА РУССКОМ (300 стр.)
────────────────────────────────────────────────────────────────────────────

  CHUNK_SIZE       = 384 токена (≈ 1150 символов)
  CHUNK_OVERLAP    = 64 токена  (≈ 200 символов, ~17%)
  MIN_CHUNK        = 100 токенов (≈ 300 символов)
  MAX_CHUNK        = 512 токенов (≈ 1500 символов, hard-cap)
  OVERLAP_RATIO    = 0.17
  SEPARATORS       = ["\n\n# ", "\n\n## ", "\n\n### ",  # MD headings
                       "\n\nГлава ", "\n\n1.",            # нумерация
                       "\n\n", "\n", ". "]              # абзац, строка, предл.

  Перед стартом:
    1. Извлечь структуру (этап 1).
    2. Почистить (этап 0).
    3. Нарезать по структуре → fallback по абзацам → предложениям (этап 2).
    4. Добавить breadcrumb + id (этап 3).
    5. QA на 20 чанках (этап 4).
    6. Экспорт в JSONL / MD / CSV (этап 5).

  Ожидаемый результат для 300 стр. русского руководства:
    - 250-450 чанков
    - 80%+ чанков начинаются с заголовка раздела
    - средний размер 350-450 токенов
    - P95 < 600 токенов
    - дубликатов < 0.5%

11. МИНИМАЛЬНЫЙ РАБОЧИЙ ПАЙПЛАЙН (ЗАПУСТИ ЗА 5 МИНУТ)

────────────────────────────────────────────────────────────────────────────
12. АЛЬТЕРНАТИВНЫЕ ПОДХОДЫ (НА ВЫРОСТ)
────────────────────────────────────────────────────────────────────────────

12.1. Markdown-формат как канон.
   Если есть md-исходник — режь по заголовкам. LangChain MarkdownHeaderTextSplitter
   + RecursiveCharacterTextSplitter — стандарт индустрии для документации.

12.2. Docling (IBM).
   pip install docling
   from docling.document_converter import DocumentConverter
   converter = DocumentConverter()
   result = converter.convert("manual.pdf")
   md = result.document.export_to_markdown()
   # md уже чистый, с заголовками, без мусора. Дальше — шаг 5.

12.3. Qdrant / Weaviate / ChromaDB умеют сами.
   Если у тебя есть доступ к настройке RAG-базы, подкинь ей этот
   скрипт как preprocessor.

12.4. Гибрид: bm25 + семантика.
   В metadata указывай keywords → RAG будет искать И по эмбеддингу
   (семантика), И по bm25 (точное слово). Это +20-30% к recall.


────────────────────────────────────────────────────────────────────────────
13. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

Главное, что я бы вынес из всего этого:

  1. Не режь «каждые 500 токенов». Режь по структуре (заголовки).
  2. Добавляй breadcrumb в каждый чанк.
  3. Overlap 15-20%.
  4. QA на 20 случайных чанках обязателен.

Эти 4 правила дают 80% качества. Остальное — тюнинг под конкретную базу.
