# Порядок работы с документом в VS Code + Hermes

> Объединяет два обсуждения:
> 1. Как работает создание сложного документа с моей помощью в VS Code
> 2. Как я параллельно наращиваю профиль `document-authoring` для повторного использования
> Дата: 2026-08-08

---

## Часть I. Как происходит создание документа

### Общая картина

```
┌─────────────────────────────────────────────────────────────┐
│ VS Code (Windows)                                           │
│                                                             │
│  Tab 1: [requirements.md]   ← правила и требования          │
│  Tab 2: [context-A.md]      ← исходный контекст 1           │
│  Tab 3: [context-B.json]    ← исходный контекст 2           │
│  Tab 4: [context-C.txt]     ← исходный контекст 3           │
│  Tab 5: [example-600.docx]  ← пример на 600 страниц         │
│  Tab 6: [new-document.md]   ← ПУСТОЙ, ты в нём пишешь       │
│                                                             │
│  Боковая панель: [ACP: Hermes]   ← чат со мной              │
└─────────────────────────────────────────────────────────────┘
```

### Шаг 1. Открытие workspace

1. Открываешь VS Code
2. Подключаешься к mima_g_01 через Remote-SSH
3. Открываешь папку с файлами
4. Открываешь 6 табов (5 контекстных + 1 пустой)
5. Запускаешь ACP-клиент с агентом Hermes

### Шаг 2. Явное подключение контекста

Главная ошибка — считать, что я **вижу** открытые табы. На самом деле:

| Я знаю | Я НЕ знаю |
|---|---|
| имя файла из пути | что ты его открыл |
| содержимое из read_file | что ты его редактируешь |
| выделенный текст из ACP API | что ты печатаешь прямо сейчас |

Поэтому **обязательно** в начале сессии:

```
@Hermes, контекст сегодня:
1. requirements.md — правила
2. context-A.md — данные
3. example-600.docx — образец
4. new-document.md — рабочий файл

Прочитай первые два, потом я буду спрашивать по разделам.
```

### Шаг 3. Я подгружаю контекст

| Действие | Что я делаю |
|---|---|
| Читаю requirements.md | парсю правила, требования, ограничения |
| Читаю context-A.md | запоминаю структуру данных |
| Записываю в свою память | сессия: задача X, контекст: 5 файлов, цель: новый документ |

### Шаг 4. Три режима работы

#### Режим A: «Ты пишешь, я комментирую»

```
ты: Я только что написал раздел 1. Проверь по requirements.md.
```

Что я делаю:
1. Читаю что ты написал (в текущем файле)
2. Сверяю с requirements.md
3. Возвращаю отчёт:
   - что соответствует
   - что требует доработки
   - что нарушает правила

#### Режим B: «Я предлагаю, ты принимаешь»

```
ты: Сгенерируй раздел 2 по аналогии с example-600.docx,
    используя данные из context-B.json
```

Что я делаю:
1. Читаю example-600.docx (через read_file или python-docx)
2. Читаю context-B.json
3. Сверяю с requirements.md
4. Генерирую черновик раздела
5. Возвращаю diff

Ты нажимаешь Apply в VS Code → текст вставляется в new-document.md.

#### Режим C: «Итеративная доработка»

```
ты: [выделяешь абзац в new-document.md]
ты: Перепиши это короче и в стиле example-600.docx
```

Что я делаю:
1. Вижу выделенный текст (через ACP selection API)
2. Читаю стиль из example
3. Перефразирую
4. Возвращаю замену

### Шаг 5. Сборка по кусочкам

```
[Ты] Начнём с раздела 1. Прочитай requirements.md полностью.

[Я] Прочитал. 47 требований. Раздел 1 — обзор, 3 требования
    покрывают. Структура раздела 1 по example:
    - Введение (1 параграф)
    - Цель (1 параграф)
    - Область применения (1-2 параграфа)
    Готов дать черновик.

[Ты] Давай первый подраздел.

[Я] [черновик Введения]

[Ты] [Правишь вручную]

[Ты] Окей, теперь Цель. Опирайся на context-B.json, поле goal.

[Я] [черновик Цели на основе JSON]

[Ты] Хорошо. Следующий — Область применения. Возьми данные
    из context-A.md и context-C.txt.

[Я] [черновик, использующий оба источника]

[Ты] Сравни с примером — у меня стиль короче.

[Я] [переписанная версия]

[Ты] Идём в раздел 2...
```

## Часть II. Стратегия для большого примера (600 страниц)

### Проблема

600 страниц = ~1.5 млн слов = ~2 млн токенов. Это в 10 раз больше моего контекста.

### Решение

| Шаг | Что делать |
|---|---|
| 1 | Нарезать example на разделы |
| 2 | Я читаю только нужный раздел как шаблон |
| 3 | Когда генерируешь раздел N — я подгружаю example[N] |
| 4 | Не держать весь example в памяти |

Команда для нарезки:

```bash
# На mima_g_01
python3 -c "
from docx import Document
doc = Document('example-600.docx')
for i, p in enumerate(doc.paragraphs):
    if p.style.name.startswith('Heading'):
        print(f'{i}	{p.text}')
" > example-toc.txt
```

Я буду знать: «Раздел 1 на стр 1-15, Раздел 2 на стр 16-40...»

## Часть III. Что я могу и что не могу

### Могу

| Возможность | Как это работает |
|---|---|
| Читать все открытые файлы | через read_file (один запрос) |
| Помнить контекст сессии | привязан к моей сессии, не к файлу |
| Сравнивать с требованиями | правила в requirements.md = чеклист |
| Использовать пример как образец | структура = template для подражания |
| Делать выборку из JSON | конкретные поля как data source |
| Insert в текущий файл | через ACP edit/suggest API |
| Не терять прогресс | каждое сообщение = checkpoint |

### Не могу

| Что | Почему |
|---|---|
| Видеть всё в одном контексте | лимит ~200K токенов |
| Читать .docx напрямую | надо через python-docx |
| Писать в файл без твоего OK | нужен Apply |
| Угадывать если правила неполные | спрошу |
| Видеть что ты НЕ сохранил | только после Ctrl+S |

## Часть IV. Параллельное наращивание профиля document-authoring

### Зачем

После первой задачи у тебя должен остаться **готовый переиспользуемый профиль** для следующих похожих документов.

### Структура будущего профиля

```
/root/.hermes/profiles/document-authoring/
├── README.md                  # инструкция как развернуть
├── PROFILE.md                 # описание профиля
├── OVERLAY.md                 # дополнения к SOUL.md
├── skills/
│   ├── 01-context-loader/
│   │   ├── SKILL.md          # как подключить N файлов
│   │   └── scripts/
│   │       └── attach_context.py
│   ├── 02-requirements-extractor/
│   │   ├── SKILL.md          # парсит requirements.md → чеклист
│   │   └── scripts/
│   │       └── parse_requirements.py
│   ├── 03-example-styler/
│   │   ├── SKILL.md          # анализирует example → style guide
│   │   └── scripts/
│   │       └── analyze_style.py
│   ├── 04-section-generator/
│   │   ├── SKILL.md          # генерация раздела по шаблону
│   │   └── scripts/
│   │       └── generate_section.py
│   └── 05-quality-checker/
│       ├── SKILL.md          # проверка по requirements
│       └── scripts/
│           └── verify_compliance.py
├── memory/
│   └── seed-memory.md         # стартовое содержимое MEMORY.md
├── config.yaml.template       # конфиг для нового профиля
└── examples/
    ├── good-section.md        # эталон раздела
    └── bad-section.md         # антипаттерн
```

### Как наращивается в процессе работы

| Триггер | Что я делаю |
|---|---|
| «Сгенерируй раздел» → я делаю | записываю workflow в 04-section-generator |
| «Проверь по требованиям» → я делаю | записываю в 05-quality-checker |
| «У меня не получилось» → разбор | записываю в anti-patterns |
| «Этот раздел идеален» → пример | копирую в examples/good |
| «Этот workflow неудобный» | записываю в anti-patterns профиля |
| «Добавь в skills: парсить .docx» | создаю соответствующий скилл |

### Команды для наращивания

| Команда | Что делаю |
|---|---|
| «Создай профиль document-authoring» | стартовая структура |
| «Запиши в skills: X» | добавляю новый скилл |
| «Сохрани как эталон» | копирую в examples/good |
| «Это антипаттерн» | записываю в anti-patterns |
| «Закрой профиль» | финализирую README + запаковываю |

### Варианты хранения

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Заметки в сессии | быстро | теряется при reset |
| 2. Draft в /root/ | просто | без структуры |
| 3. Полноценный профиль | готов к использованию | нужно время |
| 4. Git репозиторий | история версий | нужно git init |

Рекомендую: **вариант 3** (= вариант 4 после `git init`).

## Часть V. Пошаговый план на сессию

### Шаг 0. Подготовка (5 мин)

| Действие | Команда |
|---|---|
| Создать профиль | `@Hermes, создай профиль document-authoring в /root/.hermes/profiles/document-authoring/` |
| Проверить структуру | `@Hermes, ls -la /root/.hermes/profiles/document-authoring/` |

### Шаг 1. Подключение контекста (3 мин)

```
@Hermes, сегодня работаю над [название документа].
Открыто 5 файлов:
1. requirements.md — правила и требования
2. context-A.md — [что]
3. context-B.json — [что]
4. context-C.txt — [что]
5. example-600.docx — образец структуры

Пустой файл: new-document.md

Прочитай requirements.md и context-A.md. Скажи когда готов.
```

### Шаг 2. Нарезка примера (если 600 страниц)

```
Прочитай example-600.docx через python-docx.
Сделай ТОС: список всех заголовков с номерами строк.
```

### Шаг 3. Генерация раздела за разделом

```
[Для каждого раздела]
@Hermes, сгенерируй раздел N.
- Используй example[N] как образец
- Возьми данные из context-X
- Проверь по требованиям
```

### Шаг 4. Параллельное сохранение в профиль

```
@Hermes, запиши в профиль document-authoring:
- Скилл: чтение .docx через python-docx
- Workflow: TOC → генерация раздела → проверка
- Антипаттерн: [что не сработало]
- Эталон: раздел N — хороший пример
```

### Шаг 5. Закрытие сессии

```
@Hermes, закрой профиль document-authoring.
Сделай README с инструкцией.
```

## Часть VI. Главные правила успеха

| Правило | Зачем |
|---|---|
| Явное подключение контекста | иначе я не вижу |
| Разделы по одному | не раздувать контекст |
| Чеклист требований | брать из requirements.md |
| Apply, не copy-paste | меньше ошибок |
| Сохраняй каждый этап | backup в /root/ |
| Спрашивай что непонятно | я переспрошу, а не угадаю |
| Параллельно копи профиль | чтобы не потерять находки |

## Часть IX. Главная мысль

> В VS Code я становлюсь «умным напарником», который видит твой workspace,
> помнит контекст, может править точечно. Для документа — это разгон:
> ты ставишь правила, я генерирую, ты правишь.
> Параллельно я коплю профиль document-authoring — следующий раз ты начнёшь
> не с нуля, а с готовых skills, workflows, чеклистов.
