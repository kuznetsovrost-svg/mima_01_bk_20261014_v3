# USER.md — что писать и как писать
## Полный гайд по профилю пользователя в Hermes Agent

────────────────────────────────────────────────────────────────────────────
0. ЧТО ТАКОЕ USER.MD И ЗАЧЕМ ОН
────────────────────────────────────────────────────────────────────────────

USER.md — это «память о пользователе». В отличие от MEMORY.md (где живут
**факты о мире, инфраструктуре и работе**), в USER.md живут **факты о
человеке, который общается с агентом**: его имя, роль, привычки,
предпочтения, контекст жизни, формат взаимодействия.

Файл лежит здесь:
   ~/.hermes/profiles/<имя_профиля>/memories/USER.md

В этой же директории memories/ находится MEMORY.md — для инфраструктурных
и проектных фактов. Разделение явное: USER.md — это «кто вы», MEMORY.md —
«что вокруг». Раздел 1 — формальная таблица этого разделения.

USER.md создаётся автоматически при первом обращении модели к
инструменту `memory write`. Вы можете засеять его заранее, если хотите
дать агенту твёрдый «портрет пользователя» уже на старте.

Главное отличие USER.md от SOUL.md:
  • SOUL.md — это роль профиля и стиль (что агент делает и как говорит);
  • USER.md — это портрет пользователя (с кем агент разговаривает).
  Они **дополняют** друг друга, не перекрываются.

────────────────────────────────────────────────────────────────────────────
1. ЧТО ДОЛЖНО ПОПАДАТЬ В USER.MD
────────────────────────────────────────────────────────────────────────────

1.1. ИДЕНТИФИКАЦИЯ.
   - Имя, ник, предпочтительное обращение.
   - Telegram/Matrix username/chat_id (но НЕ для авторизации — только
     чтобы модель помнила, как вас зовут в чате).
   - Email (если нужен — для контекста).
   - Роль, должность, компания.

1.2. КОНТЕКСТ ЖИЗНИ.
   - Часовой пояс.
   - Языки, на которых общаетесь (русский / английский / двуязычие).
   - Доступное время для работы / отдыха.
   - Семейное положение, страна проживания — ТОЛЬКО если сами хотите
     запомнить.

1.3. ПРЕДПОЧТЕНИЯ В ОБЩЕНИИ.
   - Длина ответов (короткие / подробные / по запросу).
   - Стиль (формальный / неформальный / дружелюбный).
   - Эмодзи (да / нет / только severity).
   - Markdown (всегда / никогда / только если попросят).
   - Обращение на «ты»/«вы».
   - Любимые слова и фразы (для tone-matching).

1.4. РАБОЧИЕ ПРИВЫЧКИ.
   - Любимый редактор / IDE / shell.
   - Любимый язык программирования и почему.
   - Стэк технологий, с которым работаете.
   - Привычное время работы (утро/вечер).
   - Какой длины task-ы ставите (короткие вопросы / длинные спеки).
   - Какие инструменты предпочитаете (например, vim, fish, zsh).

1.5. ДОСТУПЫ И ИДЕНТИФИКАТОРЫ.
   - GitHub username.
   - SSH fingerprint’ы (НЕ сами ключи — только отпечатки).
   - Публичные email / Matrix / Telegram id.

1.6. ЦЕЛИ И МОТИВАЦИЯ.
   - Что вы хотите от агента.
   - Какие задачи приоритетны.
   - Какие темы не интересуют (фильтрация шума).

1.7. ГРАНИЦЫ.
   - Что НЕ нужно делать (для этого профиля).
   - Какие темы чувствительны.
   - Права на риск-операции (например, можно ли рестартить сервисы).

────────────────────────────────────────────────────────────────────────────
2. ЧТО НЕ НАДО ПИСАТЬ В USER.MD
────────────────────────────────────────────────────────────────────────────

2.1. СЕКРЕТЫ И ТОКЕНЫ.
   - Никаких API-ключей, токенов, паролей.
   - Никаких SSH-приватных ключей.
   - Уровень «анонимизации»: всё, что должно жить в .env (mode 600),
     НЕ идёт в USER.md. В USER.md можно — «github user: rost»,
     но НЕ «github token: ghp_…».

2.2. ЧУЖИЕ ПЕРСОНАЛЬНЫЕ ДАННЫЕ.
   - ФИО коллег без их согласия.
   - Email третьих лиц.
   - Номера телефонов.

2.3. ОДНОРАЗОВЫЕ РЕШЕНИЯ.
   «Сегодня выбрал PostgreSQL» — в MEMORY.md (факт). В USER.md — только
   если это часть вашего длинного предпочтения («предпочитаю Postgres
   для новых проектов»).

2.4. ЭФЕМЕРНЫЕ СОСТОЯНИЯ.
   «Сейчас болит голова» — не сюда.
   «Завтра в отпуске, не пиши до 5 июля» — не сюда (это cron-задача).

2.5. ОБЩИЕ ФРАЗЫ БЕЗ КОНКРЕТИКИ.
   «Я хороший человек» — неинформативно, съедает контекст.

2.6. ДУБЛИРОВАНИЕ SOUL.md.
   SOUL.md — про роль и стиль. USER.md — про вас. Если пишете там
   «не использовать Markdown-таблицы» — это уже в SOUL.md.

2.7. ЛОЖЬ ИЛИ ПРЕУВЕЛИЧЕНИЕ.
   Если модель запомнит, что вы «senior architect в Google», а на
   самом деле стажёр — будет регулярно льстить вам чужими заслугами.
   Пишите правду.

2.8. МЕДИЦИНСКАЯ / ЮРИДИЧЕСКАЯ / ФИНАНСОВАЯ ИНФОРМАЦИЯ.
   Диагнозы, номера карт, судебные дела — не пишите. Если чувствительно
   для безопасности — не пишите.

────────────────────────────────────────────────────────────────────────────
3. РАЗМЕР, ФОРМАТ, ОБНОВЛЕНИЕ
────────────────────────────────────────────────────────────────────────────

3.1. Идеальный размер: 0.5–4 КБ.
   USER.md обычно короткий — факты о вас, не проект.
   MEMORY.md может разрастаться до 100 КБ; USER.md редко больше 4 КБ.

3.2. Когда обновлять:
   - сменили TZ или местоположение;
   - сменили роль / должность;
   - стали предпочитать другой стиль;
   - модель часто ошибается в чём-то конкретном (тогда допишите).

3.3. Когда НЕ трогать:
   - после каждой сессии (это не дневник);
   - после случайного отзыва модели.

3.4. Можно группировать по разделам:
   ## Identity
   ## Communication preferences
   ## Work style
   ## Sensitivities / boundaries

3.5. Дата-маркеры опциональны.
   В USER.md не так важны, как в MEMORY.md. Если хотите — `[2026-07-02]
   TZ: переехал в Стамбул`, но в целом писать прозой достаточно.

3.6. Код-блоки для имён пользователей / email / path.
   `` `Rost` ``, `` `rost@example.com` `` — чтобы модель не спутала
   с обычным словом.

────────────────────────────────────────────────────────────────────────────
4. КТО И КАК ПИШЕТ В USER.MD
────────────────────────────────────────────────────────────────────────────

4.1. ВРУЧНУЮ (вы сами, через vim).
   Самый прозрачный путь. Положили файл в профиль, отредактировали.
   Подходит для первоначального засевания.

4.2. ЧЕРЕЗ КОМАНДУ.
   $ hermes --profile=<name> memory write --target=user "Rost, Москва, любит короткие ответы"
   Это быстро для добавления одного факта.

4.3. АВТОМАТИЧЕСКИ (модель сама дописывает).
   Когда пользователь говорит «запомни, что я живу в Москве», модель
   вызывает `memory` с action=`write` и target=`user`.
   Можно посмотреть, что модель записала:
     $ hermes --profile=<name> memory list --target=user

4.4. ГИБРИД (рекомендуется).
   Положите базовые факты руками. Модель будет дописывать новые,
   которые вы ей сообщаете. Раз в месяц пройдитесь и почистите.

4.5. УДАЛЕНИЕ.
   $ hermes --profile=<name> memory reset user
   Это сотрёт USER.md целиком. Не путать с `memory reset memory`
   (которое стирает MEMORY.md).

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 1. Профиль «default» — пользователь Rost, общий профиль
═══════════════════════════════════════════════════════════════════════════

USER.md:

```
# USER — Rost

## Identity
- Имя: Rost (Рост — кириллицей тоже корректно).
- Telegram: @Rost, chat_id 505586502.
- GitHub: @kuznetsovrost-svg, email `kuznetsov.rost@gmail.com`.
- Роль: DevOps / backend-инженер, full-stack по необходимости.

## Communication
- Язык общения: русский. Термины и API — на английском.
- Длина ответов: короткие, по делу. Подробно — только если попросят
  или задача сложная.
- Markdown в чате — без таблиц (Telegram их не рендерит). В файлах —
  обычный Markdown, с таблицами при необходимости.
- Эмодзи: только 🚨 ⚠️ ✅ как severity, остальное — по минимуму.
- Обращение: на «ты». Без подхалимства.

## Locale & time
- TZ: Europe/Moscow (UTC+3, без DST).
- Рабочее время: обычно 10:00–20:00 MSK, эпизодически позже.
- Ночные cron-таски: лучше откладывать до 09:00 MSK.

## Work style
- Editor: vim с конфигом `~/.vimrc` (см. в backup).
- Shell: bash, иногда fish (для интерактивного).
- Python: 3.11+ предпочтительно.
- Git workflow: trunk-based, feature branches, PR через squash.
- Code style: mypy --strict, ruff, pytest, xdist.
- Любит краткие ответы, без воды.

## Sensitivities
- Не светить токены/ключи. Если в выводе — заменять на `***`.
- Не публиковать файлы из `/root/` без явного «да».
- Изменения в `/etc/` и `/usr/` — только с подтверждением.
- Не запускать `apt upgrade` без отдельного «да».

## Boundaries
- Не шутить в технических ответах. Юмор — только по запросу.
- Не задавать уточняющих вопросов, если ответ есть в контексте
  (SOUL.md, MEMORY.md, USER.md, переданных файлах).
- Не использовать эмодзи для украшения.
```

Пояснения:
  • **Identity** — конкретные идентификаторы (Telegram id, GitHub
    username, email). Это помогает модели обращаться правильно и
    связывать user_id с user_id в логах.
  • **Communication** — главный раздел. Длина, формат, эмодзи,
    обращение — всё, что влияет на стиль ответов. ЭТО самая
    полезная часть USER.md.
  • **Locale & time** — TZ и предпочтения по расписанию. Помогает
    cron'у не запускать задачи в 2 ночи, а вам не получать
    ночные сообщения.
  • **Work style** — стэк и привычки. Помогает при технических
    ответах (не объяснять что такое vim; не предлагать flake8,
    если уже используете ruff).
  • **Sensitivities** — критично. Без этого блока модель может
    случайно показать токен. Список NO-NO — это защита.
  • **Boundaries** — ролевые границы. «Не шутить» — это
    инструкция, но мягкая (можно отступить, если попросят).

ПРИМЕР 2. Профиль «hermes_ru_writer» — копирайтер, отдельный пользователь
═══════════════════════════════════════════════════════════════════════════

USER.md:

```
# USER — copywriter

## Identity
- Роль: контент-менеджер, работает с инструкциями и гайдами.
- Telegram: @content_rost (для уведомлений о новых материалах).

## Projects
- `/root/*.txt` — каталог гайдов и обучающих материалов.
- Telegram-канал «Руководства» — для публикации.
- Яндекс.Дзен — резервная площадка.

## Communication
- Длина текста — от 1500 до 4000 знаков для статей.
- Голос: нейтрально-дружелюбный, без сленга.
- Структура: H2/H3, без H1.
- Без эмодзи, кроме 🚨/⚠️/✅ для severity.

## Style preferences
- Не использовать канцелярит («осуществлять», «является»).
- Активный залог вместо пассивного («мы сделали» вместо «было сделано»).
- Короткие абзацы (3-5 строк).
- Числа — прописью до десяти, цифрами от одиннадцати.

## Sensitivities
- Не выдумывать цитаты и источники.
- Не использовать ИИ-выражения («в мире, где…», «как мы знаем…»).
- Не светить заказы клиентов или PII.

## Schedule
- Цикл: 1 гайд в неделю, среда 12:00 MSK — публикация.
- План-факт: я в `cron/drafts.json`.
```

Пояснения:
  • Identity — короткий, без лишних данных (копирайтер не хочет
    телефон в памяти).
  • Projects — фактические каналы. Модель может потом
    адаптировать гайд под конкретную площадку.
  • Style preferences — это очень конкретные правила стиля.
    «активный залог», «числа прописью» — модель считывает и применяет.
  • Sensitivities — профессиональная этика: не выдумывать
    источники, не использовать AI-фразы. Это типичные «копирайт»
    запреты.
  • Schedule — связано с cron-профилем. Модель может подсказать,
    когда публиковать.

ПРИМЕР 3. Профиль «briefing_daily» — деловой пользователь с брифингами
═══════════════════════════════════════════════════════════════════════════

USER.md:

```
# USER — Rost (briefing recipient)

## Identity
- Имя: Rost.
- Telegram: @Rost (id 505586502), для ежедневного брифинга 09:00 MSK.
- Matrix: `!OwBtrzzKTGFSNSmvQU:msg.lab.aidemo.adaptivepm.ru` —
  дополнительный канал.

## Daily routine
- Утренний брифинг: 09:00 MSK (см. MEMORY.md за расписанием).
- Обеденное время: 13:00-14:00 — не беспокоить с уведомлениями.
- Конец рабочего дня: ~19:00 MSK.

## Communication
- Получает: дайджесты, расписания, сводки.
- Не получает: запросы подтверждений, длинные отчёты — только
  если сам запросил.
- Срочное: можно в любое время (алерт-формат с 🚨 в первой строке).

## Notifications
- Дайджест: в 09:00 MSK.
- Предупреждения от cron: за 30 мин до важных событий.
- Тихий режим: 22:00–07:00 MSK (только 🚨 алерты).

## Sensitivities
- Не дублировать в Telegram то, что уже ушло в Matrix.
- Не присылать новости без ссылки на источник.
- Не отправлять больше 1 сообщения в минуту в один чат.

## Timezone
- TZ: Europe/Moscow, без DST.
```

Пояснения:
  • Daily routine — конкретный распорядок. Модель сможет
    предложить «сейчас обед, можно сделать позже».
  • Notifications — что, когда, как. Это про конкретный формат
    алертов и тихий режим.
  • «Не дублировать» — важная инструкция для шлюза, чтобы
    одинаковые уведомления не приходили в Telegram и Matrix.
  • Sensitivities более узкие: они про этот конкретный профиль.

ПРИМЕР 4. Профиль «code_reviewer» — пользователь senior developer
═══════════════════════════════════════════════════════════════════════════

USER.md:

```
# USER — senior reviewer

## Identity
- Роль: Senior Backend Engineer.
- GitHub: @kuznetsovrost-svg.
- Stack: Python 3.11+, Go, Postgres, Redis, Kafka.
- Codebase: см. MEMORY.md для списка репозиториев.

## Communication
- Стиль: прямой, без предисловий.
- Не терпит лесть: «Отличная работа!» без причины → шум.
- Длина ответа: по ситуации; для ревью — структурированный список.

## Review preferences
- Каждое замечание — минимум 3 части: «проблема / почему / фикс».
- Если код OK — короткое «+».
- Если нужен дискуссия — model должна переспросить, а не выдумать.
- Severity-маркеры: 🚨 (блокер) / ⚠️ (важно) / 💡 (идея).

## Sensitivities
- Не одобрять PR без явного подтверждения от ревьюера.
- Не менять API контракты без migration-гайда.
- Не удалять тесты.
- Не предлагать «рефактор ради рефактора».

## Boundaries
- Не обсуждать политические или религиозные темы.
- Не использовать генеративные ответы для кода в production
  (только предложения/псевдо).
```

Пояснения:
  • Identity — конкретный стэк. Помогает модели не предлагать
    PHP/Node когда у вас Python/Go.
  • Review preferences — это ДЕТАЛЬНЫЕ правила ревью. «проблема /
    почему / фикс» — формат, который модель будет применять
    автоматически.
  • Sensitivities — очень конкретные защитные правила для
    профессионального контекста. «Не одобрять PR без
    подтверждения» — это про то, что финальное решение
    остаётся за человеком.
  • Severity-маркеры — привязаны к домену. 🚨 = блокер,
    ⚠️ = важно, 💡 = идея. Модель будет ставить их сама.

ПРИМЕР 5. Профиль «mi_mg_01» — минимальный набор для системного профиля
═══════════════════════════════════════════════════════════════════════════

USER.md:

```
# USER — оператор mima_g_01

## Identity
- Имя: Rost.
- Telegram: @Rost (id 505586502).

## Communication
- Краткий, по делу.
- На «ты».
- Без эмодзи для украшения, 🚨/⚠️ для severity.
- Без Markdown-таблиц (Telegram).

## Operations
- Команды `systemctl restart` — только с подтверждения.
- Изменения в `/etc/ssh`, `/etc/fail2ban` — только с подтверждения.
- Крупные операции (`apt upgrade`, `reboot`) — отдельное подтверждение.

## Sensitivities
- Токены и ключи заменять на `***`.
- Не выводить содержимое `/etc/shadow` или `/root/.ssh/id_*`.
- Не менять ssh port без подтверждения.

## Slack time
- Тихий режим: 22:00–08:00 MSK.
- В нерабочее время шлём только 🚨 алерты.
```

Пояснения:
  • Этот USER.md короче, потому что профиль операционный —
    контекст про вас минимальный, всё остальное уже в SOUL.md.
  • Operations — специфика профиля: что считается опасной
    операцией. Не рестартить всё подряд.
  • Sensitivities — снова про безопасность. «Не выводить
    `/etc/shadow`» — конкретное правило.
  • Slack time — для cron-уведомлений и gateway.

Это USER.md для служебного профиля, поэтому он сухой и фактологичный.
Тот же человек как «пользователь» в default будет иметь гораздо
более широкий USER.md.

────────────────────────────────────────────────────────────────────────────
6. ЛУЧШИЕ ПРАКТИКИ
────────────────────────────────────────────────────────────────────────────

6.1. Одна запись = один факт о вас.
   ПЛОХО: «Я живу в Москве, работаю DevOps, люблю короткие
          ответы, у меня GitHub kuznetsovrost-svg, читаю
          OpenNet, не люблю юмор в гайдах».
   ЛУЧШЕ:
     - «Город: Москва».
     - «Роль: DevOps».
     - «Стиль: короткие ответы».
     - «GitHub: kuznetsovrost-svg».
     - «Источники: opennet.ru, lwn.net».
     - «Без юмора в гайдах».

6.2. Конкретика > обобщение.
   ПЛОХО: «Не светить токены».
   ЛУЧШЕ: «Токены и ключи заменять на `***`. Особенно `Bearer ...`,
           `ANTHROPIC_*=...`, `TELEGRAM_BOT_TOKEN=...`».

6.3. Избегайте «информационного шума».
   Не пишите то, что модель легко выводит из контекста. USER.md —
   для **долгосрочных, стабильных** фактов.

6.4. Обновляйте при смене контекста.
   Переехали в другой город — TZ в USER.md. Сменили работу — роль.
   Удалять не обязательно; допишите новую строку с датой.

6.5. Не дублируйте с SOUL.md и MEMORY.md.
   «Не использовать Markdown-таблицы» — это правило стиля (SOUL).
   «Читать OpenNet» — это ваша привычка (USER).
   «OpenNet — в whitelist источников» — это про профиль (MEMORY).
   Чёткое разделение помогает всем файлам оставаться чистыми.

6.6. Используйте «на мягких правах» для рискованных действий.
   ПЛОХО: «Нельзя делать X».
   ЛУЧШЕ: «X — только с подтверждением» (открывает дверь для
   workflow с подтверждением).

6.7. Чувствительность — отдельным разделом.
   В Security-чувствительных профилях раздел Sensitivities лучше
   держать отдельно и группировать по доменам (SSH, секреты,
   API, FS).

6.8. Используйте «связанные файлы».
   Если в MEMORY.md есть нужный список, в USER.md можно написать
   «проекты см. в MEMORY.md → раздел Проекты».

────────────────────────────────────────────────────────────────────────────
7. ЧАСТНЫЕ СЛУЧАИ
────────────────────────────────────────────────────────────────────────────

7.1. Несколько профилей — разные USER.md?
   Да. USER.md привязан к профилю.
   • `default` — общий, для всего.
   • `mi_mg_01` — тот же человек, но операции должны быть осторожными.
   • `code_reviewer` — тот же человек, но режим ревью.

   Если вы хотите единый профиль пользователя для нескольких
   профилей агента — это решается через общий memory-провайдер,
   см. §10. Но проще оставить разные USER.md.

7.2. Анонимный пользователь.
   Если по каким-то причинам не хотите, чтобы имя светился, можно
   «user» или псевдоним. Модель будет обращаться как «вы», и этого
   часто достаточно.

7.3. Семейный / рабочий аккаунт.
   Если несколько человек используют один профиль, USER.md пишется
   на всю команду. Модель будет общаться с «командой» или с тем, кто
   сейчас в чате (определяется по chat_id).

7.4. Пользователь меняет настроение.
   В USER.md — долгосрочные предпочтения. Если хотите «сегодня
   не хочу юмор», пишите в чат, не в USER.md.

────────────────────────────────────────────────────────────────────────────
8. КАК ПРОВЕРИТЬ, ЧТО USER.MD РАБОТАЕТ
────────────────────────────────────────────────────────────────────────────

8.1. Тест на «кто я?».
   Завершите сессию, начните новую. Спросите «как меня зовут?».
   Хороший USER.md → ответит с именем.
   Плохой → «не знаю, можно уточнить?» (и правильно сделает).

8.2. Тест на предпочтения.
   Спросите «как лучше мне отвечать — длинно или коротко?».
   Хороший → ответит в стиле USER.md (например, «короткие»).
   Плохой → стандартный рекомендательный ответ.

8.3. Тест на запрет.
   Попросите показать свой GitHub токен. Хороший USER.md →
   «у меня в USER.md такого нет / не хранится».
   Плохой → начнёт искать в .env (что правильно для поиска, но
   лучше сначала свериться с USER.md).

8.4. Тест на «не помнить лишнего».
   Спросите «где я сейчас живу?». Если в USER.md этого нет →
   «не знаю». Хорошая память; плохая — выдумка.

────────────────────────────────────────────────────────────────────────────
9. КОМАНДЫ HERMES ДЛЯ РАБОТЫ С USER.MD
────────────────────────────────────────────────────────────────────────────

  $ hermes --profile=<name> memory status
    Покажет размеры MEMORY.md и USER.md (отдельно).

  $ hermes --profile=<name> memory list --target=user
    Показать все записи в USER.md.

  $ hermes --profile=<name> memory write --target=user "факт"
    Добавить запись.

  $ hermes --profile=<name> memory update <id> --text "новый"
    Обновить запись.

  $ hermes --profile=<name> memory delete <id>
    Удалить запись.

  $ hermes --profile=<name> memory reset user
    ⚠ Удалить USER.md целиком.

  $ hermes --profile=<name> memory search --target=user "запрос"
    Поиск (если memory-провайдер поддерживает).

────────────────────────────────────────────────────────────────────────────
10. АЛЬТЕРНАТИВНЫЕ MEMORY-ПРОВАЙДЕРЫ
────────────────────────────────────────────────────────────────────────────

10.1. Когда выбирать провайдера только для USER.md.
   Встроенная память USER.md ограничена ~2200 chars на запись.
   Если нужно много данных (например, расписание на год),
   переходите на провайдера.

10.2. Какие провайдеры доступны в Hermes 2026.
   - mem0 — embeddings-based retrieval для фактов.
   - supermemory — быстрая векторная память.
   - retaindb — графовая память (хорошо для связей).
   - honcho — сессионная семантика.
   - openviking — мультимодальная память.
   - holographic — sparse distributed representations.
   - byterover — простой key-value.

10.3. Когда НЕ надо.
   - Один USER.md на профиль, < 4 КБ текста.
   - Если предпочитаете git-friendly plain-text.
   - Если хотите переносить USER.md руками между машинами.

10.4. Как переключить.
   $ hermes memory setup
   Запустит визард, где можно выбрать провайдера для обоих файлов
   (memory + user) или только для одного.

────────────────────────────────────────────────────────────────────────────
11. ЧАСТЫЕ ОШИБКИ
────────────────────────────────────────────────────────────────────────────

11.1. Положили токен в USER.md.
   → revoke токена немедленно, удалите запись.

11.2. USER.md раздулся до 50 КБ.
   → пора чистить; вынесите проектные факты в MEMORY.md, лишние —
      удалите.

11.3. USER.md конфликтует с SOUL.md.
   → Разведите: «не использовать Markdown-таблицы» = SOUL,
     «я люблю короткие ответы» = USER.

11.4. Модель «забывает» предпочтения.
   → Возможно, профиль использует memory-провайдера без
      USER.md. Проверьте `hermes memory status`.

11.5. USER.md слишком «романтичный».
   → Удалите всё, что не влияет на работу. USER.md = факты, не
      биография.

11.6. Модель противоречит тому, что в USER.md.
   → Возможно, USER.md слишком старый. Обновите или почистите.

11.7. Запомнили PII без разрешения.
   → Сотрите запись. Если есть сомнения — не запоминайте.

11.8. USER.md не отличается между профилями.
   → Это by design, если вы хотите одного и того же «пользователя»
      везде. Иначе — разные USER.md.

────────────────────────────────────────────────────────────────────────────
12. ЧЕКЛИСТ «ХОРОШАЯ USER.MD»
────────────────────────────────────────────────────────────────────────────

Перед продакшен-использованием профиля:

  □ Размер < 4 КБ (можно больше, но следите за расходом)?
  □ Нет токенов / ключей / паролей / PII?
  □ Нет дублей с SOUL.md и MEMORY.md?
  □ Есть раздел Identity (имя, контакт, роль)?
  □ Есть раздел Communication (длина, стиль, эмодзи, обращение)?
  □ Есть раздел Sensitivities (что нельзя)?
  □ Конкретные правила (не «хорошо» а «≤ 800 символов»)?
  □ Код-блоки для имён и username?
  □ Дата, если пишете несколько строк об одном факте?
  □ Не противоречит ли другим профилям, если они должны быть
    согласованы?

────────────────────────────────────────────────────────────────────────────
13. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

USER.md — это самый короткий из трёх файлов идентичности (SOUL, MEMORY,
USER), но часто самый полезный для персонализации.

SOUL = «кто агент».
MEMORY = «что вокруг».
USER = «с кем агент разговаривает».

Когда USER.md хорошо прописан, агент ведёт себя как коллега, который
помнит ваш стиль, имя, привычки. Без него — как случайный прохожий.

Главное правило: **USER.md — это про вас, не про проект**. Если пишете
про инфраструктуру — это в MEMORY. Если про роль агента — это в SOUL.
USER.md — только то, что лично о вас.
