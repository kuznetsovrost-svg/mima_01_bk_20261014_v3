# SKILL.md и MEMORY.md на русском языке — можно ли, зачем, и с какими оговорками
## Гайд на основе проверки исходного кода Hermes Agent

────────────────────────────────────────────────────────────────────────────
0. КОРОТКО
────────────────────────────────────────────────────────────────────────────

**Да, можно.** Проверил исходный код Hermes на этом хосте
(`/usr/local/lib/hermes-agent/`):

  • SKILL.md читается через `read_text(encoding="utf-8")` —
    любая Unicode-кодировка поддерживается.
  • YAML frontmatter парсится через `yaml.safe_load` — Python
    yaml модуль работает с любыми Unicode-значениями.
  • MEMORY.md / SOUL.md / USER.md — те же механизмы (UTF-8).
  • 20 000 chars cap считает **символы**, не байты, поэтому
    русский текст «стоит» столько же места, сколько английский.

**Но есть 5 нюансов**, которые важно знать. Эти нюансы — не
баги, а свойства платформы и модели.

────────────────────────────────────────────────────────────────────────────
1. ЧТО Я ВЫЯСНИЛ В КОДЕ HERMES
────────────────────────────────────────────────────────────────────────────

1.1. **Кодировка — UTF-8 по умолчанию**.

   Из `skills_hub.py:1447`:
   ```python
   skill_md = (path / "SKILL.md").read_text(encoding="utf-8")
   ```

   Это значит: файлы читаются как UTF-8, кириллица, диакритика,
   эмодзи — всё работает.

1.2. **YAML frontmatter — Unicode-friendly**.

   Из `skills_hub.py:1454`:
   ```python
   fm = yaml.safe_load(skill_md[3:match.start() + 3]) or {}
   ```

   `yaml.safe_load` корректно парсит любой UTF-8 текст.
   Например:
   ```yaml
   ---
   name: mima-g-01-операции
   description: Use when пользователь просит проверить состояние сервера mima_g_01.
   ---
   ```

   Это **валидный YAML** и Hermes загрузит этот skill.

1.3. **Cap 20 000 chars** (см. `tips.py:223`).

   "Context files are capped at 20,000 characters with smart
   head/tail truncation."

   ВАЖНО: это **символы** (Unicode code points), не байты.
   Кириллица в UTF-8 = 2 байта на символ, но лимит считается
   по символам. Это значит:
   - 20 000 символов кириллицы ≈ 40 КБ на диске.
   - 20 000 символов английского ≈ 20 КБ на диске.

   То есть **лимит справедлив для обоих языков**.

1.4. **Лимит модели на токены**.

   Модель (через API) видит токены, не символы. Кириллица в
   большинстве моделей токенизируется эффективнее, чем думают:
   - "Hello" — 1 токен.
   - "Привет" — 1 токен (для multilingual моделей).
   - "你好" — 2 токена.

   То есть **расход токенов на русский ≈ английский** в
   современных моделях (GPT-4o, Claude 3.5+, MiniMax).

1.5. **Default SOUL.md — английский**.

   Из system prompt Hermes (см. `default SOUL.md`):
   ```
   You are Hermes Agent, an intelligent AI assistant created by
   Nous Research. You are helpful, knowledgeable, and direct.
   ...
   ```

   Если вы **не замените** SOUL.md, модель будет считать себя
   англоязычным ассистентом. Но это легко изменить — пишите
   SOUL.md на русском, и модель переключится.

────────────────────────────────────────────────────────────────────────────
2. ПОЧЕМУ НА РУССКОМ — ДОПУСТИМО И ПОЛЕЗНО
────────────────────────────────────────────────────────────────────────────

2.1. **Язык пользователя = язык контекста**.

   Если вы общаетесь с агентом на русском, то и контекст-файлы
   должны быть на русском. Это:
   - Уменьшает «переключение контекста» модели.
   - Делает цитаты естественнее.
   - Снижает риск ложных переводов.

2.2. **Русский технический язык полноценен**.

   Терминология устоялась: репозиторий, коммит, ветка, шлюз,
   профиль, скилл, фронтенд, бэкенд. Англицизмы прижились.
   Модели их понимают.

2.3. **MEMORY.md на русском** — естественнее.

   Когда модель дописывает факты, она пишет в стиле общения.
   Если чат на русском — память тоже будет на русском.

2.4. **SOUL.md на русском** — задаёт личность.

   Можно прямо написать: «Вы — старший инженер. Говорите
   по-русски. Без подхалимства. Коротко. По делу.»

2.5. **SKILL.md на русском** — даёт конкретные инструкции.

   Когда скилл на русском, модель воспринимает инструкции
   буквально, без перевода. Это снижает шанс
   неверной интерпретации.

────────────────────────────────────────────────────────────────────────────
3. 5 НЮАНСОВ, КОТОРЫЕ НУЖНО УЧИТЫВАТЬ
────────────────────────────────────────────────────────────────────────────

3.1. **Description в frontmatter SKILL.md — лучше на английском**.

   Причина: описание используется как **триггер-загрузки**.
   Модель решает «грузить или нет» по совпадению слов в
   запросе пользователя с description.

   Если description на русском:
   - «Использовать, когда пользователь просит проверить
     состояние сервера.»
   - Модель будет триггериться только на русские запросы
     («проверь состояние», «что с сервером»).
   - Английский запрос "check server status" не загрузит
     skill.

   Если хотите **двуязычный триггер**, напишите description
   в frontmatter на английском, а тело скилла — на русском.
   Пример:

   ```yaml
   ---
   name: mima-g-01-ops
   description: Use when user asks to check / restart / audit mima_g_01 server,
     SSH into mima_g_01, проверить состояние сервера, рестарт gateway.
   ---
   # Mima_g_01 Operations (на русском)
   ...
   ```

   Это **валидный YAML** и лучший компромисс: модель
   триггерится на обоих языках.

3.2. **Примеры кода и команд — оставляйте на английском**.

   Команды, имена файлов, API-методы — всегда на английском.
   Даже если скилл на русском, примеры должны быть:

   ```bash
   ssh mima-g-01 'systemctl status hermes-gateway'
   ```

   а НЕ:

   ```bash
   ssh мима-г-01 'статус systemctl шлюза'
   ```

   Причина: команды Linux, имена методов, ключи API —
   **на английском по определению**. Русский перевод тут
   только запутает.

3.3. **Терминология — избегайте русского перевода для брендов**.

   - **Hermes**, **OpenAI**, **Anthropic**, **MiniMax** — бренды,
     не переводим.
   - **GitHub**, **GitLab**, **Bitbucket** — то же самое.
   - **Python**, **TypeScript**, **Rust** — языки, не переводим.
   - **Linux**, **Ubuntu**, **Docker** — не переводим.

   Перевод технических терминов «сервер-сервис» или «поток
   данных» — допустим. Перевод брендов — нет.

3.4. **YAML frontmatter не должен ломаться от кириллицы**.

   Вот что **нельзя**:

   ```yaml
   description: "Использовать
     когда нужно проверить
     состояние сервера."
   ```

   Тут YAML не сломается — multiline strings работают. Но
   **нельзя**:

   ```yaml
   name: имя с пробелами: и двоеточиями
   ```

   YAML интерпретирует `:` как разделитель. Кириллица
   работает, но **синтаксис YAML** — нет.

   Правило: **frontmatter — на английском, body — на русском**,
   и тогда проблем с YAML не будет.

3.5. **Markdown-таблицы в Telegram не рендерятся**.

   Это не про русский, а про платформу. Если вы пишете отчёт
   в results/, и он будет отправлен в Telegram, **не используйте
   таблицы**. Используйте списки. Иначе Telegram отобразит
   pipe-символы как текст.

────────────────────────────────────────────────────────────────────────────
4. СРАВНЕНИЕ: SKILL.md НА РУССКОМ vs АНГЛИЙСКОМ
────────────────────────────────────────────────────────────────────────────

  ┌────────────────────────┬────────────────────────┬──────────────────────┐
  │ Аспект                 │ Английский             │ Русский              │
  ├────────────────────────┼────────────────────────┼──────────────────────┤
  │ Триггеры (description) │ Работает для англо-    │ Только русские       │
  │                        │ язычных запросов       │ запросы              │
  │ Body (основной текст)  │ Одинаково              │ Одинаково            │
  │ Команды / код          │ Английский (как есть)   │ Английский (как есть)│
  │ Технические термины    │ Английский             │ Можно по-русски,     │
  │                        │                        │ но бренды — англ.    │
  │ Токенизация            │ ~1 токен/слово         │ ~1-2 токена/слово    │
  │                        │                        │ (multilingual model) │
  │ Размер cap             │ 20 000 chars           │ 20 000 chars         │
  │ Поддержка Hermes       │ Нативно                │ Нативно (UTF-8)      │
  │ Модель читает как      │ Одинаково              │ Одинаково            │
  │ Стиль цитирования      │ Английские кавычки     │ «Русские ёлочки»     │
  │                        │ "..." или '...'        │ или "..."            │
  └────────────────────────┴────────────────────────┴──────────────────────┘

────────────────────────────────────────────────────────────────────────────
5. РЕКОМЕНДУЕМАЯ ПРАКТИКА
────────────────────────────────────────────────────────────────────────────

5.1. **SKILL.md — гибридный подход**.

   YAML frontmatter (description, tags, related_skills) — **на
   английском** для широкого триггера.

   Body (When to use, Step-by-step, Pitfalls, Verification) —
   **на русском**, если пользователь общается на русском.

   Код-блоки — **на английском** (команды, API).

   Комментарии в коде — **на русском**, если это полезно.

5.2. **MEMORY.md — полностью на русском**.

   MEMORY.md — это факты о мире, и они должны быть на языке
   пользователя. Модель сама дописывает в стиле чата.

5.3. **SOUL.md — на языке пользователя**.

   Если пользователь общается на русском, SOUL.md лучше на
   русском. Это задаёт личность и тон общения.

5.4. **USER.md — на языке пользователя**.

   USER.md — факты о человеке. На его языке.

5.5. **AGENTS.md — на языке команды**.

   AGENTS.md — проектный контекст. Если в команде все
   русскоязычные — на русском. Если мультиязычная — на
   английском (или двуязычный).

6. ПРИМЕР ГИБРИДНОГО SKILL.MD
────────────────────────────────────────────────────────────────────────────

```yaml
---
name: mima-g-01-ops
description: Use when user asks to check, restart, or audit the mima_g_01 server.
  Trigger: "проверь mima", "рестарт gateway", "audit ssh", "состояние сервера",
  "ssh mima-g-01", "/etc/ssh", "fail2ban", "ufw".
version: 0.1.0
author: Rost
license: MIT
platforms: linux
metadata:
  hermes:
    tags: [mima, server, ops, ssh, fail2ban]
    related_skills:
      - systematic-debugging
      - simplify-code
---

# Операции на mima_g_01

Скилл для работы с сервером mima_g_01 (`72.56.29.69`).

────────────────────────────────────────────────────────────────────────────
КОГДА ИСПОЛЬЗОВАТЬ
────────────────────────────────────────────────────────────────────────────

Триггер-слова:
  - "проверь mima", "состояние сервера"
  - "рестарт gateway", "перезапусти шлюз"
  - "audit ssh", "fail2ban status"
  - "что с логами", "посмотри логи"
  - "ssh на mima"

Не использовать:
  - если задача про другой сервер;
  - если задача — программирование, а не ops.

────────────────────────────────────────────────────────────────────────────
ШАГИ
────────────────────────────────────────────────────────────────────────────

1. SSH через alias `mima-g-01`:

   ```bash
   ssh mima-g-01 'uptime; df -h /; free -h'
   ```

2. Проверить gateway:

   ```bash
   ssh mima-g-01 \
     'XDG_RUNTIME_DIR=/run/user/0 \
      systemctl --user status hermes-gateway.service'
   ```

3. Если нужно рестарт — **ТОЛЬКО С ПОДТВЕРЖДЕНИЯ**:

   ```bash
   ssh mima-g-01 \
     'XDG_RUNTIME_DIR=/run/user/0 \
      systemctl --user restart hermes-gateway.service'
   ```

4. Логи:

   ```bash
   journalctl --user -u hermes-gateway.service -n 50
   ```

────────────────────────────────────────────────────────────────────────────
PITFALLS
────────────────────────────────────────────────────────────────────────────

1. **Всегда `XDG_RUNTIME_DIR=/run/user/0`** для `systemctl --user`
   по SSH. Без этого `systemctl` не найдёт user-bus.
2. **Не `kill -9`** процесс gateway — пусть systemd управляет.
3. **Не `apt upgrade`** без явного подтверждения пользователя.
4. **Не выводить `/etc/shadow`** — токены утекают.
5. **Не показывать `id_*` keys** — это приватные ключи.

────────────────────────────────────────────────────────────────────────────
VERIFICATION
────────────────────────────────────────────────────────────────────────────

После операции проверить:

  □ SSH соединение установлено.
  □ Команды выполнены без ошибок.
  □ Если был restart — `journalctl` показал `Started
    hermes-gateway.service`.
  □ Если audit — `fail2ban-client status sshd` показал баны.
  □ Пользователь подтвердил результат.
```

**Что в этом примере правильно:**

- Description (триггер) — на английском с русскими триггер-словами.
- Body — на русском.
- Код-блоки — на английском (команды, API, пути).
- Pitfalls — на русском, с английскими техническими терминами в нужных местах.

8. ПРИМЕР SOUL.MD НА РУССКОМ
────────────────────────────────────────────────────────────────────────────

```markdown
# Personality

Вы — прагматичный старший инженер. У вас сильный вкус.
Вы оптимизируете под истину, ясность и полезность, а не
под вежливость.

## Стиль
- Будьте прямым, но не холодным.
- Предпочитайте суть подкладке.
- Возражайте, когда идея плохая.
- Признавайте неопределённость прямо.
- Держите объяснения компактными, если глубина не нужна.

## Чего избегать
- Подхалимства.
- Хайповых формулировок.
- Повторения формулировки пользователя, если она неверна.
- Переобъяснения очевидного.

## Техническая позиция
- Простые системы > умные системы.
- Заботьтесь об операционной реальности, а не идеализированной
  архитектуре.
- Edge cases — часть дизайна, а не уборка.

## Язык
- Русский для общения, английский для технических терминов.
- Без эмодзи как украшений. Severity-маркеры (🚨⚠️✅) — ок.

## Defaults
- Длина: 2-4 параграфа для коротких ответов, длиннее — если нужна
  глубина.
- Код — в fenced-блоках.
- При неопределённости — спросить перед тем, как предполагать.
```

**Что в этом примере правильно:**

- Полностью на русском, с混入ом английских технических слов.
- Структура и стиль — соответствуют официальным рекомендациям
  Hermes (см. `personality.md`).
- Модель подхватит эту личность.

────────────────────────────────────────────────────────────────────────────
9. ЧАСТЫЕ ОШИБКИ ПРИ РУССКОМ ЯЗЫКЕ
────────────────────────────────────────────────────────────────────────────

9.1. **YAML frontmatter на русском с переносами**.

   ПЛОХО:
   ```yaml
   description: Использовать
     когда пользователь
     просит проверить состояние.
   ```

   ЛУЧШЕ:
   ```yaml
   description: "Use when user asks to check status. Использовать
     когда пользователь просит проверить состояние."
   ```

   Или хотя бы без переноса строк (в одну строку с пробелами).

9.2. **Триггер в description только на русском**.

   ПЛОХО:
   ```yaml
   description: Использовать когда пользователь просит проверить состояние.
   ```

   ЛУЧШЕ:
   ```yaml
   description: Use when user asks to check / audit / restart a server.
     Триггеры: "проверь сервер", "состояние", "audit", "рестарт".
   ```

9.3. **Перевод команд Linux**.

   ПЛОХО:
   ```bash
   список-файлов
   ```

   ЛУЧШЕ:
   ```bash
   ls -la
   ```

9.4. **Markdown-таблицы для Telegram**.

   ПЛОХО:
   ```markdown
   | Сервер | Состояние |
   |--------|-----------|
   | mima   | OK        |
   ```

   Telegram отобразит как текст, не как таблицу.

   ЛУЧШЕ:
   ```markdown
   - mima: OK
   - myapp: degraded
   ```

9.5. **Бренды в русской транслитерации**.

   ПЛОХО: «Гитхаб», «Телграм», «Линукс».
   ЛУЧШЕ: «GitHub», «Telegram», «Linux».

9.6. **Смешивание языков в одной фразе без перехода**.

   ПЛОХО: «Проверь шлюз и restart the systemd service.»
   ЛУЧШЕ: «Проверь шлюз и перезапусти systemd-сервис.»
   ИЛИ: «Check gateway and restart systemd service.»

9.7. **Слишком много эмодзи как украшение**.

   ПЛОХО:
   ```markdown
   🚀 Задача: 🎯 проверить 📊 состояние 🌟 сервера 🚀
   ```

   ЛУЧШЕ:
   ```markdown
   Задача: проверить состояние сервера.
   ```

9.8. **Длинные русские термины без сокращений**.

   ПЛОХО: «административный интерфейс управления конфигурацией».
   ЛУЧШЕ: «config UI», «настройки», «config panel».

────────────────────────────────────────────────────────────────────────────
10. КОГДА РУССКИЙ НЕ ПОДХОДИТ
────────────────────────────────────────────────────────────────────────────

10.1. **Skill для международной команды**.

   Если скилл будут использовать англоязычные коллеги, лучше
   весь скилл на английском. Иначе будет барьер входа.

10.2. **Skill для публичного распространения**.

   Если вы публикуете скилл в GitHub-репо для сообщества,
   лучше английский. Больше потенциальных пользователей.

10.3. **Skill с API международных сервисов**.

   Если работаете с OpenAI, Anthropic, GitHub — лучше
   английский для команд и параметров.

10.4. **Чисто технический справочник**.

   Для PEP-спецификаций, RFC, RFC Python — английский обязателен.

10.5. **Универсальные шаблоны**.

   Если вы хотите использовать скилл с разными моделями и
   провайдерами — лучше английский, чтобы любая модель
   правильно интерпретировала триггеры.

────────────────────────────────────────────────────────────────────────────
11. РЕКОМЕНДУЕМАЯ КОНФИГУРАЦИЯ ДЛЯ РОСТ
────────────────────────────────────────────────────────────────────────────

На основе ваших предпочтений (русский язык, terse responses,
markdown-таблицы не рендерятся в Telegram):

11.1. **SOUL.md**: на русском, с указанием стиля и языка.

11.2. **USER.md**: на русском, про вас.

11.3. **MEMORY.md**: на русском, факты о мире/инфраструктуре.

11.4. **AGENTS.md**: на русском (проектный контекст).

11.5. **SKILL.md**: гибрид — frontmatter на английском (для
   триггеров на обоих языках), body на русском, код-блоки
   на английском.

11.6. **TASK.md / plans/<id>.md**: на русском.

11.7. **results/<id>/**: на русском (markdown), но технические
   файлы (CSV, JSON) — в стандартных форматах с английскими
   ключами.

────────────────────────────────────────────────────────────────────────────
12. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

**SKILL.md и MEMORY.md на русском — допустимо и полезно**, если:

  1. **YAML frontmatter — на английском** (или с русскими
     триггерами в description).
  2. **Body — на русском**, если пользователь русскоязычный.
  3. **Команды и код — на английском** (как есть в системе).
  4. **Бренды и языки программирования — не переводим**.
  5. **Технические термины — можно по-русски**, но аккуратно.

**Гибридный подход** — лучший: frontmatter на английском (для
триггеров), body на русском (для пользователя), код на
английском (для системы).

Hermes **нативно поддерживает UTF-8** для всех context-файлов.
Ограничений по языку в коде нет. Это значит, что русский —
не проблема, а естественный выбор для русскоязычного
пользователя.

Если вы работаете с проектом и ваша команда говорит по-русски,
**пишите контекст-файлы на русском**. Это сделает работу
агента прозрачнее и предсказуемее.
