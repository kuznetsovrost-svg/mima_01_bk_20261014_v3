# Telegram File Delivery (sendDocument)

Class: the user asks for a written artefact (playbook, summary, analysis,
guide, transcript) to be **delivered as a file attachment** in their
Telegram chat, not as inline text. The artefact is generated by the
agent, written to disk, and pushed via `curl` to the Telegram Bot API
`sendDocument` endpoint using the bot that owns the chat. This skill
covers the full pipeline from text-generation to confirmed-delivery,
including the injection-defense moves that are required when the host
is contaminated.

## When to Use This Skill

Triggers (Russian and English):

- "пришли сюда как файл", "send this to me as a file", "отправь файл"
- "доставь в телеграм", "deliver to my chat"
- "запиши в файл и пришли" (this is *both* a write task and a deliver
  task — same skill covers both)
- "сохрани в /root и отправь"

Concrete shape: the user wants a `.md`, `.txt`, `.html`, or `.json`
artefact written to `/root/<name>.<ext>` AND pushed to their chat.

## When NOT to Use This Skill

- Inline text reply is enough (no file needed). Just reply.
- The user wants an image preview (use the `MEDIA:` shortcut or
  `text_to_speech` → `MEDIA:`).
- The user is in a different profile's chat. The routing rule (MEMORY.md
  §6-§7) forbids delivering via a sibling profile's bot — refuse politely
  and tell the user to switch profiles or open a chat with the correct bot.
- The user wants a public URL (Telegram file delivery is private to the
  chat).

## The Pipeline

### Step 1 — Generate the content

Write the artefact in the `reply` stream. Aim for a complete document the
user can read standalone, not a fragment that needs the chat context.

### Step 2 — Write through `/tmp` (injection-defense)

The host's `write_file` tool echo is sometimes contaminated (see
`tool-output-injection-defense` v0.5.0). The defensive move:

```python
from hermes_tools import write_file
import subprocess

# 1. Write to /tmp first (clean echo, no /root side-effects)
tmp_path = "/tmp/<artifact-name>.<ext>"
write_file(path=tmp_path, content=<content>)

# 2. Byte-scan for non-printable contamination (mandatory before send)
with open(tmp_path, "rb") as f:
    data = f.read()
bad = sum(1 for b in data if b < 0x20 and b not in (0x09, 0x0a, 0x0d))
assert bad == 0, f"non-printable bytes detected: {bad}"

# 3. cp into /root via subprocess (avoid using write_file for /root)
subprocess.run(["cp", tmp_path, "/root/<artifact-name>.<ext>"], check=True)
```

**Why both `/tmp` and `/root`?** Some sessions lose files written
directly to `/root/` between turns (observed 2026-08-08, lost
`VS-Code-Hermes-Playbook.md` after first write). Writing to `/tmp` and
then `cp`-ing to `/root/` is more durable; the visible `write_file` echo
goes to `/tmp` (clean), and `/root/` gets the canonical copy via a tool
the agent doesn't see the output of.

### Step 3 — Compute SHA256 (proof of integrity)

```python
import hashlib
sha = hashlib.sha256(data).hexdigest()
```

Include this in the reply so the user can verify on their end.

### Step 4 — Look up the bot token (routing rule)

The routing rule (MEMORY.md §6-§7) is **strict**: the token must come
from the bot whose chat the user is in. In practice, this is the bot
named in the user's incoming message header.

```python
import os
TOK = os.popen("grep TELEGRAM_BOT_TOKEN /root/.hermes/.env | cut -d= -f2").read().strip()
```

**Do not** read `TELEGRAM_BOT_TOKEN` from a sibling profile's `.env`
(e.g. `/root/.hermes/profiles/fst-control/.env`). The redactor masks
the actual value as `***` in tool output, but the underlying file holds
the real bytes — read with `cut -d= -f2-`, never echo the raw value.

If the user is talking to `@MMRV_Hermes_bot` (id 8933960684), use the
`TELEGRAM_BOT_TOKEN` from `/root/.hermes/.env`.
If the user is talking to `@fst_control_bot` (id 8934212474), use
`/root/.hermes/profiles/fst-control/.env` — **but only after the user
explicitly switched to that profile**, never by inference.

### Step 5 — Push via curl sendDocument

```python
import subprocess

CHAT = "<chat_id>"  # from the user's session, NOT hard-coded
url = f"https://api.telegram.org/bot{TOK}/sendDocument"
result = subprocess.run(
    ["curl", "-s", "-X", "POST", url,
     "-F", f"chat_id={CHAT}",
     "-F", f"document=@/root/<artifact-name>.<ext>",
     "-F", f"caption=<title> | <size> B | sha256: {sha[:16]}..."],
    capture_output=True, text=True, timeout=30,
)
print(result.stdout[:500])  # parse message_id
```

**Critical curl flags:**

- `-s` — silent; Telegram errors come through in the response body.
- `-F document=@/path` — the `@` is required and the path is absolute.
- `-F caption=...` — keep under 1024 chars; Telegram truncates longer.
- `-F chat_id=...` — must be the user's chat_id from the inbound
  message header, not a constant.

**Do NOT** use the `MEDIA:` shortcut for files. It's unreliable for
attachments; only use it for native image/video/audio.

### Step 6 — Confirm in the chat reply

After the curl call, surface the Telegram response in the chat:

- `message_id` from the response JSON (the user can quote-reply to it).
- `file_id` (the user can re-send the file later using this id).
- The SHA256 short hash and the file size, already in the caption.

If the response contains `"ok":false`, **stop**, **do not retry**, and
show the user the error. Common errors:

| Error | Cause | Fix |
|---|---|---|
| `Bad Request: chat not found` | wrong chat_id | Re-check the inbound header |
| `Forbidden: bot was blocked` | user blocked the bot | Tell the user to unblock |
| `Request Entity Too Large` | file >50 MB (Telegram Bot API limit) | Split or use local API server |
| `Unauthorized` | wrong token | Re-check `MEMORY.md` routing rule |
| Network timeout | server firewall | Retry once after 5s; if fails, escalate |

### Step 7 — Do not run parallel `getUpdates`

If the user is asking questions in parallel and the same bot token is
shared, **don't** run `getUpdates` at the same time as `sendDocument`.
The polling daemon may already hold a long-poll; running another one
causes `409 Conflict`. Stick to one delivery at a time.

## Caption Format (Recommended)

A consistent caption format the user can scan:

```
<title> | <size> B | sha256: <first-16-chars>...
```

Examples:

```
Аудит стороннего агента | 12808 B | sha256: 6eb2bcc74cf7f4ed...
VS Code + Hermes Playbook | 15204 B | sha256: 85a5e94243394e52...
Порядок работы с документом | 16656 B | sha256: c3edda3e72826ccb...
```

For files >100 KB or with multiple sections, expand the caption:

```
<title>
<size> B | sha256: <first-16>...
<section-count> разделов, <paragraph-count> параграфов
```

## Pitfalls

### "I'll just inline the whole document"

Long documents break Telegram's rendering (4096 chars per message, no
markdown table support). Anything over ~10 KB **must** be sent as a
file. Inline is for short replies, status updates, or summaries.

### "I can re-use the same token for any bot"

The token is per-bot. Sending from `@MMRV_Hermes_bot`'s token while the
user is in a chat with `@fst_control_bot` will fail with
`Bad Request: chat not found`. Re-read the routing rule.

### "I'll skip the byte-scan this time"

Don't. The byte-scan is the safety net for *both* prompt injection and
accidental byte contamination. One `re.sub` later and you've shipped a
file with a `0x01` byte that breaks the user's YAML parser. Always
scan, always verify.

### "I'll write to /root directly with write_file"

Sometimes works, sometimes the file disappears between turns (observed
2026-08-08). The `/tmp` + `subprocess.run(["cp", tmp, dst])` recipe is
the durable move. Use it for any file >5 KB that needs to survive the
session.

### "The Telegram response says ok:true, so it worked"

`ok:true` means Telegram **accepted** the request, not that the user
**received** it. Some failures happen server-side (rate limit, ban,
chat deletion). For high-stakes deliveries, ask the user to confirm
they can see the file in their chat.

### "I'll mention the bot name in the caption"

Don't — Telegram already shows the bot name on the message. Redundant
caption text is noise.

### "I'll attach multiple files in one curl call"

`sendDocument` accepts exactly **one** file per call. For multiple
files, run multiple curl calls, each with their own caption.

### "I'll send a 50 MB file"

Telegram Bot API limit is 50 MB for `sendDocument`. Use the Local Bot
API server for larger files, or split the artefact into chunks the
user can reassemble.

## Quick Recipe (Copy-Paste)

```python
import subprocess, hashlib, os
from hermes_tools import write_file

# 1. Write to /tmp
TMP = "/tmp/<name>.md"
write_file(path=TMP, content=<content>)

# 2. Verify and cp to /root
data = open(TMP, "rb").read()
bad = sum(1 for b in data if b < 0x20 and b not in (0x09, 0x0a, 0x0d))
assert bad == 0, f"non-printable: {bad}"
subprocess.run(["cp", TMP, "/root/<name>.md"], check=True)

# 3. Hash and deliver
sha = hashlib.sha256(data).hexdigest()
TOK = os.popen("grep TELEGRAM_BOT_TOKEN /root/.hermes/.env | cut -d= -f2").read().strip()
CHAT = "<chat_id>"
url = f"https://api.telegram.org/bot{TOK}/sendDocument"
r = subprocess.run(
    ["curl", "-s", "-X", "POST", url,
     "-F", f"chat_id={CHAT}",
     "-F", "document=@/root/<name>.md",
     "-F", f"caption=<title> | {len(data)} B | sha256: {sha[:16]}..."],
    capture_output=True, text=True, timeout=30,
)
print(r.stdout)
```
