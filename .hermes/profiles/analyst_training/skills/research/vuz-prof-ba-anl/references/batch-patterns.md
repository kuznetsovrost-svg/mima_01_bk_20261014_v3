# Batch execution patterns

Когда задача требует прогнать skill по N>1 файлам из Inputs (типично: сравнение нескольких программ, батч-аудит курсов), применяй следующие паттерны. Основано на задаче `TASK-2026-07-15-SPA` (5 программ МИРЭА, академический анализ).

## Требования заказчика (типичные)

Заказчик почти всегда требует в task-файле:

- **Последовательность** — файлы анализируются по очереди, один за другим. Параллельный батч через `delegate_task` НЕ применять: выводы одного файла могут «затечь» в другой.
- **Изоляция контекста** — «не смешивать результаты одного файла с другим». Перед началом каждого файла начинай с чистого листа, не ссылайся на предыдущие выводы в §3/§4/§6.
- **Независимая оценка** — каждый отчёт пишется как единственный в своём роде. Сравнение нескольких программ — отдельная финальная секция (см. ниже), а не внутри каждого отчёта.

## Структура артефактов задачи

```
<profile_dir>/projects/<slug>/
├── Inputs/                      ← уже лежат
├── Outputs/
│   └── results/<TASK-ID>/
│       ├── SANL_<input1>.md
│       ├── SANL_<input2>.md
│       └── ...
├── progress.json                ← состояние per-file + overall
├── plans/<TASK-ID>.md           ← синхронизируется со статусом
└── tasks/<TASK-ID>.md           ← спецификация задачи
```

Префикс `SANL_` — это соглашение, принятое в `TASK-2026-07-15-SPA` (Simple ANalysis). Если заказчик не указал префикс — используй `-report.md` (как в `references/project-layout.md`).

## Шаблон progress.json

```json
{
  "task_id": "TASK-...",
  "state": "draft|in_progress|done",
  "per_file_status": {
    "<input-file>": {
      "state": "pending|in_progress|done",
      "started_at": "<ISO>",
      "finished_at": "<ISO>",
      "report_path": "Outputs/results/<TASK-ID>/SANL_<input>.md"
    }
  },
  "overall": {"state": "...", "started_at": "...", "finished_at": "..."},
  "token_budget_estimate": 80000,
  "wall_clock_budget_seconds": 600
}
```

Перед каждым файлом:
1. `per_file_status[<file>].state = "in_progress"`, заполнить `started_at`.
2. После записи отчёта — `"done"`, `finished_at`, `report_path`.
3. После последнего файла — `overall.state = "done"`.

## Шаблонные фразы для plan-файла

План в `plans/<TASK-ID>.md` должен явно содержать:
- «Для каждого файла из Inputs в указанном порядке»
- «Не смешивать с другими файлами. Анализировать независимо»
- «Если данных не хватает — записывать "трудно оценить" с указанием, чего не хватает»
- «После всех N файлов — обновить progress.json.overall и этот plan»

## Бюджет токенов — реалистичная оценка

Один отчёт по §1–§10 с 25+ ссылками — **~15–25k токенов** вывода (доминирует §7–§9 со ссылками). Для N файлов:

| N | Реалистичный бюджет |
|---|---|
| 1 файл | 20–30k |
| 5 файлов | 75–120k |
| 10 файлов | 150–250k |

**Заявленный бюджет в task ≤ 3000 — нереалистичен.** Если заказчик требует уложиться в жёсткий бюджет — сократи §7–§9 (меньше предметов или без ссылок) и зафиксируй это в task-файле.

## Финальный сравнительный раздел

Если цель задачи — выбор «наилучшей» программы из N — добавь **в последний отчёт** (не в каждый) секцию «Сравнительный анализ»:

```
## 🏆 СРАВНИТЕЛЬНЫЙ АНАЛИЗ ВСЕХ N ПРОГРАММ
| Программа | Мат. база | AI/ML | Software eng | AI-агенты | Практики | ИТОГО |
| №1 ...   | 8        | 5     | 7            | 2         | 6        | 28/50 |
| №2 ...   | 7        | 9     | 5            | 1         | 5        | 27/50 |
...
```

Рекомендация — одна программа-победитель + обязательное «доучивание вне программы» по тому, что выпало.

## Pitfalls при батче

- ❌ Писать отчёты параллельно через `delegate_task` — приводит к потере изоляции контекста между файлами.
- ❌ Использовать «общую» секцию профессий/практик для всех файлов — заказчик требует независимого анализа.
- ❌ Копировать ссылки из отчёта №1 в отчёт №2 «для полноты» — нарушает правило «не смешивать».
- ✅ Делать последовательно, в одном проходе, с обновлением progress.json между файлами.

## Полезные SQL-снипеты

Получить список проектов профиля:
```sql
SELECT id, slug, name, primary_path FROM projects WHERE archived = 0;
```

Получить активный проект:
```sql
SELECT value FROM project_meta WHERE key = 'active_id';
```

Создать новый проект (если заказчик просит):
```sql
INSERT INTO projects (id, slug, name, created_at, archived)
VALUES ('p_<hash>', '<slug>', '<slug>', <unix_ts>, 0);
UPDATE project_meta SET value='p_<hash>' WHERE key='active_id';
```
