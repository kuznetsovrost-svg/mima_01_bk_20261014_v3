## 0. Обзор

Секция «Показатели проекта» — новая секция отчёта (после секции #5 «Актуальность прогнозов»). Состоит из **16 фиксированных подпунктов** (индикаторов).

### 0.1. Структура подпункта

Каждый подпункт имеет:

| Поле | Описание |
|------|----------|
| **Префикс** | `6.N` (например, `6.1`, `6.2` и т.д.) |
| **Название** | Краткое, на русском |
| **Результат** | `Да` / `Нет` / `Да/Нет с деталями` |
| **Детализация** | Краткое описание (1 строка) |
| **Вердикт** | `Норма` / `Информационное` / `Существенное` / `Критическое` |
| **Раскрывающаяся таблица** | Опционально, вложенность 3-го уровня |

### 0.2. Вердикты

Каждый подпункт имеет **свой вердикт**:
- `Норма` — пункт в порядке, проблем нет
- `Информационное` — есть информация, не требует действий
- `Существенное` — требует внимания
- `Критическое` — требует немедленных действий

**Вердикт секции** = агрегат по подпунктам:
- `Критическое` если есть хотя бы 1 критический
- `Существенное` если есть хотя бы 1 существенный (но нет критических)
- `Информационное` если есть хотя бы 1 информационный
- `Норма` если все норма

**Вердикт проекта** (как и сейчас) — агрегат по секциям.

## 1. Структура скриптов

```
scripts/
├── project_indicators.py            ← все 16 функций-индикаторов
├── <thing>_thresholds.py            ← отдельный файл порогов на КАЖДЫЙ индикатор (Pitfall #116)
├── lc_stage_kt_registry.py          ← справочник обязательных КТ (для 6.2)
├── point_states.py                  ← справочник состояний КТ (для 6.2)
├── vat_constants.py                 ← справочник ставки НДС (для 6.12)
├── vat_calc.py                      ← формулы расчёта НДС (для 6.12)
├── mcp_config.py                     ← get_project_property() + get_project_card() (6.13)
└── ...
```

### 1.1. `project_indicators.py`

Каждая функция имеет:
- **Сигнатуру**: `def check_<name>(project: dict, sid, ...) -> IndicatorResult`
- **Docstring** с кратким описанием (Назначение / Получение / Интерпретация / Вывод)
- **Возвращает** `IndicatorResult` с полями:
  - `result: str` («Да» / «Нет» / `"-"` / конкатенированная строка)
  - `detail: str` (краткое описание)
  - `verdict: str` (`Норма` / `Информационное` / `Существенное` / `Критическое`)
  - `table: Optional[List[Dict]]` — данные для раскрывающейся таблицы (или None)

### 1.2. `<thing>_thresholds.py`

Один файл на индикатор (Pitfall #116). Содержит:
- `INDICATOR_THRESHOLDS = {"6.X_<name>": {...}}` — config + lambda predicates.
- `interpret_indicator(key, result_value, detail)` — вычисление вердикта.
- `classify_<thing>(value, cfg)` — классификация (если numeric).
- `format_<thing>(value)` — форматирование для колонки "Результат" (если нужно).

### 1.3. `vat_constants.py` и `vat_calc.py`

Отдельные файлы для налоговой логики (Pitfall #128):
- `vat_constants.py` — справочные значения (ставка, допуск)
- `vat_calc.py` — формулы (`calculate_vat_from_total`, `calculate_vat_rate`, `pick_amount_by_priority`)

### 1.4. `mcp_config.py` — get_project_property / get_project_card

Хелперы для оптимизации (Pitfall #140, #141):
- `get_project_property(sid, project_id, property_name)` — одно свойство.
- `get_project_card(sid, project_id, project_code=None)` — все свойства + кеш 5 мин.

## 4. Подпункты — детальная спецификация

### 6.13 — Бюджет проекта/пресейла ✅ done (2026-09-03)

**Назначение:** Отобразить установленный бюджет проекта, пресейла и % пресейла от бюджета.
**Получение:** `get_entity_data(Project, data_id)` → `ProjectBudgetGrade`, `PresaleLimit`, `PresaleBudgetPercentage`, `DirectProjectCostsGrade`, `ProjectLimit`.
**Интерпретация:** Вердикт всегда нейтральный (информационный индикатор).
**Вывод:** `{Сумма проекта:N руб./Пресейл:M руб./Лимит %:Y}` (без запятой между `:` и числом, Pitfall #149).
**Скрипт:** `check_budget_limits` (через `get_project_property` в `mcp_config.py`).
**Live-probe 504-595:** `Сумма проекта:54 000 000 руб./Пресейл:2 700 000 руб./Лимит %:5.0` (лимит = 5% бюджета).

### 6.14 — Расход лимита пресейла ✅ done (2026-09-03)

**Назначение:** Контроль расхода лимита пресейла. Если лимит превышен — информация для руководства.
**Получение:** A = `PresaleLimit` (get_entity_data). B = Σ расходов с меткой "Пресейл" из `ProjectBudgetCompleteBusiness` (фильтры: `ispresalebudget=True` или `PointTagName='Пресейл'`, `budgettype='Расход расчет по ресурсам'`).
**Интерпретация:** Вердикт всегда нейтральный. Δ = Лимит - Потрачено (может быть отрицательным).
**Вывод:** `{Лимит:N руб./Потрачено:M руб./Δ=X руб.}` (значения в рублях).
**Скрипт:** `check_presale_limit_spending`.
**Live-probe 503-152:** `Лимит:1 000 000 руб./Потрачено:7 057 951 руб./Δ=-6 057 951 руб.` (перерасход!).

**Важный уточнение пользователя (Q1, 2026-09-03):** «тут у меня неточность, это для всех стадий» — проверяется для ВСЕХ стадий ЖЦ, не только Пресейл.

**Уточнение (Q2, 2026-09-03):** «данные о расходах на трудозатраты бери из представлений для бюджета, сам часы на ставку не умножай! В этом представлении должны быть поля "Пресейл"/"Бюджет"». То есть берём суммы из `ProjectBudgetCompleteBusiness` напрямую, а не вычисляем `часы × ставка`.

### 6.15 — Утверждённый бюджет ✅ done (2026-09-03)

**Назначение:** Проверить, что на каждый календарный год периода проекта есть утверждённый бюджет.
**Получение:** View `Project/ApprovedBudget` с фильтром `ActivityId=<id>`. Поля: `Year`, `Value`.
**Интерпретация:**
- Все года имеют бюджет → "Да, NNN млн. руб." (Норма)
- Часть годов без бюджета → "Вопрос, NNN млн. руб." (Существенное)
- Ни один год не имеет бюджета → "Нет, -" (Существенное, по уточнению пользователя)

**Важный уточнение пользователя (Q1, 2026-09-03):** «если ни за один год нет утверждённого бюджета, это все равно существенное замечание» — НЕ critical даже когда ни один год не заполнен.

**Период проекта:** `FinishForecast` → `FinishPlan` → max из КТ (Pitfall #103).
**Вывод:** Вложенная таблица **всегда доступна** (Pitfall #150). Колонки: #, Год, Сумма/Примечание.
**Скрипт:** `check_approved_budget`.

### 6.16 — Метки КП (проект/пресейл) ✅ done (2026-09-03)

**Назначение:** Проверить, что у всех КТ проекта (кроме обязательных из 6.2) проставлена метка отнесения к проекту/пресейлу.
**Получение:**
- `Project/ProjectBudgetCompleteBusiness` (для `isprojectbudget`/`ispresalebudget`)
- `Point/AllMyPoint` (для `Code`/`pcdName`/`PlanDate`/`ForecastDate`/`PointTagName`)

**Интерпретация:** Если хотя бы у одной не-обязательной КТ метка не определена → "Нет" (Существенное). Если все — "Да" (Норма).

**Определение "определённой" метки** (Pitfall #152):
- `PointTagName ∈ {"Проект", "Пресейл"}` — допустимо
- `PointTagName == "Процесс"` — **недопустимо** (Pitfall #142)
- `PointTagName` = None / "" — недопустимо
- `isprojectbudget=True` или `ispresalebudget=True` (ровно одно) — допустимо

**Исключения (Pitfall #143):** КТ из `MANDATORY_KT_BY_STAGE[current_stage]` (справочник 6.2) **не проверяются** — для них метки не нужны.

**Вывод:** Вложенная таблица. Колонки: #, Код (из `Point.Code`), Тип ("К"/"Р"), Наименование, План, Прогноз.
**Скрипт:** `check_kp_labels`.

**Live-probe 504-595:** При добавлении 2 КТ с `Tag='?'` или `'Процесс'` → "Нет" + 2 замечания.

## 6. Optimization (v1.0.0, 2026-09-03)

Главное узкое место pipeline — множественные вызовы `ProjectParameter` view из каждого индикатора. Заменено на sentinel view `"_get_entity_data_"` в `fetch_with_cache`, который через `get_entity_data(Project, data_id)` возвращает **ВСЕ** свойства проекта одним запросом.

**Результат на 4 проектах:**
- 504-595: 27.23 сек → **8.40 сек** (-69%) на 2-м запуске
- 503-152: 41.88 сек → **8.60 сек** (-79%) на 2-м запуске

Кеш `/tmp/.cache_project_card_<pid>.json` (TTL=5 мин) делает повторные запуски очень быстрыми.

См. `references/mcp-methods-and-optimization.md` для деталей.
