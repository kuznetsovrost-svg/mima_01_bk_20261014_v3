## 1. Что это и зачем

JSON-модель — это **каноническое представление отчёта о здоровье проекта**
в машиночитаемом виде.

### Что даёт JSON

| # | Возможность | Зачем |
|---|-------------|-------|
| 1 | **Хранение в БД** | Загружать через MCP в базу данных |
| 2 | **Аналитика трендов** | Сравнивать JSON за разные даты → понимать динамику |
| 3 | **Аудит вердиктов** | Видеть raw данные + сырой snapshot MCP |
| 4 | **Миграции** | Изменения модели не ломают старые данные |
| 5 | **Версионирование** | Каждый JSON знает по какой схеме он построен |
| 6 | **Валидация** | JSON Schema проверяет структуру автоматически |

### Чего JSON **не** делает

- ❌ Не заменяет MD/HTML/WORD (это производные для человека)
- ❌ Не оптимизирует pipeline (парсинг MD в JSON = 0.5 мс)
- ❌ Не решает проблему `ProjectHealthCostMy 2000 строк` (нужен серверный фильтр)

## 3. Спецификация v0.1.0 (текущая)

JSON Schema (draft 2020-12) находится в `specs/v0.1.0.json`. Используется для:

```python
import jsonschema, json

with open("specs/v0.1.0.json") as f:
    schema = json.load(f)

with open("examples/v0.1.0_504-314.json") as f:
    data = json.load(f)

jsonschema.validate(data, schema)  # OK или ValidationError
```

### Верхний уровень

```json
{
  "_meta":     {...},   // обязательное — метаданные генерации
  "summary":   {...},   // обязательное — общая сводка
  "sections":  {...},   // обязательное — разделы отчёта
  "metadata":  {...},   // технические данные (раздел 7 + MCP-окружение)
  "_raw":      {...},   // опционально — сырые данные из MCP (для аудита)
  "_legacy":   {...}    // опционально — устаревшие поля из старых версий
}
```

**Принцип:** только 3 обязательных ключа (`_meta`, `summary`, `sections`).
Остальное — опционально и может отсутствовать в ранних версиях.

## 4. Метаданные

**`_meta`** — **точка истины** для выбора парсера. По этому полю
определяется какой schema валидировать и какую миграцию применить.

### Обязательные поля

| Поле | Тип | Описание | Пример |
|------|-----|----------|--------|
| `schema_version` | string (semver) | Версия JSON Schema (`"0.1.0"`) | `"0.1.0"` |
| `generated_at` | string (ISO-8601) | Когда сгенерирован JSON (UTC) | `"2026-08-21T22:30:00Z"` |
| `generator` | string (const) | Имя генератора | `"fst-project-health"` |
| `generator_version` | string (semver) | Версия скилла | `"0.9.0"` ⚠️ |
| `project_code` | string | Код проекта `NNN-NNN` | `"504-314"` |
| `project_id` | integer | Внутренний ProjectId | `4314` |

### Опциональные поля

| Поле | Тип | Описание |
|------|-----|----------|
| `source_md_hash` | string | SHA256 хэш исходного MD-файла |

### Реальный пример (из v0.1.0_504-595.json)

```json
{
  "_meta": {
    "schema_version": "0.1.0",
    "generated_at": "2026-08-21T20:33:19.950849+00:00",
    "generator": "fst-project-health",
    "generator_version": "0.9.0",
    "project_code": "504-595",
    "project_id": 4595,
    "source_md_hash": "c9663eac60c0ff6e"
  }
}
```

⚠️ **`generator_version: 0.9.0`** — реальное значение в существующих
JSON. С тех пор скилл ушёл далеко вперёд (v1.0.15), но примеры
**не перегенерированы**.

### Правило выбора парсера

```python
def choose_schema(json_data: dict) -> dict:
    """Выбирает правильную JSON Schema по _meta.schema_version."""
    version = json_data.get("_meta", {}).get("schema_version", "0.0.0")
    with open(f"specs/v{version}.json") as f:
        return json.load(f)

# Миграция если нужно
if json_data["_meta"]["schema_version"] != CURRENT_VERSION:
    json_data = migrate(json_data, CURRENT_VERSION)
```

## 5. Раздел summary (сводка)

Это **то, что показывается на индикаторе** (большой круг в HTML).

### Структура

```json
{
  "summary": {
    "verdict": "Болен",                      // Болен / Требует внимания / Здоров
    "verdict_status": "sick",                // sick / attention / healthy
    "indicator_text": "Проект болен",        // Текст на индикаторе
    "section_verdicts": {
      "s3": {"verdict": "Болен",   "critical": 4, "warning": 6, "info": 0},
      "s4": {"verdict": "Здоров",   "critical": 0, "warning": 0, "info": 0},
      "s5": {"verdict": "Болен",   "critical": 7, "warning": 4, "info": 2},
      "s6": {"verdict": "Болен",   "critical": 3, "warning": 0, "info": 0}
    },
    "total_counts": {
      "critical": 14,
      "warning": 10,
      "info": 2
    }
  }
}
```

⚠️ **Структура `section_verdicts` отстала от скилла.** В скилле v1.0.0+
раздел 6 «Показатели проекта» имеет 16 индикаторов, раздел 8 — сводный.
JSON model по-прежнему считает, что «раздел 6» = старые 3 показателя
фин.результата.

### Маппинг verdict → verdict_status

| verdict | verdict_status | CSS-класс | Цвет |
|---------|----------------|-----------|------|
| Болен | sick | `data-status="sick"` | красный |
| Требует внимания | attention | `data-status="attention"` | жёлтый |
| Здоров | healthy | `data-status="healthy"` | зелёный |

### Правило: общий verdict = самый плохой

```python
priority = {"Болен": 3, "Требует внимания": 2, "Здоров": 1}
worst = max(section_verdicts.values(), key=lambda v: priority.get(v["verdict"], 1))
overall_verdict = worst["verdict"]
```

## 6. Раздел sections (детальные данные)

Детальные данные по разделам отчёта. Каждый раздел — отдельный подраздел.

⚠️ **Расхождение версий:** в реальных JSON (2026-08-21) присутствуют
**s3, s4, s5, s6, s7, s8**. В скилле v1.0.0+ разделы 1, 3, 4, 5, 6
«Показатели проекта» (16 индикаторов), 7, 8 «Сводка». То есть
**раздел 6 поменял смысл**: был «Финансовый статус» (3 показателя),
стал «Показатели проекта» (16 индикаторов).

### 6.1. `sections.s3` — замечания по срокам (КТ)

```json
{
  "s3": {
    "verdict": "Болен",
    "counts": {"critical": 4, "warning": 6, "info": 0},
    "remarks": [
      {
        "code": "104-322",
        "name": "Реализация инструмента «Автопилот»",
        "plan": "2026-07-23",                 // или null
        "forecast": "2026-07-24",             // или null
        "fact": null,                         // или дата
        "owner": "Кузнецов Ростислав Владимирович",
        "status": "Существенное",             // Критическое/Существенное/Информационное
        "color": "Желтый"                     // Красный/Желтый/Синий
      }
    ]
  }
}
```

**Семантика:** `plan != forecast` И `fact is None` И `plan < forecast`
(или наоборот).

### 6.2. `sections.s4` — полнота заполнения

```json
{
  "s4": {
    "verdict": "Здоров",
    "indicators": [
      {"name": "Куратор назначен",          "result": "Да", "detail": "...", "status": "Норма"},
      {"name": "РП назначен",               "result": "Да", "detail": "...", "status": "Норма"},
      {"name": "Паспорт проекта заполнен",  "result": "Да", "detail": "...", "status": "Норма"},
      {"name": "Актуальность трудозатрат",   "result": "Да", "detail": "...", "status": "Норма"},
      {"name": "Корректность графика платежей","result": "Да", "detail": "...", "status": "Норма"}
    ],
    "effort": {
      "plan_hours": 143.90,
      "forecast_hours": 610.40,
      "fact_hours": 550.00
    },
    "budget": {
      "act_sum": 1134025.80,
      "pay_sum": 1134025.80,
      "delta": 0.00,
      "contract_count": 0
    }
  }
}
```

**5 показателей** (фиксированный порядок):
1. Куратор назначен
2. РП назначен
3. Паспорт проекта заполнен
4. Актуальность трудозатрат
5. Корректность графика платежей

**result:** "Да" / "Нет" / "Неопределено"

### 6.3. `sections.s5` — актуальность прогнозов ⭐ важный раздел

**Правило (критично!):**
- Просрочка считается **относительно `forecast`,** а не `plan`
- В `overdue` попадают **только** КТ где `forecast < today` И `fact IS NULL`
- КТ с прогнозом в будущем (`forecast >= today`) **НЕ попадают**

```json
{
  "s5": {
    "verdict": "Болен",
    "counts": {"critical": 7, "warning": 4, "info": 2},
    "overdue": [
      {
        "code": "104-318",
        "name": "Разработка MCP-сервера...",
        "plan": "2026-06-12",
        "forecast": "2026-06-15",
        "overdue_days": 67,                     // today - forecast_date
        "status": "Критическое",
        "color": "Красный",
        "owner": "..."
      }
    ]
  }
}
```

**Класс тяжести по overdue_days:**
- `>=30` → Критическое (🔴 Красный)
- `>=14` → Существенное (🟡 Желтый)
- `>=1` → Информационное (🔵 Синий)

**Почему это важно:**
- PlanDate — это когда **планировали** сделать
- ForecastDate — это когда **по прогнозу** сделают
- Просрочка — это когда **уже должны были** сделать (прогноз прошёл), а **не сделали** (нет факта)

### 6.4. `sections.s6` — финансовый статус (в JSON v0.1.0) / Показатели проекта (в скилле v1.0.0+)

**⚠️ Здесь главное расхождение модели и скилла.**

#### В JSON v0.1.0 (по реальным примерам 2026-08-21):

```json
{
  "s6": {
    "verdict": "Болен",
    "indicators": [
      {"name": "Прогноз фин.результата < 0",            "result": "Да", "detail": "..."},
      {"name": "Δ текущей стоимости от плана > 1 млн",  "result": "Да", "detail": "..."},
      {"name": "Δ прогноза от плана > 2 млн",           "result": "Да", "detail": "..."}
    ],
    "raw": {
      "plan": 6422500.0,
      "forecast": -221860.0,
      "fact": null,
      "deviation": -6644360.0,
      "devcost": 3340856.0
    }
  }
}
```

**3 показателя** (фиксированный порядок):
1. Прогноз фин.результата < 0 → `result="Да"` = убыток
2. Δ текущей стоимости от плана > 1 млн → превышение бюджета
3. Δ прогноза от плана > 2 млн → расхождение плана и прогноза

#### В скилле v1.0.0+ (по `project_indicators.py`):

`s6` = **«Показатели проекта»**, 16 индикаторов (6.1–6.16), каждый
возвращает `IndicatorResult` с полями `number`, `name`, `result`,
`detail`, `verdict`, `table`, `table_title`. Структура секции **должна
быть обновлена** в следующей версии JSON Schema (v0.2.0+).

Текущая `sections.s6` в JSON **не отражает** реальные данные скилла.
Это **самый важный пункт**, который надо учесть при следующей миграции.

```json
{
  "s7": {
    "rows": [
      {"name": "Пользователь",   "value": "N/A"},
      {"name": "Титул системы",  "value": "Копия прода для MCP"},
      {"name": "Версия Core",    "value": "2026.8.21.1040"},
```

## 8. Сырые данные (_raw)

**Опционально.** Для аудита и трассировки спорных вердиктов.

```json
{
  "_raw": {
    "myproject_row": {...},                  // Строка из MyProject view
    "project_entity": {...},                  // get_entity_data(Project, id)
    "all_my_point_count": 34,                // Сколько КТ пришло (после фильтра ?ProjectId=)
    "project_health_cost_my_count": 1,        // Сколько финансовых строк
    "project_resource_plan_count": 149       // Сколько effort rows
  }
}
```

**Когда использовать:** если в будущем алгоритм вердикта изменится —
у нас есть **сырой snapshot** для воспроизведения старых решений.

⚠️ В существующих примерах `_raw: {}` — **не заполняется**. Это
известное ограничение (см. секцию 13).

## 9. Устаревшие поля (_legacy)

При миграции `v0.1.0 → v0.2.0` некоторые поля могут быть удалены.
Чтобы не терять данные:

```json
{
  "_legacy": {
    "old_diff_days": [1, -4, 3],       // удалено в v0.2.0 — теперь overdue_days
    "removed_field_name": "...",
    "_migration_note": "Перенесено из sections.s5.overdue[].diff_days в _legacy при миграции v0.1.0 → v0.2.0"
  }
}
```

**Правило:** все удалённые поля **обязательно** сохраняются в `_legacy`
с пометкой когда и почему удалены.

## 11. Принципы версионирования

### Semver (X.Y.Z)

- **X** (major) — несовместимые изменения (breaking)
- **Y** (minor) — добавление полей (обратно совместимо)
- **Z** (patch) — исправления (обратно совместимо)

### Что считается breaking change

| Тип | Пример | Это breaking? |
|-----|--------|:-------------:|
| Переименование поля | `project_id` → `activity_id` | ❌ breaking |
| Удаление поля | убрали `fact` из `remarks` | ⚠️ breaking (если обязательное) |
| Изменение типа | `critical: int` → `critical: string` | ❌ breaking |
| Изменение enum | `"Болен"` → `"Критично"` | ❌ breaking |
| Добавление опционального поля | `+ "new_field": null` | ✅ minor |
| Изменение логики счёта | `critical >=3 → sick` (было 5) | ❌ breaking (семантика) |
| **Расширение `sections.s6` (3 → 16 индикаторов)** | — | ❌ breaking (требует v0.2.0) |

### Правила обратной совместимости

1. **Новые поля** — добавляются с `default` или `null` в schema
2. **Удалённые поля** — переносятся в `_legacy`
3. **Переименованные** — новый ключ + старый ключ в `_legacy`
4. **Изменённые типы** — major bump

### Цепочка миграций

```
v0.1.0 → v0.2.0 → v0.3.0
         ↓
   migrations/v0.1.0_to_v0.2.0.py
                  ↓
            migrations/v0.2.0_to_v0.3.0.py
```

Каждая миграция — отдельный Python-файл с функцией `migrate(old: dict) -> dict`.

## 12. Как добавить новую версию модели

### Когда нужна новая версия

- Добавляете **новое поле** (minor: 0.1.0 → 0.2.0)
- **Удаляете поле** или меняете тип (major: 0.1.0 → 1.0.0)
- **Рефакторите** без изменения контракта (patch: 0.1.0 → 0.1.1)

### ⚠️ Текущая задача: v0.1.0 → v0.2.0

Изменения, которые **должны** быть в v0.2.0 (по факту расхождения
скилла и модели):

1. `sections.s6.indicators` — расширить с 3 до 16 индикаторов, добавить
   поля `number` (1..16), `verdict` (Критическое/Существенное/Информационное/Норма),
   `table` (опциональная вложенная таблица для whitelist 6.2, 6.3, 6.4,
   6.5, 6.6, 6.7, 6.8, 6.15, 6.16), `table_title`.
2. `sections.s7.rows` — добавить 6-ю строку «Версия скилла», убрать
   «N/A» в «Пользователь».
3. `sections.s8.table` — добавить разделы 7 (Технические данные)
   и обновить «Раздел 6» как «Показатели проекта» (не «Финансовый статус»).
4. `_meta.generator_version` — обновить в новых примерах до `1.0.15`.

### Шаги для новой версии

1. **Скопировать старую спецификацию:**
   ```bash
   cp specs/v0.1.0.json specs/v0.2.0.json
   ```

2. **Внести изменения в `specs/v0.2.0.json`:**
   - Обновить `version` → `"0.2.0"`
   - Добавить/удалить поля
   - Обновить `$defs`

3. **Создать миграцию:**
   ```bash
   cp migrations/_template.py migrations/v0.1.0_to_v0.2.0.py
   ```
   Реализовать `migrate(old: dict) -> dict`.

4. **Зарегистрировать в `migrations/__init__.py`:**
   ```python
   MIGRATIONS = {
       ("0.1.0", "0.2.0"): "v0.1.0_to_v0.2.0",
   }
   ```

5. **Сгенерировать пример:**
   ```bash
   python3 scripts/generate_json.py --code 504-314 --output examples/v0.2.0_504-314.json
   ```

6. **Проверить diff:**
   ```bash
   python3 scripts/diff_specs.py 0.1.0 0.2.0
   ```

7. **Валидировать:**
   ```python
   import jsonschema, json
   schema = json.load(open("specs/v0.2.0.json"))
   data = json.load(open("examples/v0.2.0_504-314.json"))
   jsonschema.validate(data, schema)
   ```

8. **Обновить CHANGELOG.md и README.md**
