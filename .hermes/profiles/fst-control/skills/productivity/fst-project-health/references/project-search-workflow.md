# Workflow: Find record by partial Name (project, task, etc.)

Когда пользователь знает только примерное имя записи, но не её ID — типичный
сценарий: «найди мне проект, в названии которого есть ФГК». Это procedure
поиска, разработанная и проверенная на Форсайт ПМ Практики.

Применимо к любой сущности, у которой есть строковое поле `Name` и `IdFieldName`
— `Project`, `Activity`, `Risk`, `Document`, `OrgUnit` и т.д.

## Предусловия

- Активная сессия MCP `fst_pmpractice` (или `hermes mcp list` → `connected`)
- Загружен этот skill (`fst-pmpractice`)
- Известно `entityName` (например, `Project`) — обычно из контекста задачи

## Алгоритм

### Шаг 1. Получить список записей

Сначала попробуй **view «моих»** записей (быстрее, уже отфильтровано по правам):

```python
mcp__fst_pmpractice__get_view(entityName="Project", viewName="MyProject")
# → {columns: [...], data: [{ProjectId, Code, Name, ...}, ...]}
```

Fallback-цепочка, если `MyProject` пуст или недоступен:

1. `viewName="AllProject"` — все доступные проекты
2. `viewName="ProjectParameter"` — широкий view с параметрами
3. Крайний случай — `list_views(entityName="Project")` чтобы найти другие view

⚠️ Если `data` пуст — сообщи пользователю, что у него нет доступных
записей этого типа, или view ограничен по правам.

### Шаг 2. Фильтр по подстроке

```python
SUBSTRING = "ФГК"  # то, что ввёл пользователь

matches = [
    r for r in data["data"]
    if SUBSTRING.lower() in str(r.get("Name") or "").lower()
]
```

**Регистронезависимый** поиск — пользователь мог написать «фгк», «ФГК», «Фгк».

### Шаг 3. Ветвление по количеству совпадений

#### 3a. 0 совпадений

Показать 3-5 ближайших по контексту из исходного `data`, попросить уточнить:

> Не найдено ни одного проекта с «ФГК» в названии.
> Ближайшие по контексту:
> 1. 501-682 — ФГК Адаптация ИС УПД
> 2. 504-034 — ФГК Сопровождение 2026-2027
>
> Уточни запрос или пришли код.

#### 3b. Ровно 1 совпадение

Сразу вернуть результат:

> **ProjectId = `1682`**
> Проект «ФГК Адаптация ИС УПД» (Code: `501-682`)

#### 3c. Больше 1 совпадения

Показать таблицу и спросить у пользователя:

> Найдено несколько проектов с «ФГК» в названии:

| # | Code | Name |
|---|------|------|
| 1 | `501-682` | ФГК Адаптация ИС УПД |
| 2 | `504-034` | ФГК Сопровождение 2026-2027 |
| 3 | `501-610` | ФГК Сопровождение 2023-2026 |

> Знаешь ли ты **Code** нужного проекта?
> - Если да — пришли Code (формат «501-682»).
> - Если нет — выбери номер из таблицы (1, 2 или 3) или пришли часть имени.

### Шаг 4. Обработка ответа пользователя

Распознавание формы ответа:

| Форма ответа | Как распознать | Действие |
|--------------|----------------|----------|
| **Code** | Содержит дефис (например, `501-682`) | Искать точное совпадение по `Code` в **исходном** `data` |
| **Номер** | Целое число от 1 до `len(matches)` | `matches[int(ответ)-1]` |
| **Подстрока Name** | Любая другая строка ≥2 символов | Перефильтровать `matches` по новой подстроке, вернуться к шагу 3 |
| **Не распознано** | Пустая, мусор, или непонятно | Переспросить |

⚠️ Code ищи в **исходном `data`**, не в `matches` — пользователь мог
назвать Code, который не содержит искомую подстроку (например, проект
«Внедрение CRM» с Code `999-005`).

### Шаг 5. Возврат результата

Когда `ProjectId` однозначно определён:

> **ProjectId = `4034`**
> Это проект **Форсайт Сопровождение 2026-2027** (Code: `504-034`).

Опционально добавить контекст из той же строки view (если есть поля):
статус, стадия, руководитель, профиль, даты.

## Edge cases

| Случай | Обработка |
|--------|-----------|
| View вернул пустой `data` | «Нет доступных проектов. Проверь права или подожди деплоя» |
| `data` без поля `ProjectId` | Использовать `id` как fallback |
| Подстрока совпадает с >20 проектами | Ограничить таблицу 10 строками + «и ещё N, уточни» |
| Code в нестандартном формате (`501/682`, `501.682`) | Нормализовать: заменить `/` и `.` на `-` перед поиском |
| Пользователь меняет решение | После каждого ответа — заново шаги 3-4 |
| Подстрока пустая или пробельная | Не запускать поиск, попросить ввести имя |

## Практический прогон (зафиксированный)

| Шаг | Действие | Результат |
|-----|----------|-----------|
| Запрос | «Назови ProjectId проекта, где в Name "ФГК"» | — |
| 1 | `get_view(Project, MyProject)` | 4 проекта |
| 2 | Фильтр `Name LIKE %ФГК%` | 3 совпадения |
| 3c | Показать таблицу | Ответ пользователю |
| 4 | Пользователь: «2» | Берём `matches[1]` |
| 5 | Возврат | `ProjectId = 4034`, «ФГК Сопровождение 2026-2027» |

## Перенос на другие сущности

Тот же алгоритм работает для любой сущности с `Name` и `IdFieldName`:

| Entity | ViewName для шага 1 | Колонка PK |
|--------|---------------------|------------|
| Project | `MyProject`, `AllProject` | `ProjectId` |
| Activity | `MyActivity`, `AllActivity` | `ActivityId` |
| Risk | `MyRisk`, `AllRisk` | `RiskId` |
| Document | `MyDocument`, `AllDocument` | `DocumentId` |
| OrgUnit | `MyOrgUnit`, `AllOrgUnit` | `OrgUnitId` |

⚠️ **Исключение — сущности с нечисловым PK** (например, `MetaModel` с
`IdFieldName = "Name"`). Тогда `id` это строка-имя, и `data_id` /
`get_entity_data` принимает её напрямую.
