# Playbook скилла fst-project-health

**Версия:** v1.0.14 (2026-09-04)
**Автор:** ROSTISLAV KUZNETSOV
**Для кого:** коллеги, которые хотят понять что показывает отчёт о здоровье проекта, почему данные именно такие, и как они получены.

---

## 📖 Как читать playbook

Каждый пункт отчёта описан в **4 секциях**:

| Секция | Что внутри |
|---|---|
| **1. Назначение** | Зачем этот пункт, какую проблему выявляет |
| **2. Получение данных** | Из какого MCP-view, какие фильтры, в каком порядке |
| **3. Интерпретация** | Как скилл «понимает» данные, какие пороги, приоритеты |
| **4. Вывод** | Что показывается в отчёте (колонки, формат, цвета) |

---

## 🗂 Структура отчёта

| Раздел | Название | Что показывает |
|---|---|---|
| 1 | Header | Круглый индикатор (Проект болен / Требует внимания / Здоров) + метаданные |
| 3 | Замечания по срокам | КТ с просрочкой плана/прогноза |
| 4 | Полнота заполнения | 5 показателей заполненности карточки проекта |
| 5 | Актуальность прогнозов | КТ с просрочкой (есть план + прогноз + факт) |
| 6 | Показатели проекта | 16 индикаторов здоровья (открыт по умолчанию) |
| 7 | Финансовый статус | 3 сводных показателя фин.результата |
| 8 | Технические данные | Метаданные отчёта (пользователь, MCP-версия, титул) |

## 📘 Раздел 1: Header (круглый индикатор)

### 1. Назначение
Визуальное представление **общего здоровья проекта** в одном символе.

### 2. Получение данных
- Источник: `compute_verdict()` в `scripts/build_html_report.py`
- Анализирует `**Вердикт раздела:**` из разделов 3, 4, 5, 6, 7

### 3. Интерпретация
| Если хоть один из разделов 3-7 «Болен» | → `sick` (красный) |
| Если «Требует внимания» | → `attention` (оранжевый) |
| Иначе | → `healthy` (зелёный) |

### 4. Вывод
- **Цветной круг** (160×160 px) слева в header
- **Текст в круге**: «Проект болен» / «Требует внимания» / «Здоров» / «Нет данных»
- **Метаданные справа**: Target (код проекта), Дата создания отчёта, версия MCP

---

## 📘 Раздел 3: Замечания по срокам

### 1. Назначение
Показать **КТ с нарушением сроков** (план/прогноз в прошлом). Это основной сигнал тревоги для РП.

### 2. Получение данных
- **View:** `Point/AllMyPoint?ProjectId=<id>`
- **Фильтр:** все КТ текущего проекта, где есть `PlanDate` и/или `ForecastDate`
- **Порядок отбора:** severity (critical > substantial > info), затем — по дате плана

### 3. Интерпретация
- **Критическое (красный):** `diff >= 10 дней` от плана
- **Существенное (жёлтый):** `diff >= 2 дней`
- **Информационное (голубой):** `diff >= 1 день`
- Если **есть факт** (КТ выполнена) → в таблицу НЕ попадает

### 4. Вывод
| # | Код | Наименование | План | Прогноз |
|---|---|---|---|---|

- **5 колонок**, без Δ (Δ считается в разделе 5)
- **Подсветка строк** по severity
- **Открыт по умолчанию** (важная информация)

---

## 📘 Раздел 4: Полнота заполнения проекта

### 1. Назначение
Проверить, что в карточке проекта заполнены **ключевые поля** (куратор, РП, паспорт, трудозатраты, платежи).

### 2. Получение данных
- **View 1:** `Project/MyProject?ProjectId=<id>` — для куратора, РП, стадии ЖЦ, типа проекта
- **View 2:** `Project/_get_entity_data_?data_id=<id>` — для трудозатрат (plan/forecast/fact)
- **View 3:** `InContract/InContractBudgetBusiness?ProjectId=<id>` — для графика платежей

### 3. Интерпретация
5 показателей:
1. **Куратор назначен** — есть ли `Curator` ≠ пусто
2. **РП назначен** — есть ли `Owner` ≠ пусто
3. **Паспорт проекта** — есть ли прикреплённый файл паспорта (зависит от стадии ЖЦ)
4. **Актуальность трудозатрат** — есть ли `forecast_hours` за последний месяц
5. **Корректность графика платежей** — Σ актов = Σ оплат (допуск 0 ₽)

### 4. Вывод
| # | Показатель | Результат |
|---|---|---|
| 1 | Куратор назначен | Да — ФИО / Нет |
| 2 | РП назначен | Да — ФИО / Нет |
| 3 | Паспорт проекта заполнен | Да / Нет (+ стадия ЖЦ) |
| 4 | Актуальность трудозатрат | Да (с числами) / Нет |
| 5 | Корректность графика платежей | Да (Σ = ...) / Нет (Δ) |

## 📘 Раздел 5: Актуальность прогнозов

### 1. Назначение
Показать **КТ с полным набором данных** (план + прогноз + факт) и **рассчитать просрочку**.

### 2. Получение данных
- **View:** `Point/AllMyPoint?ProjectId=<id>`
- **Фильтр:** КТ где есть и `PlanDate`, и `ForecastDate` (с фактом или без)
- **Сортировка:** по Δ дн. (от большего к меньшему)

### 3. Интерпретация
- `Δ дн. = сегодня − PlanDate` (если прогноз ещё не в прошлом)
- Severity (как в разделе 3): `>= 10` (крит), `>= 2` (сущ), `>= 1` (инф)

### 4. Вывод
| # | Код | Название | План | Прогноз | Просрочка, дн |
|---|---|---|---|---|---|

- **6 колонок** (включает `Δ дн.`)
- **Подсветка** по severity

## 📘 Раздел 6: Показатели проекта (16 индикаторов)

### 1. Назначение
**Главный раздел** отчёта — 16 ключевых показателей здоровья проекта. Каждый индикатор отвечает на один конкретный вопрос.

### 2. Получение данных
Общая логика:
- **Сначала** все индикаторы получают данные через `fetch_with_cache()` (5 мин TTL)
- **Prefetch** (v1.0.1) — общие view загружаются 1 раз на все индикаторы
- **Каждый индикатор** = своя функция `check_*()` в `scripts/project_indicators.py`

### 3. Интерпретация
- **Severity** (severity = `verdict`):
 - `critical` (красный фон) — требует немедленного внимания
 - `substantial` (жёлтый) — есть проблема, но не критично
 - `informational` (голубой) — справочная информация
 - `normal` (белый) — всё в порядке

### 4. Вывод
- **Таблица**: `# | Показатель | Результат | Детали` (с ▼)
- **▼ кликабельный** (тёмно-синий, 9px) — раскрывает вложенную таблицу
- **▼ серый** (9px) — у подпунктов без данных, не кликабельный
- **▼ нет** — у подпунктов 6.1, 6.9-6.14 (там вложенных таблиц не бывает)

---

### 6.1 — Юрлицо проекта/пресейла указано

**Назначение:** проверить что у проекта заполнено юрлицо (для договоров).

**Получение данных:** `Project/MyProject?ProjectId=<id>` → поле `LegalEntity`.

**Интерпретация:** `Юрлицо ≠ пусто` → `Норма` (иначе `Критическое`).

**Вывод:** «Да — <юрлицо>» / «Нет».

---

### 6.2 — Актуальность состояния ЖЦ

**Назначение:** проверить что стадия ЖЦ проекта актуальна.

**Получение данных:** `Project/_get_entity_data_?data_id=<id>` → поля `ActivityPhaseName`, `phasefinish_forecastdate`.

**Интерпретация:** если `phasefinish_forecastdate` в прошлом — стадия не обновлялась.

**Вывод:** «Да» / «Нет».

---

### 6.3 — Прогнозы по ресурсам заданы

**Назначение:** проверить что на ближайшие месяцы есть прогнозы трудозатрат по исполнителям.

**Получение данных:** `Project/ProjectResourcePlan?ProjectId=<id>` → `forecast_hours`, `planning_date`, `username`.

**Интерпретация:**
- Для каждого месяца: если `forecast_hours < plan_hours` → замечание
- Severity: «существенное» (по умолчанию)

**Вывод:** «Да» / «Вопросы, N ч» (сумма пропущенных часов).

**Вложенная таблица:** «Месяцы с проблемами в прогнозах» — список месяцев с замечаниями.

---

### 6.4 — Плановые трудозатраты заданы

**Назначение:** проверить что плановые часы на месяц заполнены.

**Получение данных:** `Project/ProjectResourcePlan?ProjectId=<id>` → `plan_hours`.

**Интерпретация:** если `plan_hours == 0` для месяца → замечание.

**Вывод:** «Да» / «Вопросы, N ч».

**Вложенная таблица:** «Месяцы с проблемами в планах».

---

### 6.5 — Прогнозы ресурсов на исполнителя не превышают 100%

**Назначение:** проверить что прогнозная загрузка одного исполнителя ≤ 100% в месяц.

**Получение данных:** `Project/ProjectResourcePlan?ProjectId=<id>` → `forecast_hours` за каждый месяц.

**Интерпретация:** `forecast_hours / норма_часов_в_месяце <= 100%` → норма.

**Вывод:** «Да» / «Нет, N ч превышения».

---

### 6.6 — Есть нереализованные прогнозы по ролевым ресурсам

**Назначение:** найти **роли** (а не ФИО), по которым прогноз не привязан к конкретному сотруднику.

**Получение данных:** `Project/ProjectResourcePlan?ProjectId=<id>` → `username`, `specialization`, `forecast_hours`, `planning_date`.

**Интерпретация:**
- Роль = `username == specialization` (например, «Аналитик» без имени)
- Замечание: у роли есть `forecast_hours` за прошлый месяц
- **Вердикт всегда «Норма» (без подсветки)** — это справочная информация

**Вывод:** «Да» (нет нарушений) / «Нет» (есть роли с пропущенными прогнозами).

**Вложенная таблица:** «Роли с нереализованными прогнозами» — список ролей и часов.

---

### 6.7 — Есть исполнители, у которых прогноз в сумме с др. активностями > 100%

**Назначение:** найти исполнителей, **перегруженных по всем проектам** (не только текущему).

**Получение данных:**
- **Шаг 1:** `Project/ProjectResourcePlan?ProjectId=<id>` — список исполнителей текущего проекта
- **Шаг 2:** для каждого исполнителя — `Project/ProjectResourcePlan?accountid=<id>&startdate=...&enddate=...` (все его проекты)

**Интерпретация:**
- `прогноз_сумма = Σ forecast_hours по всем проектам за месяц`
- `норма = 8ч × рабочие_дни_в_месяце`
- `процент_превышения = (прогноз / норма) × 100`
- Severity: `>100%` (инф), `>110%` (сущ), `>150%` (крит)
- **Сортировка: по алфавиту ФИО** (по требованию пользователя)

**Вывод:** «Да» (нет перегрузок) / «Нет» (есть).

**Вложенная таблица:**

| # | ФИО | Прогноз по активн. | Превышение сумм. | %Превышения |
|---|---|---|---|---|
| {n} | {ФИО} | {ч} (только по **этому** проекту) | {ч} (по **всем** проектам) | {%} |

- ▼ серый (без кликабельности) если строк нет

---

### 6.8 — Соблюдение сроков финансовых КТ

**Назначение:** проверить что **финансовые КТ** (привязанные к контрактам) не просрочены.

**Получение данных:**
- **View:** `Point/AllFinancePoint?ProjectId=<id>` — все финансовые КТ проекта
- **Иерархия:** `Проект → InContract → Point` (parent = `InContract`)

**Интерпретация:**
- `просрочена = forecast_date < сегодня AND факт = None`
- Severity: `>= 10` (крит), `>= 2` (сущ), `>= 1` (инф)

**Вывод:** «Да» / «Нет».

**Вложенная таблица** (формат как раздел 3):

| # | Код | Наименование | План | Прогноз | Δ дн. |
|---|---|---|---|---|---|

---

### 6.9 — Суммы актов и оплат

**Назначение:** проверить что Σ актов ≈ Σ оплат (финансовая дисциплина).

**Получение данных:** `InContract/InContractBudgetBusiness?ProjectId=<id>` → `ActForecastSum`, `PayForecastSum`.

**Интерпретация:** `Δ = Σ актов - Σ оплат`. Severity: `>1М` (крит), `>100К` (сущ), `>0` (инф).

**Вывод:** «По актам:N руб./По оплатам:M руб./Δ= X руб.» (сокращённо в млн. руб. с 3 знаками).

---

### 6.10 — В бюджете указаны прямые затраты

**Назначение:** проверить что в статье бюджета «Прямые затраты» есть сумма.

**Получение данных:** `Project/ProjectBudgetCompleteBusiness?ProjectId=<id>` → запись `financeSourceId = "Прямые затраты"`.

**Интерпретация:** если `sum > 0` → норма.

**Вывод:** «Да, N млн. руб.» / «Нет».

---

### 6.11 — В затратах указан НДС

**Назначение:** проверить наличие НДС в бюджете.

**Получение данных:** `Project/ProjectBudgetCompleteBusiness?ProjectId=<id>` → запись `financeSourceId = 128` (статья 611-13).

**Интерпретация:** наличие ≠ 0 → норма.

**Вывод:** «Да» / «Нет».

---

### 6.12 — Сумма НДС расчётная

**Назначение:** **проверить** правильность указания НДС вручную (статья 611-13).

**Получение данных:**
- **View:** `Project/ProjectBudgetCompleteBusiness?ProjectId=<id>`
- **Только `budgettype="Доходный контракт"`** (расходы не участвуют)
- **Приоритет полей** (по убыванию): `fact → forecast → plan` (внутри: `max(pay, act)`)

**Интерпретация:**
- `total_amount = Σ amount` за **все периоды** (по проекту целиком)
- `total_vat = Σ vat` (статья 611-13) за все периоды
- `расчётный_НДС = total_amount / 21 × 5` (ставка 5% — константа)
- `фактический_% = total_vat / (total_amount - total_vat) × 100`
- **Допуск:** 0.0001 ₽ (`VAT_TOLERANCE_RUB`)

**Формула:** `НДС = Сумма / (100 + ставка) × ставка = Сумма / 21 × 5`
**Пример:** 1 500 000 / 21 × 5 = **71 428,57 ₽**

**Вывод:**
- **«Да»** если `|total_vat - расчётный_НДС| <= 0.0001`
- **«Нет, Должно быть:X руб./Указано:Y руб./%:Z»** иначе

---

### 6.13 — Бюджет проекта/пресейла

**Назначение:** проверить наличие **утверждённого** бюджета.

**Получение данных:** `Project/_get_entity_data_` + `ProjectBudgetCompleteBusiness`.

**Интерпретация:**
- Сумма проекта: `project_presale_budget.value`
- Лимит пресейла: 5% от бюджета проекта
- Если лимит превышен → замечание

**Вывод:** «Сумма проекта:N руб./Пресейл:M руб./Лимит %:X.X».

---

### 6.14 — Расход лимита пресейла

**Назначение:** проверить что потрачено ≤ лимита пресейла.

**Получение данных:** `Project/ProjectBudgetCompleteBusiness` + лимит из 6.13.

**Интерпретация:** `Δ = лимит - потрачено`. Если `Δ < 0` → замечание.

**Вывод:** «Лимит:N руб./Потрачено:M руб./Δ= X руб.».

---

### 6.15 — У проекта есть утверждённый бюджет

**Назначение:** проверить что на каждый год периода проекта есть утверждённый бюджет.

**Получение данных:** `Project/ApprovedBudget?ActivityId=<id>` → поля `Year`, `Value`.

**Интерпретация:** если на год есть `value > 0` → норма.

**Вывод:** «Да, N млн. руб.» / «Нет».

**Вложенная таблица:** «Утверждённый бюджет по годам».

---

### 6.16 — Проставлены метки для отнесения КТ к проекту или пресейлу

**Назначение:** проверить что у КТ проекта/пресейла проставлена метка (`kp_label`).

**Получение данных:** `Point/AllMyPoint?ProjectId=<id>` → `kp_label`.

**Интерпретация:** если `kp_label` пусто → замечание.

**Вывод:** «Да» / «Нет».

**Вложенная таблица:** «Элементы КП без метки» — список КТ без метки.

## 📘 Раздел 7: Финансовый статус проекта

### 1. Назначение
Сводный **финансовый итог** проекта (3 ключевых показателя).

### 2. Получение данных
- **View:** `Project/ProjectHealthCostMy?ProjectId=<id>`
- Поля: `forecast`, `devcost`, `outallforecast`, `plan`, `fact`, и др.

### 3. Интерпретация
3 показателя:
1. **Прогноз фин.результата < 0** — убыток
2. **Δ текущей стоимости от плана > 1М** — перерасход
3. **Δ прогноза от плана > 2М** — отклонение от плана

### 4. Вывод
| # | Показатель | Результат |
|---|---|---|
| 1 | Прогноз фин.результата < 0 | Да — Forecast: N руб. → критическое |
| 2 | Δ текущей стоимости от плана > 1М | Да — Δ = N руб. → критическое |
| 3 | Δ прогноза от плана > 2М | Да — Δ = N руб. |

- **Подсветка** по severity (только красный/жёлтый/нейтральный)
- **Preview** в `<summary>`: «Болен — N критических, ...»
- **Детализация** в ячейке результата: «Да — Forecast: N руб. → критическое»

## 📘 Раздел 8: Технические данные отчёта

### 1. Назначение
Метаданные отчёта — **кто** строил, **от чьего токена**, на какой версии системы.

### 2. Получение данных
- **Пользователь:** из JWT-токена `PMP_TOKEN` (поле `displayname`) — `get_current_user_from_token()`
- **Титул системы:** `MetaModel/Title`
- **URL MCP-сервера:** из `scripts/mcp_config.py::MCP_URL`
- **Версия скилла:** захардкожена в `build_section_7()` (например, `0.3.0 (V2-build)`)
- **Версия MCP:** `MetaModel/Version`
- **Версия Core:** `MetaModel/CoreVersion`

### 3. Интерпретация
Это **справочная** информация для аудита и отладки.

### 4. Вывод
| # | Показатель | Значение |
|---|---|---|
| 1 | Пользователь | `<displayname из JWT>` (например, «Кузнецов Ростислав Владимирович») |
| 2 | Титул системы | `'<title>'` (с одинарными кавычками) |
| 3 | URL MCP-сервера | `<MCP_URL>` |
| 4 | Версия скилла | `<skill_version>` |
| 5 | Версия MCP | `<mcp_version>` |
| 6 | Версия Core (ПМ «Форсайт») | `<core_version>` |

## 🔄 Процесс построения отчёта

```
1. find_project(code)               # Поиск проекта по коду (504-595)
```

## ❓ Частые вопросы

**В: Почему в 6.7 показывается «прогноз» а не «план»?**
О: С v1.0.6 — индикатор учитывает `forecast_hours` (не `plan_hours`), так как прогноз точнее показывает реальную загрузку.

**В: Почему 6.6 не подсвечивается синим?**
О: С v1.0.6 (Pitfall #194) — это справочная информация, не критичная. Палитра: только красный/жёлтый/нейтральный.

**В: Почему 6.12 показывает «Нет» для правильных данных?**
О: Скорее всего НДС указан вручную с ошибкой (5% должно быть 5.0000%, а если 5.27% — будет «Нет»). Проверьте фактический %.

**В: Почему 6.8 пустая таблица?**
О: Все финансовые КТ либо выполнены, либо прогноз не в прошлом. Это норма.
