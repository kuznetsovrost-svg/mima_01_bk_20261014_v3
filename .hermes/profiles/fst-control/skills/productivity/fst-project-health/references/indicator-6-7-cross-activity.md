# Индикатор 6.7 «Суммарный план по всем активностям»

**Реализован 2026-09-02, оптимизирован 2026-09-03.** См. `scripts/project_indicators.py::check_cross_activity_overload`.

#### Назначение

Проверить, что прогноз по исполнителю в текущем проекте кажется допустимым, но **в сумме с другими проектами** превышает 100% доступного времени в месяц.

#### Проблема: как получить данные по всем проектам исполнителя

При первой реализации (2026-09-02) делал запрос `get_view(ProjectResourcePlan, filters={})` без фильтра — получал данные **по всем проектам доступным пользователю**, но с лимитом 10000. Пользователь (2026-09-03) корректно указал:

> «С увеличенным лимитом это неправильно. Есть пользователи, которым доступно 100 или даже 200 проектов. Никакого лимита не хватит. Обычно исполнителей в проектах не так много. Характерные количества от 2 до 10-15 человек. Давай придумаем более экономную и безопасную процедуру получения данных.»

#### Решение: per-accountid фильтрация (2026-09-03)

Вместо одного большого запроса — **по одному запросу на каждого исполнителя** через `filters={"accountid": <id>}`:

```python
# Алгоритм
current_rows = fetch_with_cache(sid, "Project", "ProjectResourcePlan",
                               filters={"ProjectId": project_id}, ...)
# Получаем username → accountid для исполнителей текущего проекта

# Для КАЖДОГО исполнителя отдельно
for username, accountid in real_users.items():
    if not accountid:
        continue
    user_rows = fetch_with_cache(sid, "Project", "ProjectResourcePlan",
                                   filters={"accountid": accountid},
                                   project_id=accountid, limit=2000)
    all_rows.extend(user_rows)
```

**Преимущества:**
- Количество запросов = **числу исполнителей** (2-15), а не числу проектов (100-200)
- Данные конкретного исполнителя (а не весь `ProjectResourcePlan`)
- Безопасно — нет риска «не хватит лимита»

#### Pitfall #154 (NEW 2026-09-03): не используй `ThreadPoolExecutor` для параллельных MCP-запросов

Попытка использовать `concurrent.futures.ThreadPoolExecutor` для параллельных запросов:

```python
# ❌ НЕ работает — MCP не успевает отвечать параллельно
with ThreadPoolExecutor(max_workers=5) as executor:
    futures = {executor.submit(fetch_user_rows, item): item[0]
               for item in real_users.items()}
    for future in as_completed(futures):
        rows = future.result()  # TimeoutError!
        all_rows.extend(rows)
```

**Результат:** `requests.exceptions.ReadTimeout: HTTPSConnectionPool ... Read timed out (read timeout=60)`.

**Решение:** последовательные запросы (по одному). MCP сервер не выдерживает параллельную нагрузку.

#### Исключения

- **Роли** (`username == specialization`) исключаются из проверки — у них нет привязки к ФИО.
- Используется `is_role_resource()` из `unfilled_roles_thresholds.py`.

#### Измеренная производительность (live-probe 2026-09-03)

| Проект | Исполнителей | Время |
|--------|-------------:|------:|
| 504-595 | 3 | 16.06 сек |
| 503-434 | 12 | 67.32 сек |
| 503-152 | 12 | 57.85 сек |
| 504-314 | 5 | 29.28 сек |

Время линейно от количества исполнителей (~5 сек на запрос). Для 12 исполнителей = 60 сек, для 3 = 15 сек. Это приемлемо для финального отчёта.

#### Альтернатива: использовать `accountid` в фильтре

В `ProjectResourcePlan` поле `accountid` присутствует в каждой строке. Это **ID пользователя** в системе. Фильтрация по нему возвращает только строки этого пользователя — безопасно и быстро.

**Live-probe:** `filters={"accountid": 120872}` (Кузнецов) → 10 строк в 3 проектах. Работает.
