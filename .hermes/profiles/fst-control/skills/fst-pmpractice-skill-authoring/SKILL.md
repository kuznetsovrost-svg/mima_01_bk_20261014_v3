# Оптимизация заготовок скиллов PMForesight

## Обзор

Скилл управляет процессом оптимизации **черновика (заготовки)** SKILL.md, который описывает workflow над корпоративной PM-системой «Форсайт» через её MCP-сервер. Это **не авторский** скилл: пользователь не пишет скилл с нуля, он приносит готовый черновик (V01–VN) и просит проверить его на недостатки, исправить, и выдать новую версию. Реальный пример: V03 → V04 проекта `fst-project-health`.

Главное отличие от `hermes-agent-skill-authoring`: тот учит **писать** SKILL.md для Hermes в целом (frontmatter, валидатор, peer-matched structure). Этот — учит **оптимизировать** SKILL.md, когда домен = PMForesight, и концентрируется на специфических для «Форсайт» ловушках (плейсхолдеры шаблонов, доступность views, mixed-sum логика, терминология).

## Когда загружать

Загружай, когда пользователь:
- Прислал файл с заготовкой скилла (`.md`) и просит «проверь», «оптимизируй», «убери лишнее», «подготовь V(N+1)»;
- Говорит «доделай мой скилл», «приведи в порядок заготовку», «найди недостатки в SKILL.md»;
- Явно просит **не создавать сам скилл**, а только подготовить оптимизированный файл + (опционально) новые скрипты.

**Не загружай**, если:
- Пользователь пишет скилл с нуля (→ `hermes-agent-skill-authoring`);
- Это обычный скилл не про PMForesight (→ `hermes-agent-skill-authoring`).

## Контекст домена

PMForesight MCP предоставляет инструменты `mcp__fst_pmpractice__*`. Доменные факты, которые протекают в любую заготовку скилла:

- **Views с фильтром прав**: `ProjectHealthCostMy`, `ProjectHealthWorkload`, `MyProject`, `InContractAll`, `OutcomeContractAll`, `DocumentFileViewAll` — **доступны** обычному пользователю. Без суффикса `My` — **403 для не-админов** (`ProjectHealthCost`, `ContractPlanSummaries`, `ResourcePlanning*`, `ContractPlanSummariesValue`, `StatusReportBudget`, `ApprovedBudget`, `ProjectHealthCost` без `My`). Это нужно выговаривать в SKILL.md явно, иначе будущий агент натыкается на 403.
- **Mixed-sum (факт/прогноз)**: `FactSum > 0 ? FactSum : ForecastSum` — стандартная схема для финансов и трудозатрат. Хардкодить «используй FactSum» нельзя — формула критична.
- **Point-of-contract**: в «Форсайт» акты и оплаты — это **КТ (Point)** с `ParentId` = `ActivityId` контракта. У КТ `PlanSum`, `ForecastSum`, `FactSum`. Связь контракт↔проект — через `InContract.InContractActivity` (multi) или `OutcomeContract.OutcomeContractActivity` (multi).
- **Терминология**: «прогноз финансового результата» ≠ «прогноз расходов». `forecast` ≠ `outallforecast`. `plan` ≠ `inplan`. Это частая путаница в заготовках — отлавливать при аудите.
- **Поля PK**: `data_id` всегда **bigint-string** (`"1686"`), не `"101-686"`. `Code` (`"101-686"`) — не PK; для поиска `ProjectId` нужен `get_view` + `r["ProjectId"]`.
- **Утверждающий документ КТ**: в UI это «Паспорт», но в API это просто строка в поле «Утверждающий документ». Проверяется по тексту, не по прикреплённому файлу.

## Обязательная структура разделов

Каждый раздел SKILL.md должен содержать **4 подкаталога в этом порядке**:

```
## <N>. <Заголовок раздела>

### Назначение шага
Что делаем и зачем.

### Получение данных
Какие MCP-инструменты вызываем, в каком порядке, с какими фильтрами.

### Интерпретация данных
Как обрабатываем полученное: пороги, правила, edge-cases.

### Вывод данных
Какие плейсхолдеры шаблонов заполняются, в каком формате (MD/HTML).
```

**Это закон.** Никакие оптимизации не должны ломать эту структуру. Если раздел можно сократить — сокращай **внутри** подкаталогов, не убирай сами подкаталоги.

## Границы скилла (skill-scope discipline)

Этот скилл оптимизирует **только** черновики скиллов PMForesight (frontmatter, разделы, терминологию, плейсхолдеры). Он **не должен**:

1. **Добавлять в оптимизируемый скилл новые возможности вне его домена.** Если в процессе оптимизации ты обнаружил, что в скилле нужна новая фича (например, FIGMA-мост, новый MCP-вызов, дополнительный формат вывода) — **не включай** её в оптимизированный черновик. Опиши её в финальном сообщении как **рекомендацию** для следующего этапа. Пользователь сам решит, добавлять или нет.

2. **Менять `version` скилла произвольно.** Версия — это **контракт** между пользователем и скиллом. Если текущая версия `0.9.0`, а ты хочешь выпустить `V(N+1)`, поставь `0.10.0` только если пользователь явно согласился на добавление новых возможностей. Если ты только оптимизируешь существующий текст — сохрани версию.

3. **Модифицировать peer-скиллы (`project-search`, `project-completeness-check`, и т.п.)** в процессе оптимизации `fst-project-health`. Если во время работы над одним скиллом ты обнаружил, что в peer-скилле тоже нужна правка — **не делай её сразу**, запиши как рекомендацию.

**Live-probe (2026-08-21):** я добавил FIGMA-bridge в `description` и pitfall #65 в SKILL.md скилла `fst-project-health` (V0.10.1) во время FIGMA-экспериментов. Пользователь **жёстко** потребовал откатить всё до V0.9.0 (только 4 формата отчёта). Это заняло 4 удаления FIGMA-pitfalls + 5 удаления FIGMA-references + 2 удаления FIGMA-scripts + 1 удаление FIGMA-template + 4 удаления эталонов V9/V10. **Правило:** FIGMA-функциональность — это **отдельный скилл** (`fst-project-health-figma-bridge` или аналогичный), со своим каталогом, а **не часть** `fst-project-health`. Не ленись создавать новый скилл — это правильный путь.

4. **Не устраивать «новую фичу = новый скилл» в ущерб реальной задаче, если фича тривиально переиспользуется через subprocess.** Сателлит-архитектура — это **правильная нормальная форма**, когда новый скилл вызывает существующий через subprocess (или импортирует его функции) и не правит исходник. Триггер: «нужно делать ровно то же, что умеет X, но в другой обёртке / с другим триггером / для другой аудитории». Если вы переиспользуете `fst-project-health` через subprocess без правки, это сателлит `fst-project-health-snap-md` — и это нормально. Граница: если сателлиту нужны **новые показатели, новая терминология или новая MCP-точка**, превращайте его в полноценный peer-скилл. Если он только меняет «когда запускать, куда складывать, кто читает» — оставляйте сателлитом и записывайте принцип в его SKILL.md как «переиспользует X без модификации».

## Workflow оптимизации

### Шаг 1. Прочитай черновик
1. Прочитай присланный файл целиком (через `read_file` с лимитом, если >500 строк — читать частями).
2. Если заготовка уже лежит в `~/.hermes/profiles/fst-control/cache/documents/` или `skills/<name>/SKILL.md` — открой оттуда.
3. **Не ищи** `templates/` и `scripts/`, на которые ссылается черновик, если пользователь явно сказал «пока не ищи их». Концентрируйся только на тексте SKILL.md.

### Шаг 2. Аудит
Проведи аудит по чек-листу ниже. Запиши найденное в виде таблицы «что / где / что делаю» — это покажешь пользователю в финальном сообщении.

#### Чек-лист аудита (12 пунктов)

| # | Что искать | Где обычно |
|---|------------|------------|
| 1 | Опечатки в заголовках и служебных словах (`здоровья`, `проекта`, `Куратор`, `Руководитель`) | H1 + Overview |
| 2 | `description` на EN, когда тело на RU (или наоборот) — должно совпадать | frontmatter |
| 3 | `category: research` для скиллов-отчётов (правильно: `productivity`) | frontmatter |
| 4 | `License: MIT` — нерелевантно для личных скиллов | frontmatter |
| 5 | Версия в frontmatter (`1.4.0`) ≠ версия в тексте (`1.3`) — синхронизировать | frontmatter + раздел «Технические данные» |
| 6 | **Плейсхолдеры шаблонов перепутаны** — в колонке «Результат» стоит `{nmb}` вместо `{result}`, и т.п. | таблицы вывода каждого раздела |
| 7 | Дублирование номеров строк в таблице (`1,1,2,2,3,3` вместо `1..6`) | раздел «Технические данные» |
| 8 | Хардкод порогов (10 дней, 1 млн ₽, 2 млн ₽) — выносить в `scripts/<name>-threshold.py` | разделы 3, 4, 5, 6 |
| 9 | Логические петли: правила индикатора, где условие и следствие противоречат друг другу | раздел «Индикатор в заголовке» |
| 10 | Терминологический разнобой (`прогноз`/`прогноз фин.результата`/`прогноз расходов`) | раздел «Финансовый статус» |
| 11 | Пустая «История изменений» — заполнить предыдущими версиями + новой | конец файла |
| 12 | Повторы вроде «Шаблоны лежат в templates/» в каждом разделе — вынести в Overview один раз | все разделы |

**Дополнительные пункты для Форсайт-домена:**

| # | Что искать | Где обычно |
|---|------------|------------|
| 13 | View без суффикса `My` — для обычного пользователя 403; должно быть `*My` | разделы с финансами и трудозатратами |
| 14 | Связь контракт↔проект по `Code` вместо `ActivityId` | показатели платежей, контрактов |
| 15 | Хардкод `"https://ppreplica.hera.pmpractice.ru/mcp"` без пометки «из config.yaml» | технические данные |
| 16 | **Skill-scope violation** — добавляешь в оптимизируемый скилл FIGMA-мост, новый MCP-вызов или другой эксперимент, потому что «пока работаю над ним — удобно». Не делай этого: новая фича = новый скилл. Live-probe 2026-08-21: добавил FIGMA-bridge в `fst-project-health` → пользователь жёстко потребовал отката. Подробнее — в `references/audit-checklist-15.md`, п.16 | frontmatter description + scripts/ + references/ + version |

### Шаг 3. Оптимизируй
Сохраняя **обязательную 4-частную структуру** каждого раздела:
- Исправь опечатки и противоречия по чек-листу.
- Сократи повторы (один раз в Overview, дальше ссылка).
- Замени хардкод порогов ссылками на `scripts/<name>-threshold.py` (даже если самого скрипта ещё нет — пользователь создаст его на следующем этапе).
- Заполни «Историю изменений» — это даёт пользователю traceability.
- Синхронизируй версию во frontmatter и в тексте раздела «Технические данные».

**Не делай:**
- Не переписывай алгоритмы вычислений (пороги, формулы) — только исправляй описки и нормализуй терминологию.
- Не создавай новые скрипты в `scripts/`, если новая функциональность не появилась. Пустые обёртки — это работа следующего этапа (на нём пользователь создаёт сами скрипты, которые ты только что упомянул).
- Не убирай ссылки на существующие `scripts/<name>.py` — они часть плана пользователя.

### Шаг 4. Отдай результат
1. Сохрани новую версию **рядом с черновиком** с суффиксом `-V(N+1).md` (или по явному указанию пользователя — в другую папку).
2. Если пользователь явно просил «пришли архив скриптов» и ты **создавал** новые `.py` файлы — упакуй `scripts/` в `tar.gz` и пришли `MEDIA:` отдельным сообщением. Если новых скриптов не было — не отправляй пустой архив.
3. Сам файл `SKILL.md` — **всегда через `MEDIA:`** (даже если <30 строк: черновики скиллов пользователь предпочитает получать как файл, не inline).
4. В ответе:
   - Краткая сводка изменений (что было → что стало).
   - Таблица «найдено / исправлено».
   - Размер до/после (строки, байты).

## Распространённые ловушки

1. **Подмена задачи**: пользователь прислал черновик одного скилла, а у тебя в голове крутится другой (например, начал оптимизировать `dogfood`, а просили `fst-project-health`). Всегда проверь: что в присланном файле? Это V0X какого скилла?
2. **Создание новых скриптов без необходимости**: пользователь сказал «пока не ищи templates/ и scripts/» — это сигнал, что следующий этап будет про них. Не предвосхищай.
3. **Ломать 4-частную структуру**: даже если раздел можно сократить до одного абзаца — не убирай подкаталоги. Перенеси текст в нужный подкаталог.
4. **Поправлять алгоритмы вместо правописания**: пользователь сказал «чтобы функциональность не пострадала». Не «улучшай» формулы diff-вычислений или mixed-sum логики. Только орфография, терминология, ссылки.
5. **Несохранённая ссылка на фронтматтер**: в `category` ставь `productivity`, не `research`. В `tags` — доменные ключи (`foresight`, `pmpractice`, `ru`). В `related_skills` — реально существующие peer-скиллы Форсайт-экосистемы (`project-search`, `project-completeness-check`, и т.п.).
6. **Игнорирование `MEDIA:`-протокола**: черновики скиллов — это всегда файл, не inline-блок. Пользователь предпочитает получать их через `MEDIA:<path>`.
7. **Скрипты в формате markdown-обёртки (` ```python ... ``` `) не импортируются.** В заготовках PMForesight-скиллов часто используется конвенция: файлы в `scripts/` — это **справочные выдержки кода**, обрамлённые в `` ```python ... ``` `` для удобства встраивания в SKILL.md. Они **не запускаются как Python**. Это нормально для стадии «проект скилла». Но когда скилл переходит в фазу реального выполнения (`/skill` через Hermes), такие файлы нужно **переписать в обычный Python** (убрать обрамляющие ` ```python ` и ` ``` `). На этой фазе пользователь сам выбирает, как действовать: оставить как reference excerpts или сделать исполнимыми модулями. Не пытайся запускать `python -c "import ..."` — упадёт с `SyntaxError`.

8. **Документация скилла должна быть вылизана перед передачей другим людям.**

   Скилл часто передаётся коллегам, которые **не знают путь мысли автора**. Если `SKILL.md`/`README.md` ссылается на устаревший парсер, несуществующую зависимость, или говорит «парсит fst-project-health-word», а код уже три месяца парсит иначе — получатель тратит время на расследование, либо применяет «интуитивно» и получает шумный результат. Скилл = процедура. Процедура должна быть **буквально** верна на момент передачи.

   **Правила при передаче:**

   - Перед каждым крупным коммитом: читай SKILL.md и сверяй с реальным кодом — каждое утверждение, особенно имена функций/файлов/порядок аргументов.
   - Если видишь устаревшее утверждение — правь там, где оно лежит, не ставь «UPDATE:» в конце. Правка в тексте, не приписка.
   - Пример: «`fst-project-health-snap-md` calls `fs-project-health/scripts/run_all.py`» → если скрипт переименован, имя в SKILL.md меняется сразу же, в той же правке.
   - Когда скилл передаётся как **семейство** (основной + сателлиты), CHANGELOG пишется **один раз** в родительском скилле, а сателлиты ссылаются на него через `../<parent>/CHANGELOG.md`. Не дублировать — иначе будут расхождения.
   - Архитектурные инварианты («это правило никогда не должно нарушаться без обсуждения», например «snapshot_timestamp — единственный источник момента времени в HTML-шапке», «MD = полный source of truth», «каждый caller передаёт `--generator` своё имя») идут в **отдельную секцию** корневого CHANGELOG, **а не** в «Историю» версий. Секция инвариантов — это контракт, который переживает бампы версий; история версий — журнал, в котором они объясняются. Сателлит не должен **пересказывать** инвариант в своей SKILL.md/README.md — он ссылается на родительский CHANGELOG. Дублирование инварианта в двух местах через 5 версий порождает расхождения, которые невозможно поймать grep-ом (формулировки чуть разные, смысл тот же).

9. **Всегда проверяйте `project_id` vs `accountid`** в коде который использует MCP. Это разные сущности (Pitfall #159 `fst-project-health`):
   - `project_id` = ID проекта (например, `4595`)
   - `accountid` = ID исполнителя (например, `120872`)
   - В `fetch_with_cache(project_id=...)` нужно передавать именно project_id, не accountid.

   **Audit procedure:**
   ```bash
   grep -rn "project_id=accountid\|project_id = accountid" scripts/
   ```

   User: «projectID=accountID Это критическая ошибка Это разные сущности». Не путать!

9. **Перед отправкой developer-request MCP** проверить фильтры через live-probe. `list_views` Description может быть неполный — фильтры могут работать, но не быть задокументированы (Pitfall #161/163).

   ```python
   # Live-probe фильтра
   r = mcp_call(sid, "get_view", {
       "entityName": "Project", "viewName": "ProjectResourcePlan",
       "filters": {"accountid": 120872},  # не упомянут в description, но работает!
       "limit": 5,
   })
   ```

10. **При сборке developer-request с примерами кода — каждую команду нужно проверить через live-call.** Не выдумывать форматы запросов/ответов. User: «это разные сущности» — пример с `project_id=accountid` был синтаксически корректен, но семантически бессмыслен.

    Правильный подход — каждый пример в developer-request маркировать как "verified live" или "unverified — please confirm".
