# Шаблон feedback-письма разработчикам MCP

> Когда за 2+ часа probe-ов проблема не решается — пора собирать фидбек
> напрямую команде, которая поддерживает MCP-сервер. Этот шаблон
> проверен 2026-08-07 (см. `Вопросы по MCP 2026_08_07.md` — ответ
> дал полезные уточнения по MetaModel API).

## Когда писать

- **Не пиши** сразу — начни с `mcp_probe.py` / `mcp_config.py` / Python-прокси.
- **Пиши** после 2+ часов probe-ов без прогресса, или когда находишь **>3** проблем, которые блокируют основную функцию скилла.

## Структура документа

### 1. Раздел 1 — DATA, blockers (≤7 пунктов)

Это самый важный раздел. Для каждого факта:

| Поле | Что писать |
|------|-----------|
| **Куда нужно** | Раздел и пункт отчёта, куда эти данные должны идти. Например: «Раздел 6, показатель 1 — прогноз финансового результата». |
| **Что именно не получили** | Какие данные не удалось получить. Например: «`Point.PlanSum/ForecastSum/FactSum` — все три поля = `None` для живой КТ». |
| **Пример запроса** | Полный `mcp_call` или `mcp_probe --args '{...}'`. Без этого — разработчики не смогут повторить. |
| **Реальный ответ** | JSON ответа сервера. Полный (с заголовками), не выжимка. |
| **Workaround** | Что ты делаешь в отчёте вместо этого. Например: «В отчёте помечаю «Нет данных» + использую `ProjectHealthCostMy` (агрегат) как fallback». |

### 2. Обязательно positive case

**Включи минимум 1 положительный кейс**, чтобы разработчики видели как «working» выглядит. Без этого они не знают правильно ли они починили.

Пример: «`ProjectHealthCostMy` для 504-595 — ВСЕ поля заполнены: `inplan=6 497 500`, `infact=2 500 000`, `outplan=75 000`, `outfact=3 244 415`, `fact=-744 415`, `plan=6 422 500`, `forecast=-221 860`, `deviation=-6 644 360`. Это «working» — другие view тоже должны так работать».

### 3. Раздел 2 — UX, non-critical (≤7 пунктов)

Невудобства, **не блокеры**. Например:

- `find_entity` не возвращает MetaModel-записи (хотя они есть)
- `find_entity` не принимает `entityName` как фильтр
- `get_view` для MetaModel говорит «нет view»
- `Point.ParentFullName` всегда `null` в view (приходится N+1 через `get_entity_data`)

Аргументация: «Это ускоряет / упрощает / удешевляет работу скилла. Не блокирует, но добавляет friction».

### 4. Anti-claims (что НЕ писать)

Если вы не проверили живой probe — НЕ пишите:

- **«`Point.PlanSum` возвращает X»** — пока не сделаете `get_entity_data(Point, "<id>")` и не увидите значение
- **«`Project.PlanSum` НЕ существует»** — пока не сделаете `describe_entity(Project, "<id>")` и не увидите схему
- **«`MetaModel` мёртвая для read»** — пока не попробовали `get_entity_data("metamodel", "<Name>")` (lowercase, string data_id)
- **«Только `find_entity` для MetaModel»** — пока не проверили что `get_entity_data` действительно не работает

Причина: документация / recipe может устареть. Разработчики дадут «правильный» ответ, который ты не сможешь проверить — и они не понимают что ты описал несуществующую проблему.

### 5. Файлы и шаблоны

- **Сохранить:** `~/Вопросы по MCP YYYY_MM_DD.md` (в корне профиля) — пользователь получает через `MEDIA:`.
- **Копия в скилл:** `references/mcp-feedback-YYYY-MM-DD.md` в уместном скилле (в нашем случае — в `fst-project-health/references/`), чтобы будущая сессия **не пере-обнаруживала те же проблемы**.
- **Связь с скиллом:** в `references/` ссылка на основную recipe (`meta-model-pitfalls.md`, `mcp-quirks.md`, и т.д.) с пометкой «обновлено после feedback-сессии YYYY-MM-DD».

## Чек-лист финального письма

- [ ] **Все примеры запросов реальные** — выполнены через `mcp_probe.py` сразу, без переписывания по памяти.
- [ ] **Все ответы скопированы raw** — не пересказаны, а именно скопированы (`{"jsonrpc": "2.0", "id": 1, ...}`).
- [ ] **Есть хотя бы 1 положительный кейс** — показать «что работает».
- [ ] **Anti-claims соблюдены** — не делать заявлений без live-проверки.
- [ ] **Все запрашиваемые данные названы по-человечески** — не «XYZ123», а «прогноз финансового результата».
- [ ] **Workaround для каждого блокера** — чтобы разработчики понимали что ты не «сломал» скилл, а скилл работает с workaround.
- [ ] **≤7 блокеров** — если больше, разбей на несколько писем или приоритизируй.
- [ ] **Файл в корне профиля** — `~/Вопросы по MCP YYYY_MM_DD.md` (видно пользователю).
- [ ] **Копия в `references/`** — `references/mcp-feedback-YYYY-MM-DD.md` (видно будущим сессиям).

## Исторический пример

Самый свежий пример — `Вопросы по MCP 2026_08_07.md` в корне профиля.
Содержит 7 блокеров (MetaModel API, трудозатраты, финрезультат, бюджет, платежи, КТ, фин.поля) + 7 неудобств. Разработчики ответили по MetaModel за 1 день — после фикса были обнаружены 3 новые записи (`Title`, `Version`, `CoreVersion`), которые раньше были недоступны.

В `fst-project-health/references/meta-model-pitfalls.md` — живая методика после фикса. **Не игнорируй этот feedback-loop** — это самая ценная часть процесса.
