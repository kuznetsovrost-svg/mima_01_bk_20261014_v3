# Запрос разработчикам MCP

**Тема:** Добавление возможности фильтрации в `ProjectResourcePlan` по полю `accountid` и по диапазону дат `planning_date`

**От:** Команда `fst-project-health` v1.0.0
**Дата:** 2026-09-02

---

## 1. Контекст

В рамках реализации индикатора 6.7 «Есть исполнители у которых план в сумме с др.активностями > 100%» нам необходимо выявлять перегрузку исполнителей по **всем** проектам, в которых они участвуют (а не только по текущему).

В настоящее время `get_view(Project/ProjectResourcePlan)` с фильтром `{"accountid": <id>}` **работает корректно** и возвращает данные только по нужному исполнителю. Спасибо!

Однако обнаружена проблема: **не работает фильтр по диапазону дат** для поля `planning_date`.

---

## 2. Проблема

### Текущее поведение

При вызове:
```python
get_view(viewName="ProjectResourcePlan", filters={
    "accountid": 120872,
    "StartDate": "2026-09-01",
    "EndDate": "2026-12-31"
}, limit=100)
```

**Результат:** возвращаются **100 строк** за **разные годы** (2022-2026), а не только за указанный период 2026-09-01..2026-12-31.

**Ожидаемое поведение:** возвращаются только строки, где `planning_date ∈ [2026-09-01, 2026-12-31]`.

### Проверка

Без фильтра дат (только accountid):
```
Без фильтра: 100 строк (за все годы)
С фильтром StartDate/EndDate: 100 строк (те же самые)
```

Строки не фильтруются — MCP просто игнорирует `StartDate/EndDate`.

---

## 3. Зачем это нужно

### 3.1. Экономия трафика

Сейчас для одного исполнителя мы получаем **до 100 строк** (если он работал в разных проектах несколько лет). Из них для индикатора 6.7 нужны только **последние 2-3 месяца** (текущая дата → конец проекта).

Оптимизация: фильтрация на стороне MCP уменьшит трафик в **5-10 раз**.

### 3.2. Корректность данных

Мы фильтруем даты **в Python** после получения. Это работает, но:
- Тратим трафик на лишние строки
- Можем получить `limit` строк из прошлых лет и потерять текущие

### 3.3. Скорость

На проектах с 10-15 исполнителями каждый запрос занимает **5-6 секунд**. Если данные будут фильтроваться на стороне MCP, скорость может вырасти.

---

## 4. Что мы просим

### 4.1. Добавить поддержку фильтра по `planning_date` для `ProjectResourcePlan`

Должно работать одно из:

**Вариант A** (предпочтительный): фильтр по диапазону дат в параметре `filters`:

```python
get_view(viewName="ProjectResourcePlan", filters={
    "accountid": 120872,
    "planning_date_from": "2026-09-01",   # новое поле
    "planning_date_to": "2026-12-31"      # новое поле
}, limit=200)
```

**Вариант B**: фильтр через стандартные параметры `StartDate`/`EndDate`, но **на уровне поля `planning_date`**:

```python
get_view(viewName="ProjectResourcePlan", filters={
    "accountid": 120872,
    "StartDate": "2026-09-01",   # должно фильтровать по planning_date
    "EndDate": "2026-12-31"
}, limit=200)
```

### 4.2. Критерии приёмки

1. **Фильтрация работает** для всех 4 наших тестовых проектов (504-595, 503-434, 503-152, 504-314)
2. **Производительность**: не медленнее текущего варианта
3. **Совместимость**: не сломать существующее поведение с фильтром `ProjectId`

## Приложение A: текущая реализация в нашем коде

В индикаторе 6.7 мы делаем:
```python
# ШАГ 1: Получаем список исполнителей ТЕКУЩЕГО проекта (с их accountid)
current_rows = fetch_with_cache(
    sid, "Project", "ProjectResourcePlan",
    filters={"ProjectId": project_id},  # <-- фильтр по ПРОЕКТУ
    project_id=project_id,
    limit=2000,
)
# Получаем username -> accountid

# ШАГ 2: Для каждого исполнителя запрашиваем ВСЕ его проекты
#         (используем фильтр по ИСПОЛНИТЕЛЮ, не по проекту!)
for username, accountid in real_users.items():
    if not accountid:
        continue
    user_rows = fetch_with_cache(
        sid, "Project", "ProjectResourcePlan",
        filters={"accountid": accountid},  # <-- фильтр по ИСПОЛНИТЕЛЮ
        project_id=project_id,  # это project_id, не accountid
        limit=2000,
    )
    all_rows.extend(user_rows)

# Потом фильтруем по дате в Python
for row in all_rows:
    d = _parse_iso_date(row.get("planning_date"))
    if not d or d < effective_start or d > end_date:
        continue
```

После исправления хотелось бы:

    sid, "Project", "ProjectResourcePlan",

        "accountid": accountid,

## Приложение B: Глоссарий (чтобы не путать)

- **`project_id`** — уникальный ID **проекта** (например, 4595 для 504-595)
  - Используется в `filters={"ProjectId": project_id}`
  - В `mcp_call(sid, "get_entity_data", {"data_id": str(project_id)})`
- **`accountid`** — уникальный ID **пользователя/исполнителя** (например, 120872 для Кузнецова)
  - Используется в `filters={"accountid": accountid}` (!!!)
  - Это НЕ project_id! Это другой тип сущности.

Не путать! Разработчики в полях модели:
- В `Project`: `ProjectId`, `Code`, `Name`, ...
- В `ProjectResourcePlan` (связь): `activityid` (=ProjectId), `accountid` (=UserId), ...
