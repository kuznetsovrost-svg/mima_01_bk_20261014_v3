## 1.1 Титул системы — ✅ РЕШЕНО (live-probe 2026-08-07)

Подсказка разработчиков: `name` — PK, использовать `get_entity_data(data_id=<Name>)`.

**Что я проверил:**
- `get_entity_data(data_id="Title")` — Pydantic error (`data_id: int`).
- `describe_entity(data_id="new")` подтвердил: PK = `Name` (text).
- Реально рабочий: `get_entity_data(entityName="metamodel", data_id="Title")` (lowercase `metamodel`!).
- На сервере 3 записи: `Title`, `Version`, `CoreVersion`.
- Серверного времени в MetaModel **нет** (все ключи вернули «Запись не найдена»).

**Использование в скилле:**
```python
from mcp_config import mcp_init, mcp_call
sid, _ = mcp_init()
data = mcp_call(sid, "get_entity_data", {
    "entityName": "metamodel", "data_id": "Title"
})
# Value = "Копия прода для MCP"
```

**Изменения на бэкенде (2026-08-07):**
- `entityName` теперь `metamodel` (lowercase), а не `MetaModel` (CamelCase).
- `data_id` принимает строку (не только int).

Подробности: `references/meta-model-pitfalls.md`.

## 1.7 `ProjectHealthCostMy.outplan`/`outfact` неясны — ✅ РЕШЕНО

| Поле `ProjectHealthCostMy` | Что это | Заменено на |
|----|----|----|
| `inplan` | Плановый доход на тек. дату | `ProjectBudgetCompleteBusiness.actplansum` (по датам) |
| `infact` | Фактический доход на тек. дату | `actfactsum` |
| `outplan` | Плановый расход на тек. дату | `payplansum` |
| `outfact` | Фактический расход на тек. дату | `payfactsum` |
| `outallplan` | Плановый расход по оконч. | `payForecast` (если ввести формулой) |
| `outallforecast` | Прогноз расхода по оконч. | `payforecastsum` |
| `plan` | Плановый фин. результат по оконч. | — (нет аналога) |
| `forecast` | Прогноз фин. результата по оконч. | `actforecastsum - payforecastsum` |
| `deviation` | `forecast - plan` | — |
| `devcost` | Δ расхода на тек. дату | `payfactsum - payplansum` |
| `devallcost` | Δ расхода по оконч. | `payforecastsum - payplansum` |

**`projectprofileid` = 1 (Базовый)** — означает, что `ProjectHealthCostMy` агрегирует по профилю, а не по конкретному проекту. В этом и была проблема семантики.

**Рекомендация:** объявить `ProjectHealthCostMy` **DEPRECATED** в пользу `ProjectBudgetCompleteBusiness`.

## 2.2 Раздел 4 показатель 4 — план/факт по трудозатратам без `as_of_date`

**Где блокирует:** Раздел 4 показатель 4 (актуальность трудозатрат).

**Проблема:** `ProjectResourcePlan` имеет `planning_date`, но **нет** `as_of_date`/`as_of_datetime` — то есть непонятно, **когда** был зафиксирован план/факт. Для «актуальности» данных (разрыв план-факт > 10 дней) обычно смотрят на **текущую дату** относительно `last_plan_date` и `last_fact_date`.

**Как воспроизвести:**
```python
data = mcp_call(sid, "get_view", {
    "entityName": "Project",
    "viewName": "ProjectResourcePlan?ProjectId=4595",
    "limit": 500,
})
# 149 строк, planning_date есть, но:
# - когда этот план был зафиксирован?
# - когда этот факт получен?
# - какая версия данных?
```

**Что хотите:** добавьте в `ProjectResourcePlan` колонки `plan_created_at` и `fact_created_at` (datetime), и/или `as_of_date` — чтобы можно было отслеживать «устарел ли план/факт».

**Критичность:** Средняя. Сейчас для разрыва берём `today - last_plan_date`. Если план менялся 5 раз — мы увидим только последний, и не поймём, что это «обновлённый план», а не «старый факт».

## 2.3 Серверное время

**Где блокирует:** Раздел 7 (технические данные), сборка отчёта.

**Проблема:** В `MetaModel` нет серверного времени. `mcp_init` `serverInfo` не содержит `time`. У нас есть только `datetime.now()` локально.

**Что пробовал:**
- `get_entity_data(metamodel, "CurrentDateTime")` — «Запись не найдена».
- `get_entity_data(metamodel, "ServerTime")` — «Запись не найдена».
- `get_entity_data(metamodel, "Now")` — «Запись не найдена».

**Что хотите:** либо отдельный `ServerTime` в `mcp_init` response, либо `find_entity("CurrentTime")` с реальной записью.

**Критичность:** Низкая. Для синхронизации часов между Форсайт и клиентом можно сделать round-trip `datetime.now()` → `mcp_init` → разница.
