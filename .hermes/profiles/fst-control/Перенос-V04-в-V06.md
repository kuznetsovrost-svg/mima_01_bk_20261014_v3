# Комплексная оценка здоровья проекта по ключевым показателям

## Общее описание (readme)

Скилл реализует работу с проектами информационной системы ПМ «Форсайт» через её MCP-сервер. По результатам работы скилла формируется отчёт, содержащий итоговые сведения, позволяющие оценить здоровье конкретного проекта с точки зрения методологии проектного управления. Скилл сообщает итоговые сведения о соблюдении сроков контрольных точек проекта, проверяет полноту заполнения данных проекта, проверяет актуальность прогнозов по проекту, актуальность данных по проекту, оценивает финансовый статус проекта. Дополнительно присылаются технические данные (дата, время, имя системы, имя пользователя). Отображение данных проектов ограничено правами пользователя в основной системе «Форсайт».

### Структура отчёта

Отчёт состоит из 7 разделов:

1. **Поиск проекта** — определение ProjectId по Code/Name (если не передан).
2. **Заголовок отчёта** — метаданные (имя проекта, дата/время).
3. **Здоровье по срокам КТ** — отклонение PlanDate ↔ ForecastDate.
4. **Полнота заполнения проекта** — 5 показателей (Куратор, РП, Паспорт, трудозатраты, платежи).
5. **Актуальность прогнозов КТ** — ForecastDate < today без факта.
6. **Финансовый статус** — 3 показателя через view `ProjectHealthCostMy`.
7. **Технические данные** — пользователь, версия MCP, URL.
8. **Индикатор в заголовке** — общий вердикт по 4 содержательным разделам (3, 4, 5, 6).

### When to Use

Загружай, когда пользователь задаёт вопросы:
- упоминает «Форсайт», «ИСУП» и называет конкретный проект по `Code` / `ProjectId`;
- спрашивает «насколько проект просрочен», «что с сроками», «здоровье проекта»;
- просит «замечания по срокам», «почему красный», «диагностика проекта»;
- хочет план-факт анализ по КТ (контрольным точкам) проекта;
- хочет узнать актуальность данных по трудозатратам проекта;
- хочет узнать актуальность данных по прогнозам КТ;
- спрашивает «что с бюджетом», про финансовый результат проекта;
- спрашивает про полноту заполнения данных проекта.

**Не загружай** для задач, не связанных с PM-системой «Форсайт».

### Формат вывода

- По умолчанию — HTML-файл через `MEDIA:` (шаблон в `templates/`).
- MD-шаблон отправляется только по явной просьбе «шаблон md» или «отчёт в формате md».
- В HTML-шаблоне поля «Статус» и «Цвет» в строках таблиц скрыты; строка подкрашивается фоном по статусу замечания (красный/жёлтый/голубой/без подкраски).

## 1. Порядок выбора (поиска) проекта

### Назначение шага
Для начала работы нужно в точности установить `ProjectId` проекта, о котором идёт речь. Если это не удаётся способами, перечисленными в подразделе «Получение данных», дальнейшая работа прекращается и выдаётся сообщение: «Проект не найден. Он либо не существует, либо у пользователя нет прав для доступа к нему в системе ПМ "Форсайт"». Ни в коем случае не придумывай ничего и не продолжай работу, если не удалось установить `ProjectId` и убедиться, что доступ к его данным есть.

### Получение данных

1. Если пользователь сразу не отправил в своём запросе `ProjectId` или `Code` проекта, запроси их.
2. Варианты:
   - **Вариант A:** пользователь дал `ProjectId`, проект с таким `ProjectId` существует и доступен пользователю → переходим к разделу 2.
   - **Вариант B:** пользователь сообщил `Code` проекта → запрос к MCP:
     ```
     get_view(Project, MyProject)
     fallback: get_view(Project, AllProject)
     ```
     Извлечь: `ProjectId`, `Code`, `Name`.
     Пример кода — в `scripts/find_project_by_code.py`.
   - **Вариант C:** `Code` неоднозначен → вызвать скилл `project-search`, который должен вернуть точный `ProjectId` или извещение, что проект не найден.
   - **Вариант D:** пользователь сообщил `Name` или часть `Name` → вызвать скилл `project-search`, который должен вернуть точный `ProjectId` или извещение, что проект не найден.

### Интерпретация данных
Делается заключение — удалось ли получить корректный `ProjectId` проекта. Если не удалось — скилл прекращает работу.

### Вывод данных
Если не удалось установить корректный `ProjectId`, скилл выдаёт сообщение «Проект не найден». Ответное сообщение делается в чате, подготовка отчёта не осуществляется. Работа скилла на этом прекращается.

## 2. Формирование заголовка отчёта

### Назначение шага
На данном шаге готовятся данные для заполнения заголовка отчёта.

### Получение данных
К этому моменту должен быть известен `ProjectId`. Через MCP получаем значение поля `Name` для проекта, а также дату и время построения отчёта. Пример кода — в `scripts/build_report_header.py`.

### Интерпретация данных
Данные не интерпретируются, выводятся как есть.

### Вывод данных
Полученные данные возвращаются в чат, если от пользователя был прямой запрос именно на них. Для построения отчётов данные выводятся в плейсхолдеры шаблонов:
- `Name` → `{hero.title}`;
- дата и время → `{hero.datetime}`.

Шаблоны отчётов в форматах md и html хранятся в каталоге `templates/`.

## 3. Оценка здоровья проекта с точки зрения сроков

### Назначение шага
На данном шаге производится анализ выполнения сроков КТ и формируются замечания. Анализируются только те КТ проекта, которые подтверждаются документом «Паспорт» (поле «Утверждающий документ» у КТ). Само наличие присоединённого паспорта к проекту как файла здесь не проверяется — это делается в разделе 4 показатель 3.

### Получение данных

1. К этому моменту должны быть известны `ProjectId` проекта и значения `Code`, `Name`.
2. Получить список КТ (Point) проекта:
   ```
   get_view(Point, AllMyPoint)
   └─ фильтр по ParentCode == "<project_code>"
   ```
3. Отфильтровать полученный список КТ для поиска замечаний:
   - если нет `PlanDate` или `ForecastDate` → пропустить;
   - если `FactDate` заполнена → пропустить (КТ завершена, рассматривать не требуется);
   - если `PlanDate == ForecastDate` → пропустить (нет расхождения);
   - иначе → точка попадает в замечания.

### Интерпретация данных

1. Пороги:
   - Пороги для классификации КТ как замечания — `scripts/point-timing-remark-thresholds.py`.
   - Пороги для оценки здоровья проекта — `scripts/point-timing-health-thresholds.py`.

2. Классифицировать каждое замечание:
   ```
   diff_days = (ForecastDate - PlanDate).days      # в календарных днях
   abs_diff = abs(diff_days)

   if   abs_diff > REMARK_THRESHOLDS["critical"]["min_diff_days"]:
        color = "Красный";  status = "Критическое"
   elif abs_diff > REMARK_THRESHOLDS["substantial"]["min_diff_days"]:
        color = "Жёлтый";   status = "Существенное"
   else:
        color = "Синий";    status = "Информационное"
   ```

3. Получить исполнителя для каждого замечания:
   - `ResponsibleId` (bigint) уже есть в строке view;
   - `Responsible` (display-ФИО) уже есть в строке view;
   - отдельный запрос к User API не нужен.

4. Оценить здоровье проекта по статусам КТ:
   ```
   critical_count = число замечаний с color == "Красный"

   if   critical_count >= HEALTH_THRESHOLDS["sick"]["min_critical_count"]:
        health = "БОЛЕН";            health_color = "КРАСНЫЙ"
   elif critical_count >= HEALTH_THRESHOLDS["attention"]["min_critical_count"]:
        health = "ТРЕБУЕТ ВНИМАНИЯ"; health_color = "ЖЁЛТЫЙ"
   else:
        health = "ЗДОРОВ";           health_color = "—"
   ```
   Пример — в `scripts/project-health-summary.py`.

5. Реакция в разных ситуациях:

| Случай | Поведение |
|--------|-----------|
| У проекта нет ни одной КТ с расхождением дат | `health = "ЗДОРОВ"`, таблица пустая |
| `PlanDate` пустое, `ForecastDate` есть | КТ пропускается (нельзя вычислить diff) |
| `PlanDate == ForecastDate` | КТ пропускается (нет расхождения) |
| `FactDate` заполнена | КТ пропускается (завершена, замечание неактуально) |
| diff ровно 2 дня | `color = "Синий"` (порог «>2» строгий) |
| diff ровно 10 дней | `color = "Жёлтый"` (порог «>10» для «Красный» строгий) |
| diff = 11 дней | `color = "Красный"` |
| Проект имеет ≥ 3 критических замечаний | `health = "БОЛЕН"` (порог `≥ 3` нестрогий) |
| В view нет проекта (нет доступа) | Сообщить пользователю, предложить проверить `Code`/`ProjectId` |

6. Сортировка замечаний при выводе:
   ```python
   REMARK_SORT = ["plan_date_asc", "diff_desc"]   # сначала по PlanDate, затем по убыванию diff
   ```

### Вывод данных
Данные выводятся в отчёт в формате Markdown либо HTML (шаблоны — в `templates/`). Для подготовки данных используются плейсхолдеры, указанные ниже.

Сводка раздела: `{t1.collapsible.period.preview}` — конкатенация:
- слово-вердикт: «Болен» / «Требует внимания» / «Здоров»;
- «, »;
- число КТ, попавших в превалирующую категорию (остальные КТ не учитываются).

Примеры: `Болен, 3 КТ`, `Требует внимания, 4 КТ`, `Здоров, 12 КТ`.

- Статус раздела: «Болен» / «Требует внимания» / «Здоров».
- Цвет заголовка раздела: «Красный» / «Жёлтый» / «Зелёный».
- Итог по замечаниям: `{число критических}, {число существенных}, {число информационных}`.

| Колонка | Плейсхолдер для строк таблицы |
|---------|-------------------------------|
| Номер | `{r[N].nmb}` |
| Цвет | `{r[N].color}` |
| Статус | `{r[N].status}` |
| Код (Code) | `{r[N].code}` |
| Наименование (Name) | `{r[N].name}` |
| План (PlanDate) | `{r[N].planDT}` |
| Прогноз (ForecastDate) | `{r[N].forecastDT}` |
| Факт (FactDate) | `{r[N].factDT}` |
| Исполнитель | `{r[N].exename}` |

**Особенности HTML-шаблона:**
- В строках таблицы (tbody) поля «Статус», «Цвет» и «Факт» не отображаются.
- Строка подкрашивается цветом в соответствии со статусом её замечания:
  - «Критическое» → фон красный;
  - «Существенное» → фон жёлтый;
  - «Информационное» → фон голубой.

## 4. Проверка полноты заполнения проекта

### Назначение шага
Проверяется ряд показателей, существенных для оценки состояния проекта. Формируется таблица фиксированного размера из заголовка и 5 строк. Состав строк:
1. «Куратор назначен»;
2. «РП назначен»;
3. «Паспорт готов на стадии Инициирование»;
4. «Актуальность данных проекта по трудозатратам»;
5. «Корректность заполнения графика платежей проекта».

Формат таблицы: Номер / Показатель / Результат / Детализация / Статус.

### Получение данных

#### Граф состояний ЖЦ проекта
```
1) Пресейл
2) Инициирование
3) Подготовка
4) Реализация
5) Завершение
6) Архив
```

Это **линейный граф** — каждая следующая стадия «старше» предыдущей. Для проверок «≤ N» используется **порядковый номер** стадии (1..6).

#### Показатель 1. «Куратор назначен»
Проверка по `OwnerId`. Пример — `scripts/OwnerID-check.py`.

Особенности:
- Поле: `Project.OwnerId` (bigint, SingleSelectRole).
- Title: **«Куратор»** — не «Owner» и не «Владелец».
- `IsRequired=True`, `IsVisible=True`.
- `ItemType: Role`.
- Возможные значения: массив `[{value: <userId>, display: "<ФИО>"}]`, может быть пустым `[]`.

#### Показатель 2. «РП назначен»
Проверка по `LeaderId`. Пример — `scripts/LeaderID-check.py`.

Особенности `LeaderId`:
- `IsRequired=false` (необязательное), `IsReadonly=true`, `IsEditable=false` — система выставляет значение автоматически, но оно отображается и попадает в отчёт.
- Поле: `Project.LeaderId` (bigint, SingleSelectRole).
- Title: **«Руководитель»** — НЕ «РП».
- `IsRequired=false`, `IsVisible=true`, `IsReadonly=true`.
- `ItemType: Role`.
- Возможные значения: массив `[{value: <userId>, display: "<ФИО>"}]`, может быть пустым `[]`.

Замечания:
- `describe_entity(Project, data_id=<id>)` возвращает только схему без значений полей. Для значений — `get_entity_data`.
- Имя поля в API — `OwnerId`, но Title = «Куратор».
- `SingleSelectRole` может вернуть пустой массив `[]` — это означает «роль не назначена».
- `display` в значениях содержит ФИО с пробелом на конце (нормально для «Форсайт»).

#### Показатель 3. «Паспорт готов на стадии Инициирование»
Этот показатель **составной** — требует выполнения **двух** условий:
- (а) Паспорт (документ) прикреплён к проекту;
- (б) Состояние ЖЦ проекта ≤ «Инициирование» (т.е. «Пресейл» или «Инициирование»).

Если хотя бы одно не выполнено → «Нет». Если оба выполнены → «Да».

Пример — `scripts/Passport-check.py`.

```
1. Получить данные проекта: get_entity_data(Project, data_id=<projectId>)
   └─ properties.ActivityPhaseId.value.display  → название стадии
   └─ properties.ActivityPhaseId.value.value    → ID стадии

2. Определить порядковый номер стадии:
   PHASE_ORDER = {
       "Пресейл": 1, "Инициирование": 2, "Подготовка": 3,
       "Реализация": 4, "Завершение": 5, "Архив": 6,
   }
   current_phase = PHASE_ORDER.get(display, 999)  # 999 = неизвестно

3. Условие (б) — паспорт обязателен только с «Инициирование»:
   phase_requires_passport = current_phase >= 2

   ⚠️ Логика v2 (исправлено 2026-08-06): паспорт требуется только на
   стадии «Инициирование» и позже. На стадии «Пресейл» (current_phase < 2)
   паспорт обычно ещё не прикрепляется — это НОРМА, не замечание.

4. Условие (а) — наличие паспорта:
   docs = get_view(DocumentFile, DocumentFileViewAll)
   passport_attached = False
   for r in docs["data"]:
       if (EntityTitle == "Проект"
           and "<project_code>" in (DataName или "")
           and "паспорт" in (DocumentName или "").lower()):
           passport_attached = True
           break

5. Итог (зависит от стадии ЖЦ):
   if passport_attached:
       result = "Да"
       detail = f"Паспорт прикреплён, стадия «<phase_display>»"
   elif not phase_requires_passport:
       # Пресейл (или неизвестно) — паспорт НЕ обязателен
       result = "Да"
       detail = (f"Стадия «<phase_display>» (Пресейл/до-Инициирования) — "
                 f"паспорт на этой стадии не требуется")
   else:
       # Инициирование и позже — паспорт ОБЯЗАН быть
       result = "Нет"
       detail = (f"паспорт не прикреплён на стадии «<phase_display>» "
                 f"(обязателен с «Инициирование») — критическое замечание")

6. Строка таблицы:
   | 3 | Паспорт готов на стадии Инициирование | <result> | <detail> |
```

#### Показатель 4. «Актуальность данных проекта по трудозатратам»

Семантика:
- **Прогноз** — записи `ResourcePlanningKp` (`planning_date <= today`).
- **Факт** — записи `ResourcePlanning` (`planning_date <= today`).
- **today** — текущая дата.

Правила:

| # | Условие | Результат |
|---|---------|-----------|
| 1 | Нет ни прогноза, ни факта | **Да** |
| 2 | Прогноза нет, факт есть | **Да** (факт не требовалось заводить) |
| 3 | Есть прогноз (`last_plan_date`), нет факта | **Нет** |
| 4 | Прогноз + факт, `last_fact_date ≥ last_plan_date`, `last_fact_date − last_plan_date ≤ EFFORT_GAP_THRESHOLD_DAYS` | **Да** |
| 5 | Прогноз + факт, `last_fact_date < last_plan_date`, `today − last_plan_date ≤ EFFORT_GAP_THRESHOLD_DAYS` | **Да** |
| 6 | Прогноз + факт, `last_fact_date < last_plan_date`, `today − last_plan_date > EFFORT_GAP_THRESHOLD_DAYS` | **Нет** |
| 7 | Прогноз + факт, `last_fact_date ≥ last_plan_date`, `last_fact_date − last_plan_date > EFFORT_GAP_THRESHOLD_DAYS` | **Нет** |

`EFFORT_GAP_THRESHOLD_DAYS` — порог допустимого разрыва, вынесен в `scripts/effort-gap-threshold.py` (по умолчанию 10).

Ключевая идея: «Нет» возвращается только если **план был, но факт не заведён вовремя**.

Алгоритм:
```
1. Получить прогнозы:
   kp_view = get_view(ResourcePlanningKp, ...)
   └─ Если view недоступен (403), fallback: get_entity_data по известным id
   plan_dates = [r.planning_date for r in kp if r.planning_date <= today]
   if not plan_dates:
       plan_present = False
   else:
       plan_present = True
       last_plan_date = max(plan_dates)

2. Получить факт:
   rp_view = get_view(ResourcePlanning, ...)
   └─ ВНИМАНИЕ: ResourcePlanning привязан через ActivityId, не через ProjectId!
   fact_dates = [r.planning_date for r in rp
                 if r.planning_date <= today
                 and r.ActivityId in <project activity ids>]
   if not fact_dates:
       fact_present = False
   else:
       fact_present = True
       last_fact_date = max(fact_dates)

3. Применить правила (см. таблицу выше).
```

Пример — `scripts/Effort-check.py`.

Ограничения данных:
- Оба view (`ResourcePlanning`, `ResourcePlanningKp`) **закрыты 403** для обычного пользователя.
- `ProjectHealthWorkload` (агрегат помесячно) — открыт, но содержит `plan_m`/`fact_m` как **сумму часов за месяц**, а не отдельные даты. Для строгой проверки нужны детальные записи.

#### Показатель 5. «Корректность заполнения графика платежей проекта»

Семантика:
- Показатель определяется на уровне **ПРОЕКТА**, а не контракта. К проекту может быть привязано **несколько контрактов**. Привязка видна через строковое поле `ParentFullName` в view контракта формата `"<project_code>. <project_name>"` (например, `"504-595. Космодром Жуковский внедрение ИСУП"`). Для каждого контракта считаем Δ отдельно, затем **складываем Δ по всем контрактам** — и сравниваем уже суммарную дельту с порогами.
- В «Форсайт» акты и оплаты — это **КТ (Point)**, а не отдельные сущности. У них есть поля `PlanSum`, `ForecastSum`, `FactSum`. Контракт — это `InContract` (доходный) или `OutcomeContract` (расходный), а его КТ привязаны через `ParentId` = `ActivityId` контракта.

| Понятие | Что это | Где |
|---------|---------|-----|
| **Контракт** | Запись в `InContract` / `OutcomeContract` с `Code` и `RealSum` | `InContract.RealSum` |
| **Акт** | КТ с `ParentId=ActivityId контракта`, в имени содержит «Акт» | `Point.FactSum`/`ForecastSum` |
| **Оплата** | КТ с `ParentId=ActivityId контракта`, в имени «Оплата»/«Платёж» | `Point.FactSum`/`ForecastSum` |
| **Связь контракт↔проект** | `ParentFullName` в view (строка формата `"<project_code>. <project_name>"`) | В обоих случаях (InContract, OutcomeContract) |

Логика проверки — двухуровневая.

**Уровень 1: контракт.** Для каждого контракта:
```
effective_sum = FactSum if FactSum > 0 else ForecastSum
Δ_contract = |Σ актов_effective − Σ оплат_effective|
```

**Уровень 2: проект.** Суммируем дельты по всем контрактам:
```
Δ_project = Σ Δ_contract (по всем контрактам проекта)
```

Важно:
- Складываем **абсолютные** Δ, а не сначала суммы. Расхождения по разным контрактам **не компенсируют** друг друга.
- **Смешанная сумма**: `FactSum` имеет приоритет (если > 0), иначе `ForecastSum`.

Правила (пороги — в `scripts/Financial-deviation-threshold.py` как `PAYMENT_DEVIATION_THRESHOLDS`):

| # | Условие | Результат |
|---|---------|-----------|
| 1 | Нет ни актов, ни оплат | **Да** (платежей нет — нечего проверять) |
| 2 | `|Σ актов − Σ оплат| = 0` | **Да** |
| 3 | `0 < |Σ актов − Σ оплат| < порог_информ` | **Нет / Информационное** |
| 4 | `порог_информ ≤ |Σ актов − Σ оплат| < порог_существ` | **Нет / Существенное** |
| 5 | `|Σ актов − Σ оплат| ≥ порог_существ` | **Нет / Критическое** |

Алгоритм — пример в `scripts/Payments-graph-check.py`.

Уточнение по источнику данных:
- Акты и оплаты хранятся как **КТ (Point)** с `ParentId` = `ActivityId` контракта.
- Их финансы — в полях КТ: `PlanSum`, `ForecastSum`, `FactSum`.

```
1. Для каждого акта/оплаты определить ЭФФЕКТИВНУЮ сумму:
   if FactSum is not None and FactSum > 0:   effective = FactSum
   elif ForecastSum is not None and ForecastSum > 0: effective = ForecastSum
   else:                                        effective = 0

2. Σ актов  = sum(effective для всех актов контракта)
3. Σ оплат  = sum(effective для всех оплат контракта)
4. Δ = |Σ актов − Σ оплат|
```

Ограничения:
- Подход через `find_entity` для контракта → `get_entity_data` для каждой КТ — надёжный, но **медленный** (много запросов). Для больших проектов нужен batch-режим, который пока не реализован в MCP.
- View `ContractPlanSummaries` / `ContractPlanSummariesValue` остаются **закрыты 403** для обычного пользователя.

### Интерпретация данных
- Для показателей 1–4: «Нет» = критическое замечание.
- Для показателя 5: статус определяется через пороги (`scripts/Financial-deviation-threshold.py` → `PAYMENT_DEVIATION_THRESHOLDS`): «Критическое» / «Существенное» / «Норма».

## 5. Актуальность прогнозов по проекту

### Назначение шага
Сравнение прогнозных дат выполнения всех КТ с текущим моментом времени (исключая КТ с заполненной фактической датой). Если прогнозная дата КТ (без фактической даты) просрочена — формируется замечание.

### Получение данных
1. Должны быть известны `ProjectId`, `Code`, `Name`.
2. Получить список КТ:
   ```
   get_view(Point, AllMyPoint)
   └─ фильтр по ParentCode == "<project_code>"
   ```
3. Найти КТ с прогнозной датой раньше текущей и пустым фактом:
   ```
   overdue = []
   for p in project_points:
       forecast = parse_date(p.ForecastDate)
       fact    = parse_date(p.FactDate)
       if forecast and forecast < today and not fact:
           diff = (today - forecast).days
           overdue.append({**p, "diff_days": diff})
   ```
4. Отсортировать по убыванию `diff_days`.
5. Классифицировать:
   ```
   if diff_days >= OVERDUE_THRESHOLDS["critical"]["min_days"]:
       status = "Критическое"
   elif diff_days >= OVERDUE_THRESHOLDS["substantial"]["min_days"]:
       status = "Существенное"
   elif diff_days >= OVERDUE_THRESHOLDS["informational"]["min_days"]:
       status = "Информационное"
   ```

`OVERDUE_THRESHOLDS` — пороги для раздела 5, вынесены в `scripts/point-overdue-thresholds.py`.

Пример — `scripts/Points-forecast-relevance.py`.

### Интерпретация данных

| # | Дней просрочки (diff) | Статус | Цвет |
|---|----------------------|--------|------|
| 1 | ≥ `critical.min_days` | **Критическое** | Красный |
| 2 | `substantial.min_days` .. `critical.min_days − 1` | **Существенное** | Жёлтый |
| 3 | `informational.min_days` .. `substantial.min_days − 1` | **Информационное** | Синий |
| 4 | ≤ 0 (прогноз сегодня или в будущем) | Не попадает в таблицу | — |

Не путать с разделом 3 — там отклонение считалось как `|ForecastDate − PlanDate|`, здесь — `(today − ForecastDate).days`.

## 6. Финансовый статус проекта

### Назначение шага
Формируется таблица из заголовка и 3 строк, отражающих финансовое здоровье проекта:
1. Прогноз по окончании проекта показывает финансовый результат менее нуля: Нет/Да.
2. Отклонение текущей стоимости от плана на текущую дату более 1 млн. руб.: Нет/Да.
3. Прогноз по окончанию показывает уменьшение финансового результата от планового более чем на 2 млн. руб.: Нет/Да.

### Получение данных

#### Главная находка: view `ProjectHealthCost` (Здоровье по стоимости)
В UI «Форсайт» форма «Бюджет проекта, руб.» — это view **`ProjectHealthCost`** (или `ProjectHealthCostMy` для всех доступных проектов). Это **готовый агрегат**, который «Форсайт» считает на лету из 4 потоков:

1. Оплаты (доходы) — план и факт.
2. Оплаты (расходы) — план и факт.
3. Трудозатраты (прогноз) — часы × ставка × грейд сотрудника.
4. Трудозатраты (факт) — часы × ставка × грейд сотрудника.

Схема view `ProjectHealthCost` (15 колонок):

| API name | Заголовок | Что это |
|----------|-----------|---------|
| `projectid` | Идентификатор | ProjectId |
| `inplan` | Плановый доход (на текущую дату) | Σ план оплат (доходы) |
| `infact` | Текущий доход (на текущую дату) | Σ факт оплат (доходы) |
| `outplan` | Плановый расход (на текущую дату) | Σ план оплат (расходы) |
| `outfact` | Текущий расход (на текущую дату) | Σ факт оплат (расходы) |
| `fact` | Текущий финансовый результат | `infact − outfact` |
| `outallplan` | Плановый расход (по окончании проекта) | Σ план расходов (с трудозатратами) |
| `outallforecast` | Прогноз расходов (по окончании проекта) | Σ прогноз расходов (включает трудозатраты) |
| `plan` | Плановый финансовый результат (по окончании) | `inallplan − outallplan` |
| `forecast` | Прогноз финансового результата (по окончании) | **ЦЕЛЕВОЙ ПОКАЗАТЕЛЬ** |
| `deviation` | Отклонение финансового результата | `forecast − plan` |
| `devcost` | Отклонение расхода (на текущую дату) | `outfact − outplan` |
| `devallcost` | Отклонение расхода (по окончании) | `outallforecast − outallplan` |
| `projectprofileid` | Id профиля проекта | (как в `ProjectHealthWorkload`) |
| `projectprofilename` | Профиль | (как в `ProjectHealthWorkload`) |

#### Показатель 1. «Прогноз по окончании проекта показывает финансовый результат менее нуля»

```
1. Получить данные: get_view(Project, ProjectHealthCostMy)
   rows = mcp__fst_pmpractice__get_view(entityName="Project", viewName="ProjectHealthCostMy", limit=200)

2. Найти проект:
   project = next((r for r in rows.data if r.projectid == <ProjectId>), None)

3. Проверить наличие данных:
   if not project or "forecast" not in project:
       result = "Неопределено"

4. Извлечь прогноз: forecast = float(project["forecast"])

5. Применить правило:
   if forecast < 0:
       result = "Да";  detail = f"Прогноз фин.результата: {forecast:,.2f} ₽ — критическое замечание"
   else:
       result = "Нет"; detail = f"Прогноз фин.результата: {forecast:,.2f} ₽"

6. Строка таблицы:
   | 1 | Прогноз по окончании проекта показывает финансовый результат менее нуля | <result> | <detail> |
```

Пример (основной подход через агрегат) — `scripts/Forecasted-financial-result.py`.

**Альтернативный fallback:** если `ProjectHealthCostMy` пуст или недоступен — расчёт можно выполнить вручную через КТ-оплаты контрактов (mixed-логика: `FactSum` если > 0, иначе `ForecastSum`). Пример — `scripts/Fin-result-check.py`. Этот же подход используется в показателе 2.

#### Показатель 2. «Отклонение текущей стоимости от плана на текущую дату более 1 млн. руб.»

Семантика:

| Понятие | Что это | Где |
|---------|---------|-----|
| **Текущая стоимость** (mixed) | Σ доходов (FactSum если > 0, иначе ForecastSum) − Σ расходов (FactSum если > 0, иначе ForecastSum) | Расчёт через КТ контрактов |
| **План на текущую дату** | Сумма оплат/расходов, запланированных к сегодняшнему дню | `inplan − outplan` из `ProjectHealthCostMy` |
| **Δ** | `|текущая стоимость − план|` | — |

Важно: в `ProjectHealthCostMy` колонка `fact` (текущий фин. результат) — это **`infact − outfact`**, то есть **только факт**. По правилу показателя нужна **mixed**-сумма (факт где он есть + прогноз по незакрытым). Она **не хранится** в view напрямую — её нужно считать через КТ контрактов.

Алгоритм:
```
1. Получить план на текущую дату из ProjectHealthCostMy:
   view = get_view(Project, ProjectHealthCostMy, limit=200)
   project = next(r for r in view.data if r.projectid == <ProjectId>)
   plan = float(project.get("inplan") or 0) - float(project.get("outplan") or 0)

2. Получить доходные и расходные контракты проекта (см. показатель №5 раздела 4 — фильтр через `ParentFullName.startswith("<project_code>.")`):
   in_contracts  = [...]   # InContractMyProject с ParentFullName ⊇ project.Code
   out_contracts = [...]   # OutcomeContractMyProject с ParentFullName ⊇ project.Code

3. Получить все КТ проекта:
   points = get_view(Point, AllMyPoint, limit=3000)

4. Суммировать mixed-суммы (только КТ-оплаты — трудозатраты отдельно, через outallforecast):
   def effective(p):
       f  = float(p.FactSum    or 0)
       fc = float(p.ForecastSum or 0)
       return f if f > 0 else fc

   income_mixed  = sum(effective(p) for p in project_points
                       if p.ParentCode in {c.Code for c in in_contracts}
                       and "Оплат" in p.Name)
   expense_mixed = sum(effective(p) for p in project_points
                       if p.ParentCode in {c.Code for c in out_contracts}
                       and "Оплат" in p.Name)

5. Текущая стоимость (mixed): current = income_mixed - expense_mixed

6. Δ = |current − plan|
   if Δ > FINRESULT_THRESHOLDS["current_cost_deviation"]["max_value"]:    # порог в scripts/finresult-thresholds.py (1 млн ₽)
       result = "Да"
       detail = f"Δ = {Δ:,.2f} ₽ (текущая {current:,.2f} − план {plan:,.2f}) — критическое замечание"
   else:
       result = "Нет"
       detail = f"Δ = {Δ:,.2f} ₽ (текущая {current:,.2f} − план {plan:,.2f})"
```

Пример — `scripts/Forecasted-financial-value-deviation.py`.

Ограничения:
- Mixed-логика требует данные по КТ-оплатам всех контрактов проекта.
- Нет контрактов → «Нет» (нечего оценивать).
- Есть контракты, но нет финансовых КТ в видимой части view → «Неопределено».

#### Показатель 3. «Прогноз по окончанию показывает уменьшение финансового результата от планового более чем на 2 млн. руб.»

Семантика:

| Схема | Что это | Формула через поля `ProjectHealthCostMy` |
|-------|---------|------------------------------------------|
| **Плановый** финансовый результат | Только плановые значения оплат и затрат | `plan` (= `inallplan − outallplan`) |
| **Реальный** финансовый результат | Факт оплат + прогноз по незакрытым оплатам и расходам (включая трудозатраты) | `forecast` (= `inallplan − outallforecast`) |

Архитектурная находка: в `ProjectHealthCostMy` поля `plan` и `forecast` **уже соответствуют** схемам:
- `plan` = плановый фин. результат → «Плановый»;
- `forecast` = прогноз фин. результата (факт + прогноз по незакрытым) → «Реальный».

Правила:

| # | Условие | Результат |
|---|---------|-----------|
| 1 | В `ProjectHealthCostMy` нет строки для проекта | **Неопределено** |
| 2 | Нет данных по `plan` или `forecast` | **Неопределено** |
| 3 | `forecast − plan ≥ −FINRESULT_THRESHOLDS["end_finresult_decrease"]["max_value"]` (уклонение ≤ порога, в т.ч. улучшение) | **Нет** |
| 4 | `forecast − plan < −FINRESULT_THRESHOLDS["end_finresult_decrease"]["max_value"]` (уклонение > порога) | **Да [Критическое]** |

`FINRESULT_THRESHOLDS["end_finresult_decrease"]["max_value"]` — порог в `scripts/finresult-thresholds.py` (по умолчанию 2 000 000 ₽).

⚠️ **Логика — только ухудшение:** показатель срабатывает только когда `forecast < plan` (то есть `delta < -порога`). Улучшение (`delta > 0`) даже при большом абсолютном значении — это «Нет». Это обогащение показателя 1, а не дублирование.

Алгоритм:
```
1. Получить данные: get_view(Project, ProjectHealthCostMy, limit=200)
2. Найти проект: project = next(r for r in view.data if r.projectid == <ProjectId>)

3. Проверить наличие:
   if not project or "plan" not in project or "forecast" not in project:
       result = "Неопределено"; detail = "Нет данных в ProjectHealthCostMy"
   else:
       plan     = float(project["plan"])
       forecast = float(project["forecast"])
       delta    = forecast - plan  # отрицательное = ухудшение, положительное = улучшение

       # Срабатываем ТОЛЬКО на ухудшение (delta < -порога). Улучшение — «Нет».
       if delta >= -FINRESULT_THRESHOLDS["end_finresult_decrease"]["max_value"]:
           result = "Нет"; detail = f"Δ = {delta:,.2f} ₽ (уклонение ≤ порога или улучшение)"
       else:
           result = "Да";  detail = f"Δ = {delta:,.2f} ₽ (уклонение > порога) — критическое замечание"
```

Пример — `scripts/Forecasted-financial-result-deviation.py`.

Связь между показателями 1 и 3:

| Показатель | Поле | Логика |
|------------|------|--------|
| 1. Прогноз по окончании | `forecast` | `forecast < 0`? |
| 3. Уменьшение от плана | `plan`, `forecast` | `plan − forecast > порог`? |

Показатель 3 — **обогащение** показателя 1: не просто «убыточен ли прогноз», а «насколько хуже плана».

Связь с другими views:

| View | Отношение |
|------|-----------|
| `ProjectHealthCost` | То же, что `ProjectHealthCostMy`, но без фильтра по правам (доступен админам) |
| `ProjectHealthCostMy` | **Основной view для обычного пользователя** |
| `ProjectHealthWorkload` | Здоровье по трудозатратам (без цен) — для показателя №4 раздела 4 |
| `ProjectBudgetStandart` | Бюджет по проекту (агрегат по финансовым источникам, 16 колонок) |
| `ProjectHealthCost` (без суффикса) | **0 строк** для обычного пользователя (нет прав) — поэтому используем `My` |

Замечания:
1. Привязка по `projectid`: в `ProjectHealthCostMy` поле `projectid` — это **bigint ProjectId**, не `Code`. Сопоставление — через `get_view(Project, MyProject)` → `ProjectId` по `Code`.
2. Данных может не быть для проектов в ранних стадиях ЖЦ (Пресейл, Инициирование) — в этом случае «Неопределено», а не «Нет».
3. `outallforecast` уже включает трудозатраты — ключевое отличие от показателя 5 раздела 4 (который смотрит только на оплаты).
4. Сопоставление строк view идёт по `projectid`, не по `projectprofileid`.

### Интерпретация данных
- Показатель 1: «Да» → критическое замечание.
- Показатель 2: «Да» → критическое замечание. «Нет» — норма.
- Показатель 3: «Да» → критическое замечание. «Нет» — норма.

Если хотя бы один из трёх показателей получил статус «Критическое замечание», раздел получает статус «Критический» (Красный, «Болен»). Иначе — «Здоров» (нейтральный/зелёный).

## 7. Технические данные отчёта

### Назначение шага
Формируется таблица с **метаданными отчёта** — кто его сформировал, на какой версии системы, через какой MCP. Заполняется автоматически при каждом запуске скилла, чтобы отчёт можно было верифицировать и аудировать.

Состав таблицы (6 строк):
1. Пользователь.
2. Титул системы.
3. URL MCP-сервера.
4. Версия скилла.
5. Версия MCP.
6. Версия ПМ «Форсайт».

### Получение данных

Алгоритм заполнения:

```
1. Пользователь:
   user = mcp__fst_pmpractice__get_user_profile()
   value = user["FullName"]

2. Титул системы:
   try:
       record = mcp__fst_pmpractice__get_entity_data(
           entityName="MetaModel", data_id="<ключ_записи>"
       )
       value = record["properties"]["Value"]["value"]
   except Exception:
       value = "Нет данных"  # Pydantic-ошибка: data_id должен быть int, а PK = string

3. URL MCP:
   value = "https://ppreplica.hera.pmpractice.ru/mcp"   # из config.yaml

4. Версия скилла:
   value = "1.4.0"   # из SKILL.md frontmatter

5. Версия MCP:
   init = POST /mcp {"method":"initialize", ...}
   value = init["result"]["serverInfo"]["version"]

6. Версия ПМ «Форсайт»:
   value = f"{init['result']['serverInfo']['name']} v{init['result']['serverInfo']['version']}"
   # Workaround: парсить X-PM-Version или другие кастомные HTTP-заголовки (если есть)
```

Замечания по версии «Форсайт»:
- В MCP-протоколе версия «Форсайт» = версия MCP-сервера.
- `serverInfo.name` = «PMForesight MCP» (название MCP-сервера).
- `serverInfo.version` = «3.2.4» (версия).
- Отдельной «версии ПМ Форсайт» (без MCP) в ответе `initialize` нет.

| Что | Откуда |
|-----|--------|
| Имя «Форсайт» как продукта | «Сервер предоставляет доступ к инструментам и данным **ИСУП «Форсайт»**» (из `serverInfo.instructions`) |
| Версия MCP | `serverInfo.version` = «3.2.4» |
| Версия протокола MCP | `protocolVersion` = «2024-11-05» (это **НЕ** версия «Форсайт») |

Данные этого раздела не интерпретируются.

## 8. Формирование секции индикатора в заголовке

### Назначение шага
Готовятся данные для секции индикатора в заголовке. Индикатор принимает одно из трёх значений:
1. Проект болен.
2. Проект требует внимания.
3. Проект здоров.

### Получение данных
Анализируется статус следующих 4 разделов отчёта:
- «Оценка здоровья проекта с точки зрения сроков» (раздел 3);
- «Проверка полноты заполнения проекта» (раздел 4);
- «Актуальность прогнозов по проекту» (раздел 5);
- «Финансовый статус проекта» (раздел 6).

### Интерпретация данных
Правила (статусы разделов определены в их собственных подразделах «Интерпретация данных» — здесь берутся уже готовые):
- Если хотя бы один из 4 разделов (3, 4, 5, 6) имеет статус **«Болен»** → статус отчёта «Проект болен».
- Иначе, если ни один из 4 разделов не «Болен», но есть хотя бы один со статусом **«Требует внимания»** → статус отчёта «Проект требует внимания».
- Иначе (ни один из 4 разделов не «Болен» и не «Требует внимания») → статус отчёта «Проект здоров».

⚠️ **Терминологическая сводка** (единые имена для всех 4 разделов):
- **«Болен»** = красный = «Критический» = «Критические замечания» (раздел 3: `health == "БОЛЕН"`; раздел 4: ≥ 3 показателей «Нет»; раздел 5: ≥ `OVERDUE_THRESHOLDS["critical"]["min_days"]` КТ; раздел 6: хотя бы 1 показатель «Да»).
- **«Требует внимания»** = жёлтый = «Существенные замечания» (раздел 3: 1..2 критических КТ; раздел 4: 1..2 «Нет» или существенные; раздел 5: ≥ `OVERDUE_THRESHOLDS["substantial"]["min_days"]` КТ; раздел 6: не используется).
- **«Здоров»** = без подкраски (все показатели в норме).

### Вывод данных
Данные выводятся в плейсхолдер `{Project.indicator.status}`, который используется при построении отчётов MD и HTML.
