## Что я попробовал по вашей подсказке

> «поле `name` это первичный ключ, пробрасывай через `data_id`»

### 1. `get_entity_data` со строковым `data_id`

```bash
python3 scripts/mcp_probe.py --tool get_entity_data \
  --args '{"entityName":"MetaModel","data_id":"Title"}'
```

**Результат:**

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "content": [{"type": "text", "text":
      "1 validation error for call[get_entity_data]\ndata_id
        Input should be a valid integer, unable to parse string as an integer
        [type=int_parsing, input_value='Title', input_type=str]
        For further information visit https://errors.pydantic.dev/2.13/v/int_parsing"
    }],
    "isError": true
  }
}
```

Pydantic **однозначно не принимает строку** — `data_id` валидируется как `int`.
Похоже, на бэкенде `get_entity_data` хардкод ожидает `integer` id для всех сущностей,
даже если PK у `MetaModel` — `text` (см. ниже).

### 2. `describe_entity` подтверждает PK = `Name` (text)

```bash
python3 scripts/mcp_probe.py --tool describe_entity \
  --args '{"entityName":"MetaModel","data_id":"new"}'
```

**Схема сущности:**

```
Name:  kind=text PK=True  Title='Ключ'
Value: kind=text PK=False Title='Наименование'
```

PK действительно `Name` (text), как вы и говорите. Но `get_entity_data` об этом
не знает — он пытается парсить `data_id` как `int`.

### 4. `find_entity` НЕ возвращает MetaModel

**Это ключевая находка.** Из 152 результатов по `name="ИС"`:

```
total=152, items=152
entities: {'Contractor': 4, 'CourseWork': 1, 'InContract': 7, 'Point': 131, 'Project': 8, 'Order': 1}
```

**Ни одной MetaModel.** При поиске по любым другим именам — аналогично. Похоже, что
`MetaModel` принципиально **не индексируется** в `find_entity` (даже если записи
существуют).

## Что мне нужно от вас

### Вопрос 1. Какой конкретно `name` у записи с титулом системы?

Возможно, `name` имеет **не очевидный формат** — например:

- `version` (вместо `Version`)
- `serverTitle` (вместо `SystemTitle`)
- `MainProductName`
- `application.name`
- `system_title`
- `ProductNamePMForesight`
- `SrvTitle`

…или нечто совсем иное. Если вы можете назвать **точное значение поля Name** хотя бы
для одной записи MetaModel — я попробую `find_entity(name="...")` ещё раз.

### Вопрос 2. Есть ли отдельный эндпоинт для MetaModel?

`get_entity_data` принимает только `int data_id` — это не позволяет использовать
строковый PK. Но, возможно, есть **отдельный tool** или **отдельный endpoint** для
чтения MetaModel по `name` (строке)? Например:

- `mcp__fst_pmpractice__get_metamodel(name="...")` — отдельный tool
- `GET /api/metamodel/{name}` — REST endpoint вне JSON-RPC
- `POST /mcp` с другим `methodName` (например, `Resources/Read` или `Resources/List`)

### Вопрос 3. Не `find_entity` ли главный путь?

Если данные из MetaModel **доступны только по `name`**, и `find_entity` не возвращает
MetaModel — то, возможно, есть `find_entity` для специальных **служебных** сущностей.
Альтернативный URL `/api/search/find` (по которому `find_entity` сейчас ходит) — может,
для MetaModel он другой (`/api/metamodel/find`?).

### Вопрос 4. Минимальный пример вызова

Самый ценный для меня — **один рабочий вызов**, который возвращает MetaModel-запись.
Я смогу скопировать подход и адаптировать. В идеале — `curl` с HTTP-заголовками и
телом, чтобы я мог повторить.
