# Перенос скиллов fst-project-health и project-search на другой сервер

## Вопрос 1 (от пользователя)

> Если я запакую в архив скилл fst-project-health со всеми его подкаталогами и файлами в них и в отдельный архив скилл project-search (точно так же, со всеми файлами и подкаталогами) — а потом перенесу и разверну на новом месте и доступы настрою, заработает это?

## Ответ 1 (от Hermes)

Да, **заработает**, но с оговорками. Давай проверю каждый шаг.

### Шаг 1: Архивирование

Структура которую запакуешь:

**Архив 1: `fst-project-health.tar.gz`**

```
skills/productivity/fst-project-health/
├── SKILL.md
├── scripts/   (20 файлов)
└── references/   (8 файлов)
```

**Архив 2: `project-search.tar.gz`**

```
skills/productivity/project-search/
├── SKILL.md
├── scripts/
└── references/
```

Это **корректно** — Hermes при загрузке скилла смотрит на `metadata.hermes.name` в frontmatter, а не на имя каталога. Имя каталога — конвенция, не требование.

### Шаг 2: Разворачивание на новом месте

Распаковываешь архивы в `~/.hermes/profiles/<новый-профиль>/skills/productivity/`:

```
<новый-профиль>/skills/productivity/
├── fst-project-health/
│   ├── SKILL.md
│   ├── scripts/
│   └── references/
└── project-search/
    ├── SKILL.md
    ├── scripts/
    └── references/
```

Это **сработает** — стандартная структура.

### Шаг 3: Доступы

Что нужно:

| Что | Где взять | Критичность |
|-----|-----------|-------------|
| `PMP_TOKEN` | Перенести из старого `.env` в новый `.env` | **Критично** — без токента MCP не работает |
| `config.yaml → mcp_servers.fst_pmpractice.url` | Перенести из старого `config.yaml` | **Критично** — без URL Hermes не подключится к MCP |
| `metadata.hermes.tags` и `category` | Уже в `SKILL.md` каждого скилла | OK |

### Что заработает сразу

1. **Загрузка скиллов** — `fst-project-health` и `project-search` будут зарегистрированы в Hermes (по `metadata.hermes.name`).
2. **Триггеры** — `description` в frontmatter распознаётся, агент загрузит скилл по триггерам «здоровье проекта», «оцени проект», etc.
3. **`scripts/`** — `find_project_by_code.py`, `build_report_header.py`, `mcp_probe.py` запустятся (при наличии `requests`).
4. **Связь между скиллами** — `related_skills: [project-search]` в `fst-project-health` разрешится, потому что `project-search` лежит рядом.
5. **Все 17 справочных выдержек** — прочитаются как образец при написании `/tmp/script.py`.
6. **Все 8 references** — прочитаются при необходимости (особенно `forsight-mcp-quirks.md` с pitfalls).

### Что может НЕ заработать

**1. Отсутствие `requests` в новой среде**

Скрипты импортируют `requests`. Если в новом Hermes-инстансе его нет:

```python
ModuleNotFoundError: No module named 'requests'
```

**Решение**: добавить `requests` в зависимости. Создать `requirements.txt` рядом со скиллом:

```
# skills/productivity/fst-project-health/requirements.txt
requests>=2.28
```

**2. `PMP_TOKEN` в неправильном месте**

Скрипт `find_project_by_code.py` и `build_report_header.py` читают токен через:

```python
token = os.environ.get("PMP_TOKEN")
```

Это работает **только если** токен экспортирован в переменные окружения. В Hermes `.env` файл обычно подхватывается автоматически через какой-нибудь загрузчик, но это **зависит от конфигурации профиля**.

**Решение**: проверить как именно старый Hermes загружает `.env`. Если это через `direnv`, `dotenv` или прямое `source` — нужно повторить.

**3. Скрытые зависимости в `scripts/`**

Я не проверял каждый скрипт на импорты. Возможно где-то есть:

- `import pandas` (для отчётов)
- `import jinja2` (для HTML-шаблонов)
- `import openpyxl` (если экспорт в Excel)

**Решение**: прогнать каждый `.py` через `python3 -c "import ast; ast.parse(open('script.py').read())"` или `python3 -m py_compile`. Если есть нестандартные импорты — добавить в `requirements.txt`.

**4. `related_skills: [project-search]` в frontmatter**

В YAML указан `project-search`. Если на новом месте **нет** этого скилла — Hermes при загрузке `fst-project-health` попытается найти `project-search` и выдаст предупреждение, но сам скилл продолжит работать.

**Решение**: упаковать `project-search` обязательно, как ты и планируешь.

**5. `category: productivity`**

Это поле используется для категоризации скиллов в Hermes. Если новая версия Hermes использует другие категории — поле будет проигнорировано, но не сломается.

**Решение**: проверить документацию новой версии.

**6. `version: 0.3.0` (или какая там сейчас)**

Hermes может валидировать семантическое версионирование. Если новая версия требует `1.0.0+` — будет warning. Не критично.

**7. Frontmatter формат**

У тебя сейчас:

```yaml
metadata:
  hermes:
    tags: [report, pmpractice, ru, foresight, project-health, health-check, html, markdown, aggregator]
    category: productivity
    related_skills: [project-search]
```

Если новая версия Hermes требует другие поля (например, `metadata.platforms`, `metadata.author`) — будет warning.

**Решение**: посмотреть примеры других скиллов в новой среде.

**8. OpenClaw — другая структура frontmatter**

Если переносишь в **OpenClaw**, а не Hermes — поле `metadata.hermes` скорее всего будет проигнорировано или нужно `metadata.openclaw`. **Это требует адаптации**.

**Решение**: проверить документацию OpenClaw.

### Чеклист перед разворачиванием

Перед тем как упаковывать, проверь:

```
✅ /root/.hermes/profiles/fst-control/.env содержит PMP_TOKEN=***
✅ /root/.hermes/profiles/fst-control/config.yaml содержит mcp_servers.fst_pmpractice.url
✅ /root/.hermes/profiles/fst-control/skills/productivity/fst-project-health/ — всё в комплекте
✅ /root/.hermes/profiles/fst-control/skills/productivity/project-search/ — есть (или отдельный путь)
✅ requests установлен в окружении где запускается Hermes
```

### Что добавить в архив для безопасной переносимости

Чтобы **точно заработало на новом месте**, добавь в архив 2 файла:

**`requirements.txt` (в корне архива)**

```
requests>=2.28
```

**`DEPLOY.md` (инструкция по разворачиванию)**

```markdown
# Deploy fst-project-health to new Hermes/OpenClaw

## 1. Extract

tar -xzf fst-project-health.tar.gz -C ~/.hermes/profiles/<profile>/skills/productivity/
tar -xzf project-search.tar.gz -C ~/.hermes/profiles/<profile>/skills/productivity/

## 2. Install Python deps

pip install -r ~/.hermes/profiles/<profile>/skills/productivity/fst-project-health/requirements.txt

## 3. Configure

In `~/.hermes/profiles/<profile>/.env`:
PMP_TOKEN=*** JWT token from Форсайт>

In `~/.hermes/profiles/<profile>/config.yaml` → `mcp_servers`:
  fst_pmpractice:
    url: "https://ppreplica.hera.pmpractice.ru/mcp"

## 4. Verify

hermes mcp list                    # should show fst_pmpractice as connected
python3 scripts/find_project_by_code.py 504-595  # should return project data
```

### Вердикт

**Да, заработает**, если:

1. ✅ Оба скилла упакованы полностью (SKILL.md + scripts/ + references/)
2. ✅ На новом месте есть `requests`
3. ✅ На новом месте правильно настроены `.env` с `PMP_TOKEN` и `config.yaml` с URL MCP
4. ✅ `project-search` тоже развёрнут (для `related_skills`)

**Если что-то одно пропустишь** — скилл загрузится, но при попытке сделать реальный отчёт упадёт с понятной ошибкой (типа `ModuleNotFoundError` или `McpConnectionError`), которую легко диагностировать.

**Самый надёжный способ** — после разворачивания запустить smoke-тест:

```bash
python3 ~/.hermes/profiles/<profile>/skills/productivity/fst-project-health/scripts/find_project_by_code.py 504-595
```

Если вернёт проект с заполненными полями — всё работает.

### Что переносить на другой Hermes / OpenClaw

#### На **другой Hermes-инстанс** с тем же MCP

1. Скопировать каталог `skills/productivity/fst-project-health/` целиком → в `~/.hermes/profiles/<твой-профиль>/skills/productivity/`
2. Скопировать `skills/productivity/project-search/` (если ещё нет)
3. Настроить `config.yaml` → `mcp_servers.fst_pmpractice.url = "https://..."`
4. Положить `PMP_TOKEN` в `.env`
5. Запустить — должно работать сразу.

#### На **OpenClaw** (если у него похожая структура)

1. Найти эквивалент `~/.hermes/profiles/<профиль>/skills/` (скорее всего будет `~/.openclaw/profiles/<профиль>/skills/` или подобное)
2. Те же 4 шага
3. Если формат скиллов отличается — нужно адаптировать frontmatter

#### Отличия при переносе

| Аспект | Hermes | OpenClaw |
|--------|--------|----------|
| Frontmatter | `metadata.hermes.*` | Возможно другая структура (`metadata.openclaw.*`?) |
| Способы вызова MCP | `mcp__fst_pmpractice__*` через встроенный клиент | Может быть иначе (через свой MCP-клиент или внешний) |
| Секреты | `~/.hermes/profiles/<профиль>/.env` | Свой путь, нужно проверить документацию OpenClaw |
| `MEDIA:` протокол | Telegram-нативный | Свой формат доставки |

### Главный риск

Скилл `fst-project-health` **сильно завязан** на особенности Форсайт-MCP, которые мы обнаружили при отладке:

- UTF-8 кодировка (pitfall #2)
- Привязка через `ParentFullName` (pitfall #1)
- 403 на `ResourcePlanning*` (pitfall #6)
- Lazy token check (pitfall #7)
- Markdown-fences в .py (pitfall #4)
- Hyphenated filenames (pitfall #5)

Эти 6 pitfalls **зафиксированы** в `references/forsight-mcp-quirks.md`. Если переносить скилл без этого файла — он **сломается** при первой же попытке сделать отчёт.

Поэтому **`references/forsight-mcp-quirks.md`** — это самый критичный файл в скилле. Не потеряй его.
