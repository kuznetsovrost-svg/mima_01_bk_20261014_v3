### 1.2. Трудозатраты и разрыв «план/факт» (раздел 4, показатель 4)

**Что это.** В отчёте раздел 4 показатель 4 («Актуальность трудозатрат»)
должен показывать «Да» если последний факт ≥ последнего плана на N дней,
и «Нет» если разрыв ≤ N. Алгоритм работает через `ResourcePlanning` / `ResourcePlanningKp`.

**Проблема.** Оба view возвращают **403 Forbidden** для обычного
пользователя (без admin-роли).

**Запрос:**

```bash
python3 scripts/mcp_probe.py --tool get_view \
  --args '{"entityName":"ResourcePlanning","viewName":"ResourcePlanning","limit":3}'
# Error calling tool 'get_view': Ошибка запроса к /view/ResourcePlanning:
#   403 Client Error: Forbidden for url:
#   https://ppreplica.hera.pmpractice.ru/view/ResourcePlanning
```

**Что приходится выводить в отчёте:**

```text
| 4 | Актуальность трудозатрат | Неопределено — view ResourcePlanning/ResourcePlanningKp 403; 
                              недостаточно данных |
```

**Альтернатива через `ProjectHealthWorkload` работает, но не даёт нужного:**

```bash
python3 scripts/mcp_probe.py --tool get_view \
  --args '{"entityName":"Project","viewName":"ProjectHealthWorkload","limit":3}'
# УСПЕХ — возвращает данные по профилю проекта (Базовый, 1)
# {"id":1,"year":2024,"month":12,"name_m":"Декабрь 2024","plan_m":38,
#  "forecast_m":54,"fact_m":12,"dev_m":-26,"projectprofileid":1,...}
```

**Проблема с агрегатом:** `ProjectHealthWorkload` возвращает **помесячные итоги
по профилю проекта**, а не по конкретному проекту. Один `projectprofileid`
соответствует нескольким проектам — невозможно выделить долю одного проекта.

**Просьба:**
- Открыть `ResourcePlanning` и `ResourcePlanningKp` для уровня
  «Руководитель проекта» (минимум — чтение собственных проектов).
- Если это невозможно по политике — добавить в `ProjectHealthWorkload`
  колонку `projectid` (или `projectcode`), чтобы можно было отфильтровать
  конкретный проект (а не весь профиль).

### 1.3. Финансовый результат — план vs факт (раздел 6, показатели 1-3)

**Что это.** Раздел 6 показывает финансовое состояние по 3 показателям:

1. **Показатель 1** — прогноз финансового результата < 0 (плохо)
2. **Показатель 2** — отклонение текущей стоимости от плана (|Δ| > 1 млн)
3. **Показатель 3** — уменьшение forecast относительно plan на > 2 млн

**Алгоритм расчёта** (для показателей 1-3) — это **смесь `fact` и `forecast`**
для произвольной даты. На сегодня: `fact` есть только за прошлые месяцы,
а за текущий/будущий — нужно брать `forecast`.

**Проблема 1 — `plan` может быть None даже у живых проектов.**

```bash
python3 scripts/mcp_probe.py --tool get_view \
  --args '{"entityName":"Project","viewName":"ProjectHealthCostMy","limit":100}'
# 109 строк. Для projectid=3152 (503-152 Пресейл):
#   {"id":99,"projectid":3152,"fact":-4995218.6385,"forecast":-37489319.853,
#    "plan":null,"deviation":null,"devcost":null,"devallcost":null,
#    "projectprofileid":1,"projectprofilename":"Базовый"}
# ↑ plan = null, deviation = null. Для Пресейл-плана может не быть, но
#   для активных проектов он обычно есть.
```

**Проблема 2 — `fact`/`forecast` смешаны по периодам, и view не датирован.**

View `ProjectHealthCostMy` возвращает **одну строку на проект** (а не по периодам),
и **непонятно, на какую дату** эта строка. Поля `fact`/`forecast`/`plan` —
это **что именно?** Кумулятивный факт на сейчас? Только за последний
закрытый месяц? Последнее `ChangeDate` строки?

**Что нужно для расчёта показателя 1 (forecast < 0):**

```python
# Логика которую мы хотели бы применить:
forecast = project.get("forecast")  # числовое, но непонятно когда
deviation = project.get("deviation")  # forecast - plan, или fact - plan?
# → мы не знаем, на какую дату эта строка
```

**Что приходится выводить в отчёте:**

```text
| 1 | Прогноз фин.результата < 0 | Да |
|   | Прогноз фин.результата: −221 860 ₽ — критическое замечание |
# Мы выводим forecast из ProjectHealthCostMy как «прогноз фин.результата»,
# но без подтверждения что это именно прогноз (а не факт).
```

**Просьба:**
- Добавить колонку `as_of_date` или `period` в `ProjectHealthCostMy`,
  чтобы было ясно, какой дате соответствуют `fact/forecast/plan`.
- Документировать: `fact` — это «кумулятивный факт за период» или
  «только последний месяц»? Семантика сейчас неясна.
- Добавить отдельные view `ProjectHealthCostByMonth` / `ProjectHealthCostByQuarter`
  для расчёта показателей «отклонение за период» (не только кумулятивно).

### 1.4. Бюджет проекта — `ProjectBudgetGrade` vs `DirectProjectCostsGrade` (раздел 6)

**Что это.** В `Project` есть два поля:
- `ProjectBudgetGrade` (numeric) — оценка бюджета проекта
- `DirectProjectCostsGrade` (numeric) — оценка прямых затрат

**Проблема.** Непонятно, что это **оценка на старте** или **текущая сумма**.
Для 504-595: `ProjectBudgetGrade=54 000 000`, `DirectProjectCostsGrade=32 000 000`,
но фактический `fact` (закрытые месяцы) = −744 415 ₽. Разница в 36 раз.

В `ProjectHealthCostMy` (открытый view) — `plan=6 422 500` ₽ для 504-595,
т.е. расхождение `ProjectBudgetGrade(54М) vs plan(6.4М)` — порядок.

**Запрос:**

```bash
python3 scripts/mcp_probe.py --tool get_entity_data \
  --args '{"entityName":"Project","data_id":"4595"}'
# {"properties":{
#   "ProjectBudgetGrade":{"value":54000000.0},
#   "DirectProjectCostsGrade":{"value":32000000.0},
#   "PresaleLimit":{"value":2700000.0},
#   "PresaleBudgetPercentage":{"value":5.0},
#   ...
# }}
```

**Что хочется понять:**
- Что это за `Grade`? Оценка при инициировании? Текущий план?
- Почему она в 8 раз больше `plan` из `ProjectHealthCostMy`?
- Есть ли формула пересчёта? (например, `DirectProjectCostsGrade × 0.6`)

**Просьба:**
- Документировать `ProjectBudgetGrade`, `DirectProjectCostsGrade`, `ProjectLimit`,
  `PresaleLimit` — что это за величины, на какую дату, как считаются.
- Если это «оценка при открытии проекта», а `plan` — «текущий бюджет с
  учётом корректировок», то хочется видеть **обе цифры** в `ProjectHealthCostMy`,
  а не выбирать одну.

### 1.5. Платежи — нет `ProjectId` в view (раздел 4, показатель 5 + 6)

**Что это.** Раздел 4 показатель 5 («График платежей») считает
`Σ актов − Σ оплат` по контрактам проекта. Контракт привязан к проекту
через `InContractActivity` (multi-FK). Платежи (`Payments`) привязаны
к **ActivityName** (текстовое имя), а не к `ProjectId`.

**Запрос:**

```bash
python3 scripts/mcp_probe.py --tool get_view \
  --args '{"entityName":"Payments","viewName":"AllPayments","limit":5}'
# {"ViewName":"AllPayments","columns":[...],
#  "data":[
#    {"id":1,"PaymentsId":1118,"Name":"Оплата вознаграждения...",
#     "ActivityName":"500-656. РОСАТОМ. АСУ-ИНВЕСТ. ИС Сириус 2024...",
#     "FinanceSourceName":"414.  Прочее бухгалтерия.",
#     "SumRub":316.75,"Date":"2025-12-25T00:00:00+03:00",
#     "ContractorName":"ПАО \"Банк ПСБ\"","ContractorId":10304,
#     "CompanyName":"АТР","CompanyId":4},
#  ...
# ]}
```

**Проблема.** В `Payments` view нет:
- `ProjectId` — нельзя программно фильтровать по проекту
- `ContractId` — нельзя сопоставить платёж ↔ контракт
- `ActivityId` — только текстовое имя `ActivityName` (=«500-656. РОСАТОМ…»)

Из-за этого приходится **парсить текстовое имя** `ActivityName` чтобы
найти платежи по проекту. Это ненадёжно (пробелы, переименования) и медленно.

**Что приходится выводить в отчёте:**

```text
| 5 | График платежей | Δ = 0 ₽ по 0 контрактам (стадия Пресейл, контракты ещё не заведены) |
# ↑ Мы вообще не можем автоматически найти платежи по 503-152 (Пресейл),
#   если в нём нет контрактов. Но если контракты ЕСТЬ — мы не знаем
#   какие платежи к ним относятся.
```

**Просьба:**
- Добавить в `AllPayments` колонки `ProjectId` / `ActivityId` / `ContractId`,
  чтобы платежи можно было группировать по проекту программно.
- Альтернатива: открыть view `PaymentsByProjectXref` / `PaymentsByActivity`.

### 1.6. Связь КТ ↔ Project требует fallback через `get_entity_data` (раздел 5)

**Проблема.** В view `Point` (`AllMyPoint` / `AllPoint`) **нет `ParentFullName`**
(для привязки к проекту остаётся только `ParentCode` — но `ParentCode` — это
**активность**, не проект).

**Запрос:**

```bash

  --args '{"entityName":"Point","viewName":"AllMyPoint","limit":5}'

#    {"id":1686,"PointId":1686,"Code":"101-686","ParentCode":"501-682",
#     "ParentFullName":null,...},

# ↑ ParentFullName = null. Нельзя сделать
```

Сейчас мы вынуждены для КТ 504-595 делать **N+1 запрос**: сначала

`get_entity_data(Point, activity_id)` для каждой активности, чтобы
через `ParentFullName` в этой Activity убедиться что это КТ нашего проекта.

**Просьба:**
- Добавить `ParentFullName` в view `AllMyPoint` и `AllPoint`
  (для row-уровня фильтрации).
- Или добавить новый view `MyPointWithProject` где `projectid` /
  `projectcode` явно присутствуют.

### 1.7. `ProjectHealthCostMy.outplan` / `outfact` семантика неясна (раздел 6)

**Что это.** Поля `outplan`, `outfact`, `outallplan`, `outallforecast` —
предположительно связаны с **расходными контрактами** (outcome)
и их планом/фактом.

**Запрос для 504-595:**

```bash
python3 scripts/mcp_probe.py --tool get_view \
  --args '{"entityName":"ProjectHealthCostMy","viewName":"ProjectHealthCostMy","limit":100}'
# {"id":108,"projectid":4595,
#  "inplan":6497500.0,"infact":2500000.0,
#  "outplan":75000.0,"outfact":3244415.0,
#  "fact":-744415.0,
#  "outallplan":75000.0,"outallforecast":4221860.0,
#  "plan":6422500.0,"forecast":-221860.0,
#  "deviation":-6644360.0,"devcost":3340856.0,"devallcost":4146860.0,
#  "projectprofileid":1,"projectprofilename":"Базовый"}
```

**Проблема.** Непонятно:
- `outplan` = 75 000, `outfact` = 3 244 415 — какая разница?
- `outallplan` = 75 000, `outallforecast` = 4 221 860 — это **план** vs **прогноз**
  расходов? Тогда почему `outplan` ≠ `outallplan`?
- `deviation` = −6 644 360 — откуда такая цифра? Может, `forecast − plan`?
  Тогда −221 860 − 6 422 500 = −6 644 360. **Да!**
- `devcost` = 3 340 856 — что это? `outallforecast − outplan` = 4 146 860?
  Не 3 340 856.

**Просьба:** формальный **glossary** для полей `ProjectHealthCostMy` — что
вычисляется по каким формулам. Сейчас без догадок нельзя.

## 2. Места, где неудобно, но не критично

### 2.1. `find_entity` не ищет по `entityName` — нужен отдельный параметр

**Проблема.** Когда хочется найти **все записи** определённой сущности
(например, «все `MetaModel`»), приходится писать `name="..."` (любое имя),
а сервер возвращает 0. Логично было бы `find_entity` принимать
`entityName="MetaModel"` или `find_entity_entity("MetaModel", limit=50)`.

```bash
python3 scripts/mcp_probe.py --tool find_entity \
  --args '{"entityName":"MetaModel","limit":50}'
# {"items":[],"total":0,"limit":50,"offset":0}
# ↑ Не фильтрует по сущности, ищет по name
```

**Workaround:** `get_view(<Entity>, <View>, limit=...)` — но не у всех
сущностей есть view (см. 1.1).

---

### 2.2. `get_entity_data` для Point возвращает `PlanSum`/`ForecastSum`/`FactSum = None`

**Запрос:** для КТ 1686 (`101-686`) — `PlanSum=None`, `ForecastSum=None`,
`FactSum=None`. Хотя `ProjectHealthCostMy` для projectid=4595 имеет
`plan=6 422 500`. Поля существуют в схеме (`describe_entity` показывает
их), но **не заполнены для этой КТ**.

**Не критично**, потому что `ProjectHealthCostMy` даёт агрегат на уровень
проекта. Но **нельзя посмотреть суммы по отдельной КТ** — что для анализа
конкретных переносов сроков было бы полезно.

---

### 2.3. `describe_entity` для `MetaModel` с `data_id="new"` показывает только
`Name`+`Value`, но **не показывает ни одного примера записи**

`find_entity` возвращает 0, view нет, `get_entity_data` ломается. Получить
«хотя бы одну запись» для примера — невозможно. Это **комбинация 1.1 + 2.1**.

---

### 2.4. `contracts` через `view` есть, но без `InContractActivity` (для фильтрации по проекту)

**Запрос:** `get_view(InContract, InContractAll, limit=50)` — view открыт,
но `InContractActivity` = `null` в строке. Нужен `get_entity_data` для
каждого контракта, чтобы получить multi-FK.

**Не критично**, потому что `ParentFullName` служит fallback (pitfall #1
в `references/contract-binding-via-parentfullname.md`). Но N+1 медленный.

### 2.5. `N+1` fetch для каждой КТ проекта (раздел 5)

Из-за 1.6 (нет `ParentFullName` в view) — собираем все КТ проекта
через `get_view(Point, MyProject)` (там `ProjectName` есть), но всё равно
для подсчёта финансов КТ нужно запрашивать `get_entity_data` каждой.
Для проекта 504-595 (~30 КТ) — **30 HTTP-запросов** к серверу.

**Просьба:** либо вернуть `PlanSum`/`ForecastSum`/`FactSum` в view Point,
либо дать aggregate `PointFinancialSummary`.

### 2.6. `ProjectHealthCostMy` — нет view `ProjectHealthCostAll` (как MyProject)

Аналогично `MyProject`/`AllProject` — `ProjectHealthCostMy` есть, но `AllProjectHealthCost` не нашёл.

```bash
python3 scripts/mcp_probe.py --tool get_view \
  --args '{"entityName":"ProjectHealthCostMy","viewName":"AllProjectHealthCost","limit":3}'
```

### 2.7. `InContract` view `AllInContract` — нет возможности отфильтровать по `parent_project_id`

View есть (`InContractAll`), но `InContractActivity` = null в строках.
Spring-FK через `ParentFullName` — единственный быстрый путь. Если `ParentFullName`
пустой (такое бывает для ордерных контрактов) — полный N+1 через `get_entity_data`.
Нужно view `InContractByProject` с фильтром по `parentProjectId`.
