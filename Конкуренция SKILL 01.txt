# Skills и профили — изоляция, видимость, конкуренция
## Что доступно из нового профиля, как скилы вытесняют друг друга, когда делать отдельный SKILL.md

────────────────────────────────────────────────────────────────────────────
0. КЛЮЧЕВОЙ ВОПРОС
────────────────────────────────────────────────────────────────────────────

У Hermes Agent есть «базовый» набор скилов (bundled skills от
Nous Research + ваши добавленные глобально). Когда вы создаёте
новый профиль:

  - Видны ли эти базовые скилы?
  - Что произойдёт, если в профиле тоже положить скил с тем же
    именем?
  - Как они «конкурируют» и что побеждает?
  - Когда делать локальный SKILL.md в профиле, а когда
    пользоваться базовым?

Короткий ответ (для impatient):

  1. **ДА, базовые скилы доступны из любого профиля**.
  2. **Профильный скил с тем же именем ПЕРЕБИВАЕТ глобальный**
     для этого профиля (per-profile override).
  3. **Изменения в профильном скиле НЕ затрагивают глобальный**
     (изоляция в обе стороны).
  4. **Когда создавать отдельный** = когда для вашего профиля
     поведение отличается от базового (другие шаги, другие pitfalls,
     другие secrets).

────────────────────────────────────────────────────────────────────────────
1. АРХИТЕКТУРА SKILLS — ГДЕ ЧТО ЛЕЖИТ
────────────────────────────────────────────────────────────────────────────

В этом Hermes (mima-g-01, 2026-07) есть три уровня скилов:

1.1. ГЛОБАЛЬНЫЕ BUNDLED SKILLS (нельзя удалить без root).
   Расположение: `~/.hermes/skills/<name>/SKILL.md`
   Установщик: Hermes-разработчики (Nous Research).
   Примеры: github/, devops/, creative/, mlops/, social-media/ и т.д.
   Поведение: shared между всеми профилями.
   Управление: `hermes skills list`, `hermes skills opt-out`.

1.2. ГЛОБАЛЬНЫЕ ДОБАВЛЕННЫЕ ВРУЧНУЮ.
   Расположение: то же, `~/.hermes/skills/<name>/SKILL.md`.
   Установщик: вы сами (через `hermes skills install <url>` или
   `hermes --profile=<name> skills create <name>`).
   Поведение: shared между всеми профилями, если не указан
   `--profile=<name>` (см. ниже).
   Управление: `hermes skills list`, `hermes skills uninstall`.

1.3. PER-PROFILE ЛОКАЛЬНЫЕ.
   Расположение: `~/.hermes/profiles/<name>/skills/<name>/SKILL.md`.
   Установщик: `hermes --profile=<name> skills create <name>`.
   Поведение: только для конкретного профиля, изолировано.
   Управление: `hermes --profile=<name> skills list`,
   `--profile=<name> skills uninstall`.

1.4. Bundled manifest.
   Файл `~/.hermes/.bundled_manifest` хранит, какие скилы из bundled
   вы явно отключили.

1.5. Per-profile disabled list.
   В `config.yaml` каждого профиля может быть `disabled_skills: [...]`
   — список скилов, которые проигнорированы в этом профиле.

────────────────────────────────────────────────────────────────────────────
2. КАК ВЫГЛЯДИТ ФАЙЛОВАЯ СИСТЕМА
────────────────────────────────────────────────────────────────────────────

Реальные пути на mima-g-01:

```
~/.hermes/                                    ← default профиль (root)
├── skills/                                   ← глобальные скилы
│   ├── apple/SKILL.md
│   ├── autonomous-ai-agents/SKILL.md
│   ├── creative/SKILL.md
│   ├── devops/SKILL.md
│   ├── github/SKILL.md
│   ├── ...  (всего 18 категорий)
│   └── yuanbao/SKILL.md
└── profiles/
    ├── analyst_training/
    │   └── skills/                           ← per-profile скилы
    │       ├── apple/  (симлинк или неполная копия)
    │       ├── creative/
    │       ├── ...  (16 категорий — НЕ 18)
    │       └── ...  (нет devops, hermes-agent-vcs-portability,
    │                  hermes-internals-inspection, red-teaming — bundled)
    └── mi_mg_01/                              ← если бы вы его создали
        └── skills/                           ← per-profile скилы
            └── (опционально собственные)
```

Различия в наборе категорий между `~/.hermes/skills/` (18) и
`~/.hermes/profiles/analyst_training/skills/` (16) видны:
  - `devops/` есть только глобально.
  - `hermes-agent-vcs-portability/` есть только глобально.
  - `hermes-internals-inspection/` есть только глобально.
  - `red-teaming/` есть только глобально.
  - 4 категории отсутствуют локально в `analyst_training/skills/`.

Это важный сигнал: **per-profile skills не наследуют bundled
автоматически**. Видимо, профиль получает «стартовый набор
по умолчанию», а некоторые bundled-категории нужно добавить руками.

────────────────────────────────────────────────────────────────────────────
3. КАК МОДЕЛЬ РЕШАЕТ, КАКОЙ СКИЛ ГРУЗИТЬ
────────────────────────────────────────────────────────────────────────────

3.1. Когда модель «думает, что нужен скил»:
   - Из описания (frontmatter `description:`).
   - Из тегов (`metadata.hermes.tags:`).
   - Из related_skills (друзья друзей).
   - Из явного `/skill <name>` от пользователя.

3.2. Когда несколько скилов подходят:
   - Сначала: per-profile (локальный), он перебивает глобальный.
   - Затем: bundled (глобальный).
   - При equal weights — первый найденный.

3.3. Когда скил не загружается:
   - Скил в `disabled_skills` профиля → игнорируется.
   - Bundle opt-out → глобальный отключён, но per-profile может
     включить свою версию.

────────────────────────────────────────────────────────────────────────────
4. ИЗОЛЯЦИЯ SKILLS ЧЕРЕЗ `set_hermes_home_override`
────────────────────────────────────────────────────────────────────────────

Из кода `web_server.py:11280-11299` (проверено по сорсу):

Когда вы вызываете `hermes --profile=mi_mg_01 skills list`:

```python
from hermes_constants import set_hermes_home_override, reset_hermes_home_override

token = set_hermes_home_override(str(profile_dir))    # ~/.hermes/profiles/mi_mg_01
try:
    _skills_tool.HERMES_HOME = profile_dir
    _skills_tool.SKILLS_DIR = profile_dir / "skills"   # ← per-profile!
    _skill_mgr.HERMES_HOME = profile_dir
    _skill_mgr.SKILLS_DIR = profile_dir / "skills"
    # ... операция ...
finally:
    reset_hermes_home_override(token)
    # restore defaults
    _skills_tool.HERMES_HOME = old_home
    _skill_mgr.SKILL_DIRS = old_dirs
```

То есть `skills list` в профиле **видит ТОЛЬКО** каталог
`profile_dir/skills/`. Bundled глобальные — **НЕ ВИДНЫ** через
эту операцию.

НО модель при запуске сессии может вызывать `skill_view` без
override, и тогда видит bundled. Это отдельный кодпуть.

────────────────────────────────────────────────────────────────────────────
5. ПОЧЕМУ SKILL НЕ ВИДЕН В ПРОФИЛЕ — ЧАСТЫЕ ПРИЧИНЫ
────────────────────────────────────────────────────────────────────────────

5.1. Профиль не получил bundled-скилы при создании.
   На этом хосте `analyst_training/skills/` имеет только 16
   категорий (а bundled 18). Причина: bundled-категории
   `devops/`, `hermes-agent-vcs-portability/`, и т.п. **не были
   автоматически посеяны** в этот профиль.

   Решение:
   ```
   hermes --profile=analyst_training skills install <bundle>
   ```
   или скопировать каталог вручную.

5.2. Скил в `disabled_skills` профиля.
   Проверить:
   ```
   grep disabled_skills ~/.hermes/profiles/<name>/config.yaml
   ```

5.3. Скил не зарегистрирован в bundled_manifest.
   Проверить:
   ```
   cat ~/.hermes/.bundled_manifest | grep <name>
   ```

5.4. Bundled скил был opt-out.
   ```
   hermes skills opt-in <name>
   ```

5.5. Per-profile скил перекрывает bundled.
   Если имя одинаковое и локальный скил существует — bundled
   не используется. Включите bundled через disable локального.

6. CONCRETE EXAMPLE: SKILL В РАЗНЫХ КАТАЛОГАХ
═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 1. Bundled скил `devops/` виден всем профилям
═══════════════════════════════════════════════════════════════════════════

Bundled skill `devops/check-systemd-unit/` лежит в
`~/.hermes/skills/devops/check-systemd-unit/SKILL.md`.

Из профиля `default`, `analyst_training`, любого будущего
`mi_mg_01` — этот скил доступен, потому что:

  1. Hermes при старте сессии сканирует ВСЕ пути:
     `~/.hermes/skills/**/SKILL.md` + `~/.hermes/profiles/*/skills/**/SKILL.md`.
  2. description: "Check systemd unit state and logs."
  3. Если триггер соответствует — грузится.

Это работает потому, что bundled-скилы лежат в
`~/.hermes/skills/`, и любая модель, начинающая сессию с
любым профилем, видит эту директорию.

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 2. Per-profile скил «mima_g_01_operations» — только в профиле
═══════════════════════════════════════════════════════════════════════════

Положили в `~/.hermes/profiles/mi_mg_01/skills/mima_g_01_operations/SKILL.md`.

Из других профилей (default, analyst_training) этот скил **НЕ
виден**. Только из `mi_mg_01`.

Это by design: per-profile скил не утекает наружу.

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 3. Имя «github-pr-workflow» в обоих местах
═══════════════════════════════════════════════════════════════════════════

Глобально: `~/.hermes/skills/github/github-pr-workflow/SKILL.md`.
Per-profile: `~/.hermes/profiles/mi_mg_01/skills/github-pr-workflow/SKILL.md`.

Когда модель в профиле `mi_mg_01` думает «нужен github-pr-workflow»:
  1. Ищет в `~/.hermes/profiles/mi_mg_01/skills/`.
  2. Находит per-profile скил.
  3. Использует ЕГО, не глобальный.

Когда модель в профиле `default`:
  1. Ищет в `~/.hermes/profiles/default/skills/` (= `~/.hermes/skills/`).
  2. Находит глобальный.
  3. Использует ЕГО.

Это значит: **в одном профиле у вас один скил, в другом — другой**.
Это сильная изоляция. Можно сделать per-profile версии под
разные use-case.

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 4. Bundled `devops/` НЕ виден `analyst_training` (реально)
═══════════════════════════════════════════════════════════════════════════

На mima-g-01:
  - `~/.hermes/skills/devops/` существует (bundled).
  - `~/.hermes/profiles/analyst_training/skills/devops/` — нет.

Если модель в `analyst_training` нуждается в `devops`:
  - Вариант 1: скопировать `~/.hermes/skills/devops/` в
    `~/.hermes/profiles/analyst_training/skills/devops/`.
  - Вариант 2: использовать bundled напрямую (если оно
    auto-discoverable).

Из кода видно, что `set_hermes_home_override(str(profile_dir))`
перенаправляет **все** операции со скилами на per-profile
каталог. Это значит, что модель в сессии с профилем
`analyst_training` может не видеть bundled скилы как «свои».

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 5. Opt-out per profile
═══════════════════════════════════════════════════════════════════════════

Допустим, вам не нравится bundled `dogfood/skill`. В профиле
`code_reviewer`:

```yaml
# config.yaml
agent:
  skills:
    disabled:
      - dogfood
```

Модель не будет использовать `dogfood` в этом профиле.

Тот же скил останется включён в `default` (потому что
disabled — это per-profile).

═══════════════════════════════════════════════════════════════════════════
ПРИМЕР 6. Глобальный opt-out
═══════════════════════════════════════════════════════════════════════════

Если вы хотите, чтобы bundled не видел вообще никто:

```bash
hermes skills opt-out dogfood --all
```

Создаст запись в `~/.hermes/.bundled_manifest`. Все профили
теперь игнорируют `dogfood`. Чтобы вернуть:

```bash
hermes skills opt-in dogfood
```

────────────────────────────────────────────────────────────────────────────
7. КАК SKILL.MD РАЗНЫХ ПРОФИЛЕЙ ВЫТЕСНЯЮТ ДРУГ ДРУГА
────────────────────────────────────────────────────────────────────────────

7.1. Приоритет (от высокого к низкому):
  1. Per-profile skill (тот же `name`) — перебивает bundled.
  2. Bundled skill — для профиля, в котором нет per-profile копии.
  3. Глобально установленный (`hermes skills install`) — то же,
     что bundled по приоритету, но bundled выше.
  4. Disabled (per-profile) — пропускается.

7.2. Что определяет «тот же name»?
   Из frontmatter: `name:` в YAML в начале SKILL.md.

   Если в bundled скил `devops/check-systemd` называется
   `name: check-systemd-unit`, а в профиле вы положили
   `~/.hermes/profiles/X/skills/check-systemd-unit/SKILL.md` с
   тем же `name:`, профильный скил **перебьёт**.

7.3. Можно ли «дополнить» скил?
   Нет. Скилы не merge'атся. Либо bundled, либо per-profile
   override.

   Альтернатива:
   - related_skills в frontmatter (модель сама подтянет,
     если триггер есть).
   - Создать скил с другим name, но ОДИНАКОВЫМ frontmatter
     description → не работает, конфликт по name.

7.4. Что с логами / версиями.
   Bundled скилы обновляются через `hermes skills update`.
   Per-profile скилы не обновляются автоматически — вы их
   ведёте руками или через `profile distribution`.

────────────────────────────────────────────────────────────────────────────
8. КОГДА СОЗДАВАТЬ ОТДЕЛЬНЫЙ SKILL.MD В ПРОФИЛЕ
────────────────────────────────────────────────────────────────────────────

8.1. СИЛЬНЫЕ СИГНАЛЫ (да, нужен отдельный).

  а) **Скил для конкретного сервера / credentials**.
     Если скил зависит от IP, ключа, endpoints — это per-profile.
     Пример: `mima_g_01_operations` — содержит шаги для этого
     сервера. На `analyst_training` это неактуально.

  б) **Скил требует разных секретов**.
     Пример: «deploy_staging» требует STAGING_TOKEN; bundled
     «deploy» требует PROD_TOKEN. Сделать «deploy_staging»
     per-profile для staging-профиля.

  в) **Поведение отличается от базового**.
     Пример: bundled `github-pr-workflow` использует `gh` CLI.
     А вам нужна версия для репо, где `gh` нет (только
     git + curl). Сделать per-profile версию.

  г) **Скил слишком нишевый для глобального использования**.
     Если только один профиль пользуется — нет смысла
     загрязнять bundled.

8.2. СЛАБЫЕ СИГНАЛЫ (обычно не нужно — пользоваться bundled).

  а) Та же логика, но ваш стиль.
     → Поправить frontmatter.bundled скила (если он ваш).

  б) Косметика.
     → Нет смысла.

  в) «Просто попробовать».
     → Сделать `skills install <url>` глобально, попробовать.

  г) Override ради override.
     → Не тратьте время.

8.3. УНИВЕРСАЛЬНЫЙ ТЕСТ.
   Задайте себе вопрос:
   - Если пользователь другого профиля запустит этот скил,
     ничего не сломается?
   - Если да → скил может быть глобальным.
   - Если нет → нужен per-profile.

   Если ответ «может сломаться, потому что другой сервер» —
   per-profile.

────────────────────────────────────────────────────────────────────────────
10. КОГДА ПОЛЬЗОВАТЬСЯ BUNDLED, А КОГДА PER-PROFILE
────────────────────────────────────────────────────────────────────────────

10.1. Используйте bundled, если:
  - Скил применим для разных профилей (не специфичен).
  - Вы доверяете обновлениям от Hermes-разработчиков.
  - Хотите единый стандарт в команде.
  - Скил — стандартный для экосистемы (github, devops, и т.п.).

10.2. Используйте per-profile, если:
  - Скил для конкретной инфраструктуры (mima_g_01_*).
  - Скил требует нестандартных секретов / endpoints.
  - Скил нужно «форкнуть» под свой workflow.
  - Скил слишком нишевый и не нужен другим профилям.

10.3. ГИБРИД (распространённый):
  - Bundled для 80% стандартных операций.
  - Per-profile для специфики (5-10 скилов на профиль).

────────────────────────────────────────────────────────────────────────────
11. КОМАНДЫ HERMES ДЛЯ УПРАВЛЕНИЯ SKILLS В КОНТЕКСТЕ ПРОФИЛЕЙ
────────────────────────────────────────────────────────────────────────────

11.1. Просмотр:
  $ hermes skills list                          # bundled + global
  $ hermes --profile=<name> skills list         # per-profile + inherited

11.2. Установка:
  $ hermes skills install <url>                 # глобально
  $ hermes --profile=<name> skills install <url>  # per-profile

11.3. Создание локального:
  $ hermes --profile=<name> skills create <name>
  # Создаст ~/.hermes/profiles/<name>/skills/<name>/SKILL.md с шаблоном.

11.4. Отключение:
  $ hermes skills opt-out <name> --all           # глобально
  $ hermes --profile=<name> skills opt-out <name> # per-profile

11.5. Обновление:
  $ hermes skills update                        # все bundled
  $ hermes --profile=<name> skills update       # per-profile

11.6. Удаление:
  $ hermes skills uninstall <name>              # глобально
  $ hermes --profile=<name> skills uninstall    # per-profile

────────────────────────────────────────────────────────────────────────────
12. ЧАСТНЫЕ СЛУЧАИ
────────────────────────────────────────────────────────────────────────────

12.1. Два профиля с одинаковым скилом, но разной версией.
   Это нормальная практика per-profile override.
   Поддерживайте обе версии вручную (нет auto-sync).

12.2. Per-profile скил, который хочется сделать глобальным.
   Создайте дистрибутив:
   ```bash
   hermes profile distribution --publish
   ```
   Установите в другой профиль:
   ```bash
   hermes --profile=other skills install <dist-url>
   ```

12.3. Несколько человек делят глобальные скилы.
   Глобальный скил — общий ресурс. При обновлении все получают
   новую версию. Per-profile скилы независимы.

12.4. Скил нужен в 5 профилях, но не «всем».
   Сделайте его глобальным, opt-out в ненужных:
   ```bash
   hermes --profile=profileA skills opt-out <name>
   hermes --profile=profileB skills opt-out <name>
   ```
   Это работает, если скил виден глобально, а отключение per-profile.

12.5. Скил секретный (содержит токены).
   Не пишите секреты в SKILL.md. SKILL.md может попасть в
   shared дистрибутивы. Секреты — в .env.

────────────────────────────────────────────────────────────────────────────
13. ЧАСТЫЕ ОШИБКИ
────────────────────────────────────────────────────────────────────────────

13.1. Забыли, что bundled-скилы НЕ копируются при `--clone`.
   → Профиль после clone может не иметь всех скилов.

13.2. Перезаписали bundled скил своей версией, забыли про
   обновления.
   → Если bundled изменится upstream, ваша версия всё равно
     используется в профиле, но в других профилях — обновлённая.

13.3. Скил положен в профиль, но не загружается.
   Возможные причины:
   - Неправильное имя файла (только `SKILL.md`, не `Skill.md`).
   - Отсутствует `name:` в frontmatter.
   - Скил в `disabled_skills`.
   - Bundled opt-out.

13.4. Скил активен, но модель его не вызывает.
   Возможные причины:
   - Не подходящий `description:` (триггер не матчится).
   - Маленькая `description` (модель не понимает, когда применять).

13.5. Скил установлен в одном профиле, забыли в другом.
   → Сделать один раз глобально, если применим ко всем.

13.6. Положили в профиль bundled-скил, но не учли, что bundled
   обновился и теперь есть разные версии.
   → Это by design, не баг.

13.7. Токены в SKILL.md.
   → Срочно удалить, перенести в .env.

13.8. Скил пишет в chat не в тред, а bundled пишет в тред.
   → Конфликт форматов между bundled и per-profile. Используйте
     одно место.

14. ПОШАГОВАЯ ИНСТРУКЦИЯ «СОЗДАТЬ PER-PROFILE SKILL»
────────────────────────────────────────────────────────────────────────────

Шаг 1. Создать профиль, если его нет:
```bash
hermes profile create my_profile
```

Шаг 2. Переключиться:
```bash
hermes profile use my_profile
```

Шаг 3. Создать скил:
```bash
hermes --profile=my_profile skills create my_special_skill
```

Шаг 4. Проверить, что файл создан:
```bash
ls -la ~/.hermes/profiles/my_profile/skills/my_special_skill/SKILL.md
cat ~/.hermes/profiles/my_profile/skills/my_special_skill/SKILL.md | head
```

Шаг 5. Отредактировать:
```bash
$EDITOR ~/.hermes/profiles/my_profile/skills/my_special_skill/SKILL.md
```

Шаг 6. Заполнить frontmatter:
  - name: my_special_skill (kebab-case)
  - description: "When to use this skill. Triggers."
  - version: 1.0.0
  - tags: [tag1, tag2]

Шаг 7. Заполнить тело (When to Use, Step-by-step, Pitfalls).

Шаг 8. Убедиться, что скил загружен:
```bash
hermes --profile=my_profile skills list
```

Шаг 9. Протестировать из чата:
  В Telegram-боте профиля: «покажи мой my_special_skill».

15. ПОШАГОВАЯ ИНСТРУКЦИЯ «ОТКЛЮЧИТЬ BUNDLED В ПРОФИЛЕ»
────────────────────────────────────────────────────────────────────────────

Шаг 1. Убедиться, что bundled есть:
```bash
hermes skills list | grep annoying_skill
```

Шаг 2. Включить профиль:
```bash
hermes profile use my_profile
```

Шаг 3. Opt-out:
```bash
hermes --profile=my_profile skills opt-out annoying_skill
```

Шаг 4. Убедиться:
```bash
hermes --profile=my_profile skills list | grep annoying_skill
# пусто (или "disabled")

# Проверить в config.yaml:
grep -A2 disabled_skills ~/.hermes/profiles/my_profile/config.yaml
```

Шаг 5. Включить обратно:
```bash
hermes --profile=my_profile skills opt-in annoying_skill
```

16. ЧЕКЛИСТ «ПРАВИЛЬНАЯ СТРУКТУРА SKILLS В ПРОФИЛЕ»
────────────────────────────────────────────────────────────────────────────

  □ Bundled скилы проверены (`hermes skills list`)?
  □ Per-profile скилы проверены
    (`hermes --profile=<name> skills list`)?
  □ Нет дублей с разной версией между bundled и per-profile?
  □ Per-profile скилы с тем же именем, что и bundled — намеренные
    overrides?
  □ Нет секретов в SKILL.md?
  □ Frontmatter у всех per-profile — правильный?
  □ `description` триггерный?
  □ `name` в kebab-case и совпадает с каталогом?
  □ Disabled_skills в config.yaml — корректны?
  □ version bumped после изменений?
  □ Opt-out нужен только для скрытия bundled в конкретном профиле?

────────────────────────────────────────────────────────────────────────────
17. ЗАКЛЮЧЕНИЕ
────────────────────────────────────────────────────────────────────────────

Skills в Hermes Agent — это **глобальные (shared)** + **per-profile
(локальные)**.

Глобальные доступны по умолчанию. Если в per-profile вы положили
скил с тем же именем — он перебивает глобальный для этого профиля.

Изоляция файловой системы:
  - Bundled: `~/.hermes/skills/<name>/SKILL.md`
  - Per-profile: `~/.hermes/profiles/<name>/skills/<name>/SKILL.md`

Изоляция кода (через `set_hermes_home_override`):
  - При активном профиле `HERMES_HOME = profile_dir`,
    `SKILLS_DIR = profile_dir / skills`.
  - То есть большинство операций со скилами в активном
    профиле работают ТОЛЬКО с per-profile каталогом.

Когда создавать отдельный per-profile skill:
  - Специфика инфраструктуры (mima_g_01_*).
  - Другие секреты / endpoints.
  - Форк стандартного скила.
  - Слишком нишево для глобального.

Когда пользоваться bundled:
  - Стандартные операции (github, devops, creative и т.п.).
  - Хотите общие обновления для всех профилей.
  - Стандарт в команде.

Главное правило: **bundled = общий ресурс; per-profile =
специализация.** Создавайте per-profile, когда вам нужно
специализированное поведение в конкретном контексте.
────────────────────────────────────────────────────────────────────────────
18. ОТВЕТЫ НА ЧАСТЫЕ ВОПРОСЫ
────────────────────────────────────────────────────────────────────────────

Q: «Видны ли в новом профиле bundled скилы?»
A: В сессии — да, модель находит их по description. Но
   `hermes --profile=<name> skills list` покажет только local.
   Чтобы bundled работали в `hermes <command>`, зачастую их
   нужно ставить per-profile через copy.

Q: «Что побеждает, если имя одинаковое?»
A: Per-profile в этом профиле. Глобальный/иной профиль —
   другой скил.

Q: «Я могу просто скопировать bundled в per-profile?»
A: Да, это by design. Скопировали → bundled больше не
   используется в этом профиле.

Q: «Bundled можно отключить per-profile?»
A: Да, через `disabled_skills` или `skills opt-out --profile=<name>`.

Q: «Можно ли ОБНОВИТЬ bundled локально?»
A: Нет. Bundled — глобальный ресурс. Чтобы «обновить»
   в профиле — скопируйте в per-profile. Но тогда bundled
   перестанет работать в этом профиле.

Q: «Где скилы «официальные» vs «пользовательские»?»
A: Bundled (`~/.hermes/skills/`) — official + optional от
   Nous Research. Per-profile — пользовательские. Вы можете
   добавлять в `~/.hermes/skills/` свои.

Q: «Что с opt-in/opt-out?»
A: Opt-out — отключить. Opt-in — включить. Per-profile
   opt-out пишет в `disabled_skills` config.yaml; глобальный
   — в `.bundled_manifest`.

Q: «Если у меня 5 профилей и каждый с per-profile skill —
   это много?»
A: Если каждый скил нужен ТОЛЬКО своему профилю — это
   правильно. Если нужен нескольким — сделайте глобальным.

Q: «Per-profile скилы можно экспортировать?»
A: Через `hermes profile distribution --publish`. Выходит
   tar.gz с bundled skills.

Q: «Можно ли иметь скил с ДРУГИМ name в per-profile, но
   description похожим?»
A: Да, можно. Это другой скил. Bundled не перебивается.

Q: «Когда НЕ создавать per-profile?»
A: Когда bundled уже отлично справляется. Override ради
   override — шум.
