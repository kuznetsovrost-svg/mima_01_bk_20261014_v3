1. ПРОБЛЕМА
═══════════════════════════════════════════════════════════════════

SKILL в Hermes — это директория `~/.hermes/skills/<skill-name>/`
с обязательным `SKILL.md` и опциональными файлами.

SKILL.md содержит:
  • Описание скилла (что делает)
  • Когда применять (trigger conditions)
  • Пошаговый алгоритм (step-by-step)
  • VERIFICATION чек-лист
  • PITFALLS

Возникает вопрос: где хранить данные, которые нужны скиллу,
но которые НЕ являются его кодом/инструкцией?

Типичные примеры:
  • Шаблоны SQL-запросов для скилла `sql-analyzer`
  • Списки regex для скилла `pii-detector`
  • Справочники API-endpoint'ов для скилла `github-pr-workflow`
  • Whitelist URL для скилла `web-archive-fetcher`
  • Карта соответствий «город → timezone» для скилла `time-converter`
  • Правила валидации для скилла `docx-template-renderer`

2. ПРИНЦИПЫ РАЗМЕЩЕНИЯ
═══════════════════════════════════════════════════════════════════

2.1. Что такое «условно-постоянные данные»
───────────────────────────────────────────
  Это данные, которые:
    ✓ нужны при КАЖДОМ вызове скилла
    ✓ НЕ зависят от текущей задачи
    ✓ РЕДКО меняются (обновляются людьми, не агентом)
    ✓ Имеют смысл только в контексте этого скилла
    ✓ Могут быть большими (КБ-МБ)

  Не путать с:
    ✗ Данными конкретной задачи (→ task output / файл)
    ✗ Данными агента в целом (→ MEMORY.md)
    ✗ Данными пользователя (→ USER.md)
    ✗ Данными среды (→ /etc, .env, конфиги)
    ✗ Кодом скилла (→ SKILL.md, scripts/)

2.2. Три критерия правильного размещения
────────────────────────────────────────
  A. Discoverability — агент должен найти данные САМ
     при загрузке скилла, без подсказки пользователя

  B. Co-location — данные лежат РЯДОМ с кодом скилла,
     не в общей куче ~/.hermes/data/

  C. Versioning — данные версионируются вместе со скиллом
     (если обновился скилл — обновились и данные)

3. КАНОНИЧЕСКАЯ СТРУКТУРА HERMES SKILL
═══════════════════════════════════════════════════════════════════

Согласно hermes-cli (проверено на реальных bundled-скиллах в
/root/.hermes/profiles/analyst_training/skills/github/):

  ~/.hermes/skills/<skill-name>/
  ├── SKILL.md                 ← обязательный, основная инструкция
  ├── DESCRIPTION.md           ← краткое описание (опционально)
  ├── references/              ← документация, схемы, спецификации
  │   ├── api.md
  │   ├── schema.json
  │   └── ...
  ├── templates/               ← шаблоны (файлы, письма, код)
  │   ├── template.docx
  │   └── ...
  ├── scripts/                 ← исполняемый код (Python, bash)
  │   ├── validate.py
  │   └── fetch.sh
  └── assets/                  ← статические данные (изображения,
                                ←   дампы, справочники)

Это КАНОН. Использовать именно эти имена папок.

4. КАКУЮ ПАПКУ ВЫБИРАТЬ ПОД ДАННЫЕ
═══════════════════════════════════════════════════════════════════

4.1. references/ — для ЧЕЛОВЕКО-ЧИТАЕМОЙ документации
─────────────────────────────────────────────────────
  Что класть:
    • Спецификации API (с примерами)
    • Описание форматов данных
    • Схемы (JSON Schema, OpenAPI, SQL DDL)
    • Карты соответствий (lookup-таблицы в markdown)
    • Списки «что можно / что нельзя»
    • Best practices, edge cases

  Примеры:
    references/timezones.md       — таблица timezone для городов
    references/sql-dialects.md    — отличия PostgreSQL/MySQL/SQLite
    references/iso-3166.md        — коды стран
    references/regex-patterns.md  — regex для PII detector

  Формат: Markdown / JSON / YAML / plain text
  Агент читает по необходимости: `read_file references/sql-dialects.md`

4.2. templates/ — для ШАБЛОНОВ документов/файлов
────────────────────────────────────────────────
  Что класть:
    • Шаблоны .docx (для docx-renderer)
    • Шаблоны .tex (для LaTeX generator)
    • Шаблоны писем
    • Jinja2-шаблоны
    • Handlebars/Mustache-шаблоны
    • HTML-шаблоны
    • Prompt-шаблоны (для LLM-вложений)

  Примеры:
    templates/report.docx
    templates/cover-letter.txt
    templates/invoice.tex
    templates/api-request.json

  Агент использует: `cp templates/X output` + populate variables

4.3. scripts/ — для ИСПОЛНЯЕМОГО КОДА
─────────────────────────────────────
  Что класть:
    • Python-скрипты (валидация, парсинг, конвертация)
    • Bash-скрипты (автоматизация)
    • Утилиты (CLI-обёртки)
    • SQL-скрипты (DDL, миграции)
    • JS-скрипты (для Node.js скиллов)

  Примеры:
    scripts/validate_email.py
    scripts/fetch_github_pr.sh
    scripts/normalize_csv.py

  Агент вызывает: `terminal "python scripts/validate_email.py ..."`

4.4. assets/ — для БИНАРНЫХ/СТАТИЧЕСКИХ ДАННЫХ
──────────────────────────────────────────────
  Что класть:
    • Изображения (логотипы, иконки)
    • Шрифты
    • Бинарные справочники (SQLite, pickle, parquet)
    • CSV/Excel-датасеты
    • Скомпилированные модели
    • Бинарные diff'ы (например, geonames.dat)

  Примеры:
    assets/timezone_data.sqlite
    assets/iso_country_codes.csv
    assets/pii_patterns.bin

  ⚠ Не путать с generated output — assets это ВХОДНЫЕ данные,
     не результат работы скилла.

4.5. КОРЕНЬ скилла — для ГЛАВНЫХ файлов
────────────────────────────────────────
  SKILL.md            — обязательно
  DESCRIPTION.md      — краткое описание (для listings)
  README.md           — если нужна отдельная длинная документация
  config.json         — если скилл требует конфигурации
  CHANGELOG.md        — история изменений скилла
  LICENSE             — лицензия (если скилл shareable)

5. ДЕРЕВО ПРИНЯТИЯ РЕШЕНИЙ
═══════════════════════════════════════════════════════════════════

  У вас есть данные для скилла. Спросите:

  1. Данные ЧИТАЕТ агент для понимания?
     → references/

  2. Данные — это ШАБЛОН для подстановки?
     → templates/

  3. Данные нужно ИСПОЛНИТЬ как код?
     → scripts/

  4. Данные БИНАРНЫЕ / большие CSV-датасеты?
     → assets/

  5. Данные — это КОНФИГ скилла?
     → config.json в корне

  6. Не подходит ни одно? → пересмотреть, может это не данные
     скилла, а данные задачи (→ output/task-specific файл)

6. РЕАЛЬНЫЕ ПРИМЕРЫ ИЗ НАШЕЙ ИНСТАЛЛЯЦИИ
═══════════════════════════════════════════════════════════════════

6.1. memory-hygiene (наш самописный, single file)
──────────────────────────────────────────────────
  /root/.hermes/skills/memory-hygiene/SKILL.md
  → 10159 B, всё inline (5 шагов + audit-скрипты в виде кода)

  Замечание: если бы разрастался, стоило бы вынести:
    references/allowlist-categories.md
    scripts/audit_memory.py
    scripts/redact_sensitive.py

6.2. failsafe-rules (наш самописный)
────────────────────────────────────
  /root/.hermes/skills/failsafe-rules/SKILL.md
  → 11689 B, всё inline (11 правил + Python dict + bash)

  Что стоит вынести:
    references/enforcement-table.md  (сейчас ENFORCEMENT.md в docs/)
    scripts/check_action.py
    assets/forbidden_patterns.json

6.3. github-pr-workflow (bundled, в skills/github/)
─────────────────────────────────────────────────────
  Из реальной структуры bundled skills/github/:
    DESCRIPTION.md
    codebase-inspection/   ← это SUB-SKILL, отдельная папка
    github-auth/
    github-code-review/
    github-issues/
    ...

  Bundled-скиллы часто compound — несколько под-скиллов
  в одной категории. Каждый может иметь свой SKILL.md.

7. ССЫЛКИ В SKILL.md НА ДАННЫЕ
═══════════════════════════════════════════════════════════════════

SKILL.md должен явно указывать агенту, где его данные:

  ## Data files

  Этот скилл использует следующие файлы данных:
    - `references/timezones.md` — таблица timezone
    - `assets/country-codes.csv` — ISO 3166 справочник
    - `templates/report.docx` — шаблон отчёта

  Перед запуском прочитай `references/timezones.md`
  если задача требует timezone-конверсии.

  ## Examples

  См. `examples/` (если есть) или встроенные в этот файл.

8. CONFIG vs DATA — ВАЖНОЕ РАЗЛИЧИЕ
═══════════════════════════════════════════════════════════════════

CONFIG (конфигурация):
  • Задаёт ПОВЕДЕНИЕ скилла
  • Может меняться между запусками
  • Часто environment-specific
  • В .env или config.json
  • Пример: API_KEY, MAX_RETRIES, LOG_LEVEL

DATA (данные):
  • Задаёт СОДЕРЖАНИЕ работы скилла
  • Условно-постоянна (меняется людьми, не per-run)
  • Universal across environments
  • В references/templates/assets/
  • Пример: список regex, шаблон документа, lookup-таблица

Где граница?
  CONFIG скилла → /root/.hermes/config.yaml или в .env
  DATA скилла    → внутри директории скилла

═══════════════════════════════════════════════════════════════════
9. ВЕРСИОНИРОВАНИЕ ДАННЫХ ВМЕСТЕ СО СКИЛЛОМ
═══════════════════════════════════════════════════════════════════

Если данные меняются → меняется и поведение скилла.
Поэтому версионируются ВМЕСТЕ:

  git tag skill-name/v1.2.0  — общий тег
  references/timezones.md    — версия 2026a (IANA)
  templates/report.docx      — версия 2.0

В SKILL.md стоит писать:
  ## Version

  - skill: 1.2.0 (2026-07-17)
  - data/timezones: 2026a (IANA)
  - data/country-codes: ISO 3166-1:2020
  - template/report: v2.0 (2026-06-15)

10. КОНКРЕТНЫЙ РЕЦЕПТ СОЗДАНИЯ СКИЛЛА С ДАННЫМИ
═══════════════════════════════════════════════════════════════════

Пример: скилл `pg-schema-doc` (документирование PostgreSQL-схем)

  $ cd /root/.hermes/skills/
  $ mkdir pg-schema-doc/{references,templates,scripts,assets}
  $ touch pg-schema-doc/SKILL.md

  $ cat > pg-schema-doc/SKILL.md << 'EOF'
  ---
  name: pg-schema-doc
  description: Генератор Markdown-документации для PostgreSQL-схем.
  version: 1.0.0
  ---

  # pg-schema-doc

  ## Назначение
  Из DDL PostgreSQL → структурированный .md с описанием таблиц.

  ## Data files
    - references/pg-types.md — справочник по типам PostgreSQL
    - templates/schema.md.j2 — Jinja2-шаблон
    - scripts/extract_schema.py — парсер DDL
    - scripts/render.py — рендер в Markdown

  ## Алгоритм
    1. Получить DDL: psql -t -c "\d+ table_name" > schema.sql
    2. python scripts/extract_schema.py schema.sql > schema.json
    3. python scripts/render.py schema.json templates/schema.md.j2 \\
         > docs/SCHEMA.md

  ## VERIFICATION
    - [ ] schema.json содержит все таблицы
    - [ ] docs/SCHEMA.md валиден (md lint)
    - [ ] ссылки на типы работают
  EOF

  # Заполнить references/
  curl -o pg-schema-doc/references/pg-types.md \\
      https://wiki.postgresql.org/wiki/PostgreSQL_Data_Types

  # Создать шаблон
  cat > pg-schema-doc/templates/schema.md.j2 << 'EOF'
  # {{ schema.name }}

  ## Tables

  {% for table in schema.tables %}
  ### {{ table.name }}
  {% for col in table.columns %}
  - `{{ col.name }}` ({{ col.type }}, {{ col.nullable }})
  {% endfor %}
  {% endfor %}
  EOF

  # Реализовать scripts
  # ...

  # Зарегистрировать в Hermes
  $ hermes skills refresh
  $ hermes skills show pg-schema-doc

11. АНТИ-ПАТТЕРНЫ (чего НЕ делать)
═══════════════════════════════════════════════════════════════════

❌ Анти-паттерн 1: Данные в SKILL.md inline
───────────────────────────────────────────
  Плохо: 50 КБ данных в SKILL.md → скилл невозможно прочитать.
  Лучше: данные в references/assets/, SKILL.md содержит ссылку.

❌ Анти-паттерн 2: Данные в MEMORY.md
─────────────────────────────────────
  Плохо: «Используй список timezone: Europe/Moscow, ...»
  в MEMORY.md. MEMORY — это контекст агента, не скилла.
  Лучше: в skills/timezone/references/timezones.md

❌ Анти-паттерн 3: Данные в общей куче ~/.hermes/data/
────────────────────────────────────────────────────────
  Плохо: ~/.hermes/data/timezones.txt (не привязано к скиллу)
  Лучше: ~/.hermes/skills/time-converter/references/timezones.md

❌ Анти-паттерн 4: Хардкод данных в коде
─────────────────────────────────────────
  Плохо: TIMEZONES = {...} в scripts/main.py
  Лучше: scripts/main.py читает assets/timezones.json

❌ Анти-паттерн 5: Данные в /tmp или рабочей директории
──────────────────────────────────────────────────────
  Плохо: /tmp/sql_patterns.sql (теряется при reboot)
  Лучше: ~/.hermes/skills/sql-analyzer/references/patterns.sql

❌ Анти-паттерн 6: Данные размазаны по нескольким скиллам
───────────────────────────────────────────────────────
  Плохо: pg-schema-doc имеет /root/data/postgres/, а
  pg-query-optimizer имеет /root/data/postgres/.
  Лучше: общий скилл `pg-common` с references/,
  остальные импортируют.

12. БЕЗОПАСНОСТЬ ДАННЫХ СКИЛЛА
═══════════════════════════════════════════════════════════════════

12.1. Permissions
─────────────────
  ~/.hermes/skills/<skill>/             drwx------ (700)
  ~/.hermes/skills/<skill>/SKILL.md     -rw------- (600)
  ~/.hermes/skills/<skill>/references/  drwx------ (700)
  ~/.hermes/skills/<skill>/assets/      drwx------ (700)

12.2. Чувствительные данные
────────────────────────────
  Если данные содержат токены / ключи / PII:
    → НЕ класть в скилл (скиллы могут шериться)
    → Использовать ${ENV_VAR} в config.json + .env
    → Или вынести в Bitwarden через skill secrets

12.3. Источник данных
──────────────────────
  Если данные — скачанные (например, geonames.dat):
    → указать источник и дату в references/SOURCES.md
    → license файл, если требуется
    → пример: assets/geonames/SOURCES.md, assets/geonames/LICENSE

13. ТЕСТИРОВАНИЕ СКИЛЛА С ДАННЫМИ
═══════════════════════════════════════════════════════════════════

Скилл должен тестироваться с реальными данными:

  ~/.hermes/skills/<skill>/
  ├── SKILL.md
  ├── references/
  ├── templates/
  ├── scripts/
  ├── assets/
  └── tests/
      ├── test_basic.py           ← минимальные кейсы
      ├── test_edge_cases.py
      └── fixtures/
          ├── sample_input.sql
          └── expected_output.md

Запуск тестов:
  $ cd ~/.hermes/skills/<skill>/
  $ python -m pytest tests/

14. ИНСТРУМЕНТЫ HERMES ДЛЯ РАБОТЫ СО СКИЛЛАМИ
═══════════════════════════════════════════════════════════════════

  $ hermes skills list                    # список всех скиллов
  $ hermes skills show <name>             # показать скилл
  $ hermes skills refresh                 # перечитать с диска
  $ hermes skills update <name>           # обновить скилл
  $ hermes skills remove <name>           # удалить

  В skill_manage (Python API):
    action='create'                       # создать
    action='patch'                        # точечная правка
    action='edit'                         # полная перезапись
    action='delete'                       # удалить

15. ИТОГОВАЯ ШПАРГАЛКА
═══════════════════════════════════════════════════════════════════

  «У меня есть данные для скилла. Куда класть?»

    Спрашиваю себя:
    ┌──────────────────────────────────┬──────────────────────┐
    │ Что с данными делать?            │ Папка                │
    ├──────────────────────────────────┼──────────────────────┤
    │ Читать как документацию          │ references/          │
    │ Подставлять как шаблон           │ templates/           │
    │ Исполнять как код                │ scripts/             │
    │ Загружать как бинарь/датасет     │ assets/              │
    │ Использовать как конфиг          │ config.json (корень) │
    │ Ничего из выше — пересмотреть    │ (это не данные скилла)│
    └──────────────────────────────────┴──────────────────────┘

  «А как агент их найдёт?»
    → Читает SKILL.md → видит секцию «Data files» → читает
      по ссылке.

  «А если данных много?»
    → Подпапки по темам: references/network/, references/api/
    → Или индексный файл references/INDEX.md

  «А если данные меняются?»
    → Версионировать (см. §9)
    → Указать в SKILL.md «Data version»
    → CHANGELOG.md для истории
